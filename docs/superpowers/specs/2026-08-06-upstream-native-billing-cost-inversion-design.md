# 多上游原生计费与成本倒挂告警设计

**日期：** 2026-08-06（Asia/Shanghai）  
**状态：** 已被 `2026-08-06-account-card-cost-inversion-alert-design.md` 替代；本文仅保留为完整经营设计背景，不作为当前实施范围。

## 一、目标和核心结论

一个本站分组可以同时包含多个 Sub2API、New API 上游和自有账号。用户价格与上游成本必须完全分离：

```text
用户计费 = 本站模型价格 × 本站分组倍率
上游成本 = 本次实际命中账号的上游原生账单
本次利润 = 本站用户实际扣费 - 上游实际扣费
```

上游模型价格和倍率只在管理员内部用于计算成本、判断路由风险和解释账单；不得更改用户已看到的本站价格，不得向用户暴露命中账号、上游名称、上游倍率或利润。

账号卡片使用「成本折合本站倍率」和当前分组倍率做同口径比较；但请求级成本和利润始终优先使用已对账的上游实际扣费，不使用倍率反复估算已知金额。

## 二、术语和中文字段

### 用户可见字段

| 中文名 | 含义 |
|---|---|
| 模型标准费用 | 本站模型价格表按本次用量计算的未乘分组倍率金额 |
| 分组倍率 | 本次请求实际采用的本站用户分组倍率 |
| 本次扣费 | 模型标准费用乘以分组倍率 |

用户不可见：命中账号、命中上游、上游模型价格、上游倍率、上游实际扣费、成本折合本站倍率、本次利润。

### 管理员可见字段

| 中文名 | 含义 |
|---|---|
| 命中账号 | 本次请求实际使用的 Sub2API 账号 |
| 命中上游 | 账号对应的上游站点或自有账号类型 |
| 本站模型标准费用 | 与用户看到的模型标准费用同口径 |
| 本站分组倍率 | 本次用户计费使用的分组倍率 |
| 本站实际扣费 | 本站实际从用户余额扣除的金额 |
| 上游计费模型 | 上游账单或日志记录的实际模型 |
| 上游模型标准费用 | 按上游模型价格表计算的未乘上游倍率金额；存在时展示 |
| 上游原生倍率 | Sub2API 原生计费接口或 New API 原生定价接口返回的当前倍率 |
| 上游实际扣费 | 上游逐笔账单已对账的本次金额 |
| 成本折合本站倍率 | 上游实际扣费除以本站模型标准费用 |
| 本次利润 | 本站实际扣费减去上游实际扣费 |
| 成本来源 | 账单实测、额度测得、上游定价、人工配置或待对账 |

「成本折合本站倍率」的用户可读解释固定为：

> 若统一按本站模型价格计算，乘以该倍率后的金额等于上游实际成本。

## 三、计费与成本公式

对一笔请求：

```text
site_standard_cost
  = Σ(本站各计费项单价 × 对应用量)

site_user_charge
  = site_standard_cost × site_group_multiplier

upstream_actual_charge
  = 上游原生逐笔账单金额

cost_equivalent_site_multiplier
  = upstream_actual_charge / site_standard_cost

request_profit
  = site_user_charge - upstream_actual_charge
```

当 `site_standard_cost = 0` 时，不计算成本折合倍率，显示 `—`，但不影响已知上游实际扣费的记账。

已经取得 `upstream_actual_charge` 时，该金额是成本事实源；不得再用成本折合倍率反向覆盖它。成本折合倍率只用于同口径展示、账号卡片风险判断、分组资格判断和后续成本预测。

## 四、具体数字示例

本站价格：输入 `$10/M`、输出 `$30/M`；本站分组倍率 `0.18x`。  
上游价格：输入 `$12/M`、输出 `$36/M`；上游原生倍率 `0.17x`。  
本次用量：输入 `100,000`、输出 `20,000` Token。

```text
本站模型标准费用
  = 0.1 × $10 + 0.02 × $30
  = $1.6000

本站实际扣费
  = $1.6000 × 0.18
  = $0.2880

上游模型标准费用
  = 0.1 × $12 + 0.02 × $36
  = $1.9200

上游实际扣费
  = $1.9200 × 0.17
  = $0.3264

成本折合本站倍率
  = $0.3264 / $1.6000
  = 0.204x

本次利润
  = $0.2880 - $0.3264
  = -$0.0384
```

虽然上游原生倍率 `0.17x` 低于本站分组倍率 `0.18x`，但上游模型价格更高，成本折合本站倍率为 `0.204x`，因此本次仍确认亏损。

## 五、上游原生数据源

### Sub2API 上游

优先级从高到低：

1. `GET /v1/usage/records` 的逐笔 `actual_cost`：作为本次上游实际扣费。
2. `GET /v1/sub2api/billing` 的 `effective_rate_multiplier`：作为上游原生倍率和定价变更证据。
3. 上游原生账单未返回时，仅允许显示「待对账」或「上游定价估算」，不得冒充真实扣费。

### New API 上游

优先级从高到低：

1. `GET /api/log/token` 的逐笔 `quota`，结合 `GET /api/status` 的 `quota_per_unit`：换算本次上游实际扣费。
2. `GET /api/pricing` 的模型定价与 `group_ratio`：作为上游原生价格和倍率。
3. New API 公开定价不能自动证明某个 API Key 属于哪个上游分组时，使用「本站账号 → 上游分组名」映射；映射只保存分组名，不硬编码倍率数值。
4. 主动发请求前后读取 `total_used` 的「额度测得」只是诊断兜底，不作为上游原生倍率事实源。

### SHUAI 账号口径

- `Pro-SHUAI-0.17` 若映射到 SHUAI `codexPro分组`，卡片的「上游原生倍率」展示 SHUAI `/api/pricing` 当前返回的 `0.17x`。
- 曾经通过额度差测得的 `0.2512x` 不得标成 SHUAI 原生倍率；它只能标为「本站口径测算」或在有逐笔对账后作为成本折合倍率。
- SHUAI 上游自身的计算过程与 `0.17x` 一致时，上游原生倍率以 `0.17x` 为准；不用本站主动探测值覆盖它。

## 六、数据来源和可信度

| 成本来源 | 显示文案 | 能否确认本次利润 | 用途 |
|---|---|---:|---|
| 逐笔上游账单已对账 | 账单实测 | 是 | 请求成本、利润、成本折合倍率、确认亏损 |
| New API 额度前后差 | 额度测得 | 否 | 诊断和无账单时的临时风险证据 |
| Sub2API 原生计费接口 | 上游声明 | 否 | 当前上游倍率展示和变更提示 |
| New API 原生定价接口 | 上游定价 | 否 | 当前上游价格、分组倍率和计算解释 |
| 人工配置 | 人工配置 | 否 | 原生接口不可用时的显式兜底 |
| 无可用数据 | 待对账 | 否 | 禁止伪造成本和利润 |

数据新鲜度必须伴随数值返回。账号卡片不使用过期或失败证据生成「确认亏损」，但应显示「成本待确认」并保留上一次成功值和时间作为历史参考。

## 七、账号监控卡片

当前分组视图中，账号卡片增加：

| 字段 | 示例 |
|---|---|
| 上游原生倍率 | `0.17x` |
| 倍率来源 | `上游定价` |
| 成本折合本站倍率 | `0.204x` |
| 成本来源 | `账单实测` |
| 当前分组倍率 | `0.18x` |
| 成本状态 | `确认亏损` |

卡片判定状态：

| 状态 | 条件 | 视觉和文案 |
|---|---|---|
| 确认亏损 | 新鲜、已对账的成本折合倍率 `>` 当前分组倍率 | 红色边框、红色「成本倒挂」状态和明确差额 |
| 无利润空间 | 两者在货币最小精度容差内相等 | 橙色提示 |
| 成本覆盖 | 新鲜成本折合倍率 `<` 分组倍率 | 绿色或中性安全状态 |
| 倒挂风险 | 只有上游原生定价推算，没有逐笔对账 | 橙红色「可能亏损」，不写「确认」 |
| 成本待确认 | 数据不支持、失败、过期或没有账单 | 黄色或灰色提示 |

红色强提醒固定包含：

```text
成本倒挂
成本折合本站倍率 0.204x，高于当前分组倍率 0.18x。
按每 $1 本站模型标准费用计算，预计亏损 $0.024。
```

卡片的成本状态和服务质量状态分开。账号请求正常但成本倒挂时，不得用「服务正常」的绿色覆盖成本告警。

「立即标记」的时间语义为：逐笔上游成本对账交易成功写入后，下一次账号监控投影/API 响应即必须返回新状态；不要求在上游异步账单尚未生成时伪造已确认成本。

## 八、多分组账号和分组资格

同一账号可同时属于多个本站分组。成本折合本站倍率属于账号/模型成本证据；判定结果必须逐分组计算：

```text
GPT-Pro 0.30x：成本覆盖
GPT-特惠 0.18x：确认亏损
```

- 当前分组 Tab 只展示该分组的判定。
- 全站账号视角显示「1 个分组成本倒挂」，并可展开查看分组名和差额。
- 不得将不同账号或不同上游的倍率取平均后判断资格。
- 如果不同模型的成本折合倍率不同，必须保留模型维度。账号级红色告警以当前分组中任一已确认模型发生成本倒挂为触发条件，不使用请求量加权平均掩盖某个亏损模型。

第一阶段只强提醒和标记，不自动暂停账号、不修改绑定、不修改账号优先级、不改变生产调度。自动停调属于另一项需要独立审批的后续功能。

## 九、请求详情和报表

管理员请求详情顺序：

1. 本站计费：本站模型标准费用、本站分组倍率、本站实际扣费。
2. 上游计费：命中账号、上游计费模型、上游模型标准费用、上游原生倍率、上游实际扣费、成本来源。
3. 利润结果：成本折合本站倍率、本次利润、利润率和对账状态。

全站、分组和账号报表必须汇总金额事实：

```text
营收 = Σ 本站用户实际扣费
支出 = Σ 已对账上游实际扣费
利润 = 营收 - 支出
```

报表不能通过平均倍率乘以汇总标准费用伪造精确金额。成本未对账的请求进入「待对账」和成本覆盖率，不计入「已确认精确利润」。

## 十、与现有设计的关系

本规格补充并收紧现有的账号监控、全站账务和账号倍率同步设计：

- 保留「上游真实扣费、用户实际计费、纸面利润、成本覆盖率」的既有账务架构。
- 将账号卡片中模糊的「倍率」拆成「上游原生倍率」和「成本折合本站倍率」。
- `accounts.rate_multiplier` 可继续作为调度/统计配置，但不得伪装成逐笔上游实际扣费。
- Sub2API 原生 `effective_rate_multiplier` 可按现有策略同步管理账号的 `accounts.rate_multiplier`；New API 主动额度测得值不自动覆盖上游原生定价或逐笔账单。
- 现有账号监控分组资格使用 `account.BillingRateMultiplier()` 直接与分组倍率比较的做法需要在实施阶段调整：展示和成本告警使用带来源、新鲜度和模型维度的成本证据，不用一个过期或语义不同的标量盖住真实成本。

## 十一、失败处理和安全边界

- 上游账单和本站请求优先通过上游请求 ID 匹配，次选本地请求 ID；匹配冲突不自动选择，进入对账异常。
- 上游异步结算允许短时「待对账」；超过既有对账宽限仍未匹配时标记异常。
- 上游退费以追加的退费交易冲减成本，不改写原始扣费记录。
- 任何管理员 API 和前端投影都不返回 API Key、Cookie、Token、密码或 OAuth 凭据。
- 上游定价接口不可达时保留最后成功快照和时间，但过期快照不触发新的「确认亏损」。
- 不自动调价、不自动改分组倍率、不自动暂停账号、不自动改路由。

## 十二、验收标准

1. 用户请求的模型标准费用、分组倍率和本次扣费不受命中上游影响。
2. 管理员可以在请求详情看到本站和上游两套计费及对账状态。
3. Sub2API 上游逐笔 `actual_cost` 和 New API 逐笔 `quota` 能与本地请求对账后进入成本账本。
4. SHUAI `Pro-SHUAI-0.17` 显示上游定价接口当前的 `0.17x`，不被额度差测算值覆盖。
5. 有上游实际扣费时，成本折合本站倍率等于「上游实际扣费 / 本站模型标准费用」。
6. 成本折合本站倍率高于当前分组倍率时，当前分组卡片立即显示红色「成本倒挂」，但不自动改变调度。
7. 只有上游定价推算、没有逐笔对账时，显示「可能亏损」而不是「确认亏损」。
8. 同一账号属于多个分组时逐分组判定，不使用平均分组倍率。
9. 不同模型成本不同时保留模型维度，不用账号平均值掩盖亏损模型。
10. 全站营收、支出和利润由逐笔金额汇总，未对账请求明确进入成本覆盖率和异常列表。
