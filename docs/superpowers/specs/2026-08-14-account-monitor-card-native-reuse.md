## 1. 目标

- 监控列表继续只使用现有精简 `AccountMonitorAccount` 投影，保留卡片当前全部字段、指标、优先级、成本、余额、探测、调用折叠和刷新入口。
- 卡片右上角增加低干扰的“账号信息”入口。点击后按账号 ID 请求完整原生 `Account`，在只读信息壳中展示账号管理页已有、卡片没有的账号级字段。
- 卡片提供与账号管理页一致的 `编辑`、`删除`、`更多` 三个操作入口。入口触发后按账号 ID 获取完整 `Account`，复用原生 `EditAccountModal`、`AccountActionMenu`、原生删除确认和原生操作处理器。
- 账号管理页保持不变；不搬迁列设置、批量操作、导入/导出、自动刷新、分组全局设置等全局能力。

## 2. 方案比较

### 方案 A（采用）：卡片入口 + 按需完整账号加载 + 原生组件复用

监控卡片只发出 `accountInfo`、`edit`、`delete`、`more` 事件。监控视图统一维护一个按账号 ID 加载完整账号的流程和操作状态，成功后打开原生组件或只读信息壳。列表 DTO 不变，账号管理页不改。

优点：请求边界清晰，保持监控列表轻量；编辑、删除、更多的视觉与行为直接沿用原生组件；后续原生账号管理新增字段不需要复制到监控列表。代价：首次打开入口多一次详情请求，需要处理加载和失败状态。

### 方案 B：把完整账号嵌入监控 projection

一次列表请求返回全部原生账号字段，再直接驱动入口。

拒绝原因：破坏精简 DTO，扩大监控接口负载和敏感字段暴露面，且原生账号字段变化会与监控 projection 形成长期同步成本。

### 方案 C：在监控页复制账号管理表格和操作逻辑

拒绝原因：重复实现弹窗、权限/账号类型门控、确认和错误处理，容易与原生账号管理产生行为漂移，且超出“只增加入口”的要求。

## 3. 选定架构

### 3.1 卡片

- 保留现有卡片结构和所有字段，不删除或重命名现有 `data-test` 与事件。
- 在卡片 header 右侧状态徽章旁增加低视觉权重按钮 `账号信息`，使用 `data-test="account-info"`。
- 在卡片 footer 或 header 操作区增加三个原生同名按钮：`编辑`、`删除`、`更多`，使用 `data-test="account-edit"`、`account-delete`、`account-more`。
- 卡片仅发出账号 ID 或当前投影对象，不持有完整 `Account`。

### 3.2 监控视图

- 新增 `loadNativeAccount(accountID)`，调用 `adminAPI.accounts.getById(accountID)`；按 ID 去重并在打开入口前显示加载态。
- 完整账号成功后：
  - `账号信息` 打开只读信息壳；
  - `编辑` 打开原生 `EditAccountModal`；
  - `删除` 进入原生 `ConfirmDialog` 文案与 `adminAPI.accounts.delete` 流程；
  - `更多` 打开原生 `AccountActionMenu`，并复用 AccountsView 的事件处理器及账号类型门控。
- 操作成功后重新加载监控 projection；不改变监控列表请求的字段集合。
- 同一账号的并发入口请求共享 pending promise，避免重复详情请求；失败时使用现有 app store 错误提示，卡片数据保持不变。

### 3.3 只读账号信息壳

新增一个最小只读组件，仅渲染完整原生 `Account` 中监控卡片缺失的账号级管理字段（例如平台/类型、状态、备注、分组、代理、过期时间、调度与凭据状态等安全脱敏字段）。不显示凭据原文，不复制编辑表单，不新增业务写入接口。视觉容器复用 `BaseDialog`。

## 4. 明确不变项

- `AccountMonitorAccount` 类型与监控列表 API projection 不扩张。
- 账号管理页面 `AccountsView.vue` 不修改。
- 不搬迁全局列设置、筛选/批量选择、批量删除、导入/导出、自动刷新、全局分组/评分设置。
- 不新增后端 API、数据库迁移、配置或生产发布流程。

| 账号管理页回归 | 现有页面和其测试不变 |
