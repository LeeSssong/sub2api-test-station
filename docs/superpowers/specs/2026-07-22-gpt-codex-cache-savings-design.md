# GPT/Codex 缓存让利与命中优化设计

**日期：** 2026-07-22

**状态：** 已确认

**首期范围：** `GPT-Pro`、`GPT-Plus` 中当前公开的 GPT/Codex 文本模型

## 1. 目标

中转站将提示词缓存带来的价格差额完整让利给用户，同时保留上游账号采购折扣作为站点经营空间。首期在不缓存完整回答、不改变模型语义和不扩大敏感数据采集的前提下，提高 GPT/Codex 请求的上游 Prompt Cache 命中率，并让用户能够核对缓存节省金额。

成功必须同时满足：

- 缓存读取按公开 `cache_read_price` 扣费，不按普通输入价格扣费。
- 普通输入、缓存读取、缓存写入和输出分别计量、计价和展示。
- 同一请求的 Sub2API 用量、用户扣费与上游统计能够对账。
- 优化不降低请求正确性、流式响应可用性或现有路由故障恢复能力。
- 日志和指标不保存提示词、响应正文或可逆的用户会话标识。

## 2. 商业口径

“缓存差价全部让利”只针对缓存相对普通输入产生的价格差额。用户仍按本站公开模型基础价和现有用户组倍率付费；`GPT-Pro`、`GPT-Plus` 上游账号的采购折扣或成本倍率仍属于站点毛利，不传导到用户价格。

单次请求的用户扣费为：

```text
customer_debit =
    uncached_input_tokens * input_price
  + cache_read_tokens * cache_read_price
  + cache_write_tokens * cache_write_price
  + output_tokens * output_price
```

所有价格使用请求发生时的渠道模型价格快照和用户组倍率。历史请求不能因后续改价而重新计算。

当模型或上游可能产生某类 Token 时，对应价格必须明确配置。上游未返回可靠缓存明细时，不得猜测命中量或把未知输入当作免费缓存；该请求按可确认的普通输入口径计费，并标记缓存统计不可确认。

## 3. 请求与路由行为

Sub2API 继续作为请求转发、账户选择和运行时调度的唯一权威组件。现有运维侧车不代理用户生成请求，也不建立第二套路由控制面。

首期遵循以下规则：

1. 完整透传客户端提供的 `prompt_cache_key`、缓存选项和兼容字段，不覆盖客户端自带值。
2. 不重排消息、工具定义或内容块，不对系统/开发者消息做动态注入，不以格式化方式改变稳定前缀。
3. 继续使用 Sub2API 原生粘性会话，让同一用户会话在账号健康且可调度时稳定落到同一上游账号。
4. 路由粘性不能越过模型资格、并发限制、账号健康、余额和人工禁用条件。发生故障时优先保证正确性和可用性，允许切换账号后缓存暂时失效。
5. 重试沿用现有安全边界：只有明确未开始响应且不会造成重复扣费时才允许；重试保留原始请求体和缓存键。
6. 首期不由网关自动生成 `prompt_cache_key`。先测量现有 Codex/GPT 客户端的字段覆盖率和命中率，再通过独立设计决定是否生成不可逆的稳定键。

中转站不实现完整回答缓存、语义缓存或跨用户响应复用。Prompt Cache 只复用上游模型对相同提示词前缀的中间计算，最终响应仍由模型重新生成。

## 4. 用量归类与账单展示

每个请求至少保留以下非内容字段：

- 请求 ID、发生时间、公开模型名和实际路由渠道。
- 普通输入 Token、缓存读取 Token、缓存写入 Token 和输出 Token。
- 四类 Token 对应的价格快照、用户组倍率和最终扣费。
- 缓存统计来源及其可信状态。
- 不可逆的用户和会话哈希，仅用于聚合与路由效果分析。

用户账单展示：

- 普通输入、缓存读取、缓存写入和输出数量。
- 假设全部输入未命中缓存时的参考费用。
- 实际扣费。
- 缓存节省金额。

计算口径为：

```text
cache_hit_rate = cache_read_tokens /
                 (uncached_input_tokens + cache_read_tokens)

cache_savings = cache_read_tokens *
                (input_price - cache_read_price)
```

当分母为零时命中率显示为不可用。`cache_savings` 不包含上游采购折扣，也不把缓存写入成本伪装成节省。

## 5. 可观测性与隐私

运营侧按模型、用户组、渠道和时间窗口聚合：

- 缓存命中率。
- 缓存读取与缓存写入 Token。
- 缓存节省金额。
- 缓存统计缺失率。
- 粘性命中、账号切换及切换后缓存命中变化。
- 用户扣费与上游账单的差异。

禁止记录提示词、响应正文、文件内容、原始 API Key、原始 `prompt_cache_key` 或可逆会话标识。哈希必须使用服务端密钥参与计算，避免通过字典枚举恢复低熵标识。不同用户的数据不得为了提高命中率而建立共享的网关缓存。

## 6. 异常处理

- **缓存字段缺失：** 将该请求全部可确认的提示词输入 Token 按普通输入计费，记录 `cache_usage_unconfirmed`，不展示虚构节省。
- **缓存价格缺失：** 对可能产生该类 Token 的公开模型阻止发布或改价，不以零价格兜底。
- **上游字段不一致：** 保留原始非内容用量证据，进入对账告警，不静默改写 Token 分类。
- **粘性账号不可用：** 按现有资格和健康规则切换；请求可用性优先于缓存命中率。
- **流式请求中断：** 不为追求缓存跨上游重放已开始的响应。
- **缓存写入收费：** 使用明确的 `cache_write_price` 计费；写入价格未知时不得把该模型投入公开流量。

## 7. 发布与验收

发布分三步进行：

1. **只读基线：** 连续观察至少 24 小时，并为每个用户组取得至少 20 个成功请求；记录四类 Token、缓存字段覆盖率、命中率、账号切换率和当前用户扣费，不改变生产路由或价格。任一用户组样本不足时继续观察，不以小样本进入下一阶段。
2. **计费让利：** 在邀请测试组启用缓存读取低价计费和账单明细，使用真实小额请求逐笔核对 Sub2API、用户余额变化和上游统计。
3. **透明优化：** 确认字段透传和前缀稳定性，验证 Sub2API 原生粘性会话后再扩到 `GPT-Pro`、`GPT-Plus` 全部邀请用户。

进入下一阶段必须满足：

- 测试样本的四类 Token 分类与上游证据一致。
- 用户扣费严格符合价格快照公式，缓存节省金额可复算。
- 无跨用户数据、提示词或原始缓存键进入日志。
- 同步与 SSE 请求均通过；与同模型、同渠道的只读基线相比，成功率下降不超过 0.5 个百分点，TTFT P95 上升不超过 10%。
- 故障切换仍遵守现有模型资格、健康、重试和扣费安全边界。

若计费不一致、缓存字段缺失率异常上升或出现隐私风险，停止扩大流量并回到上一阶段。回滚只关闭新展示或新计费策略，不删除历史用量证据，不改变账号、分组、模型映射或现有路由角色。

## 8. 后续范围

以下内容不属于首期：

- 自动生成或改写 `prompt_cache_key`。
- 非 OpenAI 兼容供应商的显式缓存协议。
- 完整回答缓存、语义缓存和跨用户缓存。
- 为命中率牺牲健康检查、并发限制或故障切换。
- 将上游采购折扣全部返还用户。

首期稳定后，只有在真实数据证明客户端缓存键覆盖不足且存在可衡量收益时，才为网关生成稳定缓存键编写独立设计和隐私评审。
