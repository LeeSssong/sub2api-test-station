# Sub2API 0.1.171 Release Recovery Design

## Goal

Restore the unattended Sub2API release path for official `v0.1.171`, adapt the
host updater to the production blue-green topology, and promote the qualified
image to production with focused online acceptance and rollback protection.

The official release identity is fixed to:

- tag: `v0.1.171`
- annotated tag object: `afd154b92aac36c6dafb1fa8e181ca827c78c465`
- commit: `f0e7a9c7a23a7d02fb159b62fa809621eb0475a6`

Completion requires all three conditions: the final source is pushed to the
server, production is running the qualified `0.1.171` image, and the focused
online acceptance checks pass.

## Scope

This delivery includes:

1. Deterministic, fail-closed conflict resolution for the exact transition
   from the current Xingqiao `0.1.169` provenance to official `0.1.171`.
2. Preservation of both Xingqiao customizations and relevant official
   `0.1.170`/`0.1.171` behavior in the resolved source tree.
3. Candidate qualification, immutable image publication, production staging,
   source advancement, and audit evidence.
4. Host updater delegation to the installed blue-green production executor.
5. Final production cutover and focused runtime verification.

It does not include relay-ops, Feishu, accounting UI, account-monitor visual
acceptance, or unrelated operational backlog.

## Root Cause

The release workflow overlays Xingqiao customizations on the last imported
official source and merges the new official release. The merge helper allows
only the generated `backend/cmd/server/wire_gen.go` conflict. Official
`v0.1.171` conflicts in eleven files, so the helper exits before qualification
or image construction. Production consequently has qualified local images
through `0.1.169` only.

The previous `0.1.169` host update also used the retired single-service
executor. Production now has `sub2api-blue`, `sub2api-green`, and one worker,
so the old executor fails while resolving a unique `sub2api` service and does
not load `release.env`.

## Release Conflict Resolution

The release helper will delegate known semantic conflicts to a separate,
version-pinned resolver. The resolver data is keyed by all of these values:

- current provenance version and official commit;
- target tag object and official commit;
- exact sorted unresolved-file list;
- per-file conflict preimage identity.

The known `v0.1.171` resolution may run only when every identity matches. A
missing record, changed preimage, additional conflict, removed conflict, or
different target must fail before candidate creation. The general release
path remains fail-closed for future versions.

The recorded semantic resolutions must preserve Xingqiao account monitoring,
managed/manual multiplier behavior, procurement cost fields, and associated
tests while incorporating official profit control, upstream multiplier
support, authentication/settings changes, Codex identity fixes, and current
official API contracts.

Generated files are not accepted as opaque conflict choices:

- `backend/cmd/server/wire_gen.go` is regenerated from the resolved providers;
- `backend/go.sum` is regenerated by the Go toolchain;
- all conflict markers and unmerged index entries must be absent before the
  candidate source commit is created.

The resolver records only the minimal conflict postimages needed for this
transition. It does not store a second full Sub2API source snapshot.

## Host Updater Blue-Green Adapter

The updater continues to accept the current browser/API request and qualified
local image ID. The host executor detects the canonical blue-green release
state and translates that image into the existing blue-green executor contract.

The adapter must:

1. Inspect the local image and require one approved GHCR RepoDigest.
2. Read and validate the qualification labels for upstream version/commit,
   source commit/tree, tested tree, and migrations hash.
3. Require source tree and tested tree equality.
4. Invoke `/usr/local/libexec/deploy-sub2api-blue-green-host.sh` in production
   mode with `RELEASE_PRELOADED_IMAGE=true`, the immutable RepoDigest, exact
   labels, and an absolute deadline.
5. Use the existing canonical production paths for `compose.yaml`, `.env`,
   `release.env`, release state, record root, and protected API-key files.
6. Forward the blue-green event trace and terminal result to the updater state.

If the protected blue-green state is absent or inconsistent, the adapter must
stop. It must not fall back to rewriting Compose or recreating a legacy single
`sub2api` service on the current production topology.

## Publication And Deployment Flow

The delivery sequence is:

1. Merge the implementation branch into the canonical release source and push.
2. Run one release workflow for `v0.1.171`.
3. Require successful discovery, deterministic merge, qualification, image
   build, immutable GHCR publication, production staging, and source advance.
4. Confirm production has `xingqiao-sub2api:upstream-0.1.171` with matching
   labels and RepoDigest.
5. Submit the authorized immediate update through the host updater path.
6. Let the blue-green executor start the inactive API slot, run its internal
   health checks, reload Caddy, verify public acceptance, update the worker,
   and atomically persist release state and the final record.

No direct Compose edit, `docker compose down`, shared-service recreation, or
database restore is permitted.

## Agile Verification Matrix

Local verification is limited to impacted behavior:

- release merge/resolution tests, including an exact red/green reproduction;
- affected Go packages and generated dependency/wire checks;
- affected account/settings frontend tests;
- updater Go tests and focused host/blue-green shell tests;
- shell syntax and `git diff --check`.

CI performs the single authoritative candidate qualification:

- full Sub2API backend test and vet;
- full Sub2API frontend test and build;
- release/update focused shell tests;
- qualified Linux AMD64 image build.

Production acceptance is limited to:

- reported version `0.1.171`;
- public health;
- authenticated admin availability;
- authenticated `/v1/models` response;
- worker health;
- unchanged PostgreSQL, Redis, and Caddy container identities;
- release state and final release record matching the promoted image.

Relay-ops, Feishu, accounting pages, account-monitor presentation, and other
unrelated acceptance suites are intentionally excluded.

## Failure And Rollback

Every pre-publication mismatch fails without publishing a candidate. Every
pre-cutover production mismatch fails without changing the active upstream.
After a cutover attempt, the existing blue-green checkpoint and rollback path
must restore the previous upstream, release state, and worker image. Shared
PostgreSQL, Redis, and Caddy containers are never recreated by rollback.

The project ledger remains `in progress` after any rolled-back or partially
qualified attempt. It changes to `completed` only after push, deployment, and
focused online verification all succeed.
