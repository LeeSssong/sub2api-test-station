# 账号卡片轻量成本倍率与倒挂预警设计

**日期：** 2026-08-06（Asia/Shanghai）  
**状态：** 待用户确认书面规格；确认后再编写实施计划。

## 一、本次任务的唯一目标

在管理员「账号监控」页的账号卡片上，增加一组轻量成本字段，并对当前账号在当前本站分组中的成本倒挂进行强提醒。

本次只回答：

```text
这个账号的上游原生倍率是多少？
按本站模型价格折算后，它的成本相当于本站多少倍？
这个成本是否高于当前分组倍率？
```

不在账号卡片上扩展任何总账、对账、营收、支出、利润或历史走势功能。

## 二、未来信息架构，不在本次实施

后续将另立项建设管理员页面「站点经营看板」，统一承载：

- 全站营收、上游支出和利润；

- 逐笔对账状态、待对账数量和对账异常；
- 历史按日数据和利润走势。

本次任务不创建该页面，不设计该页面的路由、接口、存储和交互，也不迁移或删除账号监控页已有的全站/分组总览。这些改动等「站点经营看板」单独立项时一并处理，避免新页面尚未完成时丢失现有管理功能。

## 三、账号卡片最终展示

账号卡片在现有服务质量信息之外，只增加下列轻量字段：

| 中文名 | 示例 | 说明 |
|---|---:|---|
| 上游原生倍率 | `0.17x` | 上游原生计费/定价接口返回的当前倍率 |
| 倍率来源 | `上游定价` | `上游声明` / `上游定价` / `人工配置` / `待确认` |
| 成本折合本站倍率 | `0.204x` | 上游成本按本站模型价格口径折算后的成本倍率 |
| 成本来源 | `账单实测` | `账单实测` / `上游定价推算` / `额度测得` / `待确认` |
| 当前分组倍率 | `0.18x` | 当前分组 Tab 对应的本站用户倍率 |
| 成本状态 | `确认亏损` | 当前账号在当前分组的判定结果 |

辅助提示可以使用小字展示，不增加新的金额卡片：

```text
成本模型：gpt-5.4
更新：5 分钟前
```

卡片不新增下列金额字段：

- 上游实际扣费；
- 用户实际计费；
- 纸面利润；
- 利润率；
- 对账覆盖率；
- 待对账笔数。

现有账号卡片中的「投入产出」详细金额区不符合本设计。本次实施时从账号卡片移除该区块；底层对账和账务数据不删除，保留给未来「站点经营看板」复用。

## 四、倍率和成本证据

### 上游原生倍率

Sub2API 上游：

```text
GET /v1/sub2api/billing
→ effective_rate_multiplier
```

New API 上游：

```text
GET /api/pricing
→ group_ratio[该账号的上游分组名]
```

New API 账号无法从标准 API 自动确定上游分组名时，使用「本站账号 → 上游分组名」映射。映射只保存分组名，倍率数值每次从上游定价接口读取，不在代码或配置中硬编码。

### 成本折合本站倍率

有逐笔上游实际扣费时：

```text
成本折合本站倍率
  = 上游实际扣费 / 本站模型标准费用
```

没有逐笔账单，但同时有上游模型价格和上游原生倍率时：

```text
上游定价推算成本
  = Σ(上游各计费项单价 × 对应用量) × 上游原生倍率

成本折合本站倍率
  = 上游定价推算成本 / 本站模型标准费用
```

主动发探测请求前后读取上游额度的结果只能标注「额度测得」，不得覆盖上游原生倍率。

## 五、模型维度和轻量聚合

不同模型的上游价格可能不同，成本折合本站倍率必须在后端保留「账号 + 模型」维度，不在数据层平均成一个账号倍率。

为保持卡片轻量，当前分组卡片只展示「当前分组范围内最高的可信成本折合本站倍率」，并在小字中显示对应模型。

示例：

```text
成本折合本站倍率  0.204x
成本模型                  gpt-5.4
```

这个「取最高值」规则只用于风险卡片和预警，不用于计算全站或分组利润。某个模型已确认亏损时，不能被其他盈利模型的平均值掩盖。

## 六、当前分组判定规则

账号成本状态按当前分组 Tab 单独计算。同一账号在不同分组可以出现不同结果。

| 后端状态 | 中文文案 | 条件 |
|---|---|---|
| `loss_confirmed` | 确认亏损 | 任一模型有新鲜逐笔账单证据，且成本折合倍率 `>` 当前分组倍率 |
| `zero_margin` | 无利润空间 | 最高可信成本折合倍率与分组倍率在数值容差内相等 |
| `cost_covered` | 成本覆盖 | 所有已知模型都低于分组倍率，且没有已知倒挂模型 |
| `loss_risk` | 可能亏损 | 上游定价推算值高于分组倍率，但没有逐笔实际扣费证据 |
| `unknown` | 成本待确认 | 无可用证据、证据过期、探测失败或上游不支持 |

`cost_covered` 只表示「当前已知成本没有发现倒挂」，不代表所有未发生请求的模型已获得逐笔真实账单。卡片通过成本来源和更新时间表达证据局限。

## 七、强提醒视觉

### 确认亏损

`loss_confirmed` 时：

- 整张卡片保留现有服务质量边色，另外增加明确的红色「成本倒挂」告警条；
- 不将账号服务状态伪装成失败，服务质量和成本风险保持两个独立状态；
- 告警条展示成本折合倍率、当前分组倍率、差额和触发模型。

示例：

```text
成本倒挂 · gpt-5.4
成本折合本站倍率 0.204x > 当前分组倍率 0.18x，高出 0.024x。
```

### 其他状态

- `zero_margin`：橙色「无利润空间」；
- `loss_risk`：橙红色「可能亏损·上游定价推算」；
- `unknown`：黄色或中性色「成本待确认」；
- `cost_covered`：低强度绿色或中性「成本覆盖」。

「立即标记」指新的成本证据被后端成功写入后，下一次账号监控投影/API 响应必须返回新状态。上游异步账单尚未生成时，不伪造「确认亏损」。

## 八、SHUAI 账号验收口径

该规则不在业务代码中针对 SHUAI 硬编码；SHUAI 只是生产验收样本。

- `Pro-SHUAI-0.17` 按「本站账号 → SHUAI codexPro分组」映射，从 SHUAI `/api/pricing` 实时读取 `0.17x`。
- 卡片显示「上游原生倍率 0.17x·上游定价」。
- 曾经额度差测得的 `0.2512x` 不得覆盖 `0.17x`，也不得标成 SHUAI 原生倍率。
- 只有逐笔上游实际扣费与本站请求成功匹配后，才可用该金额计算「成本折合本站倍率」并生成 `loss_confirmed`。

## 九、后端投影合同

账号监控分组投影为每个账号返回一个轻量成本对象：

```json
{
  "cost_guard": {
    "upstream_multiplier": 0.17,
    "upstream_multiplier_source": "upstream_pricing",
    "equivalent_site_multiplier": 0.204,
    "cost_source": "reconciled_bill",
    "model": "gpt-5.4",
    "group_multiplier": 0.18,
    "gap": 0.024,
    "status": "loss_confirmed",
    "observed_at": "2026-08-06T12:00:00Z"
  }
}
```

合同规则：

- 金额、账单列表、用户账务数据和凭据不进入 `cost_guard`；
- 数值不可用时返回 `null` 和明确状态，不默认为 `1.0`、`0` 或账号配置值；
- `observed_at` 是生成判定的成本证据时间，不是页面刷新时间；
- 同一账号在不同分组投影中可返回不同的 `group_multiplier`、`gap` 和 `status`。

## 十一、测试与验收标准

1. Sub2API 上游有新鲜 `effective_rate_multiplier` 时，卡片正确显示数值和「上游声明」来源。
2. New API 账号映射到上游分组后，卡片从定价接口读取当前 `group_ratio`，不使用硬编码倍率。
3. SHUAI `Pro-SHUAI-0.17` 显示 `0.17x·上游定价`，不被 `0.2512x` 额度测得值覆盖。
4. 逐笔对账成本可用时，成本折合倍率等于「上游实际扣费 / 本站模型标准费用」。
5. 任一模型的新鲜账单实测成本折合倍率高于当前分组倍率时，显示红色「成本倒挂」告警条。
6. 只有上游定价推算时显示「可能亏损」，不显示「确认亏损」。
7. 证据失败、过期或缺失时显示「成本待确认」，不默认使用 `1.0x`。
8. 账号同时属于多个分组时，在每个分组 Tab 中分别使用该分组倍率判定。
9. 账号支持多个模型时，卡片展示当前分组内最高的可信成本折合倍率和触发模型。
10. 账号卡片不再展示上游真实扣费、用户实际计费、纸面利润和利润率的详细金额区。
11. 服务质量仍为正常时，成本倒挂以独立告警展示，不把账号伪装成请求失败。
12. 红色告警只展示倍率、差额、模型和证据时间，不增加营收、成本金额或对账明细。
