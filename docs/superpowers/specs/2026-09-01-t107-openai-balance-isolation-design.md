# T107 OpenAI 明确余额错误统一账号隔离设计

**日期：** 2026-09-01
**任务：** T107
**状态：** DESIGNING

## 1. 问题与证据

OpenAI 上游在余额或额度耗尽时，可能返回 402、403 或其他错误状态，并通过结构化错误码或明确文案表达余额已耗尽，例如 `insufficient_balance`、`insufficient_quota`、`insufficient_user_quota`、`E44001`、`balance exhausted`、`run out of credits` 或中文余额/额度耗尽文案。

当前 Sub 定制代码已经具备原生账号临时隔离能力：`temp_unschedulable_until`、`SetTempUnschedulable`、运行时调度阻塞、探测恢复以及请求级切号返回。但统一入口 `RateLimitService.HandleUpstreamError` 在池模式、自定义错误码和部分状态处理前存在早退；现有确定性错误分类器也没有覆盖全部已观察到的 OpenAI 余额证据。因此明确余额错误可能只被当作普通 403/402 处理，导致账号没有写入临时不可调度状态，后续请求再次选中同一账号并重复失败。

## 2. 第一性原理与目标

用户请求成功的必要条件是：上游已经明确证明余额耗尽的账号，不能继续作为下一次请求的候选账号；当前请求应沿用既有切号/重试链路寻找其他账号；余额恢复后账号仍可重新调度。

本任务目标：

1. 只覆盖 `PlatformOpenAI`。
2. 识别 OpenAI 明确的账号余额/额度耗尽证据。
3. 在池模式、自定义错误码和其他通用错误处理早退之前，统一写入原生 `temp_unschedulable_until`。
4. 账号保持 `active`，使用现有探测/恢复链路清除隔离。
5. 返回既有 `shouldDisable=true` 语义，使当前请求继续使用既有切号与重试策略。

## 3. 非目标

- 不处理国产、Anthropic、Gemini、Grok、Antigravity 或其他平台。
- 不建立通用跨平台余额抽象。
- 不引入新的账号状态、余额字段、账务事实源或管理页面。
- 不区分模型级余额；所有明确 OpenAI 余额/额度耗尽均按账号级隔离。
- 不改造 OpenAI 四次切号、重试次数、T87 逻辑请求终态或用户侧错误文案。
- 不把普通 403、权限不足、`insufficient_scope`、模型不可用、普通 429、网络错误或服务端 5xx 判定为余额耗尽。

## 4. 方案比较与选择

### 方案 A：扩充现有确定性分类器并前置调用（采用）

扩充 `deterministic_failure_isolation.go` 中的 OpenAI 余额证据判断，覆盖已确认的结构化错误码和明确文案；在 `HandleUpstreamError` 的池模式、自定义错误码等早退之前调用。命中后复用现有 `SetTempUnschedulable`、运行时阻塞和探测恢复。

优点：改动最小，直接修复根因，继续使用 Sub 原生账号状态与恢复链；切号、重试、错误透传保持不变。

### 方案 B：在各个 OpenAI 网关入口分别判断

在 Responses、Chat Completions、Count Tokens、流式终态等入口分别增加余额判断。

缺点：容易漏入口，重复实现，入口间顺序和语义可能再次分叉；不符合统一状态入口的原生结构。

### 方案 C：新增 OpenAI 余额状态系统

新增独立余额状态、恢复任务和管理投影。

缺点：产生第二套账号状态事实源，扩大数据与恢复复杂度，无法解决当前原生入口早退问题本身。

选择方案 A，因为当前缺陷不是缺少状态存储或恢复能力，而是 OpenAI 余额错误没有被完整分类并送入已有原生链路。

## 5. 端到端数据与控制流

1. OpenAI 网关收到上游错误响应。
2. 统一错误入口提取错误码、错误类型、消息和原始响应体中的必要字段。
3. 仅当状态码与结构化字段/明确文案共同形成“余额耗尽”证据时，返回账号级余额耗尽决策。
4. 余额决策优先于池模式、自定义错误码、普通 403/402 和其他通用早退。
5. 使用现有确定性隔离逻辑写入：
   - `accounts.temp_unschedulable_until`
   - 稳定的余额耗尽原因，包含脱敏后的有限错误摘要
   - OpenAI 运行时调度阻塞通知
6. 返回 `shouldDisable=true`，由调用方按现有请求级切号/重试逻辑处理。
7. 余额探测成功时，沿用既有 `ClearTempUnschedulable` 恢复账号；不通过短时间自然过期重新放行余额未恢复的账号。

## 6. 错误证据契约

余额分类器只允许使用明确证据，不使用单独状态码推断：

### 允许的结构化证据

- `error.code`、`error.type` 或顶层 `code` 等于或明确包含：
  - `insufficient_balance`
  - `insufficient_quota`
  - `insufficient_user_quota`
  - `quota_exhausted`
  - `balance_exhausted`
  - `credits_exhausted`
  - `E44001`
- 结构化字段表达 spending limit、余额耗尽或额度耗尽，且不是权限/模型限制。

### 允许的明确文案

- `insufficient balance`
- `insufficient quota`
- `balance exhausted`
- `quota exhausted`
- `run out of credits` / `out of credits`
- 明确的中文“余额不足”“余额耗尽”“额度不足”“额度耗尽”“配额已用完”等。

### 明确排除

- `forbidden`、`permission_denied`、`permission_error`
- `insufficient_scope`、`insufficient permissions`
- `model_not_found`、模型不可用或模型权限不足
- 没有余额证据的 402、403、429
- 网络错误、连接断开、502、503、504 等传输或服务可用性错误

分类器需要保持大小写不敏感、对 JSON 层级有兼容读取，并限制写入原因中的原始消息长度；不得持久化完整凭据、完整请求体或完整响应体。

## 7. 状态与兼容性

- 继续使用 `temp_unschedulable_until` 作为唯一账号级临时调度事实源。
- 继续保持账号 `status=active`，使现有余额探测和恢复服务能够工作。
- 继续使用现有余额隔离的长期时间戳与成功探测清除语义。
- 不改变普通 403 的现有 OpenAI 403 计数、临时冷却和达到阈值后的错误处理。
- 余额证据优先级高于池模式和自定义错误码，但不改变自定义错误码对非余额错误的既有语义。
- 不修改用户可见错误投影；用户仍按现有脱敏错误协议收到最终错误。

## 8. 场景化验收矩阵

| 场景 | 预期行为 |
|---|---|
| OpenAI 402 + `insufficient_balance` | 账号级临时不可调度，账号保持 active，当前请求允许切号 |
| OpenAI 403 + `insufficient_user_quota` | 同上，不被普通 403 或池模式早退吞掉 |
| OpenAI 403 + `E44001` | 同上 |
| OpenAI 403 + 中文余额/额度耗尽文案 | 同上 |
| 池模式 + 明确余额证据 | 仍执行账号级临时隔离 |
| 自定义错误码开启 + 明确余额证据 | 仍先执行余额隔离 |
| 普通 403 / `permission_denied` | 不进入余额隔离，保留原有权限错误语义 |
| `insufficient_scope` | 不进入余额隔离 |
| 404 模型不存在 | 不进入余额隔离，保留模型级现有处理 |
| 普通 429、502、503、网络错误 | 不进入余额隔离，保留既有限流/瞬时错误链路 |
| 余额探测成功 | 清除原生临时不可调度状态，账号恢复候选资格 |
| 重复收到同一余额错误 | 不新增第二套状态，不破坏已有隔离原因和恢复链 |

## 9. 测试策略

只增加与本任务直接相关的单元测试和必要的入口回归测试：

- 分类器覆盖所有新增 OpenAI 结构化错误码和中英文明确文案。
- 覆盖 `402/403`、池模式、自定义错误码早退顺序。
- 覆盖普通 403、权限、`insufficient_scope`、模型错误、普通 429 和 5xx 的排除。
- 验证 `SetTempUnschedulable` 被调用、`SetError` 未被调用、返回 `shouldDisable=true`。
- 验证已有恢复路径可识别并清除 `balance_exhausted` 原因。
- 运行 OpenAI 相关 service 定向测试、格式检查和必要构建；不扩大为无关全仓回归。
