# 官方 Sub2API v0.1.175 快速升级与定制回接规格

日期：2026-08-12  
状态：已批准（用户于 2026-08-13 明确批准并要求立即实施）

## 1. 目标

基于当前生产已验证的 `main@86abfde64`（生产版本 `0.1.173`）引入官方
Sub2API `v0.1.175`，保留现有星桥用户可见行为、计费安全边界、管理员入口和
发布合同，并通过最小必要门禁快速部署。

## 2. 范围

只处理本次官方三方合并产生的 9 个冲突文件：

- 后端网关处理、计费/定价、调度、流读取错误相关 6 个文件；
- 管理员用量页面及其 3 个前端测试/视图文件。

工作方式为：保存当前定制行为基线和测试证据，升级官方源码，再逐文件把定制
行为语义合并回官方实现。合并以行为为单位，不使用整文件 `ours/theirs` 覆盖。

## 3. 非目标

- 不进行架构外置或 `external-primary` 切换；
- 不实施 T03-R1 异步上游扣费持久化；T03-R1 仅在新基线稳定后继续；
- 不做无关模块重构、全仓性能优化或历史数据回填；
- 不改变客户售价、账号调度策略、管理员权限、主域名、菜单和 URL；
- 不使用 GitHub Actions。

## 4. 必须保留的现有行为

1. 现有客户计费、账号成本快照、利润字段和管理员/非管理员可见性。
2. T01/T02/T03/T04 已部署能力及其错误转译、上游扣费详情和账号监控原生接口。
3. 现有官方更新器、候选资格标签、迁移哈希和宿主蓝绿执行合同。
4. 用量页面现有筛选、分页、排序、详情和导出行为。

官方 `v0.1.175` 的响应模型计费、Responses/流错误、调度阈值和用量请求 ID
修复应在不破坏上述边界的前提下接入；若两者语义无法同时成立，候选停止并记录
冲突，不猜测取舍。

## 5. 实施流程

1. 从当前 `main` 创建独立升级候选 worktree，保留 T03-R1 worktree 不变。
2. 记录冲突文件的本地基线 blob、官方目标 blob 和现有定向测试。
3. 将官方 `v0.1.175` 合并到候选；逐文件完成定制行为回接，并新增必要的最小
   回归断言。
4. 更新 `XINGQIAO_UPSTREAM.md`、版本身份和候选报告；生成可恢复 bundle。
5. 在候选上执行最小资格门禁，确认迁移分类和 `downtime_required`。
6. 经独立复审后合入 `main`；在合并后的 `main` 上做同一组快速回归，推送并按
   宿主蓝绿链部署。
7. 线上只验收健康、版本身份、管理员更新状态、用量页面加载和一条非付费功能
   请求；失败保留候选并回滚到上一活动槽。

## 6. 最小验证矩阵

- 后端：冲突涉及包的 `go test`，以及 `go vet` 仅覆盖受影响包；
- 前端：`UsageView`、`UsageTable` 定向测试、typecheck 和生产构建；
- 发布：版本/官方 commit/镜像标签一致性、迁移哈希分类、`downtime_required`；
- 线上：`/healthz`、`/readyz`、公共版本、管理员会话版本状态、用量页请求。

不重复运行与本次冲突无关的全仓专项套件，除非定向测试或构建暴露跨模块回归。

## 7. 失败、冲突与回滚

- 出现未覆盖冲突、测试失败、版本身份不一致、迁移非 expand-only 或
  `downtime_required=true`：立即停止，不推送、不部署，保留 worktree、日志和报告。
- 蓝绿部署或线上验收失败：保留候选和失败证据，切回上一个活动槽；不删除候选。
- 回滚不修改数据库结构；如发现破坏性迁移，停止并进入人工维护流程。

## 8. 验收条件

候选在无未解决冲突、最小验证矩阵通过、迁移为 expand-only、
`downtime_required=false` 且版本身份一致后，才允许合入 `main` 和部署。
只有“推送成功 + 部署成功 + 线上验证生效”全部满足，才将本次升级标记完成。
