# 管理员经营页三层视图与异常状态设计

**日期：** 2026-08-15（Asia/Shanghai）  
**状态：** 设计已确认，待实施计划批准  
**任务性质：** 原生 Sub2API 管理员经营页的单一垂直体验修复

## 1. 问题证据与当前行为

当前管理员路由 `/admin/operations/account-profitability` 使用原生
`/api/v1/admin/operations/account-financial`，页面只渲染 `summary` 和
`accounts` 两层中的账号表格，没有全站固定摘要下的分组经营视图。现有财务服务按账号聚合
`usage_logs`，快照条目没有分组投影，因此前端无法可靠展示“全站 -> 分组 -> 账号”的层级。

账号行点击异常数量后，页面跳转到
`/admin/usage?tab=cost-exceptions&range=...&account_id=...`。用量页能读到路由 Tab，
但首次挂载时没有保证成本异常表在路由恢复后立即加载；`CostExceptionTable` 也没有加载中、
请求失败和成功空结果的可见状态，导致用户看到筛选区后下方像是没有内容。

## 2. 目标与非目标

### 目标

1. 经营页首屏保留全站固定财务摘要，并按“全站 / 分组 / 账号”逐层展开。
2. 分组金额由后端依据流水真实 `group_id` 聚合；未归属流水只进入全站，不被猜测归组。
3. 账号层继续支持今日营收/成本覆盖和 OAuth 每日成本录入。
4. 异常跳转保留账号、时间范围和待核对筛选；异常表提供 loading、empty、error/retry 三态。
5. 全站、分组、账号和异常核对继续读取同一份原生财务证据，不引入外部控制面或第二账务源。

### 非目标

- 不改变计费公式、调度、账号评分、分组排序或账号监控卡片。
- 不新增历史回填、延迟补查、上游重试、汇率或采购成本分摊。
- 不创建新的平行经营 API、外部控制面、账务数据库或普通用户入口。
- 不迁移既有 `usage_logs` 结构；预计不新增数据库迁移。

## 3. 影响用户与边界条件

- 影响对象：已登录管理员，尤其需要先看全站经营结果、再定位分组和具体账号的运营人员。
- 财务范围：继续按当前原生财务启用时间和时间范围语义计算；未知成本不计入利润，进入异常核对。
- 跨分组账号：账号可属于多个分组，但一条真实流水只按其 `usage_logs.group_id` 进入一个分组；全站按流水去重。
- 无分组流水：保留在全站摘要，并在分组维度显示“未归属”投影，不伪造分组归属。
- OAuth：不查询上游；仍由管理员按北京自然日填写成本，未填写时不进入可确认利润汇总。
- 空数据：合法的零流水显示明确空状态；接口失败显示错误和重试动作，不静默清空旧内容。

## 4. 方案比较与选择

### 方案 A：仅前端拼装

使用现有账号行在浏览器内相加，拼出全站和分组。实现快，但会重复计算跨分组账号、无法处理未归属流水，也违反财务聚合必须由后端提供的边界。

### 方案 B：扩展原生财务报告（选择）

在现有 `/admin/operations/account-financial` 报告中新增 `groups` 与分组关联字段，后端在同一财务快照中按真实流水聚合；前端只负责维度切换和展示。异常跳转继续使用原生用量页，并补齐路由加载与状态呈现。

优点是保持单一事实源、无需迁移、兼容旧客户端；代价是需要扩展快照条目和聚合测试。

### 方案 C：新建 v2 经营 API

另建完整经营 API 并保留旧财务 API。隔离性强，但会复制证据、核对和 OAuth 语义，形成两个可能漂移的账务入口，范围超过本请求。

## 5. 页面与数据流

```text
管理员进入经营页 / 刷新 / 切换时间范围
        |
        v
GET /api/v1/admin/operations/account-financial?range=<...>
        |
        v
原生财务快照 -> 全站 summary + groups[] + accounts[]
        |                         |
        |                         +--> 当前分组账号列表
        +--> 固定全站摘要 / 分组摘要

账号异常数量点击
        |
        v
/admin/usage?tab=cost-exceptions&review=pending&range=...&account_id=...
        |
        v
成本异常列表：loading / rows / empty / error + retry
```

经营页结构固定为：

1. 时间范围、刷新和全站摘要卡片；
2. 维度 Tab：`全站`、各分组、`未归属`（若存在）；
3. 当前维度摘要与账号列表；全站 Tab 显示全站账号，分组 Tab 只显示该分组真实流水/关联账号；
4. 账号异常数量作为进入异常核对页的显式操作。

## 6. 接口与字段契约

现有接口保持路径和查询参数不变：

`GET /api/v1/admin/operations/account-financial?range=today|24h|7d|31d`

响应保持现有字段，并以向后兼容方式增加：

```json
{
  "summary": { "revenue": 0, "cost": 0, "profit": 0, "margin": null, "exception_count": 0 },
  "groups": [{
    "id": 1, "name": "GPT-Pro", "revenue": 0, "cost": 0,
    "profit": 0, "margin": null, "exception_count": 0,
    "account_count": 0, "unassigned": false
  }],
  "accounts": [{
    "id": 1, "name": "account", "group_ids": [1],
    "amounts": { "revenue": 0, "cost": 0, "profit": 0, "margin": null },
    "exception_count": 0
  }]
}
```

字段命名可按现有 Go JSON 序列化约定落地；`groups` 缺失时旧客户端继续使用 `accounts`。
分组金额必须来自后端快照，前端不得从账号金额反推。

异常列表接口保持：

`GET /api/v1/admin/usage/cost-exceptions?account_id=...&start_time=...&end_time=...&review_status=pending`

## 7. 失败、安全与兼容语义

- 财务报告读取失败：保留页面结构，显示可重试错误；不得用旧缓存或估算值冒充实时事实。
- 异常列表读取失败：保留筛选栏并显示错误行和“重试”，不得渲染空表误导用户。
- 合法零结果：显示“当前筛选无待核对流水”，同时保留筛选条件和刷新能力。
- 异常跳转默认 `review=pending`，与经营页异常计数语义一致；用户可在异常页切换为全部/已核对。
- 所有接口继续使用既有管理员认证；响应不得暴露凭据、完整 API Key 或敏感请求体。
- 页面不得引入 `/xingqiao/**`、控制面状态、外部回退或联网补查。

## 8. 兼容性、迁移与发布

- 预计仅修改原生 Go service/repository/handler、Vue 页面、异常表、路由恢复逻辑和定向测试。
- 不修改数据库 schema、迁移、计费写入或调度字段；最终以根发布预检确认迁移集合不变。
- 生产发布只能从验证后的根 `main`，不使用 GitHub Actions；若预检给出 `downtime_required=true`，在停服前停止并等待用户确认。
- 部署或线上验证失败时保留候选 worktree、失败证据和可回滚 SHA，在同一候选修复。

## 9. 场景化验收矩阵

| 场景 | 验收条件 |
| --- | --- |
| 首次进入经营页 | 全站摘要、全站 Tab 和账号列表可见；只调用原生财务接口 |
| 切换分组 | 仅显示该分组后端返回的汇总和账号；不在前端二次累加 |
| 跨分组账号 | 全站流水只计一次；分组按真实 `group_id` 展示 |
| 未归属流水 | 只计入全站，并显示未归属提示/投影 |
| 点击异常 | URL 包含 `tab=cost-exceptions`、`review=pending`、账号和范围；列表请求发出 |
| 异常加载中 | 表格区域显示加载状态，不显示空表 |
| 异常无结果 | 显示明确空态和当前筛选仍可操作 |
| 异常接口失败 | 显示错误和重试；不吞掉错误 |
| 今日编辑 | 今日范围仍可编辑覆盖和 OAuth 成本，写入后刷新同一报告 |
| 非管理员/敏感数据 | 继续按既有鉴权和脱敏合同拒绝或隐藏 |
| 线上验收 | 管理员登录态初载、刷新、分组切换、异常跳转均成功；无控制面请求 |
