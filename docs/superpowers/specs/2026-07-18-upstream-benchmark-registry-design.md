# Spec: 上游渠道统一验收与历史台账

## Problem

首版中转站依赖其他中转站作为上游。价格、模型覆盖、真实并发、长流稳定性、计费口径和商业授权都可能变化，单次人工测试无法保证不同渠道使用同一标准，也无法保留可追溯的历史选择依据。

## Goal

建立一套可重复、可比较、可审计的上游验收机制。每个新渠道先按同一基准完成隔离测试，再决定是否进入候选、备用或生产；每次测试和选择都追加保存，使后续选择基于累积证据而不是当时印象。

## Non-goals

- 首版不建设数据库、Web 仪表盘或自动生产切流。
- 不自动充值、付款、注册、创建外部上游账号或同意供应商条款。
- 不把一次短测解释为长期 SLA、商业转售授权或供应商承诺。
- 不在文件、日志、Git 或报告中保存 API Key、Cookie、密码、TOTP、完整提示词或完整模型输出。
- 不自动删除现有生产账号、分组、用户或历史证据。

## Architecture

采用“项目内确定性脚本 + 可发现 Codex Skill + 追加式台账”结构：

1. Ruby CLI 执行 OpenAI 兼容渠道的直接 API 基准测试，使用环境变量注入临时 Key。
2. 渠道档案保存非敏感静态事实；运行记录保存一次测试的结构化指标；决策记录保存选择和复审条件。
3. 比较命令读取所有已验证渠道的最新合格运行，也允许指定历史时间点，生成 JSON 和 Markdown 排名表。
4. Codex Skill 规定外部控制台、Sub2API 隔离闭环、人工条款核验和清理流程，并调用项目脚本完成可自动化部分。
5. Neko 与 Aliu 使用相同字段进入台账；旧报告作为历史证据导入时必须标记 `evidence_source: historical_report`，不得伪装成新脚本运行。

## Components

### Channel Registry

`config/upstream-benchmarks/channels.yaml` 保存渠道非敏感身份：

- 稳定 ID、显示名称、Base URL、API 类型。
- 已知计费分组及标称倍率。
- 商业转售授权状态：`confirmed`、`denied`、`unknown`。
- 当前生命周期：`discovered`、`candidate`、`qualified`、`production`、`paused`、`rejected`。
- 证据链接和复审时间，不保存任何凭证。

### Benchmark Profile

`config/upstream-benchmarks/mvp-text-v1.yaml` 定义固定测试口径：

- 模型目录探测。
- 指定模型的同步最小请求。
- 指定模型的 SSE 流式请求和完整结束事件检查。
- 2 路与 3 路并发测试。
- 可配置的重复请求批次，用于错误率、P50/P95、首 Token 和总耗时。
- 响应 usage Token 汇总和响应结构校验。
- 默认严格限制最大请求数、最大输出 Token 和单请求超时。

长流测试使用较长但有上限的确定性输出，不使用用户业务内容。首版默认批次保持低成本；24 至 72 小时持续观察属于独立阶段，不在一次 CLI 运行中无限等待。

### Runner

`ops/upstream-benchmark.rb` 提供以下命令：

```text
run       执行直接上游测试并写入一次不可变运行记录
import    将已有 Aliu/Neko 报告转换为带来源标记的历史记录
compare   比较渠道最新合格记录或指定时间点记录
decide    追加保存选择、理由、拒绝项和复审条件
validate  校验渠道档案、测试配置和台账结构
```

`run` 只从调用时指定的环境变量读取 Key。输出必须自动清除认证头、Key 形态文本和响应正文，只保留状态码、事件类型、Token、时间、错误类别及哈希化请求模板 ID。

### Append-only Ledger

机器可读台账位于 `config/upstream-benchmarks/ledger/`：

- `runs.jsonl`：每行一次测试运行，使用 UUID、时间戳、profile 版本和渠道 ID 唯一标识。
- `decisions.jsonl`：每行一次渠道选择或状态变更，引用一个或多个运行 ID。

脚本只允许追加，不允许按 ID 覆盖旧行。若需要纠错，追加 `supersedes` 记录。比较输出是可重建派生物，不作为真相源。

### Comparison

比较结果至少包括：

- 模型覆盖及目标模型成功率。
- 同步、流式、并发、重复请求成功率。
- 首 Token、总耗时的 P50/P95。
- 最大已验证并发，不等同于供应商承诺上限。
- 标称倍率、实测实际/标准费用倍率、计费核对完整度。
- API usage、Sub2API 扣费、上游账单三方差异。
- 商业授权、国内/首尔链路、长期观察和证据新鲜度。
- 阻断项与适用角色：生产、候选、冷备用、拒绝。

排名不把未知项当作零风险。商业转售授权未知、三方计费未闭环、长流未验证等会显示为明确缺口；价格不能覆盖阻断项。

## Verification Flow

每个渠道按以下阶段推进：

1. `direct`：直接上游模型、同步、流式、并发、重复请求和 usage 测试。
2. `gateway`：通过 Sub2API 隔离账号、隔离分组、低余额临时用户和临时 Key 跑同步/流式闭环。
3. `billing`：核对 API usage、Sub2API 用户扣费、上游计费 Token 和上游实际金额。
4. `network`：从腾讯云首尔生产机测试，并记录中国大陆真实用户链路证据是否存在。
5. `terms`：记录商业转售授权、价格调整权、退款和容量条款的证据状态。
6. `decision`：追加选择结果和复审条件；不自动切流。
7. `cleanup`：禁用或删除测试 Key、临时用户、隔离分组和测试账号，确认生产对象未变。

阶段允许部分完成，但比较报告必须显示缺失阶段。只有明确完成的证据才能标记为 `verified`。

## Error Handling

- DNS、连接、TLS、超时、HTTP、协议、SSE、模型不可用和限流错误分开分类。
- 任一测试达到成本或请求数上限后立即停止剩余可选测试，并保存部分结果。
- 运行记录即使失败也追加，状态为 `failed` 或 `partial`，用于观察供应商历史波动。
- 台账 JSONL 有无效行、重复运行 ID、未知渠道 ID 或时间倒退时，`validate` 返回非零。
- 对比时不静默丢弃失败记录；最新失败会影响证据新鲜度和当前判断。

## Security and Production Safety

- Key 仅通过用户指定的环境变量名读取，不接受命令行明文 Key。
- 默认拒绝 localhost 以外的明文 HTTP Base URL。
- 默认不允许测试生产分组；Sub2API 阶段必须使用带日期的隔离对象。
- 自动化脚本不直接操作浏览器、支付或生产切流；这些动作由 Skill 按授权边界执行。
- 报告中只保留非敏感统计和脱敏错误摘要。

## Test Strategy

- 使用 Ruby Minitest 和本地临时 HTTP 服务验证目录、同步、SSE、超时、限流、错误分类和并发计时。
- 测试 Key 脱敏、响应正文不落盘、JSONL 追加、重复 ID、纠错记录和比较排序。
- 使用固定 fixture 导入 Aliu 与 Neko 历史报告，验证来源标签和不可伪造的证据级别。
- 真实 Neko 运行作为联网验收，不替代离线自动化测试。
- Skill 使用 `quick_validate.py` 校验，并通过一次真实项目调用验证命令、产物和安全流程。

## Acceptance Criteria

- [ ] 一个命令可对 OpenAI 兼容渠道执行低成本直接基准测试，且 Key 和响应正文不落盘。
- [ ] 每次成功、失败或部分测试都追加一条不可变运行记录。
- [ ] Aliu、Neko 和后续渠道可以使用同一字段生成对比报告。
- [ ] 可以追加记录最终选择、理由、阻断项和复审条件，并追溯到测试运行。
- [ ] 历史报告导入与实时脚本结果具有不同证据级别。
- [ ] Neko 完成与 Aliu 等价的 Sub2API 同步、流式和三方计费闭环，或明确记录无法完成的具体阻塞。
- [ ] 清理测试资源后，生产 Aliu 和 `openAI` 路由保持不变。
- [ ] 新 Skill 可被后续 Codex 用于“验证新渠道、比较上游、决定是否切换”等任务。

## Risks

- 供应商控制台没有计费 API 时，账单核对仍需要浏览器人工取证，脚本只能记录结果。
- 短测不能替代 24 至 72 小时持续观察和中国大陆多线路样本。
- 不同模型可能采用不同计费单位，首版 profile 仅覆盖 OpenAI 兼容文本 Token；图片、音频和实时模型必须新增独立 profile。
- 单一综合分数容易掩盖阻断项，因此报告优先展示门槛、证据和分项指标，综合排序只作辅助。
