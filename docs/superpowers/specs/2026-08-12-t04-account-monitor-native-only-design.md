# T04 账号监控仅使用原生 Sub 数据设计

## 问题证据与当前行为

账号监控页面 `upstream/sub2api/frontend/src/views/admin/AccountMonitorView.vue` 当前存在两条串行读取链路：页面先调用原生 `adminAPI.accountMonitor.list(range)`，随后调用外部控制面的页面决策接口；在决策允许时继续调用外部账号监控投影接口。外部投影通过完整性校验后可以替换原生投影，否则页面回到原生卡片并显示控制面降级状态。

现有页面因此具有以下可观察行为：

- 首次加载、时间窗切换以及写操作后的重载都会经过外部控制面决策，可能继续请求 `/xingqiao/accounts/monitor`。
- 外部读取失败、超时或被拒绝时，原生卡片仍可显示，但页面会出现“控制面暂时不可用”“完整性 unknown”等状态。
- 外部请求串行位于原生读取之后，会延后一次页面加载周期的提交完成时间。
- 外部主读模式下，通过校验的外部投影可以替换 `/admin/accounts/monitor` 返回的原生投影，使账号监控并非始终只有一个页面数据源。

组件测试 `upstream/sub2api/frontend/src/views/admin/__tests__/AccountMonitorView.spec.ts` 当前明确覆盖 shadow 模式、external-primary 替换、外部失败降级、401/403 降级和控制面状态条。这些测试证明上述行为是页面现有的显式契约，而不是未使用代码。

## 目标

- 账号监控在首次加载、时间窗切换、用户刷新、以及任意写操作后的页面投影重载中，对 `/xingqiao/**` 实现零请求；既有独立并发轮询继续使用其原生接口。
- `/admin/accounts/monitor` 始终是账号监控页面卡片和分组投影的唯一数据源。
- 删除账号监控页面上的外部控制面状态、完整性信息、外部投影校验和数据源切换逻辑。
- 不新增“原生数据源”“完整性”或其他替代性常驻状态条；正常状态只显示原有账号监控内容。
- 保持现有卡片、布局、样式、筛选、时间窗、分组、弹窗、按钮、轮询及写操作交互不变，用户可见变化仅为不需要的控制面状态条消失。
- 保持原生请求失败时现有的快照保护、错误提示和重试语义。

## 非目标

- 不修改 T05 用量页、T06 利润页、T07 全局评分、T08“暂不建议入组”或 T09 官方更新。
- 不清理共享 `controlPlane.ts`、`ReadModelStatus.vue`、`useReadModelFreshness.ts`、外部化决策配置或其共享测试；这些边界留给严格串行的 T05/T06。
- 不引入 external-primary、relay-ops 主路径依赖、新平行控制面或新的数据源抽象。
- 不修改账号卡片信息、排序、评分、排名、成本、倍率、并发、分组汇总或任何业务计算。
- 不修改后端接口、数据库、迁移、权限、路由、运行配置或生产数据。
- 不做全站回归、长时间轮询观测、专项性能测试或 T05/T06 页面验证。

## 影响用户与边界条件

直接影响对象是使用原生 Sub2API 管理后台账号监控页面的管理员。正常情况下，管理员继续看到相同卡片和交互，但页面不再等待或呈现外部控制面状态。

需要保持的边界条件包括：

- 首次进入页面时没有可用快照。
- 已成功加载卡片后，刷新或切换时间窗失败。
- 用户快速切换多个时间窗，旧请求晚于新请求返回。
- 页面卸载或新请求开始时，旧请求被主动取消。
- 批量探测、单账号探测、优先级、采购成本、倍率和评分权重等写入已成功，但随后的原生卡片重载失败。
- 并发轮询失败或延迟时，现有 delayed 状态及重新轮询行为保持不变。
- 外部控制面成功、失败、超时、401、403 或响应字段变化均不影响本页面，因为本页面不再发出相关请求。

## 方案比较与选择

### 方案 1：删除页面级外部依赖与切换逻辑（采用）

从 `AccountMonitorView.vue` 删除外部控制面导入、状态条、外部状态、投影校验和 `loadControlPlane()`；将既有 `load()` 收敛为原生单读。仅重写账号监控组件测试，证明所有页面场景均为原生加载且不存在 `/xingqiao/**` 请求。

优点是数据流单一、零请求契约直接、删除范围与 T04 完全一致，且不影响共享设施和其他页面。代价是账号监控不再保留页面级外部切换能力；这是本任务的明确目标。

### 方案 2：用永久页面开关短路外部逻辑（不采用）

保留外部导入和分支，通过固定开关阻止请求。短期改动较小，但留下不可达代码、状态和测试歧义，未来配置漂移可能重新产生外部请求，不能形成稳固的零请求契约。

### 方案 3：在共享控制面客户端短路账号监控（不采用）

修改 `controlPlane.ts` 使 monitor 调用不再访问网络。该方式会把页面职责隐藏到共享层，并扩大到 T05/T06 依赖的公共边界，产生跨任务耦合，不符合本轮只修改账号监控页面的范围。

选择方案 1，因为它以最小、显式且可测试的页面级删除实现用户已经确认的唯一数据源和零 `/xingqiao/**` 契约。

## 端到端数据与控制流

### 读取流程

1. 页面挂载或用户选择时间窗时，`load(range)` 取消上一轮原生请求并递增 generation。
2. 页面设置 loading/pending 状态并清除本轮 `rangeError`。
3. 页面只调用 `adminAPI.accountMonitor.list(range, { signal })`，对应原生 `/admin/accounts/monitor`。
4. 返回后先检查请求是否已取消或 generation 是否过期；过期结果静默丢弃。
5. 校验响应 `range` 与请求时间窗一致；一致时提交 `projection` 和 `activeRange`，并保留现有分组选择修正逻辑。
6. `finally` 仅由当前 generation 清理 loading/pending 状态。

此流程没有外部决策、外部 monitor 获取、外部投影校验或数据源替换阶段。

### 写后重载流程

批量探测、单账号探测、优先级、采购成本、账号倍率和分组评分权重等现有写操作不改变请求、按钮、对话框或反馈流程。写操作成功后仍调用同一个 `load(activeRange)`；该共享加载函数已经是原生单读，因此所有写后重载自然满足零 `/xingqiao/**`。

### 并发轮询

账号并发数据继续使用既有原生 `getConcurrency` 路径。可见账号集合、页面隐藏处理、in-flight/queued 合并和 delayed 标记不变。本任务不把并发轮询合并进 monitor 投影，也不改变其失败语义。

## 接口与字段契约

- `/admin/accounts/monitor` 的请求参数、`range` 语义、响应类型 `AccountMonitorProjection` 和全部字段保持不变。
- 页面仍使用响应中的 `schema_version`、`range`、`observed_at`、`stale`、`settings`、`health`、`groups` 和 `accounts`；不新增、不删除、不改名字段。
- 账号卡片、筛选器、成本弹窗和评分权重弹窗的 Props、事件和数据结构保持不变。
- 所有写接口及并发接口契约保持不变。
- 页面不再消费外部控制面的 decision、freshness、degraded、calculation version 或 monitor items；共享控制面接口本身保持可用，供其他页面后续任务处理。
- 不新增 API、DTO、特性开关、环境变量或配置项。

## 失败与安全语义

- 原生请求成功：提交新投影，正常显示原有页面内容，不显示任何数据源或完整性常驻状态。
- 首次加载失败且没有成功快照：结束加载骨架，显示原生错误空态及明确重试入口。
- 已有成功快照后加载失败：保留最后一次成功的 `projection` 和卡片，同时显示原生加载错误及重试入口；不得清空快照或回退到外部数据。
- 原生响应时间窗不匹配：按原生加载失败处理，不提交错误时间窗的数据。
- 主动取消或 generation 过期：静默丢弃，不显示错误，不覆盖新请求状态。
- 写操作成功但原生重载失败：保留现有针对该操作的明确“操作成功，但最新卡片加载失败，请重试”反馈和已有卡片快照。
- 外部控制面的网络、鉴权、完整性或字段状态不再具有页面失败含义，因为账号监控不会请求或解析外部数据。
- 不在前端伪造原生成功数据，不把外部响应作为容灾备份，也不改变权限或会话处理。

## 兼容性与迁移

- 这是前端页面级删除，不需要数据库迁移、数据回填、后端兼容层或配置迁移。
- 原生 API 和全部卡片组件契约不变，因此无需双读、灰度字段或消费者迁移。
- 共享控制面设施不删除，T05/T06 可以在后续串行任务中独立决定对应页面的收敛方式。
- 已保存的浏览器状态不需要迁移；页面重新加载后自然使用原生单读流程。
- 回滚时可以反向恢复本任务的页面和测试提交，不涉及数据恢复。

## 测试策略（最小 MVP）

仅调整账号监控组件测试，并保留与本次范围直接相关的既有回归。最小验证覆盖：

1. 首次加载与时间窗切换只调用 `adminAPI.accountMonitor.list`，且页面不再导入、mock 或调用账号监控控制面 API。
2. 选取一个代表性写操作，验证写后重载复用原生 `load()`；不为每一种同构写操作重复新增测试。
3. 正常成功状态显示原有卡片，页面不存在“控制面暂时不可用”“完整性”或替代常驻状态。
4. 原生首次加载失败时显示错误空态和重试；已有快照后失败时保留快照并显示错误和重试。
5. 保留请求取消/generation 保护和主要卡片交互的既有测试，不扩大到全站或 T05/T06。

实施验证至少运行：

- `AccountMonitorView.spec.ts` 专项组件测试。
- 前端构建或仓库规定的一个最低必要静态检查；实施计划根据实际 package scripts 写出准确命令。
- `git diff --check` 和变更范围检查。

不执行额外全站回归、长时间轮询观察或专项性能测试，除非最小检查暴露共享回归风险。

## 发布、线上验证与回滚条件

### 发布属性

- 预计为纯前端页面改动。
- 无数据库迁移、配置变化或停机要求，`downtime_required=false`；最终以合并后发布预检为准。
- 不使用 GitHub Actions，继续使用项目既有、已审查的本地/宿主发布链。

### 门禁与发布顺序

1. 独立候选完成规格、获批计划、实现、任务复审和整分支终审后，报告 `READY_FOR_ROOT_REVIEW`。
2. 未收到根任务包含目标 `main` SHA 的 `AUTHORIZE_MERGE_TO_MAIN` 前，本任务不得合并、推送或部署。
3. 获得授权后，将候选合并到指定 `main`，在合并后的 `main` 上执行最低必要专项测试和构建检查。
4. 推送已验证的 `main`，再通过既有本地/宿主链部署生产。
5. 只有推送、部署和线上验证全部成功，才能在总账标记完成并按工作区生命周期规则清理候选。

### 线上最小 MVP 验证

- 使用登录态打开账号监控页，确认原有卡片正常显示且无控制面状态条。
- 切换一个时间窗，并触发一次手动刷新或代表性写后重载。
- 在上述最小流程的浏览器网络记录中确认存在原生 monitor 请求且 `/xingqiao/**` 请求为零。
- 确认页面主要卡片和交互没有明显变化，公网及发布链要求的基础健康检查通过。

### 失败和回滚条件

- 专项测试、最低构建检查、合并后检查、部署或线上 MVP 验证任一失败，均不得标记完成。
- 失败时保留候选 worktree、提交和证据，在同一候选上修复，并重新执行“合并到 `main`、并版验证、推送、部署、线上验证”链路。
- 若线上出现 `/xingqiao/**` 请求、卡片/主要交互回归、原生错误语义丢失或基础健康异常，则回滚本任务候选提交，通过同一受控发布链重新发布并验证。
