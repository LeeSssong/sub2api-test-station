# 飞书确定性运维命令设计

## 状态

本设计于 2026-07-20 由用户确认。它扩展现有 `relay-ops-service`，让已发布的“星桥AI监控Agent”接收飞书群消息，并以固定命令控制 Sub2API 公开分组的主、灾备上游绑定。

本文只定义实现和上线边界。设计、测试和本地构建不得修改生产 Sub2API 分组；真实凭据安装、飞书权限发布、事件回调启用和生产写模式开启必须在实现验证完成后分别执行。

## 目标

机器人加入任何飞书群后，该群所有成员都可以使用以下固定命令：

```text
切换 GPT-Pro 到灾备
切换 GPT-Plus 到灾备
恢复 GPT-Pro 主分组
恢复 GPT-Plus 主分组
查询当前分组状态
```

切换操作只改变 `GPT-Pro` 或 `GPT-Plus` 公开分组绑定的上游账号，不改变用户、API Key、分组名称、用户价格、模型价格或权限范围。机器人必须把最终状态和执行结果回复到发出命令的群聊。

## 非目标

- 不使用大模型解释、改写或选择命令。
- 不执行消息中的 shell、参数、URL、账号 ID 或其他动态内容。
- 不接受模糊匹配、别名、自然语言意图或组合命令。
- 不自动判断何时发生故障；本期只处理人工发出的确定性命令。
- 不迁移用户或 API Key 到另一个分组。
- 不调整价格、余额、模型目录、支付、注册或候选上游配置。
- 不允许飞书私聊执行生产切换；私聊只返回命令必须在群聊中使用。
- 不允许机器人、应用或系统消息触发动作。

## 总体架构

在现有 `relay-ops-service` 内增加四个边界清晰的单元：

1. `feishuevents`：验证飞书回调、解析文本事件并快速应答。
2. `commands`：规范化消息、精确匹配命令、去重、排队和审计。
3. `routingcontrol`：读取并切换 Sub2API 公开分组的主/灾备上游账号。
4. `feishuapi`：获取 `tenant_access_token` 并向原群聊回复执行结果。

数据流如下：

```text
飞书 im.message.receive_v1
  -> POST /relay-ops/api/feishu/events
  -> 签名、时间戳、verification token 和加密信封校验
  -> 解析文本、群聊、发送者和 event_id
  -> 精确命令匹配
  -> PostgreSQL 幂等写入并排队
  -> HTTP 200 快速返回飞书
  -> 单独 worker 获取分组锁
  -> Sub2API 管理 API 预检、切换、复读验证
  -> 飞书 OpenAPI 回复原 chat_id
  -> 保存脱敏结果和最终状态
```

事件入口不得同步等待 Sub2API 切换完成。飞书可能重试超时事件，先持久化再快速返回可以避免同一命令被执行两次。

## 飞书事件接收

公开入口固定为：

```text
POST /relay-ops/api/feishu/events
```

Caddy 只把这一个路径转发给 `relay-ops-service`。入口不使用 Sub2API 管理员登录，而使用飞书事件协议自身的验证机制。

服务必须支持飞书 URL 验证 challenge，并校验：

- 请求时间戳在允许窗口内，默认最多偏差 5 分钟。
- 请求签名与配置的 Encrypt Key 一致。
- 解密后的 verification token 与秘密文件一致。
- 事件类型严格等于 `im.message.receive_v1`。
- 消息类型严格等于 `text`。
- chat type 为群聊。
- sender type 为真实用户，不是 bot、app 或 system。
- `event_id`、`message_id`、`chat_id` 和 sender `open_id` 均存在且满足长度上限。
- 请求体不超过 256 KiB，解密后的文本不超过 4 KiB。

飞书侧需要启用机器人接收消息能力、订阅 `im.message.receive_v1`，并增加接收群消息所需的最小权限。现有 `im:message:send_as_bot` 继续用于回复。权限变更和新版本发布在回调服务可从公网完成 challenge 后进行。

## 命令规范化与匹配

群聊通常需要先 `@` 机器人。处理器只允许以下规范化：

1. 解析飞书文本消息的结构化 JSON。
2. 删除消息开头由飞书事件明确标记为当前机器人的一个 mention。
3. 删除命令前后的 Unicode 空白。

规范化后必须与五条白名单命令之一逐字相等。不得做大小写折叠、标点替换、分词、正则意图匹配或相似度判断。消息含额外参数、第二条命令、链接、代码块或其他文本时一律不执行，只回复固定帮助文本。

所有机器人已加入的群都允许使用命令，不配置 `chat_id` 白名单。所有群成员权限相同。由于这是用户明确选择的授权模型，审计记录必须保留发送者和群聊标识。

## 动作注册表

生产代码内使用不可由配置扩展为任意程序的固定动作注册表：

| 命令 | 动作 |
|---|---|
| `切换 GPT-Pro 到灾备` | `SwitchGroup(GPT-Pro, backup)` |
| `切换 GPT-Plus 到灾备` | `SwitchGroup(GPT-Plus, backup)` |
| `恢复 GPT-Pro 主分组` | `SwitchGroup(GPT-Pro, primary)` |
| `恢复 GPT-Plus 主分组` | `SwitchGroup(GPT-Plus, primary)` |
| `查询当前分组状态` | `ReadAllGroupStatus()` |

本期不调用 `/bin/sh`、`bash -c` 或从消息拼接 `exec.Command`。用户所说的“脚本 A”在实现中等价为一个固定、可测试的 Go 动作函数；它直接调用受约束的 Sub2API 管理客户端，因此没有 shell 注入面。

## 主灾备配置

每个公开分组在部署时必须配置以下不可由飞书消息修改的标识：

```text
public_group_id
primary_account_id
backup_account_id
```

仅允许 `GPT-Pro` 和 `GPT-Plus` 两项。标识来自权限为 `0640` 或更严格的本地配置文件，文件中不得包含上游 API Key。配置加载时必须验证：

- 两个公开分组 ID 不重复。
- 每个分组的主、灾备账号 ID 不同。
- 同一个账号不能同时作为两个公开分组的可写目标，除非未来设计另行批准。
- 所有 ID 为正整数，且运行时从 Sub2API 读出的名称与预期名称一致。

任一校验失败时，命令服务保持 `disabled`，但现有监控和公开价格服务继续运行。

## 切换算法

每个公开分组使用独立的 PostgreSQL 锁，同一分组同一时刻最多执行一个状态变更。`GPT-Pro` 与 `GPT-Plus` 可以独立处理，但单个 worker 默认串行执行，以保持首版行为简单。

切换步骤固定为：

1. 读取公开分组、主账号和灾备账号的最新状态。
2. 验证三个对象都存在，名称和配置匹配，目标账号已启用、凭据状态正常、支持该公开分组要求的模型集合。
3. 若当前状态已经等于目标状态，记录 `no-op` 并回复成功，不发送写请求。
4. 先把目标账号加入该公开分组并设为可调度。
5. 复读确认目标账号已可调度且绑定正确。
6. 再从该公开分组移除源账号的可调度绑定；保留源账号对象和凭据，不删除账号。
7. 再次复读，确认目标可调度、源不再承接该分组、分组名称和价格未变化。
8. 保存前后快照和最终结果，并向原群回复。

“恢复主分组”执行同一算法，只是目标和源互换。先启用目标、后停用源会产生短暂重叠，但不会产生没有可用上游的空窗，优先保证服务连续性。

若步骤 4 或 5 失败，不修改源账号。若目标已启用而步骤 6 或 7 失败，保留双账号可调度状态，不自动进行第二次写操作；结果标记为 `partial`，机器人明确提示需要人工复核。系统不得在状态未知时声称切换成功。

## Sub2API 客户端边界

扩展现有 `relay-ops-service/internal/sub2api` 客户端，使用现有受限管理员凭据访问已安装版本提供的管理 API。客户端必须：

- 先读取、后修改、再复读，不直接写 PostgreSQL。
- 对请求和响应设置大小上限与超时。
- 不记录 Authorization、Cookie、上游 Key、完整响应体或其他秘密。
- 对账号、分组和绑定响应使用严格 JSON 解码并拒绝未知关键状态。
- 将冲突、权限不足、对象不存在、上游凭据异常和状态未知分类为稳定错误码。
- 只暴露读取状态和设置固定账号分组绑定所需的方法，不提供通用管理 API 代理。

实现前必须针对生产正在运行的 Sub2API 版本确认实际管理 API 契约，并用本地 fake server 固定请求与响应测试。不得为绕过缺少的 API 直接修改生产数据库。

### 已核验的 v0.1.161 原生契约

实现依据已固定到官方仓库 `Wei-Shaw/sub2api` 的 `v0.1.161`（commit `19149ca196eeae4a4482e5299dc6fa4ba0b06c8c`）。该版本确认支持：

- `GET /api/v1/admin/groups/:id` 读取公开分组。
- `GET /api/v1/admin/accounts/:id` 读取账号及其 `group_ids`、`status`、`schedulable` 和凭据存在性状态。
- `GET /api/v1/admin/accounts/:id/models` 读取账号当前可用模型集。
- `PUT /api/v1/admin/accounts/:id` 仅提交 `{"group_ids":[...]}` 时，未提供的名称、凭据、优先级、倍率和状态保持不变；服务先验证分组存在性与混合渠道风险，再通过 `BindGroups` 原子替换该账号的完整分组绑定。
- `POST /api/v1/admin/accounts/:id/schedulable` 以 `{"schedulable":true}` 设置账号全局可调度状态。
- 上述管理路由同一 Admin 中间件保护，支持现有 `x-api-key` 管理密钥。

官方网关在 standard 模式下通过 `ListSchedulableByGroupIDAndPlatform` 选择账号，其权威条件是账号已绑定该 `group_id`、`status=active`、`schedulable=true`，且不处于临时不可调度、过期、过载或限流窗口。因此本设计不修改 Channel，不直连 Sub2API 数据库，而是保留两个账号现有的其他 `group_ids`，使用上述原生 API 完成先目标、后源账号的绑定替换。若 Sub2API 返回 HTTP 409 `mixed_channel_warning`，命令必须失败，不得自动提交 `confirm_mixed_channel_risk`。

## 运行模式与安全门

新增独立模式：

```text
RELAY_OPS_FEISHU_COMMAND_MODE=disabled|dry_run|enabled
```

- `disabled`：默认值；验证回调并回复“命令功能未启用”，不读取写凭据。
- `dry_run`：完整执行校验、状态读取、锁和审计，但不调用 Sub2API 写 API；回复预计变化。
- `enabled`：允许四条切换/恢复命令调用固定写 API；查询命令始终只读。

生产首次上线顺序固定为 `disabled -> dry_run -> enabled`。只有 dry-run 在真实飞书群和真实 Sub2API 只读状态上通过后，才能单独批准 `enabled`。现有 `RELAY_OPS_MODE` 继续控制监控和探测，不被此功能重定义。

## 幂等、并发与审计

新增 PostgreSQL 命令表，至少保存：

- 飞书 `event_id` 唯一键和 `message_id`。
- `chat_id`、sender `open_id`、规范化后的白名单命令。
- 目标公开分组和目标角色 `primary|backup`。
- `received|running|succeeded|no_op|partial|failed|rejected` 状态。
- 执行前后非敏感状态快照、稳定错误码、耗时和时间戳。
- 飞书回复的 message ID 或投递失败状态。

同一 `event_id` 的重试只读取已有记录，不再执行。若首次进程在执行中退出，worker 只能在租约超时后恢复未完成任务，并在重新写入前重新读取 Sub2API 当前状态。恢复逻辑仍必须满足幂等条件。

审计只保存规范化后的白名单命令，不保存原始聊天内容。日志不得输出完整 `chat_id` 或 `open_id`，只输出带进程内密钥的短哈希；数据库保留原 ID 用于回复和事故追踪，访问沿用现有 PostgreSQL 权限边界。

## 飞书回复

回复使用自建应用凭据获取短期 `tenant_access_token`，并通过飞书 OpenAPI 发送到原 `chat_id`。App ID、App Secret、verification token 和 Encrypt Key 分别从只读秘密文件加载，不写入 Git、环境变量值、日志或审计表。

状态变更成功回复包含：

- 命令名称。
- 执行者的飞书显示 mention 或脱敏 ID。
- 目标公开分组。
- 执行前主/灾备角色。
- 执行后主/灾备角色。
- `succeeded` 或 `no-op`。
- 耗时和短审计编号。

失败或部分成功回复包含稳定错误码、已完成步骤、复读到的最终非敏感状态和明确的人工复核提示。不得返回管理员凭据、上游 Key、原始 HTTP 响应、堆栈或服务器路径。

收到有效命令后可先回复一次“已受理”，最终结果随后发送。飞书投递失败不得回滚已经完成的 Sub2API 切换；worker 应记录失败并有限重试回复，最多 3 次。

## 错误处理

- 无效签名、token、时间戳或密文：返回拒绝，不创建命令记录。
- 非群聊、非用户、非文本：返回 200 并忽略，避免飞书重复投递。
- 未知命令：不执行，向群聊回复固定帮助文本；同一消息只回复一次。
- 配置不匹配：命令标记 `rejected`，不写 Sub2API。
- Sub2API 读取失败：命令标记 `failed`，不尝试写入。
- 写入超时或响应未知：立即复读；无法确认时标记 `partial`，不自动反向写入。
- 数据库不可用：事件入口返回可重试错误，禁止在没有幂等记录时执行动作。
- 飞书 token 或回复失败：保留动作结果并重试回复，不重复执行动作。

## 测试策略

实现严格遵循测试先行：

1. 飞书 challenge、签名、加密、过期时间戳、请求大小和事件解析测试。
2. leading bot mention 删除、五条精确命令、未知/组合/带参数消息拒绝测试。
3. 群聊所有真人成员允许、私聊和机器人消息拒绝测试。
4. `event_id` 去重、并发锁、worker 重启恢复和回复重试测试。
5. 主到灾备、灾备到主、已是目标状态、预检失败、第一步失败、部分成功和复读不一致测试。
6. fake Sub2API server 契约测试，确认只调用允许的读取和绑定接口。
7. fake Feishu OpenAPI 测试，确认 token 缓存、chat_id 定向回复和秘密不泄漏。
8. HTTP server 测试，确认事件路径公开但其他管理路径仍要求管理员鉴权。
9. Compose/Caddy 契约测试，确认只公开精确回调路径、秘密文件只读、默认模式为 `disabled`。
10. PostgreSQL E2E 测试和 `go test ./... -race`、`go vet ./...` 全量回归。

真实上线验收分三阶段：

1. `disabled`：飞书 challenge、事件接收和拒绝回复通过。
2. `dry_run`：五条命令在真实群聊返回正确的预计前后状态，Sub2API 无写入。
3. `enabled`：在用户明确批准后，对一个公开分组执行灾备切换、状态查询和主分组恢复；每一步核对 Sub2API 后台、网关同步请求、SSE 完整性和审计记录。

## 部署与回滚

部署新增秘密文件和主灾备配置，但默认保持 `disabled`。Caddy 路由、飞书事件订阅和应用新版本发布都在服务健康后配置。

关闭命令功能只需把 `RELAY_OPS_FEISHU_COMMAND_MODE` 设为 `disabled` 并重建 `relay-ops`；这不会改变当时已经生效的 Sub2API 绑定。若需要恢复主分组，应在禁用命令前执行固定恢复命令或通过 Sub2API 官方管理界面人工恢复，并复核请求。

代码回滚不得自动改变生产路由。任何处于 `partial` 的命令必须先人工确认实际绑定，再决定恢复方向。

## 完成标准

- 五条命令均通过精确匹配、权限、幂等和并发测试。
- 不存在从飞书消息到任意 shell 或通用管理 API 的路径。
- 未知命令、私聊和机器人消息不能修改状态。
- 主灾备切换遵守先启用目标、复读、后停用源、再复读的顺序。
- 所有成功、无操作、失败和部分成功均产生可追踪审计和飞书结果。
- 默认部署不能写生产；dry-run 验收和用户单独批准后才能启用写模式。
- 真实切换验收证明用户 API Key、分组价格和模型范围保持不变，网关同步和 SSE 请求正常。
