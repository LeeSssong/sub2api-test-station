# 账号监控：全站经营、分组运营与账号质量设计

**日期：** 2026-08-01（Asia/Shanghai）  
**状态：** 产品设计已确认；待用户审阅本书面规格后再编写实施计划。

## 目标

将管理员账号监控页重构为一个用于运营决策的页面：先判断全站是否健康、是否赚钱；再按分组观察服务质量与投入产出；最后使用账号质量分辅助查看每个分组内的账号。质量分和分组排序均只影响监控展示，绝不改变生产调度。

## 一、页面层级与排序

```text
账号监控
├── 全站经营总览（默认“今日”，同时显示历史累计）
├── 固定全站摘要栏（进入分组后保持可见）
├── 分组 Tab（按分组倍率从高到低）
│   └── 当前分组的服务健康 + 经营结果 + 评分规则
└── 当前分组的账号卡片
    ├── 正常、成本合格账号（按账号质量分排序）
    ├── 不可用 / 成本不合格 / 待确认账号折叠区
    └── 暂停账号说明区
```

- `全站`为首个入口；分组 Tab 统一按分组倍率从高到低，倍率相同则保持 Sub2API 原有稳定顺序。
- 不创建分组质量分，不按分组质量分排序，不创建可编辑的分组优先级。
- 分组排序只影响账号监控页展示，不写入 `groups.sort_order`，不影响用户可见顺序、账号调度或流量分配。
- 账号的唯一可编辑调度字段仍是 Sub2API 原生 `accounts.priority`。它是全局调度优先级，不是监控评分权重。

## 二、全站与分组经营视图

### 全站首屏

默认时间范围为服务器配置时区当日 `00:00` 至当前时间，并在同一屏低强调显示历史累计；点击“账务历史”后从右侧打开抽屉，查看按日数据（默认最近 30 天，支持 7 天、30 天和自定义范围）。

全站总览固定分为两个区块：

| 区块 | 指标 |
|---|---|
| 经营结果 | 上游真实扣费、用户实际计费、纸面利润、利润率、成本覆盖率、待对账笔数 |
| 服务健康 | 可用、不可用、待确认、暂停账号数量；成功率、TTFT P50、总耗时 P95 |

进入任一分组后，全站总览收缩为固定摘要栏，继续显示今日成本、营收、利润、成本覆盖率和待对账，避免用户失去全局感。

### 分组视图

每个分组 Tab 的头部复用同样的两类信息，但统计范围只限当前分组：

- 服务健康：可用 / 不可用 / 待确认 / 暂停数量、成功率、TTFT P50、总耗时 P95；
- 经营结果：请求、Token、上游真实扣费、用户实际计费、纸面利润、利润率、成本覆盖率、待对账；
- 低强调展示历史累计，并提供当前分组范围的“账务历史”入口；
- “评分规则”入口用于编辑本分组的账号质量评分权重。

分组没有质量评分。其异常语义如下：

- `inactive` 或当前未向任何有效用户开放的分组显示“已关闭”或一次性运营提示，不作为故障反复报警；
- 已开放且无可用账号的分组才进入异常状态；真实用户请求失败可覆盖“未开放”的抑制条件。

## 三、账号卡片

账号卡片必须复用现有渠道监控的深色卡片、双列布局、状态边色和“最近 5 分钟监测情况”绿色柱状时间序列；不能替换为普通统计卡或表格。

每张卡片分为两个可扫描区域：

| 区域 | 内容 |
|---|---|
| 服务质量 | 质量评分、组内质量名次、成功率、TTFT P50、总耗时 P95、数据来源、置信度、样本数、更新时间 |
| 投入产出 | 上游真实扣费、用户实际计费、纸面利润、利润率、成本覆盖率、待对账信息；今日为主、历史累计为次级行 |

- 卡片中部保留绿色监测柱状图：明确不可用时才使用红色；可用但较弱仍用绿色深浅和柱高表达；无数据或过期使用中性灰。
- 真实账单未覆盖完整时，利润须标记“待对账”，不能用倍率估算伪造真实利润。
- 卡片中“账号权重”可直接编辑 Sub2API 原生 `priority`；保存后立即刷新原生优先级显示，但不得改变质量分排序。

## 四、账号质量评分

质量分只存在于账号层面。不可用、暂停、成本不合格或证据过期账号不进入正常排序，分别显示在独立折叠区或说明区。

每个分组拥有独立、持久化的四项权重；它们只决定该分组中账号的质量分和展示排序：

| 指标 | 新分组默认权重 | 含义 |
|---|---:|---|
| 成本优势 | 15 | 账号倍率相对当前分组倍率的安全余量 |
| 成功率 | 45 | 当前统计窗口内成功请求比例 |
| TTFT P50 | 20 | 首 Token 延迟中位数 |
| 总耗时 P95 | 20 | 总耗时的 P95 |

- 权重为非负整数，必须合计 100。
- 评分规则只提供四项直接百分比配置、合计校验、保存与“恢复默认”；不提供特惠、均衡、Pro 等预设模板。
- 成本优势不是实际利润率。其在当前分组的得分依据为：`15 × (分组倍率 - 账号倍率) ÷ 分组倍率`，结果限制在 0–15 分。
- 实际利润率仅由真实账单计算：`(用户实际计费 - 上游真实扣费) ÷ 用户实际计费`，在投入产出区展示并受成本覆盖率约束。
- 同一账号位于多个分组时，因分组倍率与分组评分权重不同，可有不同的成本优势、质量分与展示名次；其真实调度优先级保持全局唯一。
- 评分证据优先采用当前分组最近 5 分钟真实请求；样本不足时可使用账号全局服务样本补充，但必须标记“全局样本补充”。置信度独立显示，不计入 100 分。

## 五、账务与跨分组口径

- 上游真实扣费来自 New API / Sub2API 的逐笔真实账单；用户实际计费来自本站请求 `actual_cost`。
- 纸面利润 = 用户实际计费 - 上游真实扣费；利润率 = 纸面利润 / 用户实际计费。用户实际计费为 0 时显示 `—`。
- 成本按上游 `attempt` 计入，失败重试若已产生上游费用也必须计入；不能只算最终成功账号。
- 全站按请求流水去重，每条请求只计一次；账号跨分组不造成全站重复。
- 分组按请求真实 `usage_logs.group_id` 聚合；每条请求只进入实际服务的一个分组。
- 缺少 `group_id` 的请求只计入全站，并在全站经营区说明为“未归属请求”，以解释分组总和和全站的差额。
- 成本覆盖率是已匹配真实成本的 attempt / 应对账 attempt。实时允许短暂“待对账”；请求结束超过 10 分钟仍未对齐则标记“对账异常”。

## 六、实现边界与验收

1. 评分规则必须有独立的管理员受限存储与接口；不得复用 OpenAI 原生调度器 `scheduler_score_weights`、账号 `priority` 或分组排序字段。
2. 全站、分组和账号的经营汇总必须由后端聚合接口提供；前端不得累加卡片数据，也不得复用旧 `today_stats` 作为真实上游成本。
3. 刷新探测只更新服务质量证据；账务刷新必须先采集上游真实账单、对账后再更新经营汇总。
4. 修改一个分组的评分规则后，只重算该分组内账号的质量分与展示排序；不影响其他分组和生产调度。
5. 同一账号跨分组时，全站请求、成本、营收、利润不重复；分组经营数据按真实 `group_id` 归属。
6. 今日归零后，历史累计仍可见；历史抽屉按当前全站、分组或账号范围读取按日汇总数据。
7. 账号卡片保留既有渠道监控视觉样式，并同时清晰展示服务质量与投入产出。
