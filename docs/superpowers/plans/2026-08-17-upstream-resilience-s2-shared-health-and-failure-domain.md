# S2 Shared Health and Failure-Domain Implementation Plan

> **For agentic workers:** Execute this plan task-by-task in the current S2 worktree. Keep each checkbox tied to a focused test cycle; do not merge, push, deploy, or touch production from this worktree.

**Goal:** Add Redis-backed, fail-safe shared OpenAI account-model health and failure-domain retry budgets while preserving S1 vetoes, existing billing idempotency, sticky routing, and stream replay safety.

**Architecture:** A service-level `OpenAISharedHealthStore` wraps the existing Redis client. The repository stores versioned account/domain snapshots and fencing-token leases with short TTLs; the gateway service combines shared state with the existing local transient state and a 30-second local snapshot. Responses and Messages share a request-local retry budget and domain-aware selection helpers, so Redis is never the source of billing or deterministic isolation truth.

**Tech Stack:** Go 1.26, Gin handlers, `go-redis/v9`, PostgreSQL-backed native repositories, existing scheduler snapshot/outbox, testify/sqlmock, Redis integration fixtures.

## Global Constraints

- Redis is a rebuildable runtime projection; S1 database vetoes remain authoritative.
- Default budget is max 4 attempts, max 3 account switches, max 2 ordinary failure domains, max 5 seconds total retry time.
- `Retry-After` is honored; 5xx/transport failures use bounded exponential backoff.
- Output-started, side-effecting, or unknown-idempotency requests are never automatically replayed.
- Redis read failure uses at most a 30-second trusted local snapshot; stale/unknown state never clears an S1 veto.
- No database migration, billing formula change, price/rate change, Top-K/sticky change, external control plane, or GitHub Actions.
- Scope is OpenAI Responses/Messages text failover paths; other endpoint-specific retry loops retain existing behavior.
- Candidate stops at `READY_FOR_ROOT_REVIEW`; deployment waits for a later explicit user instruction.
