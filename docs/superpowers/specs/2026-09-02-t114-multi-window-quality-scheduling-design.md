# T114 多窗口服务质量评分与慢首输出观测规格

**日期：** 2026-09-02  
**任务包：** T114  
**状态：** 设计已确认，待实施计划  
**范围：** OpenAI 普通 HTTP 文本请求的统一质量调度、账号质量快照和 60 秒慢首输出观测

## 1. 背景与问题

T96 已将普通 HTTP 文本请求接入统一质量调度。当前候选账号按以下字典序排列：

```text
成功率 DESC
→ 7 天 5% 截尾平均 TTFT ASC
→ 有效成本 U ASC
→ 账号 ID ASC
```

2026-09-02 生产只读证据显示，该规则能优先保证长期成功率，但不能充分反映当天客户体验：

- 业务请求 P50 TTFT 约 6.7 秒，P95 约 49.5 秒。
- `gpt-5.6-sol` P95 TTFT 约 37.5 秒，`gpt-5.5` 约 50.9 秒。
- 多个账号的当天 P95 TTFT 达 45–66 秒，但 7 天截尾平均仍只有 7–12 秒。
- 7 天窗口会稀释当天突发变慢；两端各删除 5% 样本会主动移除最慢尾部。
- 成功率字典序绝对优先，使 `100% 成功 + 18 秒 TTFT` 排在 `99.65% 成功 + 4.7 秒 TTFT` 前。
- 当前已有首输出超时能力，但默认关闭；直接启用并自动切号会产生无法证明未扣费的第一个上游 attempt，存在重复上游成本和利润失真风险。

GPT-Plus 当前只有一个有效候选是管理员在分析期间主动关闭其他账号后的临时状态，不作为白天高 TTFT 的根因证据。本规格不修改账号 `schedulable`、分组关系或账号池配置。

## 2. 第一性原则

服务质量排名只回答：

> 对当前请求，哪个合格账号最可能成功，并最快提供可用输出且持续稳定生成？

因此质量维度固定为：

1. 最终成功概率。
2. 首个有效语义输出速度。
3. 输出开始后的生成速度。
4. 当前账号的实时容量状态。

成本和利润不是用户感知质量，不进入质量分；继续由现有原生利润保护独立处理。账号状态、模型能力、余额、冷却、并发槽和安全重放边界仍是质量评分之前的资格门禁。

服务质量评分不得形成新的硬性 TTFT 淘汰线。所有账号都慢时仍必须选择相对最优账号，不能因为质量分低而把服务变成不可用。

## 3. 目标

1. 将统一质量调度从单一 7 天字典序升级为 `1h + 24h + 7d` 多窗口综合质量分。
2. 综合质量分固定为成功质量 40%、首字体验 40%、输出速度与实时负载合计 20%。
3. 首字体验同时体现普通体验和尾部体验，不再以删除最慢 5% 的截尾平均作为唯一排序指标。
4. 当账号连续 60 秒没有首个有效语义输出时，立即形成慢速证据并影响后续新请求排名。
5. 60 秒慢速观测不得取消当前上游请求、不得自动切换账号、不得创建第二个上游 attempt。
6. 保持现有错误 failover、安全重放、账务、账号状态、利润保护和并发槽语义不变。
7. 保证样本少的新账号不能凭少量成功直接获得最高排名。
8. 提供 shadow 对比和上线后指标，证明体验改善没有以成功率或成本恶化为代价。

## 4. 非目标

- 不设置 `TTFT > N` 后账号不可调度的硬门槛。
- 不启用或复用现有自动 failover 型 `openai_first_output_timeout_seconds` 作为 60 秒切号能力。
- 不因纯粹慢响应取消、关闭或重放已发送的上游请求。
- 不承担首个 attempt 可能已被上游计费后的第二次请求成本。
- 不修改用户价格、分组倍率、长上下文计费或服务档位。
- 不自动打开、关闭、归组或迁移账号。
- 不修改生图、WebSocket、协议强制绑定或非 OpenAI 平台调度。
- 不恢复 T100 已移除的 admission、slow-session 或额外账号并发限制。
- 不在本任务拆分管理员流量与业务流量的质量事实源。
- 不新增数据库表、历史回填或第二套质量事实源。

## 5. 方案选择

### 5.1 保留字典序，只缩短窗口

近期变慢能更快反映，但成功率仍绝对压过 TTFT，小幅成功率差异仍可能覆盖十几秒的体验差异。不采用。

### 5.2 TTFT 硬门槛

能快速排除慢账号，但所有账号同时超过阈值时会耗尽候选，直接降低可用性。不采用。

### 5.3 多窗口综合质量分 + 60 秒观测型慢信号

将成功、首字、输出速度和实时负载转换为统一分值；使用近期窗口快速响应变化，保留长期窗口抑制抖动；60 秒只产生后续排名信号，不重放当前请求。该方案兼顾体验、可用性和账务安全，采用。

## 6. 适用路径与处理顺序

本规格只修改已经显式启用 `unified_quality` 的普通 HTTP 文本入口，包括现有 Responses、Chat Completions、Messages 兼容文本入口和 Embeddings 中已接入统一质量选择的路径。

处理顺序保持：

```text
原生账号资格
→ 模型与协议能力
→ 状态、余额、冷却和并发槽
→ 原生利润保护分区
→ 多窗口质量评分
→ 分数最高且有空闲槽的账号
→ 上游请求
→ 60 秒慢首输出观测
→ 原请求继续等待直至正常终态或真实错误
```

协议强制绑定、生图和 WebSocket 继续走各自现有路径，不被本规格改写。

## 7. 多窗口质量数据

### 7.1 事实源

继续复用现有：

- `usage_logs` 中完整、真实、非生图、非视频的上游 attempt。
- `ops_error_logs` 中可明确归属账号、非客户端责任、非本站业务限制、非模型不支持的真实失败。
- 原生并发槽与等待状态。

不写新的质量事实表。查询仍按物理 attempt 去重，继续排除 `usage_completeness='unknown'`、客户端责任错误、本站本地拒绝和明确模型不支持。

### 7.2 时间窗口

为避免一条近期样本被重复计算三次，运行时使用三个互斥区间：

```text
W1  = [now-1h, now)
W24 = [now-24h, now-1h)
W7  = [now-7d, now-24h)
```

对外仍显示为 `1h / 24h / 7d` 质量来源，但计算贡献互不重叠。

基础时间权重：

```text
W1  50%
W24 30%
W7  20%
```

### 7.3 样本置信度

每个指标按自己的有效样本数计算置信度：

```text
W1  目标样本 20
W24 目标样本 100
W7  目标样本 300
confidence = min(1, sample_count / target_sample_count)
```

某窗口未获得完整权重时，剩余权重向更旧窗口转移。7 天样本仍不足时，剩余部分回退到当前候选池的中性基准，不把未知值当 0，也不让 `1/1` 成功账号直接排第一。

成功率使用置信度平滑后的值，不直接使用原始 `successes / attempts`。TTFT、输出速度同样按有效样本独立回退。

## 8. 综合质量分

每个账号生成 `0–100` 的质量分：

```text
quality_score =
    success_score      × 0.40
  + first_output_score × 0.40
  + output_rate_score  × 0.10
  + live_load_score    × 0.10
```

### 8.1 成功质量 40%

成功质量使用多窗口置信度平滑后的最终成功率，并通过非线性曲线转换：

| 平滑成功率 | 成功质量分 |
|---:|---:|
| 100% | 100 |
| 99% | 95 |
| 97% | 80 |
| 95% | 60 |
| 90% | 25 |
| 80% | 5 |
| <80% | 逐步接近 0 |

表格节点之间线性插值。该曲线让明显失败的账号很难靠速度补偿，但不把账号从候选池硬删除；所有账号都差时仍可选出最高分账号。

### 8.2 首字体验 40%

首字定义为客户端可实际消费的第一个有效语义内容，包括：

- 文本或 reasoning summary 的非空内容。
- 工具调用参数或 custom tool input。
- 音频 transcript、refusal 内容和图片有效片段。

以下不算首字：`response.created`、空 reasoning item、心跳、空白 SSE、纯结构状态、`[DONE]` 和失败事件。

首字分拆为：

```text
P50 TTFT 24%
P90 TTFT 16%
```

P50 和 P90 分别通过同一软评分曲线转换：

| TTFT | 首字分 |
|---:|---:|
| ≤2s | 100 |
| 5s | 80 |
| 10s | 50 |
| 20s | 20 |
| 40s | 5 |
| ≥60s | 0 |

节点之间线性插值。该曲线只影响排名，不形成不可调度状态。

### 8.3 输出速度 10%

使用成功 attempt 的 `output_tokens / 可见输出后的持续时间`。按相同请求模型的候选池做稳健分位归一化：候选池 P20 对应 0 分，P80 对应 100 分，区间内线性插值，超出范围截断。

输出 Token 或持续时间证据不足时使用候选池中性值 50，并按样本置信度向长期窗口回退。不得用总耗时直接替代输出速度，避免惩罚正常的长回答。

### 8.4 实时负载 10%

实时负载只描述当前选中该账号后预计是否排队：

```text
70%：当前原生并发槽剩余比例
30%：当前等待队列反向归一分
```

无负载证据时使用中性值 50。实时负载不得新增并发限制，也不得绕过原生槽位获取和释放。

## 9. 排名与选择

资格账号在利润保护分区内按以下顺序排列：

```text
quality_score DESC
→ success_score DESC
→ P50 TTFT ASC
→ account_id ASC
```

选择器依次尝试获取账号原生并发槽，选择排名最高且成功取得槽位的账号。账号没有空闲槽时继续尝试下一名；所有账号均占满时沿用现有等待计划。

质量评分不读取旧 priority、Top-K 随机、普通 sticky 奖励或成本权重。有效成本继续只用于现有利润保护分区及质量完全相同后的既有经济安全语义，不得稀释质量分。

## 10. 60 秒慢首输出观测

### 10.1 定义

从本次上游 attempt 实际发起开始计时。请求正文上传、认证和选号时间不计入 60 秒。

若 60 秒内没有第 8.2 节定义的有效语义内容，记录：

```text
event = openai.first_output_slow
ttft_lower_bound_ms = 60000
```

### 10.2 强制账务安全边界

60 秒触发时必须：

- 不取消上游 context。
- 不关闭上游响应体。
- 不向 handler 返回 failover error。
- 不切换账号。
- 不增加 attempt 数。
- 不修改 `usage_completeness`、用户扣费或上游成本。
- 不写账号持久化错误、临时不可调度或模型冷却。
- 当前请求继续等待同一上游的首字、终态或真实错误。

原因是“客户端尚未看到内容”不能证明上游没有接受、处理或计费。任何纯 TTFT 超时自动重放都会引入无法核实的重复上游成本，本规格明确禁止。

### 10.3 后续请求即时降权

慢信号按 `(group_id, account_id, attempt_id)` 写入现有进程内质量运行态，作为一个 `TTFT >= 60000ms` 的右删失样本。它立即参与后续新请求的 W1 首字评分。

原 attempt 最终完成后：

- 若取得真实 TTFT，以真实值替换同一 attempt 的 60 秒下界，不重复计数。
- 若最终失败，删除慢速占位并按原生失败结果更新成功质量。
- 若客户端断开或 usage 状态未知，保留本次慢速证据至 W1 过期，但不推断上游成本为 0。

进程重启后未完成的内存慢信号允许丢失；已完成请求会由 `usage_logs` 在下一次质量快照刷新时补入。该限制必须在管理员观测中明确，不新增持久化表。

### 10.4 与现有超时的关系

- `gateway.openai_first_output_timeout_seconds` 保持 `0`，不得因本规格设置为 60。
- `gateway.openai_high_effort_first_output_timeout_seconds` 保持原行为，不启用独立覆盖。
- 现有响应头超时、180 秒流数据空闲超时和真实传输错误处理保持不变。
- 真实错误是否切号继续由现有 `safe_to_replay`、output、usage、副作用和重试预算决定。

## 11. 观测合同

管理员调度观测增加：

- 质量分及四项分值。
- 每项指标的 W1/W24/W7 样本数、置信度和实际权重。
- P50/P90 TTFT、输出速度和实时负载。
- `quality_snapshot_at`、`quality_snapshot_stale`。
- `first_output_slow_count`。
- 60 秒慢信号是否已被最终真实 TTFT替换。
- 选中账号排名、质量分差和未选择原因。

不得记录请求正文、响应正文、API Key、OAuth token、Cookie、代理密码或其他凭据。

## 12. 兼容性与数据边界

- 无数据库迁移。
- 不修改 `usage_logs`、`ops_error_logs` 既有字段含义。
- 质量查询尽量在一次 7 天范围扫描内通过条件聚合产生三个窗口，避免执行三次全量查询。
- 快照继续按现有分钟级缓存刷新；60 秒慢信号使用进程内覆盖层实现即时生效。
- 老调用方仍可读取既有成功率和 TTFT 字段；新增综合分值为 additive 字段。
- T96 的账号池、资格、安全重放、额外恢复次数、利润保护和生图隔离继续有效；本文只替换普通文本质量排序和质量窗口。
- T113 的流生命周期和关联 ID用于定位慢信号与最终 attempt，不改变其错误分类合同。

## 13. 测试策略

### 13.1 质量聚合

- 三个互斥窗口边界和时区测试。
- 同一 attempt 不得跨窗口重复计数。
- 样本置信度、权重转移和中性回退测试。
- 成功率非线性映射和节点插值测试。
- P50/P90 TTFT 软评分测试。
- 输出速度与实时负载归一化测试。

### 13.2 排名

- `100% + 18s` 与 `99.65% + 4.7s` 的样例必须由综合质量分决定，后者排名更高。
- 成功率明显差的快速账号不得靠 TTFT 完全补偿。
- 所有账号 TTFT 均超过 60 秒时仍返回最高分账号，不返回本地无候选。
- 少样本账号不得凭 `1/1` 成功排名第一。
- 无 TTFT、无输出速度或无负载证据时使用中性回退，不产生 NaN。
- 排名完全同分时按账号 ID稳定排序。

### 13.3 60 秒慢观测

- 60 秒前收到文本、reasoning summary、工具参数或 transcript 时不记录慢信号。
- 只有 `response.created`、空 reasoning item或心跳时，60 秒必须记录慢信号。
- 触发慢信号后上游 context、响应体和当前 attempt 保持运行。
- 触发慢信号不得产生第二次账号选择、第二个上游请求或 account switch 指标。
- 最终真实 TTFT 替换同 attempt 下界，不重复计数。
- 最终失败按失败处理，不把慢速占位同时计为成功样本。
- 现有首输出 failover 配置保持关闭。

### 13.4 账务不变量

- 纯慢速观测前后，上游请求次数恒为 1。
- 用户扣费、账号成本和 billing dedup 只消费最终原 attempt 的现有 usage。
- 没有 usage 时不得推断成本为 0，不得创建第二个 attempt 补结果。
- 现有真实错误安全切号测试继续通过。

## 14. 发布与验收

建议采用两阶段启用：

### 阶段一：shadow 计算

- 保持现有生产选择结果。
- 同时计算新质量分和“新策略本应选择的账号”。
- 持续至少 24 小时，比较实际选中账号与 shadow 第一名。
- 验证查询开销、分数稳定性、候选集中度和质量改善预测。

### 阶段二：正式选择

- 在验收站启用新排序，执行真实但受控的普通文本请求。
- 验证账号选择、槽位释放、60 秒慢信号和零额外 attempt。
- 用户明确批准后再按现有主站发布门禁处理。

本规格不授权验收站或主站部署。所有部署仍只能从已推送、干净且与 `origin/main` commit/tree一致的根 `main`发起。

## 15. 预计客户体验效果

以下为基于 2026-09-02 数据的工程估算，不是上线承诺；以阶段一 shadow 结果和验收站数据为准。

### 15.1 预期改善

- 当分组至少有两个有效候选时，近期变慢账号预计在 1 小时内降序，不再等待 7 天历史被稀释。
- 成功率接近的账号将由 TTFT 明显区分；例如 4.7 秒账号预计超过 18 秒账号。
- P50 TTFT 预计下降约 10%–25%。
- P90 TTFT 预计下降约 15%–35%，改善幅度应高于 P50。
- 60 秒以上请求不会被即时挽救，但同一慢账号对后续请求的影响会快速下降。
- 所有账号都慢时服务仍然可用，只会选择其中质量分最高者。

### 15.2 成功率影响

- 成功质量仍占 40%，并使用陡峭的非线性曲线，预期总体成功率保持稳定。
- 允许的验收波动目标为相同流量结构下最终成功率不下降超过 1 个百分点。
- 若 shadow 显示快速账号成功率不足导致预计最终成功率下降，必须调整成功曲线，不得直接上线。

### 15.3 当前请求体验限制

- 60 秒慢信号不会取消当前请求，因此单个用户仍可能等待超过 60 秒。
- 本规格改善的是后续调度和总体分布，不承诺救回正在变慢的同一个请求。
- 这是为保证账务正确性接受的明确代价。

## 16. 预计成本与资源代价

### 16.1 上游成本

- 纯 TTFT 慢速观测不产生第二个 attempt，预计新增上游调用成本为 0。
- 不取消已发送请求，不引入“第一个上游已计费但第二个账号再次计费”的隐藏损失。
- 质量排序可能把流量从低价慢账号转向高价快账号；该变化仍受现有利润保护分区约束，并应在 shadow 阶段单列预计成本差异。

### 16.2 数据库与计算

- 当前已有 7 天质量扫描；增加三个窗口、P50/P90 和输出速度会提高聚合复杂度。
- 通过单次范围扫描和条件聚合实现后，预计质量快照刷新时数据库 CPU开销增加约 50%–150%，但不是请求级持续开销。
- 快照仍按分钟缓存，普通请求只读取内存快照；不允许每个请求重新扫描数据库。
- 进程内慢信号数量受最近 1 小时 attempt 数量约束，内存开销预计较小。

## 17. 风险与缓解

### 17.1 排名抖动

风险：1 小时窗口对突发样本敏感。  
缓解：样本置信度、权重向长期窗口转移、分钟级快照和稳定 ID排序。

### 17.2 流量过度集中

风险：质量最高账号持续获得多数流量，随后自身变慢。  
缓解：实时负载占 10%，并继续使用原生并发槽；shadow 阶段监控第一名流量占比。

### 17.3 快速但不稳定账号上升

风险：TTFT 权重提高后低成功账号排名上升。  
缓解：成功率非线性曲线、样本置信度和 40% 成功权重；成功率明显下降时必须阻止上线。

### 17.4 60 秒信号误判

风险：账号在 61 秒正常输出，但 60 秒时已被临时降权。  
缓解：最终真实 TTFT替换下界；该请求仍正常完成，降权只影响短期后续排名。

### 17.5 内存信号丢失

风险：容器重启会丢失尚未完成的慢信号。  
缓解：接受该非持久化限制；完成后的真实 TTFT由 usage 快照补入，不为此增加数据库写路径。

### 17.6 账务风险

风险：自动取消并换号可能产生双重上游计费。  
缓解：本规格明确禁止纯 TTFT 自动取消、自动切号和第二个 attempt；账务风险不由平台承担。

### 17.7 单候选账号池

风险：分组只有一个有效账号时，任何排名策略都无法改善选路。  
缓解：质量分仍正常生成并展示，但不伪造调度收益；账号池配置继续由管理员独立维护。

## 18. 成功标准

- shadow 数据覆盖至少 24 小时且无查询错误、NaN 或分数缺失。
- 至少两个候选的分组中，明显更快且成功率接近的账号排名提升。
- 预计 P50/P90 TTFT均下降，且 P90 改善幅度不低于 P50。
- 预计最终成功率下降不超过 1 个百分点。
- 60 秒慢信号触发后，上游请求数仍为 1，account switch 数不增加。
- 无新增重复上游成本、未知首 attempt 成本或利润漏记。
- 所有账号都慢、样本不足或质量快照读取失败时仍保持可用性。
- 生图、WebSocket、账务、利润保护和真实错误 failover 回归通过。
