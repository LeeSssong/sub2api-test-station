# 飞书运营报告重设计（日报 + 分组可用性告警）

## 目标

把当前混装的 `relay-ops 每日运营摘要` 拆成两条职责清晰的推送：**每日中转站运营日报**与**分组可用性告警**。报告接收者是中转站运营者，其关注优先级明确为：**质量（稳定、低延时）第一，利润第二**。

本设计只覆盖日报重设计与分组可用性告警。上游账号余额监控、new-api 倍率测算修复各自单独立项。

## 现状缺陷（均已在生产验证）

| 缺陷 | 证据 | 性质 |
|---|---|---|
| 账号显示为 `账号 20` 而非用户命名 | `opsmetrics.AccountRuntime.Name` 已填充（`snapshot.go:130`），但 `digestAccountLines` 写死 `"账号 " + ID`（`feishu.go:411`） | 渲染层丢弃可用数据 |
| 「上游账号情况」区看不出重点 | 该区实为分组内「当前账号 vs 候选账号」A/B 推荐，但 6 个分组的 `CandidateAccountID` 均为 0，对比的另一半永远缺席，退化成清单；且同一账号跨分组重复出现 | 语义退化 |
| 「上游账号质量」区倍率恒为 `1x` | `ops/collect-account-quality-pulse.rb:335` 读取 `accounts.rate_multiplier`（本地计费字段），生产实测 12 个账号该字段全部为 `1`。2026-07-26 计划已明确废弃该字段作为倍率来源 | 使用已废弃数据源 |
| 同一卡片出现两个同名不同义的「倍率」 | 「账号情况」区用 schema v2 可信倍率（0.05x–0.25x），「账号质量」区用废弃字段（恒 1x） | 指标歧义 |
| 站内运行区 11 行零信息噪声 | 取 15 分钟窗口自然流量，站点当前无真实请求，11 行全为「请求 0，错误率 未知，样本不足」，占卡片近半篇幅 | 无条件展开 |
| 成功率无法反映趋势 | 列表成功率来自 `ListAggregates(ctx, ids, now-7d)`，是 **7 天累计聚合**。账号今天刚挂与挂了一周，数值几乎相同 | 口径错误 |
| 上游成本被高估 4–20 倍 | `GetAccountTodayStats` 中 `cost = SUM(COALESCE(account_stats_cost, total_cost) * COALESCE(account_rate_multiplier, 1))`，乘数仍是恒为 1 的废弃字段。真实倍率为 0.05x–0.25x | 利润口径错误 |

## 架构

### 新增判定包 `accounthealth`

将「原始探测记录 → 健康结论」从渲染层剥离为独立的纯函数包。无 IO、无外部依赖、可独立表驱动测试。当前判定逻辑散落在渲染函数中，是「数据有 `Name` 却渲染成 ID」这类缺陷的根源。

```
Sub2API                              relay-ops                          飞书
──────────────────────────────────────────────────────────────────────────────
GET /api/v1/admin/account-monitors        ┐
  （11 账号当前快照，schema v2）             │
                                          ├─→ accounthealth.Classify()  ─┬─→ 日报卡（每日 09:00）
GET /api/v1/admin/account-monitors/       │     · 三档判定                │
    :id/history?limit=N    × 11           ┘     · 今日 / 昨日切片          └─→ 告警卡（每 5 分钟检查）
  （覆盖今天 + 昨天）                            · 分组可用性汇总
```

Sub2API 保留 7 天逐条探测记录（`AccountMonitorHistoryDays = 7`）。拉取条数按当前探测间隔动态计算，不得硬编码：`N = ceil(48h / settings.interval_seconds) × 1.2`（上浮 20% 容错），并以 2000 为上限。当前间隔 300 秒对应 N ≈ 692。探测间隔可由管理员修改，硬编码条数会在间隔调小后静默丢失昨日数据。

relay-ops 在生成日报时按账号拉取历史并自行按日切片聚合。不改 Sub2API，不新增快照表。

### 组件边界

| 组件 | 职责 | 依赖 |
|---|---|---|
| `accounthealth`（新建） | 三档判定、日切片聚合、分组可用性汇总、利润计算。纯函数 | 无 |
| `sub2api.Client`（扩展） | 新增 `ListAccountMonitorHistory(ctx, accountID, limit)` | HTTP |
| `dailyreport`（改造） | 编排：拉取数据 → 调用 `accounthealth` → 渲染 → 投递 | 上述两者 |
| `notify`（改造） | 新增 `RenderOperationsDigestV2`、`RenderGroupAvailabilityAlert`；账号一律使用 `Name` | `accounthealth` |
| `scheduler`（扩展） | 新增 `group-availability` 作业，间隔 5 分钟 | `accounthealth` |

## 判定规则

### 账号健康三档

同一套规则用于两个窗口：日报用**当日 00:00 起累计**（口径稳定，可与昨日同口径对比），告警用**最近 1 小时滚动窗口**（响应快）。

| 档位 | 判定条件 |
|---|---|
| 不可用 | 成功率 < 50%，或最近一次探测错误码为 `balance_exhausted` |
| 降级 | 50% ≤ 成功率 < 95% |
| 健康 | 成功率 ≥ 95% |

`balance_exhausted` 直接判定为不可用，不受成功率影响 —— 余额耗尽的账号即使历史成功率高，也已无法服务。

### 延时标记

TTFT P95 > 3000ms 标记为「偏慢」。**偏慢不降档**，仅在质量行单独标注计数。延时与稳定性是两个独立维度，混为一档会掩盖信息。

### 分组可用性

分组可用账号数 = 该分组内「健康 + 降级」账号数。

告警条件按分组容量分档，避免单账号分组永久刷屏：

| 分组总账号数 | 告警条件 |
|---|---|
| ≥ 3 | 可用数降到 1（失去冗余）或 0 |
| 2 | 可用数降到 0 |
| 1 | 可用数降到 0（单账号分组本无冗余，不为「只剩 1 个」告警） |

### 利润口径

```
真实上游成本 = standard_cost × 可信倍率
毛利         = user_cost − 真实上游成本
毛利率       = 毛利 / user_cost        （user_cost = 0 时不计算，显示为「—」）
```

其中 `standard_cost = SUM(total_cost)`（官方标准价）、`user_cost = SUM(actual_cost)`（用户实际支付），均取自 `today_stats`。可信倍率取 schema v2 的 `multiplier.value`（`source` 为 `declared` 或 `measured`，`status` 为 `ok`）。

金额单位沿用 Sub2API 原生口径 USD，卡片以 `$` 呈现，不做汇率换算。实现首步须以生产真实数据核对该单位假设；若 Sub2API 实际以其他币种记账，仅调整卡片符号，计算公式不变。

**禁止使用 `today_stats.cost` 字段**，因其乘数为已废弃的 `account_rate_multiplier`（恒为 1）。

倍率不可用（`status` 为 `failed` / `stale` / `unsupported` / `unavailable`）时，该账号毛利标记为「无法核算」并计入待处理项，**不得以 1 兜底**。分组与全站毛利汇总时排除这些账号，并注明排除数量。

## 日报卡片结构

标题：`relay-ops 中转站日报 YYYY-MM-DD`，四层由结论到明细递进。

```
① 质量        稳定 6 / 降级 2 / 不可用 3          健康账号较昨日 ↓1
              延时 P95 中位 3.9s ｜ 2 个账号偏慢

② 利润        今日收入 $—   上游成本 $—   毛利 $—（—%）
              〔无调用时折叠为一行：今日无真实调用〕

③ 待处理      Plus-XN-0.09     余额耗尽        已持续 3 天
              Plus-XM-0.1      余额耗尽        已持续 5 天
              Plus-TK-0.08     成功率 70% ↓     http_error
              Pro-SHUAI-0.17   倍率测不出 → 利润无法核算

④ 明细（折叠） 逐账号：账号名 · 成功率 · TTFT P50 · 延迟 P95 · 倍率 · 今日毛利贡献
              站内流量：无调用时一行带过，有调用时展开请求数 / 错误率 / SLA
```

约束：

- 账号一律使用用户命名的 `Name`，不显示数据库 ID
- 质量层置于利润层之前
- 第 ③ 层只列需要人工介入的账号；倍率发生变化时在此层追加一行提示
- 第 ④ 层为折叠内容，站内流量在无调用时收敛为单行
- 移除「补充证据」区（候选站计数、活动事件计数、只读分析结语），证据仍落库，不上卡片

## 告警卡片结构

仅在分组可用性触发时推送，不与日报合并。

```
⚠️ 分组可用账号不足：GPT-Plus

可用 1 / 共 3
Plus-XN-0.09    余额耗尽    已持续 3 天
Plus-XM-0.1     余额耗尽    已持续 5 天

建议：为上述账号充值，或临时关闭 schedulable 止血
```

- 检查频率：5 分钟（与账号探测同频）
- 判定窗口：最近 1 小时滚动
- 防抖：复用 `incidents.Machine`，`ConfirmationWindows = 2`（连续 2 次确认，约 10 分钟）
- 恢复：分组可用数回升到告警阈值以上时推送恢复卡
- 告警卡不包含任何凭据、Base URL、上游原始错误

## 错误处理

原则为 **fail-safe 而非 fail-alarm**：监控自身故障不得伪装成业务故障。

| 场景 | 行为 |
|---|---|
| Sub2API 不可达 | 日报标记「数据不可用」并注明原因类别，不发假数据；分组告警**静默**，不因读不到数据而报「分组瘫痪」 |
| 单账号 history 拉取失败 | 该账号标记「趋势不可用」，其余账号正常输出 |
| 无昨日基线（首日运行） | 不显示同比，仅输出今日绝对值 |
| 倍率不可用 | 该账号毛利标记「无法核算」，计入待处理项，不以 1 兜底 |
| 卡片超出 30KB 上限 | 优先保留第 ①②③ 层，截断第 ④ 层明细并注明截断数量 |

## 测试策略

**`accounthealth` 表驱动测试**

- 三档边界：成功率 49.9% / 50% / 94.9% / 95% / 95.1%
- `balance_exhausted` 直判不可用，且不受高成功率影响
- 延时标记边界：TTFT P95 2999ms / 3000ms / 3001ms；确认偏慢不改变档位
- 日切片聚合：跨日边界记录归属正确；昨日缺失时不产生同比
- 分组可用性：容量 1 / 2 / 3 / 4 各档的触发与不触发；**单账号分组可用时不告警**
- 利润：倍率可用时的计算正确性；倍率不可用时标记「无法核算」且不参与汇总

**渲染测试**

- 账号名使用 `Name` 而非 ID
- 无流量时站内流量收敛为单行
- 倍率缺失时输出「利润无法核算」而非数值
- 卡片体积不超过 `maxCardBytes`（30KB），超限时按优先级截断

**告警状态机测试**

- 成功率在 70% 上下抖动时不重复推送
- 恢复通知仅在跨越阈值时推送一次
- 数据不可用时静默，不推送分组瘫痪告警

**契约测试**

- schema v2 的 `multiplier.{value, source, status, observed_at}` 解析
- `today_stats.{standard_cost, user_cost}` 字段存在性
- 断言渲染输出不包含 API Key、Base URL、上游原始错误

## 不在本设计范围内

以下各自单独立项，不在本次实现：

- **上游账号余额监控**：已验证 sub2api 系上游可通过 `GET /v1/usage` 读取 `quota.remaining`（7 站端点均存在），new-api 系走 `/api/usage/token/`。需先带 key 实测各站 key 是否为限额类型
- **new-api 倍率测算修复**：已定位真实错误为 `quota delta must be positive` —— shuaiapi 的 `total_used` 在请求完成后未即时增长（异步结算或缓存），测算读取 after 过早。修复方向为轮询重读或改用余额差值
- 分组结构治理（`GPT特惠` 与 `GPT-PLUS-内测` 共用同一账号）
