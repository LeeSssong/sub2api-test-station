## Settings Incident And Recovery

During Admin API method discovery, an unintended `PUT /api/v1/admin/settings {}` reset 21 settings to zero or default values. The issue was detected immediately in Sub2API logs before any D04 user, balance, route, or container change.

Recovery used the official Sub2API `v0.1.161` API and the server audit record, not a direct PostgreSQL write:

- audit record `283` identified the affected settings;
- all 21 fields were restored through the official Admin API;
- TOTP was restored to `true`;
- OIDC token authentication was restored to `client_secret_post`;
- the other 243 settings remained hash-identical during recovery;
- recovery was recorded as audit `289`.

The verified final settings SHA-256 is:

```text
52eff24fce0338ee4f8f81ad12a5d1406c46b6de050c99587035cdfd1f71a28e
```

The production recheck confirmed native registration disabled, public registration disabled, the historical site identity restored, Sub2API healthy, and the original Sub2API container retained. This incident is closed, but it establishes a process rule: never use an empty-object settings update for endpoint discovery; inspect the official handler/DTO first and use read-only requests for discovery.
