# Spec: T5 `monitor_v4_probe_terminal_missing` 终态完整性

## 1. 问题与当前行为

Monitor V4 在某个 5 分钟桶没有真实请求时，使用主动探测作为兜底。正常链路应先写入账号级探测结果，再由 `EnsureProbeBucketTerminal` 汇总为分组级终态。当前汇总 SQL 使用 `HAVING COUNT(r.account_id) > 0`；如果该桶没有任何账号级探测结果，就不会生成分组级终态。

读取投影时发现“无真实请求、无探测终态”，会记录 `monitor_v4_probe_terminal_missing`，并将该桶按失败兜底。这个告警说明观测账本缺行，不等于已经证明上游请求失败。

## 2. 目标与非目标

目标：保证需要主动探测兜底的分组/桶拥有明确的终态；区分真实探测失败与没有观测证据；保留管理员完整性告警。

非目标：不改变主动探测账号池策略、不恢复已取消的自定义并发控制、不新增监控事实源、不把用户真实请求改成主动探测。

## 3. 终态模型

分组/桶终态至少区分：

- `success`：至少一个账号级探测成功。
- `failed`：已产生账号级探测结果，但没有成功结果。
- `missing`：该桶需要探测兜底，但没有可归并的账号级探测结果。

`missing` 是数据完整性状态，不得伪装成 `failed`。它应记录分组、桶起止时间、生成运行标识和缺失原因摘要；不得记录凭据或完整请求/响应。

## 4. 计分与可用性语义

- 真实请求优先；同桶有真实请求时，探测终态不进入该桶指标。
- 没有真实请求且终态为 `success`/`failed` 时，主动探测贡献一个逻辑请求。
- 终态为 `missing` 时，只增加独立的完整性告警计数，不进入服务成功率失败分母。
- `missing` 不得单独把分组当前可用性判定为不可用。
- 明确的探测 `failed` 才按一次 `0/1` 进入分母。
- 管理员页面和日志显示缺失桶数量；用户不看到该内部诊断。

## 5. 闭环要求

探测运行、结果写入、终态结算和快照刷新必须具备可重试和幂等语义：

1. worker 未完成探测时，watchdog 能在桶到期后补写 `missing` 终态。
2. 账号全部被跳过、探测结果写入失败或 worker 异常时，不能留下无记录的静默空洞。
3. 真实流量到达后，读取侧仍以真实请求覆盖探测终态。
4. 结算与快照读取之间的短暂竞态不能永久污染后续快照；下一次刷新应重新读取权威终态。

## 6. 验收矩阵

1. 无真实请求、探测成功：计一个成功兜底请求。
2. 无真实请求、探测明确失败：计一个失败兜底请求。
3. 无真实请求、没有账号级结果：生成 `missing`，产生管理员告警，但不计服务失败。
4. 有真实请求、没有探测终态：真实请求仍独占该桶，不能产生探测缺失失败。
5. worker 重试或多实例并发结算：同一分组/桶只有一个最终终态，成功可覆盖失败但不重复扩大分母。

## 7. 测试与发布边界

测试覆盖空结果、明确失败、成功覆盖失败、真实流量覆盖探测、watchdog 重试和快照读取。无用户账务、账号状态、支付数据或历史指标回填；如需数据库字段变更，只允许 expand-only 且必须单独列出迁移与回滚条件。
