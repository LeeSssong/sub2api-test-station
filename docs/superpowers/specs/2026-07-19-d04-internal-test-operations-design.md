# D04 内测自动化服务设计

## 状态

这是 2026-07-19 的历史自动化基线，已完成本地实现与只读部署准备。它仍描述首批邀请用户的签到、推荐和额度账本，但不再定义产品命名、公开页面、上游监控或预警 Agent。用户已确认首批用户按正式产品口径运行，产品和后台不展示“内测”标签；新的服务器端监控和预警设计以 `docs/superpowers/specs/2026-07-19-relay-ops-monitoring-and-alert-agent-design.md` 为准。真实凭据、生产写入和外部邀请码仍受生产交接门禁控制。

## 运营约束

本项目是用户的副业，用户白天几乎没有时间进行日常管理。注册控制、签到、奖励、累计额度、预算核对和异常通知必须默认无人值守运行；人工操作只保留给安全审批、内测关闭、异常处置和不可自动恢复的故障。

## 目标

为最多 15 名邀请制内测用户提供自动签到、固定推荐奖励、累计额度、总预算保护、审计和告警，同时尽量复用 Sub2API `v0.1.161` 的原生能力，不修改其数据库或维护私有镜像。

## 已确认业务规则

- 内测最多 15 个注册用户；不开放无限制公开注册。
- `GPT-内测` 分组保持站内倍率 `1.0x`，只绑定 Neko。
- 每个用户每天按 `Asia/Shanghai` 日期签到，获得固定 `$20` 站内额度。
- 签到额度累计，不在上海时间跨日时清空；内测关闭前保持可用。
- 被推荐用户首次产生成功计费请求后，推荐人获得固定 `$5` 奖励。
- 推荐人不设个人成功推荐数量上限；全站 15 人上限是硬边界。
- 签到奖励和推荐奖励进入同一个累计站内余额，不按来源拆分可消费额度，也不在内测期间自动清空。
- 注册动作本身不产生奖励；自荐、重复绑定和同一被推荐人多重绑定不合格。

## Sub2API 原生能力核对

源码版本：`v0.1.161`，提交 `19149ca196eeae4a4482e5299dc6fa4ba0b06c8c`。

### 可以直接复用

- 注册总开关和一次性邀请码注册；邀请码可批量生成，也可以不设置具体到期时间。
- 原生邀请关系：注册页支持 `aff` / `aff_code`，后端会防止自荐和重复绑定。
- 用户 JWT 接口 `GET /api/v1/auth/me`，可供同源签到页面确认当前用户。
- 管理员 API Key，使用 `x-api-key` 调用 Admin API。
- `POST /api/v1/admin/users/:id/balance`，要求 `Idempotency-Key`，幂等存储不可用时默认拒绝写入。
- 用户用量、余额历史、邀请关系和邀请记录查询接口。

### 不能直接满足

- 没有每日签到功能。
- 没有可配置的“全站最多注册 15 人”数值开关；需要在所有注册提交到达 Sub2API 前由独立服务做原子人数检查。
- 原生邀请返利按被邀请人的充值金额乘百分比计算，不支持“首次成功计费请求后固定奖励 `$5`”。
- 原生余额和流水不能识别 D04 签到、推荐奖励及其幂等业务键，需要独立服务维护发放事件账本并同步余额变化。

## 推荐架构

新增单实例 `internal-test-service`，作为现有 Compose 的第五个容器：

- 使用 Go 实现小型 HTTP 服务和后台调度器，编译为无 shell 的最小镜像。
- 使用独立 SQLite 持久卷保存内测用户、统一额度发放事件、邀请、用量游标、任务和审计事件，不直接读取或写入 Sub2API PostgreSQL。
- Caddy 将同一正式域名的 `/internal-test/*` 转发给该服务；其余路径继续转发 Sub2API。
- Caddy 还把 `POST /api/v1/auth/register` 强制转发给该服务的注册网关；Sub2API 容器不暴露宿主机端口，因此外部请求不能绕过人数检查直达注册接口。
- 服务不发布宿主机端口，只能通过 Caddy 或 Docker 内网访问。
- 用户浏览器复用 Sub2API 已登录 JWT；服务把 JWT 转发到内网 `GET /api/v1/auth/me` 验证身份，不读取 JWT 密钥、不持久化用户 Token。
- 服务使用单独生成的 Sub2API Admin API Key 调用管理接口；该 Key 仍具有管理员级权限，所以只以只读文件挂载到容器，不进入 Git、普通文档、日志或前端，也不交给 LLM Agent。
- D04 只接管专用内测用户：纳管时要求期初余额为零、只使用 `GPT-内测` 分组，且内测期间不得人工充值、兑换其他余额或加入商业分组。否则无法从 Sub2API 单一余额中准确区分签到、推荐和其他资金。

### 总预算模型

- D04 使用一个可配置的内测总预算 `D04_TOTAL_BUDGET_USD`，不再按日预算计算。
- 注册人数上限使用可配置的 `D04_MAX_USERS`，内测初值为 `15`；提高名额后，之前尚未使用且内测仍开放的邀请码可以继续注册。
- 预算按 Neko 实际成本口径核算：`已消耗成本 = 成功用量 × 0.07`。
- 为避免累计余额在未来集中使用时突破预算，服务同时计算当前未消费余额和已注册但尚未触发的推荐承诺：`预算占用 = 已消耗成本 + 当前 D04 用户余额合计 × 0.07 + 待触发推荐奖励数 × $5 × 0.07`。
- 签到和新用户注册在写入前都检查变更后的预算占用。推荐注册成功时即预留 `$5 × 0.07`；首次成功计费请求只把这笔预留转换为推荐人余额，不会因当时预算已满而拒发。
- 当预算占用达到总预算时，服务停止新的签到、邀请码生成和新用户注册并告警；已有余额仍可正常使用，已预留的推荐奖励仍可触发。未使用额度不是当日成本，但会作为未来成本预留。
- 每日报告同时展示实际成本、未消费额度、预算占用和剩余预算，避免把“已发额度”误报成“已发生成本”。

## 注册与推荐流程

1. 正式域名和极低额度写入验收通过后，管理员只做一次“启用邀请”的安全审批并生成首个邀请码。首位用户加入后，每个已登录内测用户都可以通过 `POST /internal-test/api/invitations` 自行生成一次性邀请码和专属推荐链接，不需要管理员逐个审批，也不限制每人生成数量。
2. Sub2API 开启注册和邀请码注册；不持有有效一次性邀请码的用户不能注册。
3. 生成邀请码时只检查 `已注册内测用户数 < N`，当前 `N=15`。允许多个用户同时持有尚未使用的邀请码，不计算或预留“剩余邀请名额”。
4. 服务生成 `/internal-test/join` 推荐链接。该页面先显示当前人数；人数达到 `N` 时显示“内测用户已满，请等待站长增加名额”，不进入注册页。
5. 人数未满时，加入页显示一次性邀请码并提供复制按钮，再把 Sub2API 原生 `aff_code` 带到原生注册页。原生注册页会自动读取 `aff` / `aff_code`，邀请码由用户粘贴到邀请码输入框。
6. 所有 `POST /api/v1/auth/register` 都由注册网关串行处理：持有互斥锁，通过 Admin API 统计 D04 已签发邀请码中非空 `used_by` 的去重用户数，达到 `N` 则返回 `409 INTERNAL_TEST_FULL`；推荐注册会使总预算不足时返回 `409 INTERNAL_TEST_BUDGET_FULL`；其余请求原样转发给 Sub2API。网关透传成功响应和登录 Token，但不记录请求体、密码、Cookie、Authorization 或响应 Token。这样多个未使用邀请码可以并存，而并发注册仍不能产生第 `N+1` 个用户。
7. 注册成功后，服务记录返回的数字用户 ID；若转发成功后服务在本地提交前崩溃，则通过邀请码 `used_by` 和 Admin 用户列表补记。D04 人数以 D04 邀请码的去重 `used_by` 为权威来源，不包含管理员和历史测试用户。
8. 内测只开放邮箱/密码注册；所有可能新建账户的 OAuth `complete-registration`、`create-account` 和 `pending/create-account` 路径在 Caddy 层关闭，避免绕过注册网关。登录和已有账号绑定流程不受影响。
9. 邀请码不设置具体到期时间；在 D04 邀请开关保持开启期间可使用一次。关闭内测时，服务关闭邀请码注册并批量使未使用邀请码失效。
10. 服务轮询原生邀请记录，确认被推荐用户与推荐人绑定；注册本身不发奖励。
11. 服务从用量接口确认被推荐用户出现第一笔成功计费请求后，以 `d04-referral-<invitee_user_id>` 为固定幂等键给对应推荐人增加 `$5`，每个被推荐用户只奖励一次；注册时的预算预留同时转为实际余额占用。
12. 同一推荐人若有 `n` 个不同被推荐用户均完成首次成功计费请求，则可获得 `n` 次 `$5`，不设置个人推荐次数上限；自荐、重复绑定和失败请求不产生奖励。
13. 原生“按充值比例返利”和“管理员充值参与返利”保持关闭，避免与固定 `$5` 奖励叠加。

## 签到与统一额度账本

Sub2API 中每个内测用户只保留一个累计余额。独立服务维护统一的 `credit_grants` 发放事件账本：

- `daily_checkin`：每个上海日期最多一笔 `$20` 发放事件。
- `referral_reward`：每个合格被推荐人最多一笔 `$5` 发放事件。

两种事件只用于来源审计和幂等控制，实际余额合并使用、不设置消费顺序，也不按来源拆分用量。服务按用户保存 Sub2API 用量游标，并使用以下恒等式核对余额：

```text
预期余额 = 期初余额 0 + 累计签到发放 + 累计推荐发放 - 累计成功消费
```

签到流程：

1. `POST /internal-test/api/checkin` 验证用户 JWT、内测资格和上海日期。
2. SQLite 事务创建唯一 `(user_id, grant_date)` 签到记录；重复请求返回当天既有结果。
3. 先同步该用户最新用量，再调用 Sub2API 余额增加接口，幂等键为 `d04-checkin-<user_id>-<YYYY-MM-DD>`。
4. Admin API 成功后提交本地状态；超时或不确定结果先查询余额历史，禁止更换幂等键重复发放。

预算与关闭流程：

1. 后台任务每分钟同步用量，按统一余额计算全站预算占用；签到和推荐奖励都不跨日清空。
2. 达到 `D04_TOTAL_BUDGET_USD` 后停止新的签到、邀请码生成和新用户注册，不扣除已有余额；已经在注册时预留的推荐奖励仍按首次成功调用自动发放。
3. 关闭内测时停止新签到、新奖励和新邀请码；未消费余额默认保留为只读审计记录，是否最终清零由单独的关闭决策处理。
4. 如果 Sub2API 余额与本地额度总额无法解释，停止该用户自动写入并发出高优先级告警，不自动覆盖余额。

## 自动任务

- 每分钟：同步新增用量、处理首次成功请求推荐奖励、重试结果明确的幂等任务。
- 每 5 分钟：按统一发放账本和成功用量核对 Sub2API 用户余额。
- 上海时间跨日后：仅切换新的签到日期，不清空前一日额度。
- 每小时：检查有效邀请码、注册总数、失败任务、服务健康和 Neko 成本。
- 每天：生成签到、奖励、用量、实际 Neko 成本、错误率、P95 延迟和待处理异常报告。

## 止损与告警

- 内测总预算占用达到阈值时暂停新的签到、邀请码生成和注册；已预留推荐奖励不受影响。活跃用户达到 10 人、出现连续 429/超时/SSE 未结束或余额核对失败时进入相应只读/暂停状态并发送飞书告警。
- 写入 Admin API 连续失败时进入只读模式；用户可查看状态，但不能领取新额度。
- SQLite、Sub2API 或幂等存储不可用时不降级为“继续发钱”；任务保持待处理并告警。
- 自动化服务只处理 `GPT-内测` 用户，不接触生产 `GPT` 用户、支付余额或 Aliu 候选账号。

## 安全边界

- Admin API Key 使用独立受限文件、容器只读根文件系统、非 root 用户、`no-new-privileges` 和最小 Linux capabilities。
- 页面设置严格 CSP；不加载第三方脚本，不记录 JWT、Admin API Key、密码、Cookie 或完整请求头。
- SQLite 仅保存 Sub2API 数字用户 ID、非敏感邀请关系、额度事件和用量游标；邮箱只在实时显示时使用，不持久化完整值。
- 所有外部写操作都有稳定幂等键、请求哈希、结果状态和审计事件。

## 分阶段发布

1. 本地使用假的 Sub2API HTTP 服务完成全部自动化测试，不接触生产。
2. 部署只读模式，只验证 JWT、用户资格、邀请记录、用量和余额读取。
3. 使用隔离测试用户和极低额度完成并发注册上限、多人并行邀请码、签到、重复签到、统一累计余额、首次推荐、重复推荐检测和失败重试验证。
4. 清理隔离数据后启用正式 `$20` / `$5` 规则，但保持邀请码签发关闭。
5. 正式域名、TLS 和公开入口验收通过后，才开启邀请码签发并邀请首位用户。

## 验收标准

- 没有人工参与时，签到、一次性发放、累计余额、首次推荐奖励和日报能够持续运行。
- 多个未使用邀请码可以同时存在；第 `N+1` 个注册提交返回 `409 INTERNAL_TEST_FULL`，界面显示“内测用户已满，请等待站长增加名额”。
- 同一用户同一天重复签到不会重复增加余额。
- 跨上海午夜后，签到和推荐形成的统一余额仍然保留，预算占用计算准确。
- 推荐注册只预留预算、不立即发奖励；第一笔成功计费请求只触发一次 `$5`，即使总预算随后已满也不会拒发已预留奖励。
- 自荐、重复绑定、失败请求和管理端探测不会触发奖励。
- Admin API 超时重试不会重复入账；余额不一致时自动停止写入并告警。
- 服务重启后 SQLite 任务、幂等状态和用量游标保持一致。
- 测试、日志和仓库不包含真实 JWT、Admin API Key 或用户 API Key。

## 不在本轮范围

- 自动支付、公开无限注册、商业套餐和真实收费。
- 自动修改 Neko 账号、Sub2API 分组倍率或生产上游。
- 让 LLM Agent 直接持有 Admin API Key 并自主改变用户余额。
- 多节点高可用；当前 15 人内测先保持单实例，通过健康检查、重启策略和告警降低风险。
