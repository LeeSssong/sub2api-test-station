# 第四套混合性能监测设计规格

## 1. 问题与现状证据

当前渠道监测存在多套语义，但管理员设置入口只提供原有的两种模式。现有代码与线上页面证据如下：

- 原生设置通过 `channel_monitor_enabled` 与 `channel_monitor_mode` 控制监测路径，前端设置页当前只有两个选择项。
- 现有自建 Monitor V2 页面复用 `MonitorV2RouteView`、`MonitorV2GroupCard`、`MonitorV2Timeline` 及 `/api/v1/monitor-v2` 合同；它主要展示主动探测投影。
- 主动探测结果保存在 `account_monitor_results`，包含状态、首 Token 耗时和总耗时。
- 用户请求流水保存在原生 `usage_logs`，包含 `group_id`、`first_token_ms`、`duration_ms`；当前项目已经有严格有效服务响应口径，使用 `actual_cost > 0` 并排除失败/`usage_completeness='unknown'` 占位流水。
- 仓库已有 PostgreSQL `percentile_cont` P95 查询能力，但现有自建卡片使用的并不是本规格要求的混合样本和视觉形态。

本任务新增第四种并列模式，不替换前三种：

1. 原生主动探测；
2. 原生真实请求聚合；
3. 现有自建 Monitor V2；
4. 新的混合性能监测。

前三种的已有入口、数据语义和页面不在本任务内改写。

## 2. 目标与非目标

### 目标

- 在原生管理员设置中增加第四种可选监测模式，并保留旧模式读取与回滚能力。
- 以五分钟为基础聚合桶，把主动探测成功和严格定义的真实用户请求成功统一为同一类性能样本。
- 每个可见分组展示一张独立性能卡片，以大型空心圆环作为视觉中心。
- 可用性按五分钟桶计算：桶内只要出现一次主动探测成功或严格定义的真实请求成功，该桶即为可用。
- 首字速度和总耗时均使用同一批统一样本的 P95；旁边只展示一次“基于 N 次真实请求”。
- 圆环颜色按可用性显示：`>=85%` 绿色，`>=50% 且 <85%` 黄色，`<50%` 红色。
- 用低干扰呼吸光晕表达持续监控；百分比、文字和指标保持静止。

### 非目标

- 不修改前三种模式的监测算法、页面布局或既有文案。
- 不改变主动探测调度、重试、账号选择、计费、错误处理或分组权限。
- 不建立第二套账务事实源，不修改 `usage_logs` 的写入语义，不回填历史数据。
- 不新增横向柱状时间线、粒子、轨道点、旋转扫光或颜色解释图例。
- 不使用 GitHub Actions，不改变既有本地/宿主发布链。

## 3. 产品与数据语义

### 3.1 统一模式与兼容

对外展示四个清晰的模式标签；内部使用稳定的显式模式标识，不依赖数字顺序解释业务含义。旧 `v1`/`v2` 值继续按当前生产语义解析，未知值安全回退到当前默认模式。新增模式只在显式选择后生效，回滚为切回任一旧模式。

第四模式的页面继续复用现有登录、分组可见性和设置刷新机制；渲染分支使用独立的混合卡片组件，避免改写第三模式的组件合同。

### 3.2 严格成功与统一样本

严格成功必须复用当前 Monitor V2 使用的有效服务响应谓词，不在新查询中复制一套近似判断。该谓词至少满足：

- 用户请求的 `usage_logs.actual_cost > 0`；
- 请求不属于失败/未知完整性占位（`usage_completeness='unknown'` 不计入）；
- 保留当前项目对完整/部分有效流水的既有兼容语义。

统一性能样本只收纳成功记录且同时具备两项性能字段：

```text
主动探测成功（ttft_ms -> first_token_ms，latency_ms -> duration_ms）
+ 严格成功的真实用户请求（first_token_ms，duration_ms）
并且两项字段均非空且为非负有限值
```

内部可以保留 `sample_source=probe|user` 供诊断和测试使用，但第四套页面不区分来源，统一以“真实请求”展示。

### 3.3 五分钟桶与可用性

- 桶使用 UTC、半开区间 `[bucket_start, bucket_start + 5m)`，边界归属稳定。
- 选定窗口内每个五分钟桶都生成，即使该桶没有记录。
- 桶内存在至少一个主动探测成功或严格真实请求成功时，桶状态为可用。
- 当前窗口可用性为：

```text
可用桶数量 / 窗口总桶数量 * 100
```

- 24 小时、7 天、30 天窗口分别对应 288、2016、8640 个五分钟桶。
- 第四套卡片不展示横向柱状时间线；五分钟桶只作为可用性和数据聚合的基础事实。

### 3.4 P95 与样本数

- 首字 P95：窗口内统一样本 `first_token_ms` 的 `percentile_cont(0.95)`。
- 总耗时 P95：同一批统一样本 `duration_ms` 的 `percentile_cont(0.95)`。
- 页面只展示一次样本数，取统一样本集合数量：`基于 N 次真实请求`。
- P95 直接基于窗口内原始统一样本计算，不对每个五分钟桶的 P95 再做二次百分位，避免百分位数的错误合并。
- 因统一样本要求两项字段同时存在，首字、总耗时和样本数严格对应同一批记录。

### 3.5 无成功样本时的连续值

当当前窗口没有统一成功样本时：

1. 可用性仍按五分钟桶计算，通常为 `0%`，圆环为红色；
2. P95 与样本数优先沿用同一分组最近一次成功统一样本窗口的值；
3. 若当前实例没有窗口内值，则查询同一分组最近的历史成功统一样本作为参考；
4. 若历史上从未存在成功样本，接口返回确定性的零值和 `sample_count=0`，不返回空字符串、`null`、“暂无数据”或“无真实请求”文案。

该回退只用于保持卡片连续展示，不改变当前窗口可用性，也不把失败请求伪装成成功样本。

## 4. 接口与字段契约

第四模式使用独立版本的监测快照合同，避免破坏现有 Monitor V2 合同。路径固定为登录态 `GET /api/v1/monitor-v4?window=24h|7d|30d`，与现有路由鉴权和分组可见性规则一致。

```json
{
  "contract_version": "1",
  "mode": "hybrid_performance",
  "window": "7d",
  "refresh_interval_seconds": 60,
  "generated_at": "2026-08-25T06:00:00Z",
  "groups": [
    {
      "id": 12,
      "name": "OpenAI 高速组",
      "platform": "openai",
      "rate_multiplier": 0.3,
      "status": "operational",
      "availability_percent": 96,
      "ttft_p95_ms": 1820,
      "latency_p95_ms": 4760,
      "sample_count": 128,
      "source_updated_at": "2026-08-25T06:00:00Z",
      "is_fallback_metric": false
    }
  ]
}
```

字段约束：

- `availability_percent` 为 `0..100` 的有限数，前端按整数百分比展示；
- `ttft_p95_ms` 与 `latency_p95_ms` 为非负有限数；无当前样本时按 3.5 节回退，禁止 `null`；
- `sample_count` 为非负整数，首字/总耗时和该数量来自同一统一样本集合；
- `is_fallback_metric=true` 只用于内部合同和定向测试，不改变用户文案；
- `status` 由当前窗口新鲜性和可用性投影决定，不能用历史回退 P95 反推当前可用；
- 分组列表必须继续使用现有权限和专属分组过滤；不得因为监测查询改写可见范围。

## 5. 页面与视觉结构

### 5.1 卡片结构

每个可见分组渲染为一张独立卡片，内部使用稳定的单列栅格：

1. 顶部：左侧分组名称与平台/窗口，右侧显示 `倍率：0.3x`；
2. 分组信息下显示低干扰绿色状态点和“监测中”；
3. 中部：大型空心圆环，约占卡片 50% 的视觉重量并水平居中；
4. 圆环中心固定显示可用性百分比和“可用性”；
5. 下部：等宽双列、同一基线的“首字速度 P95”和“总耗时 P95”；
6. 底部居中只显示一次“基于 N 次真实请求”，下一行显示最近探测时间。

卡片不得出现标题、圆环、指标、样本数之间的歪斜；桌面和窄屏均使用同一对齐规则，必要时在卡片内部换行而不是造成整页横向溢出。

### 5.2 圆环状态与动效

- 圆环为完整闭合空心环，不显示缺口；可用性百分比不会随动效旋转。
- `>=85%` 使用现有绿色；`>=50% 且 <85%` 使用黄色；`<50%` 使用红色。
- 只保留圆环整体的缓慢呼吸亮度/外圈光晕；不使用粒子、轨道点、扫光、旋转缺口或旋转数字。
- `prefers-reduced-motion: reduce` 时关闭呼吸动画，保留静态颜色和结构。
- 动画不能改变圆环尺寸、百分比位置、卡片高度或指标布局。

## 6. 数据流与失败语义

```text
管理员选择 hybrid_performance
  -> 登录态第四模式页面
  -> 读取可见分组与可调度账号范围
  -> 读取 account_monitor_results 成功探测
  -> 读取 usage_logs 严格成功请求
  -> 映射统一字段并按 UTC 五分钟分桶
  -> 计算桶可用性 + 窗口统一样本 P95
  -> 必要时回退最近成功性能值
  -> 返回 v4 快照
  -> 卡片渲染圆环与双 P95 指标
```

- 主动探测查询失败或真实请求查询失败时，接口返回明确的监测快照错误；前端保留上一份成功快照并按既有刷新重试策略处理，不把查询失败转换成成功样本。
- 单个分组没有当前成功样本时仍返回该分组卡片，使用 3.5 节性能回退和当前可用性。
- 任何来源的错误流水、未知完整性尝试、凭据或原始请求体都不能进入页面性能字段。
- 不持久化原始请求/响应，不新增敏感字段返回，不改变用户或管理员的权限边界。

## 7. 兼容、迁移与回滚

- 默认关闭第四模式，旧配置和旧页面行为不变。
- 设置 API、公开设置 DTO、前端类型和验证器增加新枚举值，并保留旧值兼容。
- 优先复用现有表和索引进行读时聚合，不新增数据库迁移、不回填历史、不写新事实表。
- 如实施阶段的查询性能证据证明必须增加派生缓存，需另立规格；本任务不引入第二事实源。
- 回滚优先通过管理员设置切回任一旧模式；代码回滚只涉及第四模式新增路由、组件、查询和合同，不需要数据库回滚。
- 预期发布预检 `downtime_required=false`；若发布预检返回 `true`，按项目停机门禁暂停。

## 8. 场景化验收矩阵

| 场景 | 预期结果 |
| --- | --- |
| 选择前三种旧模式 | 现有页面、接口和设置行为不变 |
| 选择第四模式 | 页面渲染独立混合性能卡片，旧模式不被覆盖 |
| 五分钟桶只有主动探测成功 | 桶可用，探测样本进入两个 P95 |
| 五分钟桶只有严格真实请求成功 | 桶可用，用户样本进入两个 P95 |
| 五分钟桶两类成功都存在 | 桶只计一次可用，统一样本共同参与 P95 |
| 五分钟桶没有用户请求但有探测成功 | 不出现空性能值，探测样本补足性能 |
| 成功记录缺少任一性能字段 | 不进入统一样本和样本数 |
| `actual_cost=0` 或 `usage_completeness='unknown'` | 不计为真实成功，不进入统一样本 |
| 可用性为 96% | 圆环绿色，中心显示 96% |
| 可用性为 72% | 圆环黄色，中心显示 72% |
| 可用性为 0% | 圆环红色，卡片仍有确定性性能显示 |
| 当前窗口全失败但历史有成功 | 当前圆环红色，P95/样本数沿用最近成功值 |
| 历史从未成功 | 不返回 null/空文案，返回确定性零值和样本数 0 |
| 普通桌面与窄屏 | 卡片内部对齐稳定，整页无横向溢出 |
| 减少动态效果设置 | 呼吸动效关闭，数据和颜色不变 |

## 9. 测试策略

- 后端：严格成功谓词复用合同、主动/用户样本映射、五分钟边界、可用性 OR 规则、统一样本 P95、缺字段排除、历史性能回退和新模式 API 合同测试。
- 前端：模式选择与旧值兼容、v4 快照校验、卡片阈值颜色、统一样本文案只出现一次、倍率完整文案、圆环中心静止、呼吸动效与 reduced-motion、桌面/390px 对齐和无溢出测试。
- 必要的 Go 定向测试、前端 Monitor V4/设置页 Vitest、`go build ./cmd/server`、`pnpm typecheck`、`pnpm build`、`gofmt` 和 `git diff --check`；不执行无关全仓回归。
- 视觉验收至少覆盖绿色、黄色、红色三张卡片，以及当前窗口全失败回退状态。

## 10. 发布、线上验证与剩余风险

- 实施必须在独立任务 worktree 中完成，基线为当时最新干净 `main`；不能从当前 T58 候选分支派生。
- 合并前只运行本任务直接相关门禁；根合并后按发布链运行必要回归、构建和发布预检。
- 线上专项验收：管理员设置能读取并保存第四模式；登录态页面能看到每个分组卡片、三种颜色阈值、稳定圆环和 P95；1440px/390px 无整页横向溢出；公网健康端点保持 200。
- 失败时保留候选 worktree、测试证据和回滚提交，不覆盖或清理失败候选。
- 剩余风险：真实请求量很大时，30 天读时 P95 查询可能需要继续观察数据库执行计划；本规格要求先复用现有事实源和索引，若性能不足必须另立优化任务，不以降低数据口径换取速度。
