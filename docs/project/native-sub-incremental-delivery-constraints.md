# 原生 Sub 小步发布全局约束

## 1. 目标与事实源

- 本轮只在官方 Sub2API 原生后端、前端、运维页面和宿主发布链中嵌页面或增加功能。
- 不建设、恢复或切换 `external-primary`，不新增平行控制面、平行账务源或平行管理入口。
- 当前代码、测试和生产只读证据优先于历史计划；本文件和 `native-sub-task-package-queue.md` 优先于派生线程聊天上下文。
- 每个任务包只交付一个用户可感知或管理员可验证的垂直功能，不顺带实施相邻任务。

## 2. 顶层任务启动硬门禁

- 从 T03 之后任何任务包的启动或继续实施起，强制执行：`一个任务包 = 一个用户可见的独立顶层 Codex 任务 = 一个独立 worktree = 一份正式规格书 = 一份实施计划 = 独立任务复审与全分支终审 = 一次根任务授权合并 = 一次部署 = 一次线上验收`。
- 根任务按队列严格串行创建用户可见的顶层任务；前一任务包未完成线上验证、明确冻结或由用户明确处置前，不创建或启动下一实现任务。
- 根任务只负责排队、创建顶层任务、读取交接、授权合并、合并后门禁、发布和线上验收；根任务内部 `spawn_agent` 只能用于根任务自身的辅助核对，不能替代任务包的用户可见顶层任务隔离，也不得直接承担整个任务包。
- 每个顶层任务必须先完整阅读本文件、任务队列、`AGENTS.md`、项目进度总账及自己的任务包描述，并从当时最新且干净的 `main` 创建自己的 `codex/<task-name>` 分支和独立 worktree；禁止从其他任务分支、旧候选或生产运行提交派生。
- 顶层任务先在自己的 worktree 登记总账，再按本节规定完成 brainstorming、规格书批准和实施计划；规格书、计划、代码、测试和验证证据都归入同一任务包。
- 顶层任务不得改动其他任务包文件，不得自行扩大需求，不得触碰生产，不得自行合并 `main`、推送或部署。

### 2.1 Brainstorming 与规格书批准门禁

- 每个新顶层任务必须完整执行 Superpowers brainstorming，不能用创建 `docs/superpowers` 路径、简短技术摘要或内部代理讨论代替。
- 固定顺序为：探索现状和证据；一次只问一个澄清问题；提出 2–3 个可选方案及取舍和推荐；分段展示设计并逐段取得用户批准；写正式规格书；完成规格书自审；请用户明确审阅并批准书面规格书；之后才能调用 writing-plans。
- 正式规格书至少覆盖：问题证据与当前行为、目标与非目标、影响用户和边界条件、2–3 个方案比较与选择理由、端到端数据/控制流、接口与字段契约、失败与安全语义、兼容性与迁移、场景化验收矩阵、测试策略、发布/线上验证/回滚条件、仍待决事项和用户批准记录。
- 未取得用户对书面规格书的明确批准前，禁止调用 writing-plans、编写实现代码、派生实现代理或进行其他实施动作。
- 计划获批后，独立顶层任务内部才可按 `AGENTS.md` 使用 fresh implementer subagent、独立任务复审者和最终全分支复审者；内部 subagent 是实施工具，不是顶层任务的替代。

## 3. 任务包完成与汇报协议

- 顶层任务完成实现、定向测试、类型检查或构建、diff 自查、独立任务复审和最终全分支终审后，状态只能是 `READY_FOR_ROOT_REVIEW`，不能声明已完成或已部署。
- 汇报必须包含：任务包编号、基线 `main` SHA、提交 SHA、变更文件、测试结果、未验证项、迁移变化、配置变化、`downtime_required`、回滚方式和剩余风险。
- 根线程确认该任务包是当前队列唯一可部署候选后，发送带目标 `main` SHA 的 `AUTHORIZE_MERGE_TO_MAIN` 指令。
- 顶层任务收到明确指令后才能把自己的已审查分支合入根目录 `main`；合并前必须确认根目录干净、目标 SHA 未漂移、没有其他合并或部署在进行。
- 合并完成后顶层任务只汇报合并 SHA 和冲突/验证结果，继续等待；不得推送或部署。

### 3.1 既有任务流程偏差记录

- T01、T02 的独立 worktree、规格书、计划、复审、部署和线上验证证据继续有效，技术成果不回滚、不重做；但它们没有按用户原始要求创建“每个任务包一个用户可见的独立顶层 Codex 任务”，原会话使用的内部 `spawn_agent` 不能替代顶层任务隔离，因此不得宣称 T01/T02 顶层任务流程合规。
- T03 是流程纠偏指令到达前已在途、由根任务内部代理实施并完成合并发布的任务包，同样不得倒称满足本文件新增的顶层任务与完整 brainstorming 门禁；保留其实现、审查、合并、发布和运行健康证据，按线上专项验收是否闭环决定完成状态。
- 上述偏差是流程合规记录，不推翻已验证技术成果；新门禁从后续任何任务启动或继续实施时强制执行。

## 4. 根线程快速发布协议

- 根线程在合并后的 `main` 只运行与当前任务包直接相关的回归、必要构建/类型检查、迁移检查和发布预检，不重复扩大到无关功能。
- 生产推送和部署只能来自已经验证的 `main`；禁止从派生 worktree、临时目录或候选分支直接发布。
- 发布准备不得使用 GitHub Actions，继续使用已审查的本地/宿主脚本和蓝绿链。
- 发布预检必须明确输出 `downtime_required=true|false`。为 `false` 时根线程可按已确认队列执行快速部署；为 `true` 时必须在任何停服、迁移、重启或切换动作之前停止。
- 一旦某次候选需要停机，本次及其后所有部署都暂停，等待用户人工确认；不得绕过、拆分或把停机包装成普通蓝绿更新。
- 部署成功后必须完成该任务包的线上专项验证和健康检查，再更新总账、授权清理对应 worktree/分支并派生下一任务。
- 部署或验证失败时保留工作区、分支、失败证据和回滚依据，在原任务包继续修复，不启动下一任务包。

## 5. 产品与数据边界

- 错误转译不新增平行页面。管理员在“管理后台 -> 用量明细 -> 错误请求 -> 错误详情”查看“管理员诊断”；运维总览的请求错误/上游错误详情复用同一诊断结构。
- 用户只看到脱敏中文含义和可执行建议；管理员可看到错误阶段、归属、是否已选账号、账号/分组、原始上游状态与原始错误，但不得把凭据、完整 API Key 或敏感请求体返回用户。
- 上游错误优先复用 Sub 原生错误透传规则；本站限流、鉴权、路由和请求体读取失败使用同一解释字典的本地分支，不伪装成上游错误。
- 大上下文上传问题按入站链路处理：保留请求体大小和安全边界，修复固定 300 秒代理窗口对慢速上传的误伤；不得仅把 502 改文案而不处理根因。
- Sub/New 原生账单返回是非 OAuth 上游账号的唯一逐笔成本事实源；精确命中后实际扣费 blank、`null` 或空字符串按 `0` 登记。不得估算、模糊匹配、以 `account_cost` 冒充原生账单，或引入外部账务前置条件。OAuth 自购账号不查询上游，由管理员按账号和北京自然日填写人民币成本。
- T03-R1 必须纠正 T03 仅在管理员打开详情时同步查询、未实现异步持久化的缺口，同时保持官方 `usage_logs` 结构和插入语义不变。部署启用后的官方流水通过独立一对一证据模型登记；正常非零证据直接参与财务汇总，零成本或无法取得精确证据的流水进入管理员异常核对。不得历史回填、延迟补查或上游重试。管理员详情、异常视图和账号财务页读取同一本地事实；人工核对与每日金额覆盖必须保留原始证据并写审计。
- “控制面暂时不可用 / 完整性 unknown”从原生账号监控、用量和利润页面移除，不以其他外部控制面提示替代。
- “暂不建议入组”保持轻提示：桌面悬浮或点击、移动端点击，仅显示一到两行原因，不新增常驻说明区。
- 全局评分权重与分组评分权重独立持久化，复用现有分组评分设置交互，不改变既有排序之外的调度行为。
- 官方更新无冲突时快速准备；出现冲突立即停止、保存完整冲突日志，禁止猜测解决或自动部署，界面固定提示：`存在冲突，需要手动查看冲突日志并更新。`

## 6. 禁止事项

- 禁止把多个任务包合成一次大发布。
- T03-R1 未完成推送、部署和线上验收前，禁止启动 T05 或后续任务包。
- 禁止同时让多个派生线程操作根目录 `main`。
- 禁止在任务包中引入 `external-primary`、relay-ops 主路径依赖或新的平行控制面。
- 禁止为了清理工作区而丢弃未合并提交、未提交内容或失败证据。
- 禁止在没有线上验证时把任务标记为“已完成”。
- 禁止在检测到冲突、停机需求或目标 `main` 漂移后继续自动推进。
