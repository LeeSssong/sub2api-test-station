## 问题与证据

账号监控当前使用四套没有统一边界的投影：

1. 卡片成功率和 TTFT P95 读取 `usage_logs` 与 `ops_error_logs` 的真实请求证据。
2. 当前可用状态在 `projectAccountMonitorProbe` 中只读取主动探测；没有新鲜探测时，即使刚有真实成功请求，卡片仍显示“待确认”。
3. 时间线对每个 5 分钟源桶采用真实请求优先、主动探测回退，但保留来源、颜色和独立计数。
4. 质量融合把整个窗口的真实请求与探测样本相加；分组投影在没有真实窗口行时又错误丢弃探测。

这会造成用户看到成功率、TTFT、状态、柱状图与排名互相矛盾。截图中的 `#190` 有 93.9% 成功请求但仍“待确认”；`#289` 的成功请求没有 `first_token_ms`，TTFT P95 为 `--`；灰色柱表示该桶既无真实请求也无探测结果。现有实现证据位于：

- `backend/internal/service/account_monitor_service.go`
- `backend/internal/service/account_monitor_quality_fusion.go`
- `backend/internal/repository/account_monitor_repo.go`
- `frontend/src/components/admin/account-monitor/AccountMonitorCard.vue`

另一个独立回归：原生 `EditAccountModal` 已在 `AccountMonitorView.vue` 接线，但 `AccountMonitorCard.vue` 的遗留样式将 `[data-test="account-edit"]` 设为 `display: none`，因此用户只看到“账号详情”和“账号操作”。

## 目标与非目标

### 目标

1. 管理员只看到一类“请求”：真实调用与无流量时的主动探测在统计、API 和卡片上完全等价，不展示来源、分类、独立颜色或独立计数。
2. 当前状态、窗口成功率、TTFT P95、时间线、当前/历史质量与调度质量输入均由同一套请求选择规则产生。
3. 卡片的“本组调度优先级”继续直接读取实际调度器的实时投影，不由监控页重算。
4. 恢复“编辑账号”原生入口和已有弹窗，不改变卡片布局或新增页面。

### 非目标

- 不改变真实用户请求的路由、重试、计费、成本、收入、利润或调度策略。
- 不伪造主动探测的业务流水、token、收入、成本或利润；这些账务字段继续只来自 `usage_logs`。
- 不删除 `usage_logs`、`ops_error_logs` 或 `account_monitor_results` 的来源记录。来源可保留于内部原始事实，不能作为监控 API、统计口径或 UI 的可见分类。
- 不增加迁移、历史回填、配置项、控制面或平行数据源。

## 方案比较

### 方案 A：统一请求选择器（选择）

以账号和 5 分钟自然桶为单位选择一个请求集合：有真实逻辑请求则选择真实请求；没有真实请求则选择一个主动探测终态；两者皆无为空桶。所有监控质量指标读取该集合。实现能复用现有原生事实源和时间线 SQL，且每个数字都能被同一规则解释。

### 方案 B：双指标并列

保留“真实请求”和“探测请求”两组计数、成功率及色彩，给用户选择查看。这保留更多诊断信息，但直接违背“不要区分探测和真实请求”的产品要求，也会延续矛盾。

### 方案 C：窗口级加权融合

保留现有整窗混合，再引入权重平衡探测和真实流量。它无法保证同一时间桶不重复统计，权重也无法向运营人员解释，不采用。

采用方案 A。

## 统一请求契约

### 时间与去重

- 所有时间使用 UTC；查询窗口为 `[start, end)`。
- 原始时间按 5 分钟自然桶归属。展示的 24 个柱可将这些源桶汇总为等宽显示桶，但不能改变源桶选择结果。
- 真实调用沿用现有逻辑请求去重键：`logical_request_id`，其次 `request_id`，最后源记录 ID。自动切号和内部重试只保留最终用户可见终态。
- 每个账号、每个源桶：若存在至少一个去重后的真实逻辑请求，选择该桶全部真实逻辑请求，且忽略该桶全部主动探测。
- 若没有真实逻辑请求，选择该桶 `checked_at` 最新且终态为 `success` 或 `failed` 的一条主动探测，作为一条普通请求。
- 若两者皆不存在，该桶为空；不计请求数、成功率分母、TTFT 样本、质量样本或柱高。

主动探测的原始 `account_monitor_results` 记录仍存在，以支持任务调度、重试保护和运维追溯；统一口径只影响其进入账号监控统计后的语义。

### 聚合指标

对于所选请求集合：

| 指标 | 规则 |
| --- | --- |
| 请求数 | 所选请求总数。探测补位后就是普通请求。 |
| 成功率 | 成功请求数 / 请求总数；空窗口显示 `--`。 |
| TTFT P95 | 所有成功且 `first_token_ms`/`ttft_ms` 非空的所选请求的原始 TTFT 样本 P95；不能计算“P95 的 P95”。有成功请求但没有 TTFT 样本时显示 `--`。 |
| 时间线 | 每个显示桶汇总已选择请求，按统一成功/失败和 TTFT 规则渲染；空桶灰色。颜色不再表达请求来源。 |
| 当前状态 | 使用最近一条所选请求。该请求的新鲜度阈值为 `2 * interval_seconds`；新鲜成功为“正常”，新鲜失败按既有连续失败/致命错误规则为“异常”或“不可用”，没有新鲜请求为“待确认”。 |
| 当前与历史质量 | 从同一所选请求集合聚合，不再整窗叠加真实请求和探测。 |

真实调用存在时，探测不计入该桶，避免重复放大分母。探测不存在且没有真实调用时，空桶不伪装为成功、失败或零请求。

### 排名与账务边界

- 调度排名必须继续调用 `schedulerProjection.Project`，展示调度器返回的 `rank`、`rank_total`、`eligible`、`snapshot_at` 与原因。账号监控不得根据页面聚合重新推导排名。
- 调度器所使用的质量事实改为上述统一请求聚合；这保证历史质量与排名输入一致，但不改变调度器的权重、资格、并发负载、冷却或重试预算。
- 请求数不再区分来源，包含补位探测；但业务累计成本、收入、利润率和 token 继续只由原生 `usage_logs` 聚合，主动探测没有业务账务值。

## API 与前端合同

`GET /api/v1/admin/accounts/monitor?range=...` 保持现有 URL 和账号、分组结构。账号监控的请求/质量字段改为统一语义：

- `request_count`、`error_count`、`success_rate`、`ttft_*`、`real_request_evidence` 和 `real_request_timeline` 的值全部来自统一请求集合；字段名在本任务中为兼容客户端保留，但不再承诺“real”的来源语义。
- API 不新增 `probe_count`、`probe_success_count`、`source`、`real_request_count` 或任何等价的来源拆分字段；现有时间线响应中的这些字段从公开合同和前端类型中移除。
- 卡片标题、计数、成功率、TTFT P95 和柱状图只称“请求”。不添加来源提示、双色图例、悬浮来源细目或新布局。
- 柱状图颜色仅表达统一请求的状态/性能：无请求灰色；全失败红色；成功但 TTFT P95 超过 10 秒黄色；其余成功绿色。
- 现有“编辑账号”按钮保持文字、位置和事件；删除仅隐藏该按钮的遗留 CSS。点击后继续加载原生账号、代理与分组并打开现有 `EditAccountModal`。

在所有内部聚合完成切换前，允许后端短期保留旧 Go 字段名和结构适配，禁止向前端同时输出旧/新两套不同数值。

## 数据与控制流

```text
usage_logs + ops_error_logs --去重/按桶--> 真实逻辑请求
account_monitor_results --每空桶最新终态--> 主动探测请求
                    \                         /
                     \--统一请求选择器--------/
                                  |
             账号窗口指标 / 时间线 / 当前状态 / 质量事实
                                  |
             调度器投影（真实 rank） --> 账号监控卡片

usage_logs --原生账务聚合--> 成本 / 收入 / 利润（不接入主动探测）
```

实现优先扩展现有 `account_monitor_repo.go` 的批量 SQL，使窗口聚合与时间线使用相同的选择器或同一可测试 SQL 片段；服务层只消费统一结果。不能新增第二套统计 repository 或缓存事实源。

## 失败与兼容语义

- 读取真实请求、主动探测或统一聚合失败时，账号监控接口返回既有错误；不得回退到旧的真实优先/探测混合口径，也不得填充假成功。
- 真实请求成功但没有 TTFT 样本时，成功率仍正常计算，TTFT P95 为 `--`，不是错误状态。
- 新鲜真实成功请求可以把当前状态恢复为“正常”；系统不再要求额外的新鲜探测。
- 刷新探测按钮仍只触发探测，不创建用户业务流水。其结果在所属空桶作为普通请求参加监控统计。
- 所有指标、时间线与卡片使用同一刷新快照，避免一次响应内不同字段读取到不同时间边界。
- 不回填历史数据；上线前的已存事实按统一选择规则即时重新聚合。

## 风险与控制

- **探测被误认为业务调用：** 页面和质量统计按用户要求统一，但账务路径严格隔离，探测不会写入 `usage_logs`。
- **历史字段名含 `real`：** 本任务先保留名字但统一其值，避免前后端错配；字段重命名只能另立兼容任务。
- **SQL 逻辑漂移：** 窗口聚合与时间线必须共享选择规则并通过相同场景测试锁定。
- **状态误恢复：** 只使用在 `2 * interval_seconds` 内的最近所选请求，过期请求仍为“待确认”。
- **编辑入口范围扩大：** 只删除隐藏该按钮的规则，不重构原生编辑表单、账号菜单或页面布局。
