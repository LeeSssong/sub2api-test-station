# 原生 Sub 小步发布全局约束

## 验收站与主站发布授权补充（2026-08-27）

验收站固定身份、登录/日志/宿主运维命令、凭据读取方式，以及主站发布的两条唯一授权路径，统一以 `docs/project/acceptance-station-global-constraints.md` 为准。所有线程在涉及验收站或主站发布前必须先阅读该文件；不得把主站数据/凭据带入验收站，也不得因普通“部署/上线/继续”表述直接部署主站。主站只有在用户明确说“测试站验收通过，部署主站”或“快速部署到主站”时才可发布；主站成功后必须用同一 commit/tree 立即同步或核对验收站版本。

## 1. 目标与事实源

- 本轮只在官方 Sub2API 原生后端、前端、运维页面和宿主发布链中嵌页面或增加功能。
- 不建设、恢复或切换 `external-primary`，不新增平行控制面、平行账务源或平行管理入口。
- 当前代码、测试和生产只读证据优先于历史计划；本文件和 `native-sub-task-package-queue.md` 优先于派生线程聊天上下文。
- 每个任务包只交付一个用户可感知或管理员可验证的垂直功能，不顺带实施相邻任务。

### 1.1 原生优先强制约束

- 讨论、规划或实施任何功能、优化、页面、指标、计费、监控、调度、更新或诊断能力前，必须先检查当前 Sub 原生代码、API、页面、测试和已有运维链，书面说明原生能力是否已经存在、可直接复用或可小幅扩展。
- 默认选择“直接复用原生能力”或“在原生接口/页面上做最小扩展”；只有正式规格书以代码和行为证据证明原生能力无法满足目标时，才允许设计新的子系统或事实源。
- 禁止重复建设 Sub 已有的计费口径、错误码转译、账号统计、质量监控、账号管理或其他管理事实源；补充能力必须明确与原生能力的分工，且不得改写原生语义。

## 2. 顶层任务启动硬门禁

- 从 T03 之后任何任务包的启动或继续实施起，执行：`一个任务包 = 一个用户可见的独立顶层 Codex 任务 = 一个独立 worktree = 一份正式规格书 = 一份实施计划 = 功能实现与直接相关功能测试 = 一次根任务授权合并 = 一次部署 = 一次线上验收`。自 2026-08-16 用户最新指令起，不再把逐任务独立复审、scoped re-review 或全分支终审作为强制完成门槛。
- 本项目同时只能有一个发布总控。只有发布总控可以修改根 `main`、全局队列、项目进度总账、发布证据和生产状态记录。
- 发布总控最多可让两个互不依赖的功能 worktree 并行处于设计、实现或复审阶段；前一任务包未完成线上验证、明确冻结或由用户明确处置前，不得让下一任务进入合并、部署或线上验收车道。
- 根任务只负责排队、创建顶层任务、读取交接、授权合并、合并后门禁、发布和线上验收；根任务内部 `spawn_agent` 只能用于根任务自身的辅助核对，不能替代任务包的用户可见顶层任务隔离，也不得直接承担整个任务包。
- 所有用户可见的独立顶层 Codex 任务统一使用 `GPT-5.6 Sol / medium`；顶层任务内部 fresh implementer、独立 reviewer 和最终全分支 reviewer 的模型设置继续按各自既定实施规则执行，不因本条统一改动。
- 每个顶层任务必须先完整阅读本文件、任务队列、`AGENTS.md`、项目进度总账及自己的任务包描述，并从当时最新且干净的 `main` 创建自己的 `codex/<task-name>` 分支和独立 worktree；禁止从其他任务分支、旧候选或生产运行提交派生。
- 发布总控在根 `main` 登记全局状态；顶层任务只维护自己的规格、计划、代码、测试、复审报告和交接，不得修改 `docs/project/project-progress.md` 或 `docs/project/native-sub-task-package-queue.md`。
- 顶层任务不得改动其他任务包文件，不得自行扩大需求，不得触碰生产，不得自行合并 `main`、推送或部署；同一个 worktree 同时只能有一个实现写入者，reviewer 必须严格只读。

### 2.1 统一状态机与发布单车道

- 所有任务统一使用：`BACKLOG -> DESIGNING -> IMPLEMENTING -> REVIEWING -> READY_FOR_ROOT_REVIEW -> REFRESH_REQUIRED -> INTEGRATING -> DEPLOYING -> VERIFYING -> DONE`；暂停或无法继续时使用 `FROZEN` / `BLOCKED`。
- 候选落后最新 `main` 时进入 `REFRESH_REQUIRED`，必须在候选 worktree 整合最新 `main`、仅解决本任务范围冲突，并重新完成专项验证和最终独立复审；旧 SHA 不得直接进入合并车道。
- 同时只能有一个任务处于 `INTEGRATING`、`DEPLOYING` 或 `VERIFYING`。存在另一个发布、合并或线上验收时，其他候选即使 READY 也必须排队。
- `FROZEN` 窗口、分支和 worktree 只作证据；未经发布总控明确解冻，不得恢复代理、继续写入、合并、推送、部署或清理。

### 2.2 Brainstorming 与规格书批准门禁

- 每个新顶层任务必须完整执行 Superpowers brainstorming，不能用创建 `docs/superpowers` 路径、简短技术摘要或内部代理讨论代替。
- 固定顺序为：探索现状和证据；一次只问一个澄清问题；提出 2–3 个可选方案及取舍和推荐；分段展示设计并逐段取得用户批准；写正式规格书；完成规格书自审；请用户明确审阅并批准书面规格书；之后才能调用 writing-plans。
- 正式规格书至少覆盖：问题证据与当前行为、目标与非目标、影响用户和边界条件、2–3 个方案比较与选择理由、端到端数据/控制流、接口与字段契约、失败与安全语义、兼容性与迁移、场景化验收矩阵、测试策略、发布/线上验证/回滚条件、仍待决事项和用户批准记录。
- 未取得用户对书面规格书的明确批准前，禁止调用 writing-plans、编写实现代码、派生实现代理或进行其他实施动作。
- 计划获批后，独立顶层任务内部可按 `AGENTS.md` 使用 fresh implementer subagent；功能实现和直接相关功能测试通过即可进入任务收口。只有真实失败、范围冲突或高风险问题需要时才增加针对性 reviewer；内部 subagent 是实施工具，不是顶层任务的替代。

### 2.3 用户离席期间的代审授权

- 2026-08-15 起，用户明确授权唯一发布总控代为审查并批准本轮既定队列中各任务包的正式规格书与实施计划；由发布总控形成的书面审查结论和批准记录可满足本文件的规格/计划批准门禁，不再要求用户逐份在线回复。
- 代审不得削弱完整 brainstorming、正式规格、自审、writing-plans、独立任务复审、最终全分支终审和根授权合并等其他门禁，也不得扩大任务队列已批准范围。
- 发现产品范围变化、不可逆数据操作、数据删除或历史回填、凭据/安全风险、外部付费、无法按既定方案解决的冲突，或发布预检输出 `downtime_required=true` 时，发布总控必须停止在对应动作前等待用户明确确认；用户口头所称“无限授权”不用于绕过这些安全边界。
- 规格或计划仅在证据、目标/非目标、接口与数据契约、失败语义、验收、测试、发布和回滚条件闭环且没有未决产品问题时才可批准；审查发现问题时应退回原用户可见顶层任务修订并复审。

## 3. 任务包完成与汇报协议

- 顶层任务完成功能实现、直接相关功能测试、必要类型检查或构建和 diff 自查后，状态只能是 `READY_FOR_ROOT_REVIEW`，不能声明已完成或已部署。
- 汇报必须包含：任务包编号、基线 `main` SHA、提交 SHA、变更文件、测试结果、未验证项、迁移变化、配置变化、`downtime_required`、回滚方式和剩余风险。
- 根线程确认该任务包是当前队列唯一可部署候选后，发送带目标 `main` SHA 的 `AUTHORIZE_MERGE_TO_MAIN` 指令。
- 顶层任务收到明确指令后才能把自己的已审查分支合入根目录 `main`；合并前必须确认根目录干净、目标 SHA 未漂移、没有其他合并或部署在进行。
- 合并完成后顶层任务只汇报合并 SHA 和冲突/验证结果，继续等待；不得推送或部署。

### 3.1 既有任务流程偏差记录

- T01、T02 的独立 worktree、规格书、计划、复审、部署和线上验证证据继续有效，技术成果不回滚、不重做；但它们没有按用户原始要求创建“每个任务包一个用户可见的独立顶层 Codex 任务”，原会话使用的内部 `spawn_agent` 不能替代顶层任务隔离，因此不得宣称 T01/T02 顶层任务流程合规。
- T03 是流程纠偏指令到达前已在途、由根任务内部代理实施并完成合并发布的任务包，同样不得倒称满足本文件新增的顶层任务与完整 brainstorming 门禁；保留其实现、审查、合并、发布和运行健康证据，按线上专项验收是否闭环决定完成状态。
- 上述偏差是流程合规记录，不推翻已验证技术成果；新门禁从后续任何任务启动或继续实施时强制执行。

## 4. 根线程快速发布协议

- 根线程在合并后的 `main` 只运行与当前任务包直接相关的回归、必要构建/类型检查、迁移检查和发布预检，不重复扩大到无关功能。
- 生产推送和部署只能来自已经验证的 `main`；禁止从派生 worktree、临时目录或候选分支直接发布。
- 发布准备不得使用 GitHub Actions，继续使用已审查的本地/宿主脚本和蓝绿链。
- 发布预检必须明确输出 `downtime_required=true|false`。为 `false` 时根线程可按已确认队列执行快速部署；为 `true` 时必须在任何停服、迁移、重启或切换动作之前停止。
- 只有已经满足验收站全局约束定义的两种主站明确授权之一后，`downtime_required=false` 才构成同一次发布继续执行、无需重复询问的条件；它本身绝不构成主站发布授权。授权成立且预检为 false 时，应直接完成推送、发布、健康检查和该任务线上专项验证；`downtime_required=true` 仍触发额外人工停机授权门禁。
- 一旦某次候选需要停机，本次及其后所有部署都暂停，等待用户人工确认；不得绕过、拆分或把停机包装成普通蓝绿更新。
- 部署成功后必须完成该任务包的线上专项验证和健康检查，再更新总账、授权清理对应 worktree/分支并派生下一任务。
- 部署或验证失败时保留工作区、分支、失败证据和回滚依据，在原任务包继续修复，不启动下一任务包。
- 一个任务包只对应一次独立发布和线上验收；多个 READY 候选不得合并成一次大发布。

### 4.1 官方更新快速生效例外

- 官方 Sub2API 最新稳定版更新始终作为最高优先级插队任务，暂停其他功能任务的合并、部署和验收车道。
- 官方更新的完成路径固定为：发现最新稳定版 -> 合入当前定制树 -> 人工解决全部冲突 -> 满足验收站全局约束中的常规或紧急主站明确授权 -> 合并根 `main` -> 推送 -> 使用既有本地/宿主发布链生效。
- 冲突必须解决并保留当前定制功能与官方新行为；不得因冲突停止、要求额外人工验收、关闭定制模块、改用 GitHub Actions或建立平行发布链。
- 官方更新不运行功能测试、回归测试、类型检查、独立构建验证或上线专项验收。既有发布链为生成候选制品、判断迁移/停机、原子切换和失败回滚而强制执行的内部步骤继续保留，但不扩展为额外测试或验收。
- 发布链成功切换即视为官方更新已生效并可收口；若发布链因停机门禁、迁移保护或运行就绪失败而拒绝切换，必须保留候选和证据，不得绕过保护。

### 4.2 小步快跑最小验证政策

- 默认只保留当前任务直接功能路径、最小相关回归、必要的类型检查/构建、范围与发布预检，以及上线后的即时专项验收。
- 默认不重复全仓测试、压力/重复浏览器、mutation、长时间 soak、无关模块回归或跨平台穷举；已有可靠证据可引用，不为形式重复执行。
- 涉及迁移、鉴权、安全、计费写入、不可逆数据或 `downtime_required=true` 时，仍必须保留对应定向安全门禁并在动作前取得人工确认。
- 后续每个任务包均按同一精简验证政策执行；任务规格、计划、handoff 和根发布证据必须明确列出保留的最小门禁与未验证项。
- 自 2026-08-16 用户最新指令起，功能任务默认不再执行额外独立审查、重复回归或全分支终审；“功能本身通过直接相关测试”即满足候选完成条件。发布链内置的迁移/停机保护、候选制品生成、原子切换、运行就绪与失败回滚仍不得绕过。

## 5. 产品与数据边界

- 错误转译不新增平行页面。管理员在“管理后台 -> 用量明细 -> 错误请求 -> 错误详情”查看“管理员诊断”；运维总览的请求错误/上游错误详情复用同一诊断结构。
- 用户只看到脱敏中文含义和可执行建议；管理员可看到错误阶段、归属、是否已选账号、账号/分组、原始上游状态与原始错误，但不得把凭据、完整 API Key 或敏感请求体返回用户。
- 上游错误优先复用 Sub 原生错误透传规则；本站限流、鉴权、路由和请求体读取失败使用同一解释字典的本地分支，不伪装成上游错误。
- 大上下文上传问题按入站链路处理：保留请求体大小和安全边界，修复固定 300 秒代理窗口对慢速上传的误伤；不得仅把 502 改文案而不处理根因。
- 经营/盈利页面的唯一计费事实源是 Sub 原生 `usage_logs` 统计口径：请求数 `requests`、Token 数 `tokens`、账号计费 `cost`、用户扣费 `user_cost`。`cost` 按原生有效账号成本表达式 `COALESCE(account_cost, COALESCE(account_stats_cost, total_cost) * COALESCE(account_rate_multiplier, 1))` 聚合，`user_cost` 按 `actual_cost` 聚合；利润仅可作为 `user_cost - cost` 的展示派生值，利润率仅可由该利润除以 `user_cost` 派生。
- 经营页保持 Sub 原生美元单位，不新增汇率换算、采购成本分摊、人工覆盖、估算、补查、重试、回填或第二套计费模型；全站、分组、账号与时间范围聚合必须来自同一官方流水，其中分组归属使用不可变的 `usage_logs.group_id`。
- T03/T03-R1 的独立 `usage_upstream_cost_evidence`、复核、OAuth 日成本和人工覆盖属于历史已部署能力与历史证据，短期纠偏不得破坏性删除；但自 T11-R1 起，它们不再作为经营/盈利页面的数据源、异常来源或人工输入依据。任何后续清理必须另立任务、评估兼容与数据恢复风险。
- “控制面暂时不可用 / 完整性 unknown”从原生账号监控、用量和利润页面移除，不以其他外部控制面提示替代。
- “暂不建议入组”保持轻提示：桌面悬浮或点击、移动端点击，仅显示一到两行原因，不新增常驻说明区。
- 全局评分权重与分组评分权重独立持久化，复用现有分组评分设置交互，不改变既有排序之外的调度行为。
- 官方更新按 4.1 的快速生效例外执行：出现冲突时由发布总控人工解决并继续发布，不以冲突为终止状态。

## 6. 禁止事项

- 禁止把多个任务包合成一次大发布。
- T11-R1 未完成推送、部署和即时功能验收前，禁止启动 T09、S1-R2、OAuth 图片编辑上传 MIME 兼容热修或其他后续任务包。
- 禁止同时让多个派生线程操作根目录 `main`。
- 禁止在任务包中引入 `external-primary`、relay-ops 主路径依赖或新的平行控制面。
- 禁止为了清理工作区而丢弃未合并提交、未提交内容或失败证据。
- 禁止在没有线上验证时把任务标记为“已完成”。
- 禁止在停机需求、目标 `main` 漂移或发布链运行就绪失败后绕过保护继续推进；官方更新冲突按 4.1 人工解决后继续。
