# 飞书通知现役配置收敛与人话卡片设计

## 设计状态

- 日期：2026-07-29
- 状态：用户已批准
- 范围：`relay-ops-service` 当前生产服务端配置能够触发的飞书主动通知
- 不包含：实现计划、生产部署、生产数据修改、飞书命令、GitHub Actions 发版 Webhook

本文取代既有设计中与当前生产事实冲突的飞书通知范围、事故分级和卡片文案。历史设计仍保留为审计材料，但不能仅因仓库存在旧代码就恢复候选上游、Usage Session、合成验收或其他已经退出当前产品面的通知。

## Loop Brief

### Goal

把当前混乱、重复、偏技术化的飞书推送收敛成一套由服务端显式配置驱动、按公开分组表达用户影响、运营者可以在手机首屏直接看懂并采取行动的通知体系。

### Context

生产当前使用飞书 App 向一个指定群发送主动通知，配置一名负责接收人；Webhook 未配置，飞书命令模式关闭，事故确认链接和 P0 加急链路可用。

本次审计同时发现：

- 相同分组的错误率、原生 Monitor、账号状态和容量信号可以分别创建事故，容易重复描述同一件事。
- `new_evidence` 会因数值变化生成新卡片，运营者看到的是技术状态变化，而不是用户影响是否发生实质变化。
- 价格变化被建模为 P1 事故，可能进入升级链路且没有自然恢复条件。
- 日报被建模为持续失败的 P2 事故，语义错误。
- 卡片标题可能显示 `group #16`、原始 metric 或内部 transition，无法直接看出哪个业务分组发生了什么。
- 仓库保留候选上游等历史兼容代码，但生产已无对应数据、作业和产品入口。

### Constraints

- 每一类飞书主动推送必须同时满足：通知策略启用、来源配置存在、来源数据可用、对象在允许范围内。
- 未显式配置的通知 family 必须 fail closed，不得因代码存在而自动启用。
- Sub2API 官方镜像不可修改；所需行为只能在 relay-ops、配置和独立数据库迁移中完成。
- 不修改生产路由、账号、倍率、价格、余额、Key 或飞书命令模式。
- P0/P1 的严重度和用户影响由确定性规则计算；Agent 不得决定严重度、根因或执行动作。
- 卡片不包含凭据、Base URL、完整原始错误、私有分组名或不必要的数据库 ID。
- 保留现有投递去重、有限重试、30 KB 卡片上限和审计记录。

### Plan

1. 统一当前主线、已部署告警分支和生产镜像对应的实现基线。
2. 引入服务端通知策略白名单及启动校验。
3. 将容量、真实流量、账号状态和已绑定原生 Monitor 汇入公开分组事故聚合器。
4. 将 P0/P1 事故、P2 信息事件和日报摘要拆成不同生命周期。
5. 按本设计替换首次告警、事故进展、提醒、恢复、价格事件和日报文案。
6. 迁移旧事故状态，影子运行后切换生产推送。

### Done When

- 生产上每一条主动推送都能追溯到启用的服务端通知 family 和有效来源配置。
- 候选、Usage Session、合成验收、飞书命令和发版 Webhook不会进入本通知体系。
- 同一公开分组同一时段最多存在一个用户影响事故。
- 标题直接回答“哪个分组发生了什么”，不再出现 `group #16`、`new_evidence` 或裸 metric。
- 普通数值变化不重复发卡；价格和日报不进入事故升级/恢复链路。
- 影子运行、自动化测试、真实群安全验收和 72 小时观察全部通过。

## 生产事实与设计基线

### 代码和部署来源

审计时存在三个不同基线：

| 来源 | 审计时版本 |
|---|---|
| 远端主线 | `origin/main`：`ff03844d3` |
| 已部署告警分支 | `codex/feishu-user-impact-alerting`：`56a10b18f` |
| 生产镜像 | `sub2api-relay-ops:user-impact-alerting-20260728-v1` |

本设计文档从审计时的 `origin/main` 创建，但实现不得直接基于过期本地主线。实施的第一个门禁是把生产实际部署差异纳入一个当前、可构建、可测试的主线基线，并记录源码提交与镜像的对应关系。

### 当前生产作业

生产 `relay_ops` 调度记录中实际存在且最近成功的作业只有：

1. `daily-report`
2. `group-availability`
3. `incident-escalation`
4. `production-collection`
5. `site-monitor`

不存在候选周期、candidate fast/probe 或 Usage Session 作业。

### 当前生产来源

- relay-ops 生产上游只有 `Neko`、`Wawazz` 两条 `role=production && enabled=true` 配置。
- 两条生产上游均配置公开定价、用量和性能来源。
- `probe_runs`、`quality_reports`、`candidate_comparisons` 均为空。
- Sub2API 有 6 个启用的原生 Channel Monitor；其中只有 `GPT Plus 内测` 配置了公开分组 `GPT PLUS 内测分组`。
- 未配置 `group_name` 的原生 Monitor 不进入 relay-ops 公开分组事故。
- 账号质量结果文件和上游映射文件均已配置且文件存在。

因此，候选上游属于已退出当前产品面的历史能力；原生 Channel Monitor 则是仍在运行的服务端证据源，但只有明确绑定公开分组的 Monitor 才能参与本设计。

## 方案选择

### 方案 A：只改文案

保留现有事故键、触发器和升级逻辑，仅替换卡片文字。上线快，但不能解决重复事故、日报常驻 confirmed、价格变化持续升级和 `new_evidence` 刷屏。

### 方案 B：现役配置白名单与公开分组事故收敛

只允许当前服务端配置支持的通知 family；将多个底层信号按公开分组合并；拆分事故、事件和摘要生命周期；同步重写卡片文案。

这是本设计采用的方案。它是解决当前语义和噪音问题的最小完整改造。

### 方案 C：通用通知平台

建立订阅、路由、模板、策略和多通道通知平台。长期扩展性最好，但显著超过当前问题范围，不在本次实施。

## 通知领域模型

### Incident：需要接手的用户影响事故

仅包含 P0/P1，具有：

- 确认窗口
- occurrence
- 确认接手
- 升级提醒
- 恢复
- 最新证据
- 投递审计

事故身份按公开分组收敛：

```text
group:<public-group-id>:user-impact
```

数据库 ID 只用于稳定身份和审计，绝不作为卡片显示名。

### Event：一次性运营事实

当前只包含生产上游可靠的价格/倍率语义变化。Event：

- 有稳定去重键和投递审计
- 不需要确认
- 不升级
- 不恢复
- 不保持 confirmed 状态

建议身份：

```text
pricing:<production-upstream-id>:<semantic-evidence-hash>
```

### Digest：定时摘要

当前只包含日报。Digest：

- 以业务日期幂等
- 不需要确认
- 不升级
- 不恢复
- 不进入 incidents 状态机

建议身份：

```text
daily-digest:<Asia/Shanghai YYYY-MM-DD>
```

### Delivery：传输基础设施

投递去重、失败重试、消息 ID、HTTP 结果和脱敏 payload 继续由统一 Delivery 层管理。Delivery Retry 是基础设施，不是用户可见通知 family。

## 服务端通知策略

新增单一只读策略文件，例如由 `RELAY_OPS_NOTIFICATION_POLICY_FILE` 指向。生产已配置飞书传输时，该文件必须存在、权限合规、schema 合法；否则服务启动失败，避免“看似有飞书、实际策略未知”。

建议 schema：

```yaml
version: 1
feishu_notifications:
  group_runtime_enabled: true
  group_capacity_enabled: true
  account_impact_enabled: true
  native_monitor_evidence_enabled: true
  pricing_notice_enabled: true
  daily_digest_enabled: true
  incident_escalation_enabled: true
```

### 总体门禁

一条主动推送必须满足：

```text
transport configured
AND family enabled
AND source configured
AND source fresh and valid
AND object allowed
AND lifecycle says notify
```

任一条件不满足时记录稳定的 suppressed reason，不生成飞书卡片。

### Family 与来源

| Family | 服务端作业 | 必要来源 | 可生成的内容 |
|---|---|---|---|
| `group_runtime` | `site-monitor` | 当前公开分组、15 分钟真实流量、24 小时基线 | 全部请求失败、持续错误率、持续 TTFT |
| `group_capacity` | `group-availability` | 当前公开分组、账号监控快照和历史 | 无可用账号、失去冗余 |
| `account_impact` | `site-monitor` / `group-availability` | 账号 active/schedulable、账号质量结果、公开分组成员关系 | 只作为分组事故原因或日报行动项 |
| `native_monitor_evidence` | `production-collection` | Monitor enabled、`group_name` 匹配当前公开分组、最新历史有效 | 只作为分组事故证据或日报观察项 |
| `pricing_notice` | `production-collection` | 生产上游 enabled、`pricing_url`、可靠语义 diff | 一次性 P2 价格事件 |
| `daily_digest` | `daily-report` | 日报作业启用、至少能给出数据完整性状态 | 每日摘要 |
| `incident_escalation` | `incident-escalation` | 未恢复、未确认的 P0/P1 occurrence | 有限提醒 |

### 原生 Monitor 的默认行为

`native_monitor_evidence_enabled=true` 不代表原生 Monitor 可以独立开事故。

默认规则：

- 已绑定 Monitor 异常时更新对应公开分组的证据集。
- 同时存在真实流量或容量事故时，Monitor 作为“已知线索”进入同一事故。
- 没有足够真实流量、容量仍健康时，Monitor 异常仅进入日报观察项。
- 未绑定公开分组的 Monitor 完全不进入本通知体系。

如果未来确需让 Monitor 在无流量时独立开事故，必须增加新的显式策略字段、单独设计确认窗口并再次批准，不能复用当前布尔值隐式开启。

## 公开分组事故聚合

### 输入快照

聚合器为每个当前公开分组构建一个 `GroupImpactSnapshot`，至少包含：

- 公开分组稳定 ID 和显示名
- 15 分钟请求数、成功数、错误率、TTFT P95
- 24 小时 TTFT P95 基线
- 账号总数、可用数、失效账号的脱敏名称和确定性原因类别
- 已绑定原生 Monitor 的最新状态与证据时间
- 各来源的新鲜度和不可用原因

来源读取失败采用 fail-safe：数据不可用不能伪装成业务故障。

### 主信号优先级

同一分组同时存在多个异常时，卡片标题只显示最高用户影响：

1. `no_available_accounts`
2. `all_requests_failed`
3. `partial_request_failures`
4. `lost_redundancy`
5. `ttft_degraded`

其他异常进入“已知线索”或“当前容量”，不再创建并行事故。

### 严重度

#### P0

满足任一条件：

- 公开分组可用账号为 0。
- 当前窗口有真实请求但成功数为 0。

P0 一次确认后立即发送。

#### P1

满足任一条件：

- 总账号数至少 3，当前可用账号不超过 1。
- 当前窗口至少 20 个请求，错误率连续两个观测达到或超过 5%。
- 当前窗口至少 20 个请求，TTFT P95 超过 3000ms，且相对 24 小时基线恶化至少 30%，连续两个观测成立。

两账号分组和单账号分组只有降到 0 才开容量事故；它们本来就没有可告警的额外冗余。

### 恢复

P0/P1 均需要连续两个健康观测后恢复，避免单次抖动造成“告警—恢复—再告警”。

健康要求是所有当前已确认的用户影响条件均解除。某个证据源暂时不可用时不能据此宣告恢复；聚合器保留事故并等待可验证的健康证据，但也不因来源故障升级用户影响。

### new evidence

`new_evidence` 保留为内部状态更新，不是用户消息类型。

以下变化只更新事故的最新证据，不发送新卡片：

- 错误率从一个异常值变成另一个异常值。
- TTFT 在异常区间内变化。
- 同一批失效账号的错误码或最新时间变化。
- 原生 Monitor 重复相同异常。

只有以下 material change 可以通知：

- P1 升级为 P0。
- 用户影响从部分失败变成全部失败。
- 影响范围扩大。
- 确认了新的原因，且建议处理动作发生实质变化。

material change 的用户文案统一为“事故进展”，不得显示内部 transition 名称。升级提醒必须基于事故的最新快照重新渲染，不能复制首次投递时的旧 payload。

## 生命周期与提醒策略

| 类型 | 首次通知 | @负责人 | 飞书加急 | 未确认提醒 | 恢复 |
|---|---:|---:|---:|---:|---:|
| P0 Incident | 是 | 是 | 是 | 5 分钟、15 分钟 | 是 |
| P1 Incident | 是 | 是 | 否 | 15 分钟一次 | 是 |
| P2 Event | 是 | 否 | 否 | 否 | 否 |
| Digest | 是 | 否 | 否 | 否 | 否 |

“确认并接手”只出现在 P0/P1。确认后停止后续提醒，但不停止状态观测和恢复通知。

## 卡片信息架构

P0/P1 固定采用以下顺序：

1. 发生了什么
2. 用户影响
3. 当前证据或当前容量
4. 已知线索
5. 建议处理
6. 首次发现/最新证据时间
7. “确认并接手”“查看运维后台”

文案约束：

- 标题必须包含公开分组显示名和人话问题。
- 下列示例中的分组名和数值只用于说明版式；实际渲染必须读取服务器当前 `Group.Name` 和对应观测值，不得硬编码名称。
- 使用“部分请求持续失败”，不用 `error_rate`。
- 使用“首字响应明显变慢”，不用 `ttft_p95`。
- 使用“当前已不可用”，不用 `availability=failed`。
- 没有可靠原因时明确写“尚未确认原因”，不能让 Agent 猜测。
- 卡片中不展示 incident key、evidence hash、数据库 ID 或完整内部错误。
- 时间按 `Asia/Shanghai` 展示；证据引用仍在数据库中保留 UTC。

## 确定性文案

### P0：全部请求失败

```text
P0｜GPT PLUS 内测分组当前已不可用

发生了什么
过去 15 分钟共 31 次请求，全部失败。

用户影响
该分组用户当前无法正常完成请求。

当前容量
可用账号 1 / 2；仍有账号可调度，但真实请求没有成功。

已知线索
原生 Monitor 当前异常。
尚未确认是否由单一账号或上游链路导致。

建议处理
检查该分组最近错误码和账号状态，优先确认失败是否集中在单个账号。

首次发现：21:03
[确认并接手] [查看运维后台]
```

若可用账号同时为 0，主标题改为：

```text
P0｜GPT PLUS 内测分组已无可用账号
```

```text
P1｜GPT PLUS 内测分组部分请求持续失败

该指标已连续 2 个观测超过 5% 告警线。

用户影响
部分用户可能遇到请求失败或需要重试；当前不是完全不可用。

当前容量

已知线索

建议处理
检查该分组最近错误码和账号状态，优先确认失败是否集中在单个账号。

首次发现：21:03
[确认并接手] [查看运维后台]
```

### P1：TTFT

```text
P1｜GPT PLUS 内测分组首字响应明显变慢

发生了什么
过去 15 分钟首字响应 P95 为 4.8 秒，24 小时基线为 2.9 秒，慢约 66%。
该指标已连续 2 个观测超过告警线。

用户影响
请求仍可完成，但用户开始等待首个响应的时间明显变长。

当前容量
可用账号 3 / 3，未发现容量不足。

已知线索
尚未确认慢请求是否集中在单个账号。

建议处理
查看分账号首字延迟，确认是否需要暂停明显偏慢的账号。

首次发现：21:03
[确认并接手] [查看运维后台]
```

### P1：容量

```text
P1｜GPT PLUS 内测分组只剩 1 个可用账号

发生了什么
该分组可用账号已从 3 个降至 1 个，当前没有冗余。

用户影响
请求目前仍可完成，但剩余账号一旦异常，整个分组将不可用。

已知原因
Wawazz 余额已耗尽；Neko 已暂停调度。

建议处理
确认余额和调度状态，恢复至少一个备用账号。

首次发现：21:03
[确认并接手] [查看运维后台]
```

只有服务端证据明确时才使用“已知原因”；否则使用“已知线索”并写“尚未确认”。

```text
无需立即操作，继续观察下一小时运行情况。

[查看运维后台]
```

恢复卡不含确认按钮、不 @人、不加急。

### 账号状态

账号暂停或余额耗尽不再独立发送类似“上游账号质量告警”的卡片。

若它导致公开分组达到事故阈值，作为事故证据：

```text
已知原因
Wawazz 余额已耗尽，导致 GPT PLUS 内测分组可用账号从 2 个降至 1 个。
```

若没有让公开分组达到事故阈值，只进入日报“需要处理”。

### 价格事件

```text
价格变更｜Neko 公开定价发生变化

具体变化
公开倍率由 0.07x 调整为 0.10x。
另有 3 个模型价格发生变化。

系统做了什么
已记录本次公开定价快照。
没有自动修改用户价格、账号配置或路由。

需要处理
评估当前售价和毛利是否仍符合预期。

证据时间：10:05
[查看运维后台]
```

页面内容变化但未产生可靠语义 diff 时不发送价格事件。连续采集失败如需提示，只能作为日报的“监控完整性”问题，不能写成“价格发生变化”。

同一显式映射的生产上游在相近时间同时出现公开定价变化和账号倍率投影变化时，合并为一条价格事件。没有显式映射时不得按名称猜测关联。

### 日报

```text
中转站晨报｜7月29日

一句话结论
6 个公开分组运行正常，0 个进行中用户事故，2 项需要处理。

用户侧运行
稳定 6｜降级 0｜不可用 0
昨日共恢复 1 起事故，无未恢复事故。

需要处理
1. Wawazz：余额不足，但当前未影响公开分组容量
2. Neko：公开倍率发生变化，等待确认毛利

经营情况
请求 12,480｜收入 $xx.xx｜成本 $xx.xx｜毛利率 xx.x%

监控完整性
真实流量、账号质量、生产定价数据均已更新。

[查看运维后台]
```

日报颜色由用户影响和数据完整性决定：

- 红色：存在 P0。
- 橙色：存在 P1、需要处理项或关键数据不可用。
- 绿色：无进行中事故、无需要处理项、关键数据完整。

日报移除：

- 候选站数量。
- 候选质量、候选探测和候选切换建议。
- “当前账号 → 候选账号”式建议。
- 只读 Agent 的泛化结语。
- 把日报自身写入 P2 confirmed 事故的逻辑。

## Agent 边界

飞书卡片的严重度、用户影响、数值、原因类别和建议动作由确定性规则生成。

Agent 可以在 `/ops` 中提供只读辅助分析，但：

- 不得改变 P0/P1/P2。
- 不得把推测写成“已知原因”。
- 不得新增通知。
- 不得决定提醒、恢复、路由或账号写操作。
- Agent 失败不能阻塞事故落库或确定性卡片投递。

## 错误处理

| 场景 | 行为 |
|---|---|
| Sub2API 真实流量读取失败 | 不创建流量事故；日报标记流量数据不可用 |
| 账号质量文件缺失或过期 | 不把账号判为不可用；日报标记账号质量数据不可用 |
| 原生 Monitor 历史缺失 | 不创建 Monitor 异常；保留其他分组证据 |
| 定价页抓取或解析失败 | 不创建价格变化；日报标记生产定价采集问题 |
| 单个来源失败但已有事故 | 不据此升级或恢复；保留事故等待可靠证据 |
| Feishu 投递失败 | 保留相同业务身份有限重试，不重新执行观测 |
| 卡片超过 30 KB | 保留结论、用户影响和建议处理，截断低优先级证据并注明 |

监控自身故障不得伪装成用户事故。

## 状态和数据迁移

### 需要停止的旧通知入口

实现切换时必须确认以下入口不能再注册主动通知：

- candidate cycle / fast / probe
- candidate quality report
- model publication
- usage-session
- synthetic acceptance
- Feishu command result
- GitHub Actions release preparation

代码如因历史兼容暂时保留，也必须位于未注册、无生产配置、测试明确禁止推送的路径。

### 旧事故归档

迁移脚本按 key 和业务类型识别旧状态：

- `daily-report:*`
- `native-monitor:*`
- `site:account:*:paused`
- `site:account:*:balance_exhausted`
- `site:group:*:availability`
- `site:group:*:error_rate`
- `site:group:*:ttft_p95`
- `upstream:*:pricing`
- candidate、quality report、synthetic 和 usage-session 前缀

处理原则：

- 保留历史 incident、notification delivery 和 Feishu message ID。
- 活动旧事故标记为 `superseded` 并记录迁移原因和时间。
- `superseded` 不允许再被 escalation worker claim。
- 不为迁移本身发送恢复或关闭卡片。
- 不能把旧 metric incident 的 occurrence 编号直接复用给新分组聚合事故。
- 价格旧 P1 事故归档为历史事实；不发送恢复。

### 新状态启动

切换时按当前生产快照初始化：

- 当前健康分组不创建 incident。
- 当前异常分组从 `observed` 开始走新确认窗口。
- 不从旧事故自动推送首次卡片，除非新规则在切换后完成确认。
- 日报从下一正常业务日期开始使用 Digest 身份。

## 上线策略

### Phase 0：统一源码基线

- 选择包含生产实际告警能力的当前主线提交。
- 构建镜像必须记录源码 SHA 和不可变镜像标识。
- 不从审计时已分叉的本地 `main` 直接部署。

### Phase 1：策略门禁

- 加入策略 schema、配置装载、启动验证和 suppressed reason 审计。
- 生产策略显式只开启本设计列出的 family。
- 候选等历史 family 不进入 schema。

### Phase 2：影子运行

新聚合器至少影子运行 48 小时：

- 读取真实生产快照。
- 计算“本应发送”的事故、事件和摘要。
- 不向飞书投递。
- 与当前系统逐事件比较重复数、严重度和恢复时间。

### Phase 3：迁移与切换

- 备份 relay_ops 数据库。
- 归档旧活动事故并停止旧升级 claim。
- 启用新聚合器和新模板。
- 保持 Feishu App、群 ID、接收人和确认链接路径不变。

### Phase 4：生产观察

- 不制造真实用户故障。
- 使用本地渲染 fixture 和受控非生产群确认卡片视觉。
- 生产真实群只等待自然事件、自然恢复和下一次日报。
- 连续观察至少 72 小时。

## 测试策略

### 配置契约

- 飞书传输已配置但通知策略缺失、权限错误或 schema 非法时启动失败。
- 每个 family `false` 时对应来源不能投递。
- family `true` 但必要来源缺失时产生稳定 suppressed reason，不产生卡片。
- 未知 family 和未知字段拒绝加载，防止拼写错误静默生效。

### 事故聚合

- 同一分组的错误率、TTFT、容量、账号状态和 Monitor 异常只产生一个事故。
- P1 错误率需要最少样本和两个确认观测。
- P0 全失败或无账号一次确认。
- 同一异常区间内数值变化只更新证据。
- P1 到 P0 产生一条“事故进展”。
- 两个连续健康观测只产生一次恢复。
- 来源读取失败不创建、升级或错误恢复事故。

### 生命周期

- P0 仅在未确认时于 5、15 分钟提醒。
- P1 仅在未确认时于 15 分钟提醒一次。
- 确认接手停止提醒但保留恢复。
- P2 Event 和 Digest 不进入 escalation claim。
- 升级提醒读取最新事故快照，而非首次卡片 payload。

### 渲染

- 标题包含公开分组显示名和人话问题。
- 不包含 `group #`、`new_evidence`、`error_rate`、`ttft_p95` 或裸英文状态。
- 没有可靠原因时显示“尚未确认”，不显示 Agent 推测。
- 账号使用脱敏显示名，不显示数据库 ID。
- 私有分组、Key、Base URL、完整错误正文不进入 payload。
- App Bot 卡片小于 30 KB，纯文本投影仍可读。

### Event 和 Digest

- 相同价格语义 hash 只投递一次。
- HTML 内容变化但无可靠语义 diff 时不投递。
- 价格事件没有确认按钮、升级和恢复。
- 同一天日报幂等投递且不创建 incident。
- 日报不含候选数量、候选建议或泛化 Agent 结语。

### 迁移

- 旧活动事故全部停止升级。
- 历史投递记录不丢失。
- 迁移不向飞书发送恢复或关闭消息。
- 新事故 occurrence 与旧 metric incident 不串联。

## 生产验收标准

1. 候选、发版、Usage Session、合成验收和飞书命令类主动推送为 0。
2. 任意事故标题可以直接回答“哪个公开分组发生了什么”。
3. 同一分组同一时段只有一个进行中的用户影响事故。
4. 审计样例中的错误率 `9.65% -> 14.19%` 不产生第二张数值变化卡。
5. 未确认样例最多为“首次告警、一次提醒、恢复”；确认后最多为“首次告警、恢复”。
6. 账号异常仅在影响公开分组时即时出现，否则只进日报。
7. 已绑定的原生 Monitor 只作为分组证据；未绑定 Monitor 不进入本体系。
8. 价格变化只发送一条 P2 信息卡，不升级、不恢复、不要求确认。
9. 日报不会留下活动 incident。
10. 每次投递审计可看到 family、策略版本、来源类型、业务身份、suppressed/delivered 原因和消息 ID，但不含秘密。
11. relay-ops 保持 `read_only`，飞书命令保持关闭，不发生路由、账号、倍率、价格、余额或 Key 写入。
12. 72 小时观察期内没有无法解释来源的主动通知。

## 不在本设计范围内

- 恢复候选上游、质量报告、付费 probe 或模型发布能力。
- GitHub Actions 发版准备消息的模板或传输治理。
- 开启飞书命令、群内路由切换或其他写操作。
- 修改 Sub2API 官方镜像或原生 Monitor 实现。
- 自动充值、自动启停账号、自动切换路由或自动改价。
- 通用多群订阅、多租户通知路由或独立通知平台。
- 为制造视觉证据而在生产生成合成事故。
