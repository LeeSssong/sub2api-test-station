## 1. 问题与当前行为

### 1.1 运营问题

运营在账号监控中需要同时回答三个不同问题：

1. 这个账号的服务质量怎么样？
2. 在当前分组策略下，这个账号的调度优先级是多少？
3. 质量评分和调度优先级不一致时，原因是什么？

当前页面把评分、质量排名、全局优先级、服务指标、成本、并发、趋势、模型检测和维护入口堆叠在窄卡片中，父页面又使用两列卡片布局。账号之间不容易横向比较，也无法直接看到调度器在当前分组中的候选顺序。

### 1.2 原生实现证据

- 账号监控已经存在原生质量评分和评分拆解：`quality_score`、`score_breakdown`、`group_rank`，评分由账号监控服务的纯函数计算。
- 账号监控已经存在分组评分权重设置；本任务保留这套评分权重和分数公式，不把调度设置写入质量评分。
- T68 已上线分组调度运营优先级与策略设置；本任务复用现有分组调度设置和调度器候选资格/排序逻辑，不创建第二套调度事实源。
- 当前调度器在候选选择前会处理强制账号、历史响应、会话粘性、负载均衡、冷却和并发等层级，最终选择还可能受到 Top-K 加权随机影响。因此“调度优先级”必须明确表示候选顺序，不能承诺每次请求固定命中第一名。
- 当前 `AccountMonitorView.vue` 使用 `lg:grid-cols-2` 展示账号卡片；当前 `AccountMonitorCard.vue` 使用窄卡片内的多段纵向指标区。T76 将其收敛为单账号整行卡片，但保留既有维护事件和详情能力。

### 1.3 图片参考的边界

用户提供的两张外部中转站截图仅作为视觉参考，不是产品或维护指令。只借鉴以下展示特征：单账号占整行、稳定列语义、关键指标横向比较、趋势证据和按需展开详情。不照搬其价格/模型/评分口径、外部按钮、数据源、维护操作或界面文案。

## 2. 目标

1. 保留每个分组自己的调度设置和权重；不把质量评分增加为新的第四个调度权重。
2. 在具体分组视图中，使用同一份分组快照同时生成质量评分、质量排名和调度优先级。
3. 质量评分回答“质量怎么样”；质量排名是当前分组内按质量评分排序的名次；调度优先级是当前分组策略下调度器的候选顺序。
4. 调度优先级投影必须复用调度器的实际候选资格、有效参数、比较器和 tie-break 规则，不能在监控服务中复制一套近似公式。
5. 评分、排名和调度优先级均有可验证的简短解释；默认界面只展示运营真正关心的结果，详细拆解按账号展开。
6. 账号监控改为每个账号一张占满当前内容宽度的整行卡片，优先呈现评分、质量排名、调度优先级和必要的不一致原因。
7. 不增加模型维度。所有质量排名和调度优先级都按当前分组计算；分组内不同模型合并使用既有统计口径。

## 3. 非目标

- 不修改现有分组调度权重、默认值、策略名称或管理员设置保存行为。
- 不将质量评分永久加入调度总分，不用质量评分覆盖利润、首字、完整耗时或其他现有分组策略。
- 不重做质量评分公式、重新校准分数阈值或批量修正历史分数；只补齐当前分组范围、共享调度排序和解释投影所需的边界。
- 不增加“分组 + 模型”排名，不建立模型级排名页面。
- 不新增独立监控系统、独立缓存事实源、独立调度配置或平行控制面。
- 不自动调整账号分组、账号全局优先级、账号状态、计费、余额或采购成本。
- 不把外部截图中的“使用此分组”等维护按钮带入本页；既有账号信息、编辑、删除、更多、成本和模型检测入口保持原生语义。
- 不承诺实际请求始终命中调度优先级第一名；会话粘性、强制账号、冷却、并发和 Top-K 选择仍按原生调度语义运行。
- 不做数据库迁移、历史回填或生产业务数据写入。

## 4. 术语与核心关系

### 4.1 三个结果

```text
质量评分
  现有账号监控评分，范围是当前分组，回答“账号质量怎么样”。

质量排名
  当前分组内，对有资格且有有效质量评分的账号按质量评分排序后的名次。

调度优先级
  当前分组调度设置、候选资格、实时调度快照和调度器比较器生成的候选顺序。
```

不再引入独立的“监控排名”。页面上的“质量排名”就是质量评分的排序结果；页面上的“调度优先级”就是调度器候选顺序的投影。

### 4.2 计算关系

```text
同一当前分组快照
  ├─ 质量证据 + 分组评分权重
  │      └─ 质量评分 ──> 质量排名
  └─ 分组调度设置 + 调度资格 + 实时调度状态
         └─ 调度器实际候选比较器 ──> 调度优先级
```

分组调度设置仍然决定“先用谁”。质量评分不会变成第四项调度权重。质量状态只保留现有的资格/排除语义，并在调度器已有的次级判断或同分处理适用时由共享逻辑体现。

### 4.3 全站视图

具体分组具有唯一的调度策略，因此可以同时展示质量排名和调度优先级。全站视图混合多个分组策略，没有唯一的调度顺序：

- 全站继续展示质量评分和全站质量排名；
- 全站不显示伪造的调度优先级和不一致原因；
- 运营需要查看调度优先级时必须进入具体分组 Tab。

## 5. 方案比较与选择

### 方案 A：质量评分直接成为调度排序

改动简单，页面看起来容易一致，但会削弱或绕过分组的利润、首字、完整耗时等策略，违反现有调度设置的产品含义。不采用。

### 方案 B：调度器候选排序投影到监控，质量评分独立展示（采用）

质量评分和质量排名继续服务运营质量判断；调度器使用当前分组策略生成调度优先级；监控直接读取同一排序投影。优点是分组权重继续生效，页面顺序与调度候选顺序一致，差异可以通过策略/状态解释。采用。

### 方案 C：监控和调度分别维护两套排序，再用文案解释

对现有代码侵入较小，但两套公式和资格判断会继续漂移，无法保证页面反映真实调度。不采用。

## 6. 后端与数据流设计

### 6.1 当前分组快照

账号监控请求具体分组时，服务端在同一读取流程中固定以下上下文：

- `group_id` 与分组名称；
- 当前分组评分权重和评分目标/上限；
- 当前分组调度策略及生效参数；
- 当前时间和统计窗口；
- 当前分组有效账号集合；
- 账号质量证据、调度资格、实时负载和冷却/会话相关只读状态；
- 一个统一的 `snapshot_at`。

质量排名和调度优先级必须使用这份快照生成，避免页面加载期间分别读取不同版本的分组设置或账号状态。

### 6.2 质量评分与质量排名

- 沿用现有账号监控质量评分纯函数、分组评分权重、混合证据和历史有效结果回退语义。
- 查询和聚合必须严格绑定当前 `group_id`；不能用账号在其他分组的真实请求污染当前分组质量排名。
- 不增加模型过滤；当前分组内符合既有统计资格的模型请求继续按现有口径合并。
- `quality_rank` 只在现有评分状态允许参与排名、评分非空且证据状态允许展示时生成；无有效分数显示“未排名”，不伪造 0 分。
- 质量排名的 tie-break 固定为：质量分降序、既有稳定账号顺序；具体排序实现由服务端固定并由测试锁定。
- 评分拆解继续使用现有成本、成功率、TTFT、完整耗时四项；每项都提供实际得分和对应满分，不能只返回总分。

### 6.3 调度优先级

监控不直接调用真实请求调度，也不获取并发槽位；它调用调度器的只读候选投影，使用与真实请求相同的：

- 当前分组候选资格与排除条件；
- 当前分组调度设置和有效参数；
- 账号全局优先级/分组优先级等既有字段的实际解释；
- 实时负载、排队、错误/冷却、余额或能力限制等既有条件；
- 候选比较器和稳定 tie-break；
- Top-K 之前的确定性候选排序。

投影输出的 `scheduler_rank` 表示“当前快照下的候选顺序”，不是一次请求的实际选中结果。Top-K 加权随机、会话粘性、强制账号和后续并发获取仍然可以使实际选中账号不同。

为了避免监控服务复制调度公式，实施时应将当前调度器的纯排序/解释部分抽出为共享内部函数或只读投影接口；真实调度和账号监控都调用该共享逻辑。只读投影不得获取或释放并发槽位，不得写 session sticky、冷却、usage 或审计数据。

### 6.4 评分/排名/调度解释

服务端对每个账号生成两个解释对象：

```json
{
  "quality": {
    "score": 78,
    "rank": 3,
    "rank_total": 12,
    "breakdown": {
      "cost": {"score": 10, "max": 15},
      "success": {"score": 27, "max": 30},
      "ttft": {"score": 22, "max": 30},
      "latency": {"score": 19, "max": 25}
    },
    "window": "24h",
    "sample_count": 26,
    "source": "hybrid",
    "observed_at": "2026-08-26T00:00:00Z"
  },
  "scheduler": {
    "rank": 1,
    "rank_total": 9,
    "eligible": true,
    "policy_key": "group_policy",
    "policy_label": "当前分组调度策略",
    "effective_weights": {},
    "candidate_scope": "group",
    "snapshot_at": "2026-08-26T00:00:05Z",
    "primary_reason_code": "strategy"
  }
}
```

上述数值仅为字段示例，不是默认值或新算法。`effective_weights` 必须由当前分组调度设置的实际生效参数生成；服务端负责将内部 key 映射为运营可读标签，前端不解释原始工程字段。

推荐的兼容字段如下：

- 新增显式 `quality_rank`、`quality_rank_total`、`scheduler_rank`、`scheduler_rank_total`；
- 现有 `group_rank` 在兼容期保留为 `quality_rank` 的别名，不再承载调度含义；
- 现有 `quality_score`、`score_breakdown`、`evidence` 继续返回；
- 新增 `quality_explanation`、`scheduler_explanation` 或等价嵌套投影，具体命名须与仓库现有 DTO 风格一致；
- `primary_reason_code` 只能来自服务端有限枚举，不能由前端根据排名差值猜测。

### 6.5 不一致原因

只在质量排名和调度优先级需要运营解释时返回一条主要原因。允许的原因码：

```text
strategy
  当前分组调度策略与质量评分排序目标不同，例如利润优先。

quality_gate
  账号质量资格/质量状态影响了调度候选资格或排序。

runtime_load
  当前并发、排队或实时负载改变了候选顺序。

cooldown
  短时错误、冷却或故障隔离改变了候选资格。

tie_break
  调度分相同或接近，使用既有次级排序规则。

data_freshness
  质量证据与调度快照的更新时间不同，当前结果存在时效差异。

not_eligible
  账号不具备当前分组调度资格，因此没有调度优先级。
```

会话粘性、强制账号和 Top-K 随机属于“实际选中账号偏离候选顺序”的原因，不默认伪装成静态调度排名原因；只有已有调度诊断明确提供该事实时，才在展开详情中显示。

### 6.6 可解释性硬约束

- 每个质量分必须能定位到四个评分项、每项满分、统计窗口、样本数、来源和观察时间。
- 每个质量排名必须能定位到当前分组、参与排名总数、排序方向、并列规则和快照时间。
- 每个调度优先级必须能定位到当前分组的策略、生效权重、候选资格、候选总数、排序快照和 tie-break。
- 原因文案必须由服务端原因码和事实字段生成；没有证据时显示“暂无法解释”并保留问题日志，不显示“系统综合判断”等空泛文案。
- 页面展示的策略名称、设置页名称、调度器内部 policy key 和解释映射必须来自同一个稳定标识，禁止出现“页面写完整耗时、实际按其他指标排序”的口径错位。

## 7. 前端账号卡片设计

### 7.1 布局目标

账号列表从当前两列卡片改为单列整行：每个账号卡片占满 `account-card-grid` 的可用宽度；卡片不再使用两列墙式布局。页面容器仍遵循现有后台最大宽度，卡片不强行撑出视口。

桌面端采用稳定的运营列：

```text
账号 / 状态       质量表现              调度优先级          关键指标             趋势       操作
──────────────────────────────────────────────────────────────────────────────────────────────
账号身份          评分 88              调度 #1/12          成功率 / 首字 / 耗时   近期趋势   原生入口
                  质量排名 #3/12        利润优先
```

卡片内部可以使用 CSS Grid，但列宽必须有 `minmax` 和稳定最小尺寸，避免名称、数值或按钮变化导致列抖动。禁止用彩色粗侧边条作为状态装饰；状态使用完整边框、状态徽标和轻量背景变化表达。

### 7.2 默认可见内容

每行默认只突出以下内容：

- 账号名称、编号、当前分组和可调度状态；
- `评分`，如 `88 / 100`；
- `质量排名`，如 `第 3 / 12`；
- `调度优先级`，如 `第 1 / 12`；
- 当前分组调度策略的简短标签，如 `利润优先`；
- 评分与调度不一致时的一条短原因；
- 成功率、首字延迟、完整耗时和当前并发等既有关键服务指标；
- 近期趋势的紧凑可视化；
- 既有账号维护入口和刷新入口。

成本、倍率、余额、模型检测、调用数和历史记录等已有能力不删除；它们进入紧凑次级区域或按需展开，不与双排名主区争夺首要视觉层级。

### 7.3 展开详情

评分或调度区域使用语义按钮点击展开当前账号详情，不新建常驻说明区。展开内容采用两个并列区域，移动端自动堆叠：

```text
评分依据                         调度依据
成功率       27 / 30             当前策略       利润优先
首字速度     22 / 30             生效权重       按当前设置
完整耗时     19 / 25             候选资格       可调度
成本表现     10 / 15             候选顺序       第 1 / 12
窗口/样本/来源/时间               快照/并列规则/主要原因
```

展开详情必须使用运营可读的中文标签；原始 policy key、数据库列名和内部状态码只允许在管理员已有的技术详情路径中出现，不进入默认卡片。

### 7.4 移动端

- 小于现有窄屏断点时，隐藏桌面列标题，卡片改为两段稳定的上下布局；每个字段带短标签。
- 账号身份、评分、质量排名和调度优先级保持在首屏区域；原因允许换行，不截断关键名词。
- 趋势图只在卡片内部处理必要的横向空间，禁止整页横向滚动。
- 操作按钮使用现有图标/菜单语义，保留键盘焦点、禁用、加载和错误状态。
- 展开/收起遵循 `aria-expanded` 和 `aria-controls`；减少动画时不依赖动画显示内容。

### 7.5 排序与视觉顺序

- 具体分组默认按 `scheduler_rank` 升序展示；无调度资格账号置于可调度账号之后，并按既有稳定顺序显示。
- 卡片中同时显示 `quality_score` 和 `quality_rank`，不把当前卡片顺序误称为质量排名。
- 评分与调度顺序一致时只显示双排名；不一致时显示一条主要原因。
- 全站视图按质量排名/现有全局排序展示，不渲染无意义的调度优先级。

## 8. 失败与安全语义

- 质量聚合失败时保留当前既有错误/历史回退语义，不伪造评分或排名。
- 调度只读投影失败时，不改变真实调度器的 fail-closed/fallback 语义；监控显示“调度顺序暂不可用”，不使用前端近似排序冒充真实顺序。
- 分组调度设置读取失败、快照版本不一致或策略无法解析时，监控不显示虚假的策略名称/权重；账号仍按已有安全展示状态呈现。
- 不因查看监控而获取并发槽位、写入会话粘性、改变冷却、发送上游请求或写入账务。
- 不新增敏感请求体、完整响应、凭据、API Key 或内部 token 字段。
- 监控接口沿用现有管理员认证和权限边界；普通用户接口不获得调度解释数据。

## 9. 兼容与发布

- 预期无数据库迁移、无配置 schema 迁移、无生产业务数据写入。
- 保留现有 `group_rank`、`quality_score`、`score_breakdown` 等兼容字段；新增字段采用向后兼容方式，旧客户端仍能渲染现有评分卡片。
- 现有分组评分权重和分组调度设置分别保留、独立读取和独立保存。
- 现有账号维护事件、成本弹窗、模型检测、调用展开和单卡刷新行为保持语义不变；仅改变卡片布局和解释入口。
- 预期 `downtime_required=false`，最终以既有发布预检为准。若预检返回 `true`，在任何停机、迁移、重启或切换前停止并等待授权。
- 回滚使用上一已验证蓝绿槽或不可变镜像；不需要数据回滚。

## 10. 场景化验收矩阵

| 场景 | 预期结果 |
| --- | --- |
| Pro 分组为利润优先 | 调度优先级按 Pro 当前调度设置排序；质量评分不覆盖利润策略；发生不同序时显示“当前分组策略”类原因 |
| Plus 分组三项权重相同 | 监控 `scheduler_rank` 与调度器只读候选投影顺序一致；同分使用稳定 tie-break |
| 首字速度优先分组 | 首字相关调度指标按照当前分组设置生效；页面策略标签和解释与实际 comparator 一致 |
| 完整耗时优先分组 | 完整耗时相关调度指标按照当前分组设置生效；不把其他内部指标误标为完整耗时 |
| 同一账号出现在多个分组 | 质量/调度结果按当前分组分别投影；不增加模型维度；不同分组可有不同调度优先级 |
| 当前账号质量评分高但调度靠后 | 显示质量排名与调度优先级；原因可归因于策略、负载、资格、冷却、并列或时效，不显示空泛文案 |
| 账号不可调度/余额或资格失败 | 无调度优先级或明确为不可调度；不把它伪装为低质量账号，也不让它进入正常候选排名 |
| Top-K 加权随机 | 页面显示确定性候选优先级；不宣称每次请求固定命中第一名 |
| 全站 Tab | 只显示全站质量评分/质量排名；不生成跨多个分组策略的调度排名 |
| 质量或调度投影服务失败 | 页面保留可识别错误/不可用状态，不由前端自行重算或伪造排名 |
| 桌面账号列表 | 每个账号一张占满内容宽度的整行卡片，列对齐，评分/质量排名/调度优先级可横向比较 |
| 移动账号列表 | 卡片稳定上下布局，无整页横向溢出，关键双排名和原因不遮挡、不截断 |

## 11. 测试策略

- 质量聚合严格按 `group_id`，确认其他分组真实请求不会污染当前组。

- 分组调度策略读取、有效参数映射和解释标签。
