# 多用户网关扩容与多 Key 实践研究

**日期：** 2026-07-19 Asia/Shanghai  
**范围：** 商用 AI API 网关的同供应商多 Key、负载均衡、用户级限流和扩容路径  
**当前生产上游：** Neko；Aliu 暂停保留为回滚候选

## 公开实践证据

1. [LiteLLM Proxy - Load Balancing](https://docs.litellm.ai/docs/proxy/load_balancing) 将同一模型的多个 deployment 放入同一逻辑模型组，通过 `simple-shuffle`、`least-busy`、usage/latency/cost 路由策略分配请求；每个 deployment 可单独设置 RPM。其 `enforce_model_rate_limits` 可在请求到达供应商前执行硬 RPM 限制，多实例部署使用 Redis 共享限流状态。
2. [New API 中文 README](https://github.com/QuantumNous/new-api/blob/main/README.zh_CN.md) 明确列出“渠道加权随机”“失败自动重试”和“用户级别模型限流”。这与常见中转站的做法一致：用户只看到一个逻辑模型/分组，渠道、权重、健康状态和重试属于内部调度层。
3. [AWS API Gateway 多租户限流实践](https://aws.amazon.com/blogs/architecture/throttling-a-tiered-multi-tenant-rest-api-at-scale-using-api-gateway-part-1/) 采用全局保护、租户级配额和分层限流，而不是只依赖供应商返回 429；网关要在入口处保护共享容量。

## 对本项目的结论

### 第二个 Neko Key 与第二个 Sub2API 账号

- **第二个 Neko Key 不等于第二个不同上游。** 它仍属于同一个 Neko Pro 池，成本倍率仍按 `0.07` 计算，用户售价仍由所属分组决定。
- **在 Sub2API 中应建立第二个账号对象。** 这样才能分别记录 Key 的健康状态、并发、优先级、停用状态和审计信息，再把两个账号绑定到同一个 Neko/GPT 逻辑分组。
- **不要假设多 Key 会把容量线性翻倍。** 如果 Neko 在账号、Pro 池、IP 或订阅层共享 RPM/TPM/并发，多个 Key 主要改善隔离和故障切换，不会增加总容量。新增 Key 后必须重新做同步并发、SSE 并发和 RPM 测试。
- **不同供应商才需要不同成本倍率。** Aliu 与 Neko 若同时生产，应分成不同的内部渠道/账号集合，并分别记录实际成本；不应把不同倍率的账号混在一个成本口径不清的组里。

### 推荐扩容阶梯

| 阶段 | Neko 账号对象 | 账号并发 | 每用户并发 | 每用户 RPM | 进入条件 |
|---|---:|---:|---:|---:|---|
| 当前内测 | 1 个生产账号对象 | 3（保持现状） | 1 | 3 | 已建立 `GPT-内测`，等待真实用户 |
| 内测扩展 | 1 个账号对象 | 6 | 1 | 3 | 连续 3 天 P95、错误率和 SSE 终止稳定 |
| 商用起步 | 2 个 Neko Key/账号对象，同一逻辑组 | 每个 6，合计目标 12 | 普通用户 1 | 普通用户 3 | 新 Key 的容量复测通过，且活跃用户超过 10 或出现排队 |
| 商用增长 | 2 个以上账号对象 | 按最新容量证据逐步增加 | 普通用户 1；重度用户单独 2 | 普通用户 3；重度用户单独 6 | 余额、延迟和错误率都满足运营门槛 |

账号并发是共享上游保护；Sub2API 分组 RPM 是**每用户每分钟**，不是全站总 RPM。全站保护仍需要通过账号并发、用户数上限、监控和必要时的入口级限流共同实现。

### 大用量用户

先使用用户级覆盖或单独的“GPT-重度”组，起始为并发 `2`、RPM `6`，并限制重度用户数量；不要为单个用户直接提高共享账号并发。只有连续观察其真实 Token、P95 和错误率后，才扩大额度。

## 当前执行状态

- `GPT-内测` 已在 Sub2API 创建：OpenAI、`1.0x`、专属、每用户 RPM `3`。
- 该组当前只绑定 Neko；Aliu 未绑定且保持暂停，不能接收内测流量。生产 `GPT` 组仍为 `0.15x`，Neko 生产账号当前并发 `3` 未改动。
- 内测签到和推荐奖励由独立自动化服务维护统一累计余额账本，并通过幂等 Admin API 无人值守执行；Sub2API 分组本身不负责“累计签到”“用户自助邀请码”“注册人数硬上限”和“每个被推荐用户首次成功调用奖励”这类业务规则。
- 在真实内测用户出现前，不新增第二个 Neko Key，也不上调生产账号并发。

## 未知与复核触发

- Neko 未公开证明多个 Key 是否共享 Pro 池级 RPM/TPM/并发；这必须通过新增 Key 的隔离容量测试确认。
- 当前容量报告是短测下界，不是供应商硬上限或 SLA。
- 出现 429、超时、SSE 未收到 `[DONE]`、P95 明显升高、余额低于运营底线、供应商倍率/模型目录变化或活跃用户超过 10 人时，重新测试并决定是否增加第二个 Key/账号对象。
