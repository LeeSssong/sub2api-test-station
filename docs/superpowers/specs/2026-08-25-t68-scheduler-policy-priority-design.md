# T68 分组调度运营优先级与策略护栏设计

## 1. 问题证据与当前行为

当前生产已部署 T52/T54 的原生 OpenAI 调度、公平参数、分组策略和三个内置预设，但管理员界面仍暴露底层概念：Top-K、评分权重、探索比例、最长闲置、公平权重，以及“体验优先/体验均衡/利润优先”预设。运营无法从这些数值直接判断优先级关系，也无法表达“多个指标同等重视”。

当前原生运行链已经提供并必须复用：

- `listSchedulableAccounts`、模型/传输能力、余额/资格、冷却与故障域过滤。
- S1/S2、sticky、previous response、半开探测和请求级重试边界。
- 账号并发槽位的初步负载读取、原子抢占、抢槽后 fresh account/DB recheck 和失败后候选回退。
- `LastUsedAt`、hybrid/all-eligible/top-k 公平候选池和现有 settings 缓存。
- `GET/PUT /api/v1/admin/settings`、分组策略快照、内置/管理员预设兼容读取。

生产证据显示仅靠固定 Top-K 与评分会形成账号集中：T52 基线中 GPT-Pro 24 小时 341 次请求由前 6 个账号承载 334 次（97.9%）；GPT-特惠 24 小时 880 次请求中前 2 个账号承载 499 次（56.7%）。因此 T68 需要同时改善运营表达和真实分组覆盖，但不能以覆盖探索绕过并发/资格保护。

## 2. 目标与非目标

### 目标

1. 把分组经营偏好表达为三个可比较指标的数字优先级：利润、首字速度、完整耗时；数字 `1` 最高，`3` 最低；同一数字允许多个指标并列。
2. 将服务不中断、并发容量分散、异常/冷却/配额/资格过滤和安全切号定义为固定护栏，不暴露为可关闭的目标或权重。
3. 将账号均衡使用、高峰期保护、会话连续性做成三个三段离散运营控件，并明确各自职责与相互作用。
4. 保存前实时预览平峰、高峰、会话切换三种场景，预览只使用真实策略语义，不显示底层小数或内部 key。
5. 保留每个分组可配置；以用户确认的四组偏好作为首次推荐快照，而不是按分组名称写死运行时分支。
6. 保持原生 settings、调度器、账号和计费事实源；无迁移、无第二事实源、无生产数据回填。

### 非目标

- 不建设独立调度器、独立账号池、独立公平计数表或外部控制面。
- 不把服务连续性实现为一个可调“质量阈值”；不允许运营关闭硬资格、并发上限、冷却、S1/S2、故障域或安全切号。
- 不改变用户扣费、usage_logs、账号成本、利润事实源或 Monitor V2/V4 数据口径。
- 不保证严格 round-robin、每个账号每个时间窗必然成功或每个分组精确等量配额。
- 不在本任务中改造三个历史内置预设的内部 ID 兼容读取；新界面保存新策略契约时允许服务端继续生成兼容快照。

## 3. 方案比较与选择

### 方案 A：按分组名称写死四套策略

实现简单，但策略无法由运营调整，分组重命名/新增分组会产生隐含行为，且运行时出现大量名称分支。放弃。

### 方案 B：继续暴露底层权重，只改善中文文案

不会解决运营无法理解 0.8、2.5、21600 的问题，也无法表达同级优先级。放弃。

### 方案 C：分组策略保存业务优先级与三个离散微调，由服务端编译到原生调度输入（采用）

页面只编辑数字优先级和运营语义档位；服务端规范化、保存完整策略快照，并在请求调度前将其投影到既有评分、hybrid 公平、容量分散与 sticky 逃逸输入。固定护栏仍由原生调用链执行。该方案保留可配置性、可解释性和回滚兼容性，避免把业务偏好硬编码为分组名称。

## 4. 产品与交互设计

### 4.1 分组选择

沿用 T54-R1 的原生有效 OpenAI 分组来源。页面先选择一个分组，切换分组保留未保存草稿；未选择分组时不显示可编辑策略。

### 4.2 固定服务连续性护栏

固定展示“始终保证服务不中断”，只读说明：

- 账号异常、冷却、余额/配额/资格不足时自动避开。
- 账号并发接近上限时优先分散流量；满并发时不再分配。
- sticky/会话原账号满并发、冷却或异常时允许安全切换。
- 所有探索候选仍必须经过最终并发抢槽、fresh account 和 DB recheck。

固定护栏不进入数字优先级，也不受三个微调关闭。

### 4.3 经营优先级

为三个指标各提供 `1 / 2 / 3` 分段按钮：

```text
利润       [1] [2] [3]
首字速度   [1] [2] [3]
完整耗时   [1] [2] [3]
```

- 数字越小越优先。
- 多个指标可使用同一数字；同级指标由服务端作为同一优先层参与综合排序，不再隐式拆成先后顺序。
- 不要求 1、2、3 必须全部被使用。
- 页面实时汇总，例如 `1：利润 → 2：首字速度 → 3：完整耗时` 或 `1：利润、首字速度、完整耗时`。
- 推荐快照：
  - GPT-特惠：利润 `1`、首字速度 `2`、完整耗时 `3`。
  - GPT-Plus：利润 `1`、首字速度 `1`、完整耗时 `1`。
  - GPT-Pro、【专属】GPT-PRO：首字速度 `1`、完整耗时 `2`、利润 `3`。

### 4.4 三个运营微调

每张卡使用三段横向控件，每段下方有行为说明；不使用自由数值、滑杆或小数。

#### 账号均衡使用

- `仅分散高负载`：只执行有余量账号承接和接近满载账号的容量分散，不主动补长期闲置账号。
- `标准覆盖`：在存在安全余量时，给长期未参与的健康账号正常的真实请求机会。
- `优先补齐覆盖`：在明显安全余量时，更积极补长期未参与账号；仍不绕过资格、冷却、故障域、并发和 sticky 安全规则。

这是“是否补覆盖”的强度，不改变并发硬上限。

#### 高峰期保护

- `严格保护`：检测到容量紧张时只做容量分散，暂停纯覆盖探索。
- `标准保护`：容量紧张时允许少量覆盖，但必须满足安全余量。
- `保留覆盖`：只要仍有明显安全余量，继续维持覆盖机会。

这是“高峰时是否暂停覆盖”的强度，不允许满载账号继续接请求。

#### 会话连续性

- `尽量保持`：原账号健康且有余量时尽量保持同一会话。
- `标准`：正常保持会话；拥塞或风险时及时切换。
- `更快切换`：对原账号等待容忍更低，更积极使用其他健康账号。

这是 sticky 的偏好，不得覆盖服务不中断护栏。

### 4.5 保存前策略预览

展示三个场景：

- 平峰请求：先过滤不可用/满并发，再按数字优先级选择；补充当前账号均衡档位如何处理长期未参与账号。
- 高峰请求：先分散接近并发上限的账号；根据高峰保护档位说明是否暂停纯覆盖探索。
- 会话切换：说明原账号何时保持、何时因满并发/冷却/异常安全切换。

预览不得承诺固定成功率、固定轮询次数、固定时间内覆盖每个账号或具体收益金额。

## 5. 策略数据与接口契约

继续复用 `GET/PUT /api/v1/admin/settings`。分组策略新增/规范化为：

```json
{
  "42": {
    "mode": "business_priority",
    "priority": {
      "profit": 1,
      "ttft": 2,
      "latency": 3
    },
    "operations": {
      "balance": "standard",
      "peak_protection": "strict",
      "session_continuity": "standard"
    },
    "compiled_snapshot": {
      "top_k": 7,
      "weight_overrides": {},
      "fairness": {}
    }
  }
}
```

- `priority.profit/ttft/latency` 只允许整数 `1..3`。
- `operations.balance` 只允许 `low|standard|high`。
- `operations.peak_protection` 只允许 `strict|standard|open`。
- `operations.session_continuity` 只允许 `keep|standard|switch`。
- `compiled_snapshot` 是服务端生成的只读运行快照；客户端 PUT 中若携带该字段必须忽略，不得信任客户端编译值。
- 旧 `weighted_override`/`fair`/`preset` 策略继续兼容读取；新版页面读取旧策略时按既有 preset 映射为推荐业务优先级，并保留原始底层快照，直到新版保存。
- 新版保存须一次性校验全部分组策略，非法字段、未知分组、重复/缺失结构、未知档位或越界优先级时整次更新返回 400，旧 settings 保持不变。
- 未发送 T68 字段的旧客户端更新不得清空新策略字段。

## 6. 运行时控制流

1. 请求按现有路径解析分组并列出 Sub 原生候选。
2. 先执行现有资格、模型能力、余额/配额、冷却、故障域、S1/S2、sticky/previous response 前置逻辑。
3. 获取 fresh load map；原子抢槽时以账号真实 `Concurrency` 为上限，抢槽失败继续候选回退。
4. 根据 `operations.peak_protection` 判断是否允许覆盖探索；根据 `operations.balance` 决定仅容量分散、标准覆盖或优先补覆盖。
5. 在安全候选池内，以 `priority` 编译出的同层/分层评分输入排序。优先级只影响安全候选顺序，不改变硬过滤。
6. 对非 sticky 请求，按分组覆盖状态与现有 `LastUsedAt`/公平候选排序插入长期未参与账号；覆盖候选仍经过最终并发抢槽、fresh account 和 DB recheck。
7. 对 sticky 请求，先保留原生 sticky 语义；原账号不能安全取得槽位时按会话连续性档位决定等待/逃逸，但任一档位都必须在满并发、冷却或异常时安全切换。
8. 成功选中后更新既有使用信号和 scheduler metrics；不新增账务或独立选择事实源。

## 7. 失败、安全与兼容性

- 配置解析失败 fail-closed，继续使用上一份有效 settings/运行快照。
- 覆盖探索候选永远不能绕过账号资格、并发、冷却、S1/S2、故障域、模型能力或请求排除。
- 没有安全候选时沿用现有本地容量耗尽/上游错误语义，不为了覆盖伪造成功。
- sticky 的更快切换不能重放已输出流式请求，不能改变 T66 安全切号边界。
- 旧内置预设 ID、旧 JSON 和旧客户端继续可读；回滚到旧二进制时新策略必须仍能回退为兼容快照或被忽略，不产生迁移回滚动作。
- 不记录 API Key、请求体、凭据或敏感策略来源。

## 8. 场景化验收矩阵

| 场景 | 预期 |
|---|---|
| 特惠默认策略 | 读取为利润 1、首字 2、完整耗时 3；预览和保存摘要一致 |
| Plus 默认策略 | 三项均为 1；只显示一个同级优先层 |
| Pro/专属 Pro 默认策略 | 首字 1、完整耗时 2、利润 3 |
| 修改一个指标数字 | 仅当前分组草稿和预览改变，其他分组不变 |
| 同级指标 | 服务端保留同级关系，不产生客户端隐式排序 |
| 账号均衡低档 | 不主动补闲置，只执行容量分散和硬资格过滤 |
| 账号均衡高档 + 高峰严格 | 高峰暂停纯覆盖探索，满载账号仍不接请求 |
| 高峰保留覆盖 | 只有明显安全余量时继续覆盖，抢槽失败正常回退 |
| sticky 原账号满并发 | 所有会话档位都不得硬等/硬分配满载账号，按安全边界切换 |

| 旧 T54 策略读取 | 不报错、不丢失原快照；新版显示推荐业务层解释 |
| 保存前预览 | 平峰、高峰、会话切换文字随草稿同步，不展示小数/内部 key/固定成功承诺 |
| 移动端 | 1/2/3 控件、三段卡、预览场景纵向排列，无页面横向溢出 |

## 9. 测试策略

- Go service：业务优先级解析/规范化、同级优先级、四组推荐快照、旧策略兼容、运营档位编译、非法更新原子性、峰值暂停探索、容量分散、按分组覆盖、sticky 满并发安全逃逸、最终抢槽/DB recheck 不绕过。
- Go handler/DTO：GET 返回规范化业务策略与只读 compiled snapshot；PUT 忽略客户端 compiled snapshot；未知/越界字段 400；旧客户端省略字段保留。
- Vue/Vitest：四组默认值、1/2/3 互斥选择、同级摘要、三个三段控件、每段说明、草稿隔离、预览随修改更新、恢复推荐、移动端布局合同。
- 直接门禁：相关 Go/Vitest、`go build ./cmd/server`、`pnpm typecheck`、`pnpm build`、`git diff --check`；不运行无关全仓压力或长时间 soak。

## 10. 发布、线上验证与回滚

- 无数据库迁移、无生产数据回填、无新配置文件，预期 `downtime_required=false`。
- 合并后从已验证根 `main` 使用既有本地/宿主蓝绿链发布，不使用 GitHub Actions。
- 线上管理员验收：四个目标分组、默认数字、Plus 同级摘要、三个三段卡、保存前三场景预览、设置 API 读写和旧策略兼容读取。
- 验收只使用临时未引用策略草稿，不修改生产分组成员或账务数据。
- 回滚优先切回上一蓝绿槽；若保留新 settings，旧运行时使用兼容字段/已编译快照，不需要数据库回滚。
- 若预检返回 `downtime_required=true`，在任何停服/迁移/重启前暂停；若为 `false`，按既有发布授权继续。
