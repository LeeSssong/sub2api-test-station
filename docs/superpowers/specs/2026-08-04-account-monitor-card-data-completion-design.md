# 账号监控卡片数据完善设计

## 目标

在保持已确认的账号监控视觉风格不变的前提下，完善账号成本、全局优先级、组内排名、分组汇总和实时并发。本次不恢复营收、对账或其他运营内容。

交付顺序为：

1. 先修订最小 HTML 原型，由用户确认。
2. 再制定生产实施计划并修改 Sub2API。
3. 完成推送、生产部署和必要的线上验证后，项目总账才可转为已完成。

## 范围边界

### 本次包含

- 账号一次性采购成本录入。
- 上游账号倍率成本的延续使用。
- 在卡片上直接编辑账号全局优先级。
- 每个分组桌面端一行两张卡片，并按组内排名排序。
- 仅展示用户指定的分组原生汇总字段。
- 使用 Sub2API 原生 Redis 并发槽位数据展示当前并发。
- 24 小时、7 天、30 天窗口下的真实请求评分与排名。

### 本次不包含

- 营收、利润、对账、流水或成本历史页面。
- 分组峰值倍率、模型路由、Messages/Live 开关、图片或视频计价的监控展示。
- 等待队列数量的展示。
- 汇率配置或人民币兑美元换算。

## 成本数据模型

账号增加两个可空字段：

- `procurement_cost_cny`：一次性采购金额，人民币，必须大于或等于 0。
- `procurement_cost_effective_at`：采购成本生效时间，首次录入或后续覆盖采购金额时由服务端自动写入当前时间。

采购有效期结束时间直接使用账号原生 `expires_at`，不新增结束时间字段，也不要求用户额外录入开始时间。

成本模式不增加独立的账号来源开关：

- `procurement_cost_cny` 非空：账号按真实采购账号计算，成本评分忽略 `rate_multiplier`。
- `procurement_cost_cny` 为空：账号按上游账号计算，继续使用 Sub2API 原生 `rate_multiplier`。
- 清空采购成本后，账号恢复为倍率模式。

金额数值与站内美元额度数值按 1:1 计算，因为当前业务规则是用户充值 1 元获得 1 美元额度。

## 窗口成本与等效倍率

对于真实采购账号：

```text
窗口采购成本 = 采购金额
               × 所选时间窗口与采购有效期的重叠时长
               ÷ 采购有效期总时长

等效倍率 = 窗口采购成本
           ÷ 同一时间窗口内真实请求的模型基础成本合计
```

模型基础成本使用 `usage_logs.total_cost` 的基础价值，不使用用户实际扣费 `actual_cost`，也不再叠加分组或账号倍率。

对于上游账号，等效倍率就是 Sub2API 原生 `rate_multiplier`。

异常口径：

- 未配置 `expires_at`、到期时间不晚于成本生效时间、窗口内无真实请求，或模型基础成本合计为 0 时，该账号成本项得 0 分。
- 上游账号倍率缺失时，成本项得 0 分。
- 以上情况不取消账号的评分与排名资格。

## 评分与排名

- 评分使用当前选中的 24 小时、7 天或 30 天真实请求窗口。
- 成本分继续使用现有“分组倍率与账号等效倍率的差值”公式，并受分组成本权重上限约束。
- 成功率、TTFT P50 和总延迟 P95 只使用同一时间窗口的数据。
- 真实请求少于 3 条时，可使用同窗口探测结果补足服务质量证据，但探测不计入请求数、失败数或成本。
- 有排名资格的账号按总分降序，同分按账号 ID 升序，顺序稳定。
- 组内唯一正常可用账号的排名必须为 1。
- 无排名账号放在有排名账号之后，按账号 ID 升序，显示“未排名”。

## 分组汇总

分组汇总位于时间范围选择器下方、账号卡片网格上方。仅展示以下 Sub2API 原生字段：

- 分组状态 `status`。
- 平台 `platform`。
- 分组倍率 `rate_multiplier`。
- RPM 上限 `rpm_limit`。
- 分组下原生账号数 `account_count`。
- 原生活跃账号数 `active_account_count`。
- 原生限流账号数 `rate_limited_account_count`。

分组倍率只出现在分组汇总，不出现在账号卡片。本区域不增加请求数、成功率、TTFT 或延迟等窗口汇总。

## 账号卡片

卡片沿用已确认的视觉语言和层级：

- 左上为账号名称和账号 ID。
- 顶部评分层独立展示分组评分、组内排名和全局优先级。
- 底部指标保留成功率、TTFT P50、总延迟 P95 和账号成本。
- 额外增加“当前并发 / 并发上限”，例如 `3 / 10`。
- 桌面端每个分组每行两张卡片，移动端每行一张。
- 网格按组内排名升序渲染。

### 全局优先级编辑

- 在全局优先级旁显示铅笔图标。
- 点击后原位切换为整数输入、保存和取消控件。
- 只允许大于或等于 1 的整数，并提示“数值越小，调度优先级越高”。
- 使用现有账号更新能力仅提交 `priority`。
- 服务端成功后才替换页面数值；失败保留原值和编辑上下文。

### 账号成本编辑

- 指标名称统一为“账号成本”。
- 未录入采购成本时展示倍率，例如 `0.62×`，并提供“录入采购成本”入口。
- 录入后显示采购金额，例如 `¥120.00`，辅助文字显示原生到期时间和当前窗口等效倍率。
- 成本编辑只让用户输入一次性采购金额，生效时间由服务端自动写入，`expires_at` 只读。
- 清空采购成本需要确认，成功后恢复倍率模式。
- 上游托管倍率保持只读；手动倍率遵循 Sub2API 既有更新规则。
- 成本保存成功后重新加载当前窗口的评分和排名。

## 实时并发

`current_concurrency` 使用 Sub2API 原生 `ConcurrencyService.GetAccountConcurrencyBatch`，数据来自 Redis 中的账号请求槽位和 Live/WebSocket 槽位。

为避免每 5 秒重算 24 小时、7 天或 30 天聚合，实时并发使用独立的轻量批量读取接口：

- 页面可见时每 5 秒读取一次当前页面中的唯一账号 ID。
- 页面进入后台时停止轮询，恢复可见时立即刷新。
- 单次批量 Redis pipeline 读取，不在每张卡片上发独立请求。
- 查询失败时保留上一次成功值并标记“数据延迟”，不得回退为 0。
- 该数字是近实时运维快照，不是审计数据，不计入评分和排名。
- 异常中断槽位可能在主动释放前短暂残留，最终受 Sub2API 原生槽位 TTL 清理。

## 最小 HTML 原型

原型只展示一个分组和两张账号卡片：

- 分组汇总包含七个已确认的原生字段。
- 排名 1：已录入人民币采购成本的真实账号。
- 排名 2：使用原生倍率的上游账号。
- 两张卡片在桌面端同行、移动端单列。
- 全局优先级和采购成本具备可操作的编辑、保存、取消和清空演示。
- 当前并发每 5 秒做本地模拟更新，用于确认卡片布局不会抖动。
- 24 小时、7 天和 30 天切换保留并演示评分、排名和等效倍率变化。

## 错误处理

- 采购成本或优先级更新失败时，保留服务端最后确认值，局部呈现错误，不刷新整页。
- 评分或排名刷新失败时，保留上一个完整快照并标记过期。
- 并发轮询失败不影响卡片其他数据。
- 缺失采购到期时间或基础成本时，页面显示明确原因，不显示伪造的等效倍率。

## 必要验证

验证与风险匹配，不扩展成大型验收项目：

- 后端单元测试：采购成本模式判定、窗口重叠时长、等效倍率、缺失数据成本归零、唯一可用账号排名为 1。
- 后端接口测试：采购成本更新、优先级更新、分组原生字段投影、批量并发读取。
- 前端组件测试：双列排序、两种成本展示、原位编辑成功与失败、并发轮询失败保留旧值。
- 原型和生产页各做一次桌面端与移动端布局检查，确认无重叠、无溢出、双列稳定。
- 生产只验证新增数据和操作链路，不重做与本次无关的大范围发布验收。
