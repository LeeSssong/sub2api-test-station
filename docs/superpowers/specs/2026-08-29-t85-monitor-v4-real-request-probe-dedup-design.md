# T85 Monitor V4 真实请求成功率与探测兜底去重设计

## 1. 已确认目标

Monitor V4 只展示一项质量指标：真实请求成功率。统计保留现有 5 分钟桶和真实请求优先规则：

1. 桶内存在真实请求时，只使用该桶真实请求。
2. 当前桶进入最后一分钟仍没有真实请求时，才允许使用同桶主动探测。
3. 同桶不混用真实请求和主动探测。
4. 每个分组的每个已结算 5 分钟桶都必须有一个终态：桶内有真实请求时使用真实请求；无真实请求时必须使用一次主动探测逻辑请求。主动探测成功计 `1/1`，主动探测失败、超时、无可用账号、执行异常、读取异常或持久化异常均按 `0/1` 计入分母。
5. 成功率是选中成功请求数 / 选中总请求数；真实失败请求和主动探测失败兜底桶都进入分母。正常业务结果不允许出现“无样本”桶。
6. TTFT P95、完整耗时 P95 分别从选中成功样本中独立计算。

本次优化的原因是当前 `account_monitor_results` 按账号保存探测尝试，同一分组和同一 5 分钟桶会出现十几到几十条探测结果，失败尝试被重复扩大为成功率分母。2026-08-28 生产只读证据还显示余额不足、上游 502/503、路由 503 是主要失败来源。

## 2. 当前原生能力与问题

- `usage_logs`、`ops_error_logs` 是真实请求事实源，已有请求 ID、分组、账号、时延和最终错误字段。
- `account_monitor_results` 是主动探测事实源，按账号保存每次结果，`status='success'` 表示探测成功。
- `Account.IsSchedulableAt` 已包含 active、手工可调度、过期、过载、限流、临时不可调度和 API Key 配额门禁。
- 当前 V4 仓储查询只读成功 `usage_logs` 和所有探测行，按桶可用性计算，不保留真实失败分母，也没有源仲裁。
- 当前探测运行池只检查 `Schedulable` 布尔字段，未统一调用 `IsSchedulableAt`，所以已知临时冷却/额度耗尽账号仍可能反复探测。

## 3. 目标与非目标

### 3.1 目标

- 将 V4 统计改为请求数加权成功率。
- 每个分组每个 5 分钟桶只选择一个事实源。
- 探测兜底桶聚合为一个逻辑潜在请求：同桶任一可用探测成功即为 1/1；所有探测失败才为 0/1。探测失败尝试不逐条扩大分母。
- 探测成功的 TTFT/总耗时使用该桶成功探测样本的最小值，表示路由在该桶可以取得的首个成功结果；一个桶最多贡献一个探测 P95 样本。
- 同一探测运行的跨账号尝试只保留最终聚合结果；跨运行结果仍按分组桶最终裁决，避免同一桶重复计数。
- 已知 `IsSchedulableAt(now)` 为 false 的账号不加入自动监控探测池。
- API 与前端只展示成功率、成功请求数/总请求数和成功请求 P95；保留窗口切换、刷新和现有分组可见性。
- 对已纳入监控的分组，窗口内每个已结算桶都必须产生真实请求或主动探测终态，因此正常情况下 `request_count > 0` 且 `success_rate` 为 `0–100`。`success_rate=null` 只允许表示窗口/分组事实源完整性故障，而不是无流量或探测缺失。
- 若历史数据缺少应有的探测终态，读取侧必须 fail-closed 合成为一个 `0/1` 逻辑失败，并同时记录服务端数据完整性告警；不得把缺失转成成功、静默跳过或返回正常无样本。

### 3.2 非目标

- 不改变真实成功定义、用户计费、路由重试、主动探测题面或探测调度周期。
- 不把主动探测写入 `usage_logs`，不建立第二套计费或质量事实源。为保证“每组/桶必有终态”，新增的最小分组桶结算/幂等记录只证明探测执行终态，不替代 `usage_logs`、`ops_error_logs` 或 `account_monitor_results` 原生事实源。
- 不把探测失败全部排除；所有探测均失败的已关闭兜底桶仍为一次真实失败的代理观测。
- 不修改 Monitor V2 原生页面、账号质量评分或调度选择公式。

## 4. 方案比较

| 方案 | 做法 | 取舍 | 结论 |
| --- | --- | --- | --- |
| A | 保持每账号探测行进入分母 | 失败被账号数量放大，指标继续被探测主导 | 不采用 |
| B | 统计层将每桶探测聚合为一次逻辑请求 | 不改探测执行器，语义直接对应一次潜在真实请求，改动可回滚 | 采用 |
| C | 重写探测器，使每组每桶只发一次带故障转移的探测 | 语义最接近真实路由，但需要新调度/锁/模型选择协议，风险和范围过大 | 不采用 |

选择 B，并补充一个“桶结算保证层”：运行层复用现有账号健康门禁减少已知无效探测；结算层以 `group_id + bucket_start` 幂等地产生成功/失败终态；统计层用 SQL 完成真实请求优先和探测一次化聚合。这样账号级跳过不会导致分组级桶缺失。

## 5. 数据流与 SQL 语义

### 5.1 真实请求候选

- `usage_logs` 在窗口内按 `group_id + account_id` 取请求。
- `usage_completeness='unknown'` 不作为合格真实事件；其他请求按 `actual_cost > 0` 判断成功，`actual_cost <= 0` 为失败。
- `ops_error_logs` 取非 token-counting 且最终 HTTP 状态码 >= 400 的网关错误。
- 通过 `request_id`、`client_request_id` 与 usage request ID 做有界去重；同一请求出现 usage 与错误时错误优先。
- 真实请求按 `logical_request_id` 优先，其次 `request_id`，再其次自身行 ID 形成去重键；分组和账号同时作为键约束。

### 5.2 主动探测候选

- 只读窗口内当前 scope 账号的 `account_monitor_results`。
- 先按 `group_id + bucket_start + run_id` 聚合一次探测运行：任一 `success` 即运行成功；成功运行的 TTFT/总耗时取最小非空值。
- 再按 `group_id + bucket_start` 聚合一次桶：任一运行成功即桶成功；成功运行样本取最小值。
- 真实事件存在的桶完全排除探测事件。
- 真实事件不存在且桶已关闭，或当前桶已进入最后一分钟，必须选中一个探测终态。
- 当前桶尚未进入最后一分钟时暂不结算；一旦进入最后一分钟，必须在本桶结束前落一个探测成功/失败终态。
- 对已关闭历史桶，若探测事实行缺失，按一个 `0/1` 的 fail-closed 探测终态处理，并记录完整性故障；窗口外历史不回退。

### 5.3 桶终态保证

- 每个可见分组在每个 5 分钟桶关闭时创建唯一结算键 `group_id + bucket_start`；重复调度、重试和多账号尝试不得创建第二个分母单位。实现使用最小观察表 `account_monitor_bucket_terminals` 的唯一约束保证幂等。
- 结算 worker 必须在 SLA 内写入 `success` 或 `failure` 终态；任一账号成功即成功，全部账号失败/超时/无可用账号/执行异常即失败。当前监控运行器在每轮结束时结算上一完整桶，并在当前桶最后一分钟结算当前桶。
- usage reader 不可用或读取异常时不得静默跳过探测；仍尝试执行账号探测。账号均不可调度时仍写入分组失败终态。
- runner 每轮结算后以及每分钟 watchdog 都会重复尝试关闭上一完整桶和当前最后一分钟桶；唯一键使调度重叠幂等。watchdog 不回溯重放历史探测，历史缺失终态由读取侧先合成 `failure`，记录 `missing_probe_terminal_count`，并由后续补偿任务继续处理，缺失终态不得停留为“无样本”。
- 读取侧对历史缺失终态仍 fail-closed 为 `0/1`，用于保护指标不被高估；补偿写入完成后，后续读取应与持久化终态一致。

### 5.4 聚合输出

- `request_count`：选中真实请求数 + 每个无真实请求已结算桶恰好一个探测逻辑请求（含失败、超时、无账号、执行/读取/持久化异常合成的 `0/1` 终态）。
- `success_count`：选中成功真实请求数 + 选中成功探测桶数。
- `success_rate`：`success_count / request_count * 100`。对已结算窗口正常不会无请求；仅在窗口/事实源完整性故障无法构造任何终态时返回 null。
- `real_request_count`、`real_success_count`：被选为真实源的桶中真实事件计数。
- `probe_fallback_bucket_count`：选中的无真实请求桶数，包括主动探测失败和 fail-closed 合成失败桶。
- `probe_fallback_request_count`：该值等于选中探测桶数，每桶只计一次逻辑请求。
- TTFT/总耗时 P95 独立过滤成功事件中对应字段非空的样本；真实请求保留各请求样本，探测桶每桶最多一个样本。
- `current_operational` 由窗口内最新选中成功事件投影；无选中事件为 false。

## 6. 接口与前端契约

`GET /api/v1/monitor-v4?window=24h|7d|30d` 的 `contract_version` 升为 `2`。每组返回：

- `success_rate: number|null`
- `request_count: int`
- `success_count: int`
- `real_request_count: int`
- `real_success_count: int`
- `probe_fallback_bucket_count: int`
- `probe_fallback_request_count: int`
- `ttft_p95_ms: number|null`
- `ttft_sample_count: int`
- `latency_p95_ms: number|null`
- `latency_sample_count: int`
- `source_updated_at: RFC3339|null`
- `current_operational: bool`

删除 V4 页面主合同中的 `availability`、桶总数、`sample_count` 和窗口外历史回退字段。卡片文案改为“成功率”和“成功请求 N/M”；不展示多套成功率。P95 无样本显示 `--`。

## 7. 运行层账号准入

`AccountMonitorService.listPool` 改用同一 `now` 调用 `account.IsSchedulableAt(now)`，再叠加账号/分组主动探测开关。这样临时冷却、余额耗尽配额、过载、限流和过期账号不会继续产生新的自动探测。已有历史探测结果不删除，由窗口聚合规则处理。

每轮自动监控结束后，运行器通过 `account_monitor_bucket_terminals` 对上一完整桶执行一次分组结算；当前桶仅在最后一分钟结算。运行器另有每分钟 watchdog 重复执行同一结算 pass，覆盖偶发漏跑；该结算以 `(group_id, bucket_start)` 唯一键幂等写入，账号全部被门禁排除或探测失败时仍写入 `failed` 终态；读取侧将未能落库的历史桶合成为一个失败逻辑请求并告警。

## 8. 失败、空值与安全

- 探测失败不会被静默删除：全失败探测桶仍是一次失败代理请求。
- 探测自身无法执行、状态未知、无可用账号、reader 报错或持久化失败的桶都必须落为一个失败终态；不得跳过、不选中或在正常响应中返回无样本。
- 账号级探测可以因原生调度门禁被排除，但这不能取消分组级桶终态：只要该桶无真实请求，分组必须得到一个 `0/1` 失败兜底。
- 真实网关错误进入真实分母，不因有成功 usage 行而掩盖最终错误。
- 所有查询仍受当前可见分组限制；真实请求事实 scope 使用已知历史成员，探测调用 scope 仍受当前可调度账号门禁限制，不跨租户聚合。
- 不返回请求体、提示词、密钥、上游地址或完整错误正文。

## 10. 场景化验收

| 场景 | 预期 |
| --- | --- |
| 桶内 2 个真实成功、20 个探测结果 | 只计 2 个真实请求 |
| 桶内 1 个真实失败、探测成功 | 只计 1 个真实失败，成功率 0% |
| 无真实请求、3 个探测成功、5 个探测失败 | 计 1 个逻辑成功请求，成功率 100% |
| 无真实请求、全部探测失败 | 计 1 个逻辑失败请求，成功率 0% |
| 无真实请求、探测未产生持久化结果 | fail-closed 计 1 个逻辑失败请求，并记录完整性故障 |
| 当前桶无真实请求且未进入最后一分钟 | 暂不结算；进入最后一分钟后必须落一个探测成功/失败终态 |
| 已知余额不足/临时冷却账号 | 不加入新的自动探测池 |
| 成功请求只有 TTFT 或只有总耗时 | 分别独立进入对应 P95 样本集 |
| 窗口内没有可结算桶（例如刚进入窗口且当前桶尚未到结算时点） | 暂无可结算数据；若窗口已有已关闭桶却没有终态，必须按缺失探测 `0/1` 处理并告警 |
