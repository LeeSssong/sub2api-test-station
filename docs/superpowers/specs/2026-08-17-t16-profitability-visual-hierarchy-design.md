## 2. 问题与现状证据

当前经营页已经复用 Sub 原生 `usage_logs`，支持 today/24h/7d/31d、全站/分组/账号层级、排序、原生有效账号成本、用户扣费、利润、利润率和独立探测成本。当前聚合 SQL 只按 `group_id/account_id` 汇总，因此页面不能区分：

- 管理员或内部使用产生的真实上游成本；
- 对外业务产生的上游成本与营收；
- 业务营收承担全部成本后的真实净利润。

现有 `usage_logs.user_id` 关联 `users.id`，`users.role` 的管理员值为 `admin`。代码中没有不可变的历史 actor 类型字段。用当前 `users.role` 分类会让用户角色变更影响历史区间分类，这是已知可见限制；用 `actual_cost=0` 或其他金额猜身份会把免费业务、赠送或异常流水误判为内部流量，因此禁止。

## 3. 目标

1. 默认展示全部真实结果，保留全站、分组、账号和时间范围切换。
2. 摘要突出业务营收、总消耗、净利润、对外毛利率，并单列内部运营消耗，说明其已包含在总消耗中。
3. 账号明细只展示运营消耗、业务消耗、业务营收、总消耗、净利润五项。
4. 所有金额继续来自同一次只读 `usage_logs` 快照和同一原生有效账号成本公式。
5. 桌面保持清晰层级；390px 下摘要两列、页面无横向溢出，表格横向滚动仅发生在表格容器内。

## 4. 非目标

- 不改变价格、倍率、`actual_cost`、`account_cost` 或其写入逻辑。
- 不改变原生有效账号成本公式：`COALESCE(account_cost, COALESCE(account_stats_cost, total_cost) * COALESCE(account_rate_multiplier, 1))`。
- 不创建第二账务事实源，不使用历史 evidence 或人工覆盖作为经营页主事实。
- 不做数据库迁移、历史回填、生产数据修改或账务重算。
- 不建立不可变 actor 类型字段；该能力如后续需要，必须另立任务并明确迁移与历史策略。
- 不删除现有 API 的兼容字段，不改探测成本采集或其他页面。
- 不使用 GitHub Actions。

## 5. 方案比较

### 方案 A：只读关联当前用户角色（采用）

聚合 SQL `LEFT JOIN users u ON u.id = ul.user_id`，只有 `u.role = 'admin'` 计入内部运营，其余流水计入对外业务。优点是最小扩展、零迁移、零写入，且不猜金额；缺点是角色变更会重分类历史流水。页面通过稳定说明公开这一限制。

### 方案 B：新增不可变 actor 类型

在每条 `usage_logs` 写入时记录 actor 类型。新流水准确，但需要迁移、写路径修改和旧数据处理；旧流水没有可靠回填依据。该方案超出 T16 边界。

### 方案 C：按 `user_cost=0` 推断内部流量

实现简单，但会把免费业务、赠送和零扣费异常流水误判为内部使用，与明确身份边界冲突，不采用。

## 6. 数据与公式契约

### 6.1 分类

- `is_internal := COALESCE(u.role, '') = 'admin'`。
- 只有明确管理员角色属于内部运营。
- 普通用户、其他角色和缺失角色均属于业务侧，避免把未知身份静默归入内部。
- 该分类读取查询执行时的当前角色，不宣称为请求发生时的不可变历史角色。

### 6.2 聚合字段

每个 `group_id/account_id` 聚合行新增：

- `operational_cost`：内部流水的有效账号成本之和。
- `business_cost`：业务流水的有效账号成本之和。
- `business_revenue`：业务流水 `actual_cost` 之和。

应用层派生：

- `total_cost = operational_cost + business_cost`。
- `net_profit = business_revenue - total_cost`。
- `external_margin = net_profit / business_revenue`；业务营收为 0 时返回 `null`。

为兼容既有消费者，现有字段保留并与新语义对齐：

- `cost = total_cost`。
- `user_cost = business_revenue`。
- `profit = net_profit`。
- `margin = external_margin`。
- `revenue` 与 `expense` 继续由服务层兼容派生，不新增事实源。

### 6.3 JSON 字段

`FinancialAmounts` 新增稳定 snake_case 字段：

- `operational_cost`
- `business_cost`
- `business_revenue`
- `total_cost`
- `net_profit`
- `external_margin`

后端同时保留现有 `cost/user_cost/profit/margin`。前端归一化器兼容 snake_case 与 Go 默认 PascalCase 输入，并在新字段缺失时从旧字段形成保守兼容值：`operational_cost=0`、`business_cost=cost`、`business_revenue=user_cost`。

## 7. 端到端流程

1. 管理员请求既有 `/api/v1/admin/operations/account-financial?range=...`。
2. repository 在原 repeatable-read、read-only 事务中读取账号、分组、余额和聚合流水。
3. 聚合查询关联 `users` 当前角色，并在数据库内拆分三项原始金额。
4. service 按全站、账号、分组、分组内账号四层累加三项金额，再统一派生总消耗、净利润和对外毛利率。
5. 前端继续使用既有 API 和范围/分组状态；摘要改为经营结果层级，账号区域改为紧凑表格。

## 8. 页面设计

### 8.1 摘要

摘要固定五项：

- 业务营收：蓝色语义。
- 总消耗：琥珀色语义。
- 净利润：正值绿色、负值红色。
- 对外毛利率：正值绿色、负值红色，无业务营收时显示 `-`。
- 内部运营消耗：紫色语义，副文案明确“已包含在总消耗中”。

摘要不再把请求数、Token、本站探测成本或未消费余额作为本页主卡片；后端兼容字段仍保留，其他功能不受影响。

### 8.2 账号明细

- 使用一个未嵌套卡片的紧凑表格，列为账号、运营消耗、业务消耗、业务营收、总消耗、净利润。
- 账号列保留名称及平台/类型元信息。
- 净利润为负时使用警示颜色，其余金额使用对应语义颜色。
- 排序选项收敛为上述五项金额，默认按净利润降序；排序状态在范围、分组和刷新间保持。
- 390px 时表格容器允许横向滚动，但 `main` 页面本身保持无横向溢出。

### 8.3 身份说明

在摘要下提供短说明：内部运营按当前管理员角色识别，历史角色变化可能影响历史区间分类。该说明陈述事实，不引入新的操作或回填入口。

## 9. 失败与兼容语义

- 用户角色关联不命中时归入业务侧；不会丢失成本或营收。
- repository/事务错误继续使既有 API 返回非成功，不返回部分经营结果。
- 探测聚合失败仍按现有独立字段降级，不影响本任务三项原生流水金额。
- 旧响应缺少新字段时，前端使用兼容回退，不产生 `NaN` 或空白。
- 旧调用方继续读取 `cost/user_cost/profit/margin`，数学值与新经营字段一致。
