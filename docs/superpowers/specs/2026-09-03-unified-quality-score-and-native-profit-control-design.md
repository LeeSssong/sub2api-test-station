# 统一质量评分、移除分组权重覆盖与原生利润控制规格

## 1. 文档状态

- 日期：2026-09-03
- 状态：APPROVED，待实施
- 任务性质：调度架构收敛；仅允许在独立候选 worktree 实施，未授权合并、推送、部署或写生产配置
- 相关现状：T114 多窗口服务质量评分设计、T52/T54 分组调度参数页、T68 分组调度运营优先级与策略护栏
- 用户确认目标：
  1. 移除管理员按分组自由修改的旧 weight_overrides。
  2. 所有文本分组使用同一套质量评分定义。
  3. 分组差异通过价格/利润策略、候选池和硬门禁表达。
  4. 利润不进入质量评分，改由 Sub 原生利润控制实现。

## 2. 问题与当前行为

当前 OpenAI 调度存在两层可调评分语义：

1. T114 定义统一的多窗口质量分，使用成功质量、P50/P90 TTFT、输出速度和实时负载。
2. 原生 scheduler 仍接受全局及分组 weight_overrides，按 priority、load、queue、error_rate、ttft、upstream_cost、previous_response、session_sticky 等字段改变总分。

当前候选评分先把各项指标归一化，再乘权重求和；公平因子另行加入，粘性与 previous response 在启用时还会额外加分。生产分组 20 已出现 session_sticky=4、previous_response=5、upstream_cost=3 而 ttft=0.5 的配置，导致低成本和连续性偏好可以压过响应质量。

生产分组为 GPT-Pro、GPT-Plus、【专属】GPT-PRO、GPT-特惠和生图。文本调度主要覆盖前四组；生图不属于本规格。

## 3. 第一性原理

账号调度必须分开回答：

1. 资格：账号能否被选，包括状态、能力、余额/利润、冷却、故障域、并发和重放安全。
2. 质量：在有资格账号中哪个更可能提供更好的体验，包括成功率、首字、输出速度和实时负载。
3. 连续性：是否需要延续既有会话或响应上下文，包括 previous_response_id 和普通 session sticky。

本设计的分层语义：

- 资格由 Sub 原生资格查询、原生利润控制和既有安全门禁决定；
- 质量由所有文本分组共享的一套统一动态质量分决定；
- 连续性由协议硬约束或条件性 sticky 优先决定，不使用任意大额质量加分永久压过质量；
- 价格和利润是商业准入条件，不是用户质量分。

## 4. 目标

1. 所有普通 OpenAI 文本分组使用相同的质量分定义、窗口、归一化、置信度回退和排序语义。
2. 删除管理员按分组自由覆盖质量权重的产品入口、持久化语义和运行时应用路径。
3. 保留统一评分公式中的固定产品权重，避免把权重隐式散落到代码分支。
4. 通过 Sub 原生分组倍率、profit_control_enabled、profit_min_margin、profit_safety_buffer 及原生利润终检表达商业差异。
5. 通过候选池表达组边界和可参与账号集合，不让候选池参数改变质量指标定义。
6. 通过硬门禁表达账号不可用、能力不匹配、余额/利润不合格、冷却、故障域、容量和不可安全重放等条件。
7. 保持 T114 的不设 TTFT 硬淘汰线和 60 秒慢首只影响后续排序语义。
8. 保留旧配置的读取/审计兼容，避免旧设置导致启动失败或静默切换到另一套评分。

## 5. 非目标

- 不修改用户价格、分组倍率、订阅权益或组名称。
- 不把成本、利润、采购价、倍率或利润率写入质量分。
- 不新增第二套账务、成本或质量事实源。
- 不修改生图、WebSocket、非 OpenAI 平台或协议强制绑定调度。
- 不取消原生利润控制、余额检查、并发槽、冷却、故障域和安全重放门禁。
- 不因 TTFT 慢取消当前上游请求、创建第二 attempt 或自动切号。
- 不自动迁移账号、修改账号分组、修改生产设置或删除历史数据。
- 不使用 GitHub Actions，不改变发布链。

## 6. 方案比较

### 6.1 方案 A：保留分组权重覆盖

每个分组继续独立设置 TTFT、成本、粘性等权重。

优点：短期可调，兼容现有界面。缺点：同一账号在不同分组拥有不同质量定义；成本与质量混分；调参容易造成不可解释排名；与 T114 统一质量分重复。不采用。

### 6.2 方案 B：完全删除权重

删除所有权重，按多个指标字典序或平均值排序。

优点：界面简单。缺点：数学上仍然存在隐含权重；字典序会让单一指标支配排序；无法表达成功率和尾部 TTFT 的相对重要性；加入新指标会改变旧语义。不采用。

### 6.3 方案 C：统一固定质量分 + 原生商业/安全分层（推荐）

所有文本组使用 T114 统一质量分；固定权重由版本化代码或配置常量管理，不提供分组自由覆盖。组倍率与原生利润控制负责商业准入，候选池负责组边界，硬门禁负责安全和正确性，普通 sticky 只做条件性连续性优先。

优点：评分可解释、跨组可比较、成本与体验解耦，能吸收多窗口 TTFT 与成功率信号。代价：管理员失去按组即时调权能力，需要迁移旧覆盖设置并提供只读兼容/审计视图。本规格采用方案 C。

## 7. 目标架构与端到端流程

请求解析/协议约束
-> Sub 原生组与账号资格
-> 原生利润控制与成本准入
-> 组候选池边界
-> 统一多窗口质量快照
-> 条件性 previous/session 连续性处理
-> 质量分排序与自适应 Top-K
-> 原生并发槽原子获取
-> 上游调用与既有安全重试/failover

### 7.1 资格层

先过滤不能参与的账号：

- active、schedulable，且未被临时 blocker/cooldown 排除；
- 支持请求模型、端点、协议和必要能力；
- 不违反组模型清单、OAuth/API Key 类型和隐私要求；
- 通过 Sub 原生利润控制的预检/终检。利润控制失败的账号不得通过高质量分重新进入；
- 未超过并发、等待队列和故障域保护；
- 请求尚未产生语义输出、usage 或不可逆副作用时，才允许后续安全重放。

质量分永远不能把不合格账号重新加入候选池。

### 7.2 分组差异的具体表达

#### 价格与利润策略

- 分组 rate_multiplier 继续决定用户侧价格和倍率；
- Sub 原生 profit_control_enabled、profit_min_margin、profit_safety_buffer 继续决定账号是否满足最低利润；
- 原生利润终检在抢到并发槽后再次确认，失败则释放槽位并重新选号；
- 质量分不读取、不加权、不补偿成本或利润；
- 低价组不是低质量评分组，而是拥有不同价格和利润准入边界的同一质量排序。

例如 GPT-特惠可保持较低 rate_multiplier 并设置更严格的原生利润下限；这会减少候选，但剩余候选仍按统一质量分排序。

#### 候选池

候选池只决定哪些账号进入该分组的比较集合：

- 账号与组的原生关联、平台、模型能力、账号类型和显式组规则；
- all_eligible、hybrid 等池模式只影响合格候选数量和公平探索；
- Top-K 是合格候选排序前缀，不是另一套质量分；
- 候选池不能按分组改变 TTFT、成功率、输出速度的定义；
- 候选池为空时按既有无账号或容量错误返回，不绕过利润和安全门禁。

例如 【专属】GPT-PRO 可以只包含专属账号，GPT-特惠可以只包含满足该组模型、倍率和原生利润边界的账号；两组内部仍使用相同 quality_score。

#### 硬门禁

以下条件不参与高分抵消：

- 账号被禁用、冷却或故障隔离；
- 模型、协议或能力不匹配；
- Sub 原生利润控制不通过；
- 原生并发槽不可获得且等待策略不允许；
- 故障域保护阻止继续集中；
- previous_response_id 需要 API Key 或同账号能力；
- 已输出、usage 已知、工具副作用或客户端已断开，禁止重放或换号。

### 7.3 统一质量分

所有普通 OpenAI 文本分组共享：

quality_score =
  success_score × 0.40
  + p50_ttft_score × 0.24
  + p90_ttft_score × 0.16
  + output_rate_score × 0.10
  + live_load_score × 0.10

- 数据窗口互斥：W1=[now-1h, now)、W24=[now-24h, now-1h)、W7=[now-7d, now-24h)；
- 窗口权重：50/30/20，并按有效样本和置信度向长期窗口回退；
- 成功率使用置信度平滑和非线性曲线；
- TTFT 同时使用 P50 与 P90，首字只认客户端可消费的有效语义内容；
- 输出速度使用可见输出后的 output_tokens / duration，不能用总耗时替代；
- 实时负载使用原生并发剩余比例与等待队列反向分；
- 缺少有效证据时使用中性值并标记置信度，不把未知当成零分；
- 60 秒慢首观测只写进程内右删失证据，影响后续快照，不取消当前请求。

固定系数属于统一质量定义，不是管理员按组策略。后续调整系数必须通过版本化规格、直接测试和发布流程完成。

### 7.4 连续性语义

- previous_response_id 的协议要求优先于质量分；不满足能力的账号被排除；
- 普通 session sticky 仅在账号仍合格、未冷却、未触发质量逃逸且可获取槽位时优先尝试；
- sticky 不再通过分组 session_sticky 大额加分永久压过质量；
- 账号质量恶化、原生利润终检失败、并发满或能力不匹配时清除或绕过 sticky；
- sticky 保留/逃逸原因继续进入现有调度决策事件。

## 8. 配置、接口与数据契约

### 8.1 删除的运行时语义

以下字段不再参与 OpenAI 文本质量排序：

- openai_advanced_scheduler_group_overrides[*].weight_overrides
- 全局或分组 upstream_cost 质量权重
- 分组 ttft、session_sticky、previous_response 等自由覆盖

### 8.2 兼容读取

- 历史 JSON 可以读取并展示为 legacy override ignored，但不得应用到运行时质量分；
- 保存新策略时不得继续生成 weight_overrides；
- 旧设置不立即物理删除，避免审计和回滚失去证据；后续清理另立任务；
- compiled_snapshot 仅保留统一质量版本、窗口、候选池模式和硬门禁/连续性策略摘要，不保留会改变质量定义的分组权重；
- 管理 API 返回统一评分版本和只读固定系数，明确字段不可编辑。

### 8.3 管理界面

- 移除分组权重输入、权重总和校验和调大/调小权重交互；
- 保留统一评分说明、当前质量分拆解、样本窗口、置信度、候选池模式和原生利润控制状态；
- 分组设置只允许选择候选池和连续性策略等非质量定义选项；
- 历史覆盖仅作为只读兼容信息显示，不提供重新保存入口。

### 8.4 事件与可观测性

调度决策事件继续记录：

- 统一质量版本；
- 候选数、合格数、effective Top-K、最低质量阈值；
- 每个候选的质量分拆解和置信度；
- 原生利润控制拒绝计数和非敏感原因；
- sticky 保留/逃逸原因；
- 选择层、选中账号与排名。

事件不得记录 API Key、完整请求体、凭据或完整上游响应。

## 9. 失败、安全与兼容语义

- 原生利润控制不可用或结果 unknown 时 fail-closed，不以质量分放行；
- 质量快照读取失败时使用现有中性或陈旧快照策略，不把所有账号误判为高分；
- 所有候选质量证据缺失时仍从合格池选出相对最优账号；
- 不设置 TTFT 硬淘汰线；TTFT 只影响排名和后续慢速证据；
- 上游错误继续沿用既有 401/403/429/5xx failover、cooldown、故障域和安全重放分类；
- 请求已开始语义输出、已知 usage、工具副作用或客户端断开时，禁止自动换号；
- 旧配置存在非法或未知权重时，忽略质量覆盖并记录兼容诊断，不阻断服务；
- 读取历史配置不得触发数据库写入、账号迁移或分组变更。

## 10. 迁移与发布

- 不新增数据库表、不回填历史质量数据、不删除旧设置；
- 运行时先切换为统一质量评分解释器，再在独立后续任务中清理旧 JSON 字段；
- 发布前完成旧设置读取、忽略覆盖、统一分组排序、利润控制 fail-closed、sticky 条件处理和旧客户端 API 兼容测试；
- 本规格不授权主站或验收站发布；任何部署仍需从干净且已推送的根 main，并匹配验收站全局授权路径；
- 回滚方式：恢复上一已验证版本或槽位；旧设置字段继续保留，因此回滚不依赖数据恢复。

## 11. 场景化验收矩阵

| 场景 | 预期 |
|---|---|
| 四个文本组均有多个合格账号 | 使用同一质量公式、窗口和归一化；仅候选集合不同 |
| 两个账号质量相同但价格不同 | 不因成本/利润进入质量分；由原生利润资格和组倍率表达差异 |
| 低价账号更便宜但 TTFT 明显更慢 | 若仍通过原生利润控制，按统一质量分排序，不因低价额外加分 |
| 账号利润控制失败 | 在资格或终检阶段排除，不能靠高质量分进入 |
| 分组旧 JSON 含 weight_overrides | 可读取并显示兼容诊断，但运行时不应用 |
| 管理员尝试保存分组质量权重 | API 拒绝或忽略旧字段，不产生新的覆盖配置 |
| sticky 账号质量恶化、冷却或并发满 | 绕过或清除 sticky，选择合格池中的最高质量账号 |
| previous_response_id 绑定 API Key 能力 | 只选择满足协议能力的候选，不通过评分补偿 |
| 所有账号 TTFT 都慢 | 仍选择相对质量最高者，不因质量分低而整体不可用 |
| 60 秒无首语义输出 | 记录慢速证据，影响后续排名；当前请求不取消、不换号、不创建第二 attempt |
| 已有语义输出后上游断流 | 按安全重放语义终止或返回流内错误，不自动换号 |
| 质量快照暂时不可用 | 使用既有中性或陈旧快照策略，利润和安全门禁仍有效 |

## 12. 测试策略

### 单元与服务测试

- 统一质量公式在所有文本分组产生相同分值；
- 旧 weight_overrides 无论分组内容如何变化都不影响运行时分数；
- 成本和利润字段不进入质量分；
- 原生利润控制拒绝在资格和终检路径均 fail-closed；
- 候选池只改变候选集合，不改变分数公式；
- sticky、previous response 和硬门禁优先级；
- 多窗口、置信度回退、P50/P90 TTFT、输出速度和 60 秒右删失；
- 统一质量版本和拆解事件字段完整，敏感字段排除。

### API 与前端测试

- 管理接口不再接受或持久化新的分组质量权重；
- 历史 JSON 可读，返回兼容诊断和统一评分版本；
- 设置页移除可编辑权重控件，保留只读评分说明和原生利润状态；
- 旧客户端省略新字段时行为保持兼容。

### 验证范围

- 直接相关 Go service/repository/handler 测试；
- SettingsView/调度设置相关前端测试；
- go build ./cmd/server、前端 typecheck/build、gofmt、diff-check；
- 不执行无关全仓压力、长时间 soak 或跨平台穷举。

## 13. 上线后指标与回滚条件

上线后按分组和全站观察：

- 质量分排序与实际选中排名的一致性；
- P50/P90 TTFT、成功率、输出速度和实时负载；
- 原生利润控制拒绝率、实际成本和利润率，全部来自 Sub 原生流水/利润口径，不回灌评分；
- sticky 保留率、逃逸率、第一名流量占比；
- 账号集中度、候选池耗尽率、failover 成功率；
- 旧覆盖配置被忽略数量和兼容诊断数量。

触发回滚或暂停条件：

- 相同流量结构下最终成功率下降超过 1 个百分点；
- P50/P90 TTFT 明显恶化且不是上游整体退化；
- 原生利润控制拒绝率异常升高或出现放行不确定状态；
- 质量分与实际调度决策不一致；
- 旧客户端或设置读取出现兼容性破坏。
