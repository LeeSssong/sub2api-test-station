# Spec: T4 `pool` 与可用候选诊断口径

## 1. 问题与当前行为

OpenAI 调度错误可能同时出现 HTTP 503 和 `pool=25`。当前 `pool` 表示本次调度扫描得到的原始账号数量，发生在模型、分组、额度、运行时状态、传输能力、健康门、利润门和并发槽位等过滤之前。它不表示最终可调用账号数量，也不表示实际已经尝试的账号数量。

当前部分负载均衡路径会附带 `filtered:<reason>=<count>`，但统一质量调度路径在候选耗尽时主要输出原始 `pool`，导致管理员误判“25 个账号都可用但仍返回 503”。

## 2. 目标与非目标

目标：让管理员能够区分原始账号池、资格过滤结果、实际尝试结果和上游失败结果，并保持现有 HTTP 语义和 Sub 原生调度行为不变。

非目标：不改变选号顺序、切号次数、账号状态机、并发限制、利润门、用户错误文案或监控成功率口径。

## 3. 诊断契约

调度诊断应区分以下字段：

- `pool`：进入本次调度扫描的原始账号数。
- `eligible`：通过静态/运行时资格过滤、但尚未代表槽位获取成功的候选数。
- `attempted`：实际发起上游请求的账号数；仅调度失败时可为 0。
- `filtered`：按原因聚合的账号排除数量。
- `upstream_failed`：已发起上游请求但失败的账号/尝试数量，适用于请求终态诊断。

字段语义必须明确：

- `eligible=0`：调度阶段没有候选账号。
- `eligible>0 && attempted=0`：候选存在，但可能因并发槽位、二次数据库复核或调度预算未能发起请求。
- `attempted>0 && upstream_failed>0`：已经进入上游请求与切号链路。
- `pool` 不得单独作为“可用账号数”展示或解释。

## 4. 用户与管理员语义

用户继续只收到现有脱敏 503/502 结果。管理员诊断、错误详情和运维日志可以看到上述阶段字段及过滤原因，但不得包含 API Key、私钥、完整凭据或敏感请求体。

分组视图按逻辑请求最终终态展示；账号过滤细节保留在管理员诊断和账号视图，不作为用户可见指标。

## 5. 验收矩阵

1. 原始池 25、资格候选 0 时，错误不能再被解释为 25 个可用账号。
2. 原始池 25、资格候选 3、实际尝试 0 时，诊断能区分“候选存在但未发起请求”。
3. 实际尝试 2、上游失败 2 后候选耗尽时，诊断能表明已进入上游失败链路。
4. 现有 `model_not_found`、本地容量 503、上游 502/503 和用户脱敏文案保持兼容。
5. 过滤原因计数可稳定聚合，字段缺失时不伪造为 0 个上游失败。

## 6. 测试与发布边界

测试覆盖调度器候选过滤、统一质量调度候选耗尽、槽位不可获取和上游失败终态的诊断字段。不得借本任务修改调度策略或生产账号状态。无迁移、无配置变更、无生产数据回填。
