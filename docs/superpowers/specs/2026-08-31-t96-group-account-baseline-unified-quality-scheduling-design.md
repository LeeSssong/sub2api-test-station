## 2. 问题与当前行为证据

### 2.1 当前选择不是目标中的确定性质量排序

当前 `openai_account_scheduler.go` 的文本选择顺序包含 forced account、`previous_response_id`、guardian、普通 session sticky 和 load-balance。load-balance 又综合 priority、负载、队列、错误率、TTFT、reset、quota headroom、成本、公平性和 sticky bonus，并在 Top-K 中使用带随机熵的加权顺序。因此相同资格池的相同请求不保证按 `成功率 -> P95 TTFT -> U -> ID` 得到同一候选序列。

当前 `account_groups.priority` 还会覆盖 `accounts.priority`。即使管理员手工排好账号，只要旧 priority、权重、fairness、探索或普通 sticky 仍参与，就会产生第二套排序。

### 2.2 当前恢复预算与已确认语义冲突

当前 OpenAI handler 会优先执行同账号重试，池模式的 `pool_mode_retry_count` 也可能触发同账号重试。全局预算又被硬限制为最多 4 次 attempt、最多切换 2 个账号、最多 2 个故障域和 5 秒重试墙钟。

目标语义已经确认：`extra_retry_count` 是整个逻辑请求在首次 attempt 之后可使用的额外跨账号恢复次数，不是每账号次数；安全失败后直接排除已尝试账号并选择下一名。现有“同账号先重试”和统一上限不能满足特惠组最多 4 个不同账号的尝试链。

### 2.3 当前利润门不是完整的可用性优先

原生分组利润字段和公式已存在，但当前账号成本直接读取 `accounts.rate_multiplier`；T95 之前不能表达比例型上游和 OAuth 自购账号的统一有效成本倍率 `U`。当前利润门只在配置读取失败时 fail-open；当所有可用账号均超过利润阈值时会耗尽候选并返回 503，不满足“先保利润、无合格账号时保可用性”的产品决策。

### 2.4 生图与 T100 边界

当前图片选择入口仍可进入高级 scheduler。目标要求生图只使用 Sub 原生基础调度，不消费本文的文本质量排序、组级额外恢复次数或利润兜底。

T100 已从请求链删除自定义 admission/slow-session 控制。`AcquireOpenAIAdmission` 即使还有残留定义，也不是有效请求链能力。T96 禁止重新接线、复制或变相恢复任何这类账号限制。

### 2.5 数据基线

最近 7 天只读排名报告为 `docs/superpowers/reports/2026-08-31-t96-account-quality-ranking.md`：原快照包含 65 个文本账号和 7 个生图账号，29,490 次可归属物理 attempt，其中 25,320 成功、4,170 失败。

原快照截止后新增 OAuth 账号 `293`。2026-08-31 02:40:59 +08:00 的补充只读快照中，该账号有 570 个 `complete + actual_cost > 0` 成功样本；T100 已证明的 698 个自定义 admission 本地拒绝不属于上游 attempt，排除；发布后另有 1 个失败样本，保守成功率为 570/571，即 99.82%；成功样本截尾平均 TTFT 为 3,401ms、耗时为 8,991ms；自购有效成本 `U=12/500=0.024`。因此本规格把 `293` 纳入 Pro 档。当前基线为 66 个文本账号和 7 个生图账号，共 73 个未删除 OpenAI 账号。

## 3. 目标

1. 请求先确定目标分组，再只读取管理员手工维护的该组固定账号池。
2. 所有普通非生图组使用同一选择骨架，不再按分组配置不同质量权重或随机策略。
3. 完成原生资格、T82 健康和利润优选后，严格按账号级 `成功率 DESC -> P95 TTFT ASC -> U ASC -> 账号 ID ASC` 生成确定候选序列。
4. 安全失败对用户隐藏：排除已尝试账号，按序切换下一账号，直到成功、组级额外恢复次数耗尽或池耗尽。
5. 任何已计费、部分输出、有副作用或计费状态未知的 attempt 不可重放、不可切号，保留事实并按原生账务向用户计费。
6. 每个物理 attempt 在账号监控中保持真实可见；分组性能监控继续展示逻辑请求最终用户可见结果。
7. 复用 Sub 原生账号槽位、等待队列、超时和释放，不增加任何账号限制字段或旁路机制。
8. 生图保持 Sub 原生基础调度，与文本定制调度完全隔离。

## 4. 非目标

- 不按运行时表现自动把账号加入、移出或迁移到任何分组。
- 不在模型层生成排名；模型只参与能力资格判断。
- 不设置 85% 或其他成功率硬淘汰线；样本不足 30 和无证据账号仍参与，按空值规则排序。
- 不以总耗时作为文本选路键；P95 耗时继续展示和观测，但不参与本次排序。
- 不使用旧 priority、加权分数、Top-K、随机探索、公平性、饥饿补偿或普通 session sticky 改写候选顺序。
- 不新增账号 admission、slow-session、并发、排队长度、排队超时或首输出前租约字段。
- 不另建利润参数、利润表或第二账务源；最低利润率和安全缓冲仍只在原生 Groups 页面维护。
- 不保证所有上游错误都对用户不可见。不可安全重放、客户端取消、请求截止或账号池耗尽仍会返回错误。
- 不在本任务修改 T95 的账号成本录入字段、公式和 UI。

## 5. 方案比较与选择

| 方案 | 做法 | 结论 |
| --- | --- | --- |
| A. 保留现有加权/Top-K，只调参数 | 把成功率权重调高，继续使用负载、队列、成本、sticky、随机和分组预设 | 无法保证词典序和重复请求确定性；参数之间继续相互稀释，拒绝 |
| B. 重写完整调度器 | 新建并发、队列、重试、粘性、利润和健康子系统 | 会复制 Sub 原生能力并重新引入 T80 类风险，拒绝 |
| C. 原生能力内核 + 统一质量策略层 | 保留原生资格、槽位、协议绑定和 T82 健康安全能力；替换普通文本候选排序与恢复预算，扩展原生利润门 | 满足确定排序、可用性、成本和最小改动要求，采用 |

方案 C 不是退回官方默认，也不是保留现有所有定制。它把已经验证有效的官方能力和 T82 定制保留下来，同时删除与本轮第一性原理冲突的多因子随机选路、普通 sticky 和同账号优先重试。

## 6. 术语与不变量

- **逻辑请求**：用户发起的一次请求；可包含多个物理 attempt，最终只产生一个用户可见终态。
- **物理 attempt**：对一个具体上游账号的一次真实调用。账号成功率以它为单位。
- **固定账号池**：管理员通过 Sub 原生分组账号关系维护的集合；运行时只读。
- **资格账号**：通过删除状态、平台、账号类型、status、schedulable、模型/协议能力、T82 运行时健康、请求级排除和原生账号槽位检查的账号。
- **协议强制绑定**：`previous_response_id`、guardian parent、WebSocket/工具调用续链等为了协议正确性必须保持的账号亲和。
- **普通 sticky**：仅为了缓存或会话亲和而偏向旧账号的非强制绑定；本模式不得覆盖质量排序。
- **额外恢复次数**：`extra_retry_count`，首次上游 attempt 之外允许的额外跨账号 attempt 数。
- **利润兜底**：没有利润合格账号时，从其余可用账号中继续选择，同时记录绕过原因。
- **原生账号槽位**：仅指 `accounts.concurrency` 及 Sub 已有等待队列、等待超时与释放机制，不包括 T80 admission。

以下是不变量：

1. 一个普通文本逻辑请求不得对同一账号执行两次上游 attempt。
2. 已尝试账号必须进入该逻辑请求的排除集。
3. 无上游 attempt 的本地资格/槽位跳过不消耗 `extra_retry_count`。
4. 任何不可安全重放结果立即终止恢复链。
5. 账号池关系、账号 status/schedulable 和账号并发只允许管理员通过原生入口修改。
6. Pro 与专属 Pro 的账号池必须逐项相同。

## 8. 质量数据口径

### 8.1 唯一事实源与窗口

- 质量窗口固定为滚动最近 7 天。
- 运行时排名只复用 `usage_logs`，不新增质量事实表。`ops_error_logs` 继续用于管理员诊断，但当前没有稳定的物理 attempt 关联字段，不得与 `usage_logs` 拼接后冒充逐 attempt 排名事实。
- 只统计真实上游物理 attempt；主动探测不进入文本运行时排名。
- 账号层跨分组、跨文本模型聚合；模型能力只在请求资格阶段判断。
- 新请求以 `usage_logs.attempt_id` 关联物理 attempt，以 `logical_request_id` 关联逻辑请求；账务幂等继续复用现有 attempt 派生 `request_id` 与 `api_key_id` 唯一边界。不得宣称 `attempt_id` 自身具有数据库全局唯一约束。
- 同一账号、同一物理 attempt 只计一次。历史缺少 `attempt_id` 的行仅在能由现有 `request_id` 明确证明“一行对应一次上游调用”时纳入；无法证明的旧记录不猜测、不拆分。
- `usage_completeness='unknown'` 不进入成功率分母；T100 已确认的历史本地 admission 拒绝必须排除，不能污染上游账号质量。
- 明确客户端责任、明确模型不支持和本站在选中账号前产生的本地模型不可用错误，沿用 T97 分类从本站服务质量分母排除。
- 2026-08-31 的一次性历史排名报告为补齐旧失败证据使用过 `ops_error_logs`；该历史取证方法不定义上线后的热路径 provider。

### 8.2 成功率

```text
成功 = usage_completeness = complete AND actual_cost > 0
成功率 = 成功物理 attempt 数 / 有效物理 attempt 总数
```

partial、可计费失败和真实上游失败进入分母但不进入分子。无有效 attempt 时成功率为 `NULL`，不得显示或排序为 0%。

### 8.3 P95 TTFT 与 P95 耗时

页面和 API 名称继续使用 `P95 TTFT`、`P95 耗时`。计算保持用户已确认的截尾平均：

1. 只取成功 attempt 中对应字段非空的样本。
2. 独立排序 TTFT 和耗时样本。
3. 两端分别去掉 `floor(n * 5%)` 个样本。
4. 对剩余样本求算术平均。

样本不足 30 不淘汰；没有 TTFT 样本时值为 `NULL`。P95 耗时仅用于展示、观测和运营复盘，不参与运行时选路。

### 8.4 有效成本倍率 U

T96 只消费 T95 的 `EffectiveCostProvider`：

- API Key 普通：`U=R`。
- API Key 比例型：`U=(实际成本/获得额度)*R`。
- OAuth 自购：`U=采购成本/预计可用额度`，1:1，无上游 `R`。

不得按账号 ID、上游名或 AI8 写死 `/10`。无效或缺失输入返回 `U=NULL`，不得按 0 成本处理。

### 8.5 快照与故障降级

- PostgreSQL 事实是唯一真相；实现提供内部 `OpenAIAccountQualitySnapshotProvider`，不得在每次热路径请求上重跑 7 天聚合。
- 使用现有 Redis/进程缓存模式保存可丢弃的只读快照；建议刷新周期 60 秒，任何缓存都不是第二事实源。
- 刷新失败时继续使用最后一次成功快照并标记 stale；冷启动且无快照时，所有质量字段按 `NULL` 排序，仍不得阻断请求。
- 质量快照只缓存 attempt、成功率、TTFT 和耗时统计，不包含 `U`。
- 候选构建时必须通过 T95 `EffectiveCostProvider` 读取各账号当前 `U`，并使用本次请求已经冻结的分组售卖倍率 `D`；管理员更新成本后不得继续用 60 秒质量缓存中的旧 U 排序。
- 获得原生槽位后的资格/利润终检重新读取当前有效 U；若 U 变化导致利润子集或候选顺序变化，释放槽位并按最新决策重新选择，不能只纠正利润门而保留过期的 `U ASC` 顺序。

## 9. 资格过滤与确定性排序

### 9.1 资格过滤顺序

1. 读取请求已经确定的目标分组及其固定账号池。
2. 排除 deleted、非 active、非 schedulable、平台/账号类型不符的账号。
3. 排除不支持请求模型、端点、协议或 capability 的账号。
4. 应用 T82 账号/模型/分组健康隔离、冷却、半开租约和当前逻辑请求排除集。
5. 处理协议强制绑定。绑定账号仍必须满足安全资格；不满足时沿用现有协议兼容/重建或安全失败语义。
6. 执行利润优选分区。
7. 对最终候选集执行统一质量排序。
8. 按序尝试 Sub 原生账号槽位；无法获得槽位的账号被跳过，不产生上游 attempt、不消耗恢复次数。

T82 的故障域证据继续用于健康判断和诊断，但“已观察到另一个故障域”不得作为第二排序器。只有已经被 T82 判定为 blocked/open 的账号或域才进入资格排除；故障域数量不得单独提前终止已获批准的组级恢复预算。

### 9.2 排序键

```text
success_rate DESC NULLS LAST
ttft_trimmed_mean_ms ASC NULLS LAST
effective_cost_u ASC NULLS LAST
account_id ASC
```

对同一分组，售卖倍率 `D` 是常数，因此“倍率差 `D-U` 从大到小”与“`U` 从小到大”等价。

必须满足：

- 成功率哪怕只高一点，也优先于 TTFT 和 U；不做置信区间、贝叶斯平滑或样本量加权。
- 成功率相同才比较 TTFT；TTFT 相同才比较 U；最后用 ID 稳定打破平局。
- `NULL` 不是 0。无证据账号整体排在有成功率证据的账号之后。
- 对同一资格集合重复选择，候选 ID 完整序列必须一致。
- 旧账号 priority、关系 priority、总耗时、实时负载、队列长度、旧权重、Top-K、随机数、探索、公平性、饥饿补偿和普通 sticky 都不得进入比较器。

### 9.3 sticky 与协议绑定

- 保留协议强制绑定：`previous_response_id`、guardian parent、WebSocket/工具调用续链及其他无法跨账号继续的协议状态。
- 普通 session sticky/cache bonus 不得覆盖统一质量排序，也不得作为 ID 之前的隐藏平局键。
- 由于确定性排序通常会持续选择同一健康首位账号，正常请求仍具备稳定缓存归属；发生安全切号时缓存亲和可能下降，这是恢复可用性的明确成本。

## 10. 原生利润保护与可用性兜底

### 10.1 配置与公式

继续只使用 Groups 原生字段：

- `profit_control_enabled`
- `profit_min_margin`
- `profit_safety_buffer`

账号利润合格条件：

```text
U <= D * (1 - profit_min_margin - profit_safety_buffer)
```

其中 `D` 使用本次请求已经冻结的有效分组售卖倍率/定价上下文，`U` 来自 T95。T96 不增加第二套最低利润率或安全缓冲字段。

### 10.2 两阶段候选集

1. 利润控制关闭：全部资格账号进入统一质量排序。
2. 至少一个利润合格账号：只在利润合格子集中排序和尝试。
3. 没有利润合格账号：从完整资格集排序和尝试，`profit_bypass=true`。
4. 利润配置读取失败：沿用原生 fail-open，从完整资格集排序，记录 `config_read_failed`。
5. `U` 缺失/非法：不能冒充利润合格；当仍有已知利润合格账号时不进入首选子集。全池无利润合格账号时允许可用性兜底，分别记录 `unknown_u` 或 `invalid_u`。

利润越线或 U 未知本身不得导致“无账号可用”503。槽位获得后的最新账号/定价终检也必须使用同一两阶段语义；终检失败时释放槽位并继续，不得泄漏槽位或重新变成硬 503。

## 11. 组级额外恢复预算

### 11.1 字段语义

在现有 `openai_advanced_scheduler_group_policies[group_id]` 中新增：

```json
{
  "extra_retry_count": 1
}
```

- 类型：整数。
- 合法范围：`0..3`。
- 含义：首次上游 attempt 之外，整个逻辑请求最多可执行的额外跨账号 attempt 数。
- 字段按分组读取，不按账号读取，不因切换账号重置。
- 未配置时默认为 0；上线配置通过现有 settings API 显式写入。
- API 非整数或越界返回 400，不保存部分配置。

### 11.2 当前值

| 分组 | `extra_retry_count` | 最多物理 attempt | 最多不同账号 |
| --- | ---: | ---: | ---: |
| GPT-Pro | 1 | 2 | 2 |
| 专属 GPT-Pro | 1 | 2 | 2 |
| GPT-Plus | 2 | 3 | 3 |
| GPT-特惠 | 3 | 4 | 4 |

所有普通文本组使用相同失败分类、切换算法和排序器；分组差异只有固定账号池、原生利润参数和本字段。

### 11.3 恢复状态机

```text
首次候选获得槽位并进入 Forward：不计 extra_used
  -> 上游成功：返回
  -> 不可安全重放：记账并返回原安全错误
  -> 可安全重放：记录失败 attempt，排除该账号
       -> extra_used 已达到预算：返回最终错误
       -> 按排名继续扫描未尝试候选
            -> 资格不符/利润终检否决/槽位不可得：跳过，不计 extra_used
            -> 池耗尽：返回池耗尽错误，不计 extra_used
            -> 获得槽位、通过终检并实际进入下一次 Forward：extra_used += 1
```

停止条件：

- 成功。
- 已计费、已输出、有副作用、明确不可重放或计费状态未知。
- `extra_retry_count` 耗尽。
- 账号池耗尽。
- 客户端取消。
- 请求上下文/既有端点截止时间到达。

普通文本路径不执行同账号上游重试；账号凭据中的 `pool_mode_retry_count` 不决定 T96 的恢复次数。OAuth token refresh、协议续链等内部正确性动作必须继续遵守不重复计费原则，但不能被包装为额外的普通同账号恢复机会。

`extra_used` 只计“首次真实上游 attempt 之后，已经实际进入 `Forward` 的跨账号 attempt”。选号、能力/健康过滤、利润否决、槽位 acquire、队列等待/超时、客户端在 Forward 前取消以及池耗尽均不消耗；attempt 序号允许因 Forward 前创建 metadata 而出现空洞，不能据此反推已调用次数。`switch_count` 同样只在新账号实际进入 Forward 时递增。

当前最多 2 次账号切换、最多 2 个故障域和 5 秒重试墙钟不得暗中压低上述预算。实施后：

- `MaxAttempts = 1 + extra_retry_count`。
- `MaxAccountSwitches = extra_retry_count`。
- 故障域只做健康/诊断，不作为第二个提前停止上限。
- 不新增独立 5 秒恢复截止；仅受客户端取消和现有请求上下文/端点截止时间约束。
- 跨账号切换不等待原账号的 `Retry-After`；该信息用于原账号冷却，下一账号立即按序尝试。

## 12. 失败、安全与计费语义

只有同时满足以下全部条件，才允许隐藏失败并切号：

1. 尚未向客户端输出任何语义内容。
2. 上游明确没有产生可计费 usage，且本站没有确认应计费用量。
3. 请求没有工具调用结果、写操作或其他副作用。
4. failure classifier 明确给出 `safe_to_replay=true`。
5. 计费状态不是 unknown。

以下任一情况立即不可重放：

- 已产生任何部分输出。
- 已产生 usage 或上游已扣费。
- 有工具/函数结果、上传后写操作或其他副作用。
- 上游/网络状态不足以证明未计费。
- `usage_completeness=partial`、`unsafe_to_replay=true` 或计费状态未知。

不可重放 attempt 必须：

- 保留 `usage_logs`/attempt 事实和账号归属。
- 按 Sub 原生账务规则向用户计费，不自动退款。
- 不再选择第二账号。
- 返回现有脱敏错误协议，并在管理员诊断中记录停止原因。

安全失败的中间物理 attempt 也必须进入账号监控。账号 attempt 成功率不会因为逻辑请求最终成功而抹掉中间失败；T93 分组性能监控则继续把整个逻辑请求计为一次最终成功。

## 13. 原生账号槽位与排队

- T96 只调用 Sub 原生账号槽位 acquire/wait/timeout/release。
- 账号并发上限继续读取现有 `accounts.concurrency`；等待队列和超时继续读取现有原生配置。
- 不新增 T80 lease、`admission_wait_ms`、slow-session guard、首输出前账号锁或任何同类状态。
- 即时获得、等待后获得、超时、取消、资格终检失败、利润终检、上游成功、上游失败和切号都必须保证 release 幂等。
- 槽位未获得不算物理上游 attempt，不消耗额外恢复次数；调度器继续尝试下一资格候选。
- 账号槽位全部不可得时沿用现有本地容量耗尽错误，不伪装为上游失败。

## 14. 生图路径

- image intent 直接走 Sub 原生图片 capability、账号选择、图片并发和原生失败处理。
- 不调用文本 `OpenAIAccountQualitySnapshotProvider`、统一文本比较器、文本 `extra_retry_count` 或文本利润兜底。
- 生图账号只来自生图原生池；普通文本请求不能选中生图账号。
- 图片失败继续保留 Sub 原生错误和重试语义，本任务不改图片计费或性能口径。

候选决策至少包含有序候选、排除和最终选择，不新增敏感信息。比较器消费的 U 必须来自本次候选构建，不能来自质量快照。

## 16. 可观测性

每次逻辑请求的结构化调度事件至少记录：

- `logical_request_id`、`attempt_id`、`attempt_index`
- `group_id`、`requested_model`、`image_intent`
- `candidate_account_ids`（有序）
- `excluded_account_ids`、`exclude_reasons`
- `selected_account_id`、`selected_rank`、`protocol_binding`
- `quality_window_end`、`quality_snapshot_stale`
- `profit_mode`、`profit_bypass`、`profit_bypass_reason`
- `extra_retry_count`、`extra_used`、`switch_count`
- `safe_to_replay`、`switch_allowed`、`switch_block_reason`、`stop_reason`
- `native_slot_wait_ms`、`routing_ms`、`upstream_ttft_ms`、`total_ms`

禁止记录 API Key、OAuth token、完整凭据、敏感请求体或原始上游内容。

需要补齐的运营指标定义：

- **首字超时率**：已经到达上游、在首个语义输出前因既有首字/上游截止而终止的 attempt 数 / 到达上游且适用 TTFT 的 attempt 数。普通慢 TTFT 但最终成功不算超时。
- **队列等待**：只统计 Sub 原生账号槽位等待时长，分成功获得、超时和取消；不得混入 T80 admission。
- **分段调度耗时**：固定账号池加载、资格过滤、利润分区、质量排序、原生槽位等待、跨号恢复间隔分别计时，避免把全部时间笼统归为 TTFT。
- **利润绕过率**：`profit_bypass` 逻辑请求数 / 利润控制开启的逻辑请求数，按 `margin_below`、`unknown_u`、`invalid_u`、`config_read_failed` 分原因。
- **安全恢复率**：发生至少一次安全切号且最终成功的逻辑请求数 / 发生安全切号的逻辑请求数。

## 17. 用户体验、运营收益与成本

### 17.1 预期提升

- 单账号的未计费、未输出安全故障通常被内部吸收，用户只看到后续账号的成功结果。
- 质量选择可解释且稳定：管理员看到的账号级顺序与运行时顺序一致，不再因随机、权重或普通 sticky 漂移。
- Pro/专属 Pro 只容忍 1 次额外恢复，控制尾延迟；Plus 允许 2 次，在体验和可用性间平衡；特惠允许 3 次，以更高尾延迟换取更高最终完成率。
- 账号监控保留每个真实 attempt，可准确识别故障账号；分组监控反映用户最终体验，两者不互相掩盖。
- 利润合格账号仍优先；全池越线时不因利润门直接中断服务，并能量化绕过成本。

### 17.2 明确成本

- 安全切号会增加用户等待时间，最坏路径可达到多个上游 attempt 的累计时长。
- 发生切号时，上游缓存亲和可能下降；但正常请求的确定首位账号更稳定，普通场景不一定降低缓存。
- 严格词典序会把流量集中到当前排名靠前账号。Sub 原生并发槽、T82 健康隔离和槽位不可得后的按序跳过负责防止单账号被无限占用；T96 不再增加额外限制。
- 小样本 100% 账号会按已确认规则排在大样本 99.x% 账号之前，这是“不设样本硬门槛 + 成功率绝对第一”的直接结果，管理员通过固定池归属管理风险。
- T96 只在明确未计费时重放，因此不会主动制造已知双重上游采购成本；计费未知时宁可向用户返回错误，也不冒险重放。

### 17.3 不作出的承诺

不能承诺用户永远感受不到服务中断。以下情况仍会失败：不可安全重放、所有账号不可用、组级恢复预算耗尽、请求截止、客户端取消或协议强制绑定无法安全迁移。目标是隐藏可证明安全的单账号故障，而不是用重复计费换取表面成功率。

## 18. 兼容、迁移、发布与回滚

### 18.1 兼容

- 旧 scheduler policy、preset、weight 和 fairness JSON 原样保留，避免降级/回滚时丢配置。
- 统一质量模式不读取这些字段作为文本选择因子。
- `pool_mode_retry_count` 继续供未纳入 T96 的其他平台/路径使用；普通非生图 OpenAI 路径忽略它。
- 现有错误翻译、用户协议、usage 写入、T82 健康状态和 T93 逻辑终态保持兼容。

### 18.2 实施顺序

1. T95 完成、合入并通过直接相关测试。
2. 从届时最新干净 `main` 创建独立 T96 worktree。
3. 先实现质量数据合同和纯比较器，再接利润兜底、选择器、恢复预算和 UI。
4. 在验收站手工配置账号池、priority=50 和各组 `extra_retry_count`。
5. 先以统一质量开关关闭验证兼容，再开启执行端到端验收。
6. 用户明确验收站通过后，才可按发布总控规则申请主站部署；本规格不构成主站发布授权。

### 18.3 发布属性

- 预期无 SQL migration，`downtime_required=false`，最终以发布预检为准。
- 不使用 GitHub Actions。
- 不在部署脚本中自动修改生产账号池、priority、status、schedulable、并发或利润参数。

### 18.4 回滚

- 运行时紧急回滚：关闭 `openai_advanced_scheduler_enabled`，恢复既有基础路径。
- 代码回滚：恢复上一已验证镜像/commit。
- 旧 policy JSON 和手工账号关系不删除；无数据库数据回滚。
- 若新选择器造成异常，保留调度事件和质量快照证据，不自动改账号分组。

| 协议强制绑定 | 在安全资格成立时保留绑定；不被普通质量排序破坏 |
| 有利润合格账号 | 仅在合格子集按统一质量顺序选择 |
| 全池利润越线 | 不返回利润 503；按完整质量序选择并记录 `profit_bypass=margin_below` |
| U 未知且有合格账号 | 未知 U 不进入首选利润子集 |
| 全池 U 未知/越线 | 可用性兜底，原因精确区分 `unknown_u`/`invalid_u`/`margin_below` |
| 利润配置读取失败 | fail-open，按质量序继续并记录 `config_read_failed` |
| Pro 安全失败 | 首账号失败后最多切到第二个不同账号 |
| Plus 连续安全失败 | 最多尝试 3 个不同账号 |
| 特惠连续安全失败 | 最多尝试 4 个不同账号；旧 2 次切换/故障域/5 秒上限不得提前截断 |
| 同账号 pool retry > 0 | 普通文本路径仍不重试同账号 |
| 已计费/partial/已输出/副作用/计费未知 | 立即停止，不选第二账号，保留并计费该 attempt |
| 原生槽位即时获得 | 只调用原生槽位，完成后释放 |
| 槽位等待后获得/超时/取消 | 原生语义不变；所有出口释放或未占槽；无 T80 admission 事件 |
| 最优账号槽位不可得 | 跳到下一资格账号，不消耗额外恢复次数 |
| 失败切号 | 旧账号槽位先释放；新账号独立 acquire；无槽位泄漏 |
| 账号监控 | 中间失败和最终成功分别可见，均有账号和 attempt 关联 |
| 分组性能监控 | 同一逻辑请求最终成功只计一次成功，不把中间失败重复放大 |
| 生图请求 | 只走原生图片池和原生调度，不触发文本质量/利润兜底/组级恢复 |
| 全池耗尽 | 返回现有脱敏本地/上游错误；不伪造成功、不无限循环 |

## 20. 测试策略与最小验证

### 20.1 后端单元/仓储测试

- 质量 SQL：仅使用 `usage_logs`，覆盖 attempt 派生幂等键、同一逻辑请求多 attempt、历史缺失 attempt_id、排除分类、unknown、partial、截尾平均、NULL 和 7 天边界；不得与 `ops_error_logs` 双计。
- 比较器属性测试：四级键、NULLS LAST、排列输入稳定、无随机性、无 priority/权重读取。
- 成本 provider 集成：direct、ratio、自购、unknown/invalid；不写死账号 ID 或 `/10`。
- 利润：合格子集、全池越线、U unknown/invalid、配置读取失败、槽位后终检和释放。
- 设置：`extra_retry_count` 0/1/2/3、缺失默认、越界/非整数 400、旧 JSON round-trip 不丢字段。
- 恢复预算：不同账号 2/3/4 个真实 Forward attempt、请求排除、池耗尽、取消、截止、不可重放、旧统一上限不截断；资格跳过、利润否决、槽位不可得和 Forward 前取消均不消耗。
- 原生槽位：即时、等待、超时、取消、利润否决、成功、失败切号和幂等释放。
- 源合同：OpenAI 请求链不得出现 `AcquireOpenAIAdmission` 或 slow-session guard。

### 20.2 handler/端到端测试

- Responses 流式/非流式、Chat Completions、Messages 兼容及现有其他非生图 OpenAI scheduler 入口。
- 失败分类覆盖 401/403、429、502/503、网络中断、`response.failed`、partial output、usage known/unknown 和工具副作用。
- 协议强制绑定与普通 sticky 分离。
- 物理 attempt 2 失败 + 1 成功时，账号监控可复算 3 个 attempt，逻辑监控为 1 个最终成功。
- 同一 `logical_request_id` 下不同 `attempt_id` 均可持久化；同一物理 attempt 的重复写入不重复计费，账号卡片与运行时排名读取同一物理口径。
- 文本/生图同一 API key 的路径隔离。

### 20.3 前端/API 测试

- 调度设置页按原生分组读写 `extra_retry_count`。
- 统一质量模式下旧权重/预设不再作为生效控件。
- 原生 Groups 利润设置入口不复制、不回归。
- 账号卡片物理 attempt 成功率与排名 provider 同口径；分组逻辑成功率标签保持区分。

### 20.4 最小命令门禁

实施计划须在发现实际包路径后固定精确命令，至少包括：相关 Go repository/service/handler 测试、`go build ./cmd/server`、相关 Vitest、`pnpm typecheck`、`pnpm build`、`gofmt` 和 `git diff --check`。不为形式运行无关全仓测试。

## 21. 口径限制与剩余风险

1. 账号成功率以物理 attempt 为单位；分组成功率以逻辑请求终态为单位。两者共享错误排除规则，但数值不应被要求相等。
2. P95 名称按用户要求保留，数学定义是两端 5% 截尾平均，不改成 nearest-rank percentile。
3. 7 天快照不等于本次实时资格。status、schedulable、模型能力、T82 健康、原生槽位和利润定价都可能让实际选择跳过排名靠前账号，诊断必须显示 skip reason。
4. 历史日志不能完整反推出每个旧逻辑请求的切号链；上线后的验收只能使用新请求和现有 `logical_request_id`/`attempt_id` 证据。
5. T95 尚在独立 worktree 实施；T96 不得基于未审查、未合入的临时接口直接编码。
6. 账号池是 2026-08-31 的人工基线。未来新增账号不会自动归组，管理员必须先分配归属；运行时不得代替管理员做这一决定。
