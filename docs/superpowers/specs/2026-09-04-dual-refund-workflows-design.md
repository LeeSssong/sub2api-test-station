# 双退款流程与额度语义设计

## 已确认事实

- `payment_orders` 已有 `paid_quota_usd`、`gift_quota_usd`、`total_quota_usd`、`refunded_paid_quota_usd`。
- 管理员代充值订单使用 `payment_type=admin_recharge`，没有外部支付 provider 实例。
- 当前外部退款流程依赖 provider 实例，因此管理员代充值会错误返回“退款不可用”。
- 当前手工额度退款会同时扣充值额度并清空赠送额度，不符合本业务要求。
- “用户充值和并发变动记录”基础记录来自 Sub2API 原生，额度流水页签是星桥定制。

## 目标

1. 管理员代充值订单的操作显示“账务退款”，进入管理员账务退款流程。
2. 外部支付订单显示“支付渠道退款”，只处理渠道允许退款的订单。
3. 用户记录弹窗提供“管理员账务退款”和“支付渠道退款”两个退款标签页。
4. 管理员账务退款只能关联 `admin_recharge` 订单，并要求唯一退款交易号。
5. 同一订单支持多次部分退款，累计退款不超过订单尚未退回的充值额度。
6. 账务退款只扣 `paid_quota`，保留 `gift_quota`。
7. “付费额度”统一显示为“充值额度”，“当前可消费额度”统一显示为“可用额度”。
8. “可退款现金余额”改为“可账务退款金额”，按管理员代充值订单剩余可退额度计算。

## 非目标

- 不改变外部支付渠道的 provider 退款协议。
- 不把赠送额度纳入现金退款或账务退款金额。
- 不删除历史订单、流水或用户数据。
- 不把测试站数据和凭据复制到 Git 或主站。

## 方案与数据流

复用现有 `user_quota_grants`、`user_quota_adjustments` 和 `QuotaAccountingService`。管理员代充值创建时必须有与订单关联的 payment-order grant；管理员账务退款先锁定订单及其 grant，计算剩余可退款充值额度并创建 pending adjustment，成功确认后只增加 grant/order 的 `refunded_paid_quota_usd` 并扣减钱包 paid。赠送额度和用户总可用额度中的 gift 部分保持不变。每次请求使用退款交易号派生幂等键，重复请求返回同一 adjustment。

外部支付退款沿用 provider Saga：订单必须有有效 provider 实例、provider 退款能力和支付交易号；只在支付渠道退款页签展示符合条件的订单。

## 业务规则

- 管理员账务退款：`payment_type=admin_recharge`、订单状态为已完成或可继续退款状态、退款交易号 trim 后非空且唯一。
- 可退充值额度：`paid_quota_usd - consumed_paid_quota_usd - refunded_paid_quota_usd - reserved_paid_quota_usd`，小于等于 0 时不可退款。
- 退款金额按人民币与充值额度现有换算规则转换；退款金额不得超过剩余充值额度。
- 账务退款成功后 gift 不变；订单 `refunded_paid_quota_usd` 累加，全部退完后订单进入已退款，否则部分退款。
- 交易号、原因、操作管理员和订单关联写入 adjustment/audit；交易号不可修改。

## UI

- 订单管理表格：管理员代充值按钮文案为“账务退款”，外部订单按钮文案为“支付渠道退款”。
- 用户记录弹窗：两个退款标签页分别加载管理员订单和外部可退款订单；额度流水仍独立显示。
- 用户头部显示“可用额度”和“可账务退款金额”。
- 退款弹窗按标签页显示对应字段；账务退款必须填写退款交易号，支付渠道退款使用 provider 退款字段。

## 失败与安全

- 非管理员代充值订单调用账务退款返回类型错误。
- 管理员代充值调用支付渠道退款返回不支持，不触发 provider。
- 重复退款交易号返回冲突；并发退款通过订单/grant 行锁和 adjustment 幂等约束防止超退。
- 余额、grant、订单或 adjustment 任一写入失败，整个账务退款保持可重试，不产生部分成功状态。

## 测试与验收

- Go：两类订单路由、交易号校验/唯一性、部分退款上限、gift 保留、幂等和并发锁。
- Vitest：两个退款标签页、按钮文案、订单筛选、字段必填及“充值额度/可用额度”文案。
- 发布后在独立测试站创建一笔测试管理员代充值，验证部分账务退款、重复交易号拒绝、gift 不变；再验证外部订单仍进入 provider 退款流程。

## 发布与回滚

- 从最新 `origin/main` 创建独立分支，提交并推送后才能进入测试站发布。
- 无新增 migration 预期；若发现需要调整现有约束，必须单独说明并执行迁移验收。
- 发布失败保留候选分支和 release，回滚到测试站上一已验证 release；不触碰主站。

## 用户批准

- 2026-09-04：用户确认支持同一管理员代充值订单多次部分退款，唯一退款交易号，累计不超过剩余充值额度。
