# Sub2API 官方核心与星桥定制外置设计

**日期：** 2026-08-08
**状态：** 已批准；生产发布进行中
**实施类型：** 分阶段架构迁移
**主要目标：** 使 Sub2API 官方版本升级与星桥定制功能解耦，同时保持管理员使用方式和数据口径不变。

## Loop Brief

```text
Goal: 把星桥定制从 Sub2API 官方核心中逐步外置，建立官方升级优先、定制数据和管理体验不丢失的长期架构。
Context: 当前定制深入官方 Go 二进制、前端 bundle、路由、Ent 模型和数据库迁移；官方升级按钮已被宿主更新器拦截，并依赖合格候选镜像。
Constraints: 不使用 GitHub Actions；不盲目覆盖源码或二进制；不允许外置服务直接写官方核心业务表；不改变管理员登录、菜单、筛选、导出和数据口径；不影响正在运行的生产槽位。
Plan: 先建立定制资产清单和兼容合同，再按查询页面、数据投影、写操作、请求链适配、官方升级通道的顺序迁移。
Implement: 本轮仅完成设计，不修改运行时代码和生产环境。
Validate: 设计自审覆盖当前定制面、数据源、权限、升级状态机、回退、测试和生产验收。
Review: 重点审查官方核心与外置服务的写边界、数据库向前兼容、会话隔离和页面无感迁移。
Done when: 用户确认本设计后，再编写逐任务实施计划；未经确认不进入代码实施。
```

## 1. 背景与根因

当前生产不能直接使用 Sub2API 官方原版镜像，因为星桥定制已进入：

- Go 后端服务、路由、仓储、计费与请求链。
- Vue 管理后台菜单、页面、类型和 API 客户端。
- Ent 模型及 PostgreSQL 迁移。
- 账号监控、成本倍率、盈利分析、账务对账和实际响应模型等运营能力。

当前受控更新器没有合格定制镜像时拒绝切换，这保护了星桥功能；但也使管理员点击后进入耗时的候选准备流程。生产主机缺少候选准备器时，页面会停在“候选版本准备中”。

根本问题不是按钮或超时，而是定制代码与官方发布单元绑定。只要定制仍编译在官方二进制或前端 bundle 中，每次官方更新都必须重新合并、编译、测试、部署和验收。

## 2. 设计决策

采用“**薄核心适配器 + 星桥外置控制面**”，而不是立即追求 100% 外置。

1. **可落地终态：** 大部分业务能力外置，Sub2API 仅保留可审计的极薄适配器。官方新版仅需自动合并小适配层，冲突面积显著下降。
2. **理想终态：** 官方提供稳定事件、管理 API 或扩展插槽后，移除最后的编译时适配器，生产运行官方原版核心。

不采用“官方更新后强行覆盖旧补丁”。该方法无法证明新版的类型、路由、迁移和请求链仍兼容，容易产生部分覆盖成功的带病版本。

## 3. 硬性原则

1. 官方 Release 是版本、asset、checksum 和 commit 的事实源。
2. 管理员登录、2FA、主域名、菜单、URL、字段、筛选、排序和导出原则上不变。
3. Sub2API 核心数据只通过官方服务或明确的窄写 API 修改；外置服务不直接写官方业务表。
4. 外置统计、盈利、监控和对账数据使用可重建读模型。
5. 新版本必须在非活动环境通过合同测试和数据对比才能提升。
6. 准备、迁移分析、数据对比或健康检查任一失败，活动生产槽位不变。
7. 发现、资格、发布、暂存和提升不使用 GitHub Actions，继续使用已审查的本地/宿主脚本链和 systemd 调度。

## 4. 目标架构

```text
管理员浏览器
  │ 同一域名、同一登录态、同一菜单体验
  ▼
Caddy / 管理入口
  ├─ Sub2API 官方核心
  │    ├─ 身份、账号、分组、API Key
  │    ├─ 请求路由与原始计费账本
  │    └─ 极薄事件/命令适配器（过渡期）
  ├─ 星桥管理前端
  │    ├─ 账号监控
  │    ├─ 盈利与账务
  │    └─ 对账与数据完整性
  ├─ 星桥控制面服务
  │    ├─ 事件消费与可重建读模型
  │    ├─ 余额、成本、倍率和账单采集
  │    └─ 盈利、监控、对账和通知
  └─ 宿主发布控制器
       ├─ 官方 Release 发现
       ├─ 兼容性/数据库迁移资格
       ├─ 非活动槽位验证
       └─ 蓝绿切换、回退和审计
```

### 4.1 官方核心保留的能力

- 身份、会话、2FA 和管理员权限。
- 用户、分组、账号、渠道、模型和 API Key 生命周期。
- 请求接收、上游路由、Token 统计和原始计费账本。
- 原生管理操作及审计记录。

核心中不再存放可独立计算的运营页面、报表汇总、上游账单采集和通知逻辑。

### 4.2 极薄适配器的上限

过渡期只允许保留官方稳定 API 暂时无法提供的能力：

- 请求完成事件：请求/账号 ID、请求模型、上游模型、实际响应模型、Token、成本和时延。
- 账号状态与原生健康探测变化事件。
- 外置控制面必需、但官方未提供的最小管理命令。
- 版本化菜单扩展清单或稳定外部页面入口。

适配器不包含盈利公式、评分公式、告警策略、页面布局或供应商特殊逻辑。

### 4.3 星桥控制面

控制面以当前 `relay-ops-service` 为可演进基础，但不恢复已退役的旧运维控制页或飞书入站命令。它负责：

- 消费核心事件并维护账号监控、成本、盈利和对账读模型。
- 与上游供应商对接余额、账单和费率。
- 通过官方 API 或薄适配器命令执行受控写操作。
- 存储自己的任务、对账、通知、数据源和计算版本。

## 5. 定制能力迁移分类

| 能力 | 目标归属 | 核心适配需求 | 难度 |
|---|---|---:|---:|
| 主页、文档、客服入口 | Caddy/独立前端 | 无 | 低 |
| 升级发现与发布审计 | 宿主发布控制器 | 无 | 中 |
| 盈利分析、CSV 导出 | 外置读模型/前端 | 只读事件或快照 | 低–中 |
| 账务、账单采集、对账 | 外置控制面 | 请求/计费事件 | 中 |
| 账号监控卡片和排名 | 外置读模型/前端 | 健康、优先级、请求事件 | 中 |
| 余额和成本倍率同步 | 外置采集器 | 窄账号更新 API | 中 |
| 实际响应模型记录 | 外置读模型 + 核心事件 | 请求结束 hook | 高 |
| 原始计费、路由和调度 | Sub2API 官方核心 | 仅观测事件 | 高，不强行外置 |

## 6. 数据架构

### 6.1 事实源与读模型

- Sub2API PostgreSQL 仍是用户、分组、账号、用量和原始计费的事实源。
- 星桥控制面数据库是上游采集、对账、运营计算和通知的事实源。
- 页面由版本化读模型产出统一结果，不在浏览器端临时拼装多个金额口径。

### 6.2 事件传递

首选 PostgreSQL outbox 或具有同等事务保证的事件表，不以无确认 HTTP webhook 作为唯一通道。事件包含 `event_id`、类型、时间、源/合同版本和最小业务事实，不包含凭据、Cookie 或密钥。消费者按 `event_id` 幂等去重，支持从快照和事件重建。

### 6.3 写操作

写操作的优先级是：官方已有管理 API → 向官方补充通用 API → 过渡期薄适配命令。禁止控制面用 SQL 直接修改 `accounts`、`groups`、`usage_logs`、余额或计费相关核心表。

### 6.4 新鲜度与完整性

管理数据响应增加 `generated_at`、`source_watermark`、`freshness_seconds`、`completeness` 和 `calculation_version`。页面可增加更新时间、数据来源和完整性，不能删减现有业务字段。

## 7. 管理员体验合同

### 7.1 必须保持

- 同一公网域名、Sub2API 管理员账号、2FA 和会话。
- 账号监控、盈利、账务和对账仍从管理后台菜单进入。
- 尽量保留 `/admin/accounts/monitor` 和 `/admin/operations/account-profitability` 等当前 URL。
- 保留卡片、筛选、排序、时间窗口、详情、刷新和 CSV 导出。
- 不出现第二套登录、外部跳转或用户可见的内部服务域名。

### 7.2 故障隔离

- 外置控制面不可用时，Sub2API 用户请求、官方管理页面和账号操作仍可用。
- 定制页面显示局部降级状态，不跳转登录，不清理主站会话。
- 控制面的 401/403 必须与主站会话恢复逻辑隔离。

## 8. 身份与权限

1. 浏览器只向同一公网域名发起请求。
2. Caddy 透传 Bearer 会话和原始客户端身份给控制面。
3. 控制面通过内部 `GET /api/v1/auth/me` 校验管理员、活动状态和会话绑定。
4. 浏览器会话不由管理员 API Key 替代。
5. 核心写操作使用短时内部服务身份、操作人 ID、幂等键和审计记录，不重放用户 Bearer。
6. 日志、投影和事件不记录 Bearer、Cookie、OAuth 凭据或上游密钥。

## 9. 官方升级通道

### 9.1 启用前提

只有当官方核心中的星桥业务逻辑已收敛到极薄适配器后，才启用官方优先升级通道。在此之前，继续使用合格定制镜像。

### 9.2 安全升级流程

```text
systemd timer / 管理员检查
  -> 发现官方最新稳定 Release
  -> 锁定 tag、commit、asset 和 checksum
  -> 评估适配器合同与数据库迁移
  -> 在非活动槽位/隔离数据库克隆中运行官方更新逻辑
  -> 运行官方健康、请求链、定制 API、数据对比和 UI 烟测
  -> 全部通过后记为 ready
  -> 管理员点击时只执行生产门禁和蓝绿切换
```

“沿用官方逻辑”指保留官方 Release 发现、下载、checksum 校验、平台选择和版本替换逻辑；宿主只在其前后添加隔离、验证和流量切换。不在活动容器内盲目覆盖二进制。

### 9.3 数据库迁移门禁

- **Expand-only：** 新增可空字段、新表、新索引或具有旧版兼容默认值，可在切换前受控应用。
- **Potentially breaking：** 修改类型、非空或唯一约束及数据语义，必须在生产克隆中完成新旧版回归，并人工确认。
- **Destructive：** 删表、删字段、不可逆转换或使旧版无法运行，不进入自动蓝绿通道。

迁移不自动回滚。回退运行时前必须证明旧版与已应用 schema 仍兼容。

### 9.4 管理员可见状态

1. `checking`：正在检查官方版本。
2. `qualifying`：已发现版本，后台正在资格验证。
3. `ready`：可快速升级。
4. `blocked`：存在冲突、迁移风险或测试失败，显示阶段和稳定原因。
5. `promoting`：正在切换和健康验证。

不再让管理员点击后才启动数分钟的合并和编译。背景准备未完成时，升级按钮不可用，但必须显示阶段、起始时间、最后进展和失败原因。

## 10. 兼容合同

官方版本与控制面之间定义 `integration_contract_version`，至少包含：

- 管理员身份验证语义。
- 账号、分组、优先级、健康、余额和倍率字段。
- 用量、请求、Token、原始计费和实际响应模型事件。
- 账号更新命令、幂等键和审计。
- 错误码、时间精度、金额精度和币种。
- 菜单入口、页面路由和前端资源版本。

每个官方候选必须产生机器可读的兼容报告，不接受“页面能打开”作为唯一验收。

## 11. 双读迁移与切换

```text
legacy_only
  -> shadow_building
  -> dual_read_comparing
  -> external_primary
  -> legacy_retired
```

对比要求：

- 账号、请求和账单数量精确一致。
- USD/CNY 金额使用 decimal，不用浮点容差掩盖差异。
- 倍率、利润率和评分记录计算版本后比较。
- 余额允许显式的采集时间差，不允许无来源的金额差异。
- 对比覆盖页面支持的最小、默认和最大时间范围。

只有双读对比、权限、会话、筛选、排序、分页、导出、故障状态和回退演练全部通过，才能把外置实现切为主路径。

## 12. 分阶段路线

### Phase 0：基线冻结与定制盘点

- 以当前生产已验证版本为行为基线。
- 建立“定制能力 → 源码 → API → 数据表 → UI → 生产验收”清单。
- 建立金额、倍率、评分和请求链黄金样本。
- 不改变生产行为。

### Phase 1：兼容合同与事件边界

- 定义版本化事件、管理命令和新鲜度协议。
- 建立幂等 outbox 及可重建消费者。
- 为当前页面/API 编写行为合同测试。
- 旧页面和旧计算仍是生产主路径。

### Phase 2：先迁移只读运营能力

- 迁移账号监控查询、盈利分析、账务历史、对账查询和 CSV 导出。
- 保持原 URL、菜单、会话和字段。
- 完成双读对比后逐页切换。

### Phase 3：迁移采集与受控写操作

- 迁移上游余额、账单和费率采集。
- 将余额、倍率、优先级等写入收敛到官方 API 或薄适配命令。
- 所有写操作加入幂等键、操作人和审计。

### Phase 4：收敛请求链定制

- 把实际响应模型、成本证据、延迟和请求结果收敛成稳定事件。
- 保留官方原生计费和路由，不把实时决策迁移到外部网络调用。
- 将核心改动压缩到可独立审计的薄适配器。

### Phase 5：官方优先升级通道

- 安装受控的官方 Release 发现与资格 systemd timer。
- 复用已审查的本地/宿主 `discover -> qualify -> stage -> promote` 脚本链。
- 在非活动槽位运行官方更新逻辑和全套合同测试。
- 点击更新时只进行最后门禁与流量切换。

### Phase 6：移除旧候选交互与深度 fork

- 移除“管理员点击后开始合并/编译”的交互。
- 候选未就绪时只展示资格状态和明确阻断原因。
- 官方扩展点可用后，删除最后的编译时适配器。

## 13. 测试与验证

### 13.1 合同测试

- 管理员会话、IP 绑定、Origin 和会话隔离。
- 账号、分组、健康、优先级、余额、倍率和成本字段。
- 用量、Token、模型、实际响应模型和计费事件。
- 菜单、路由、筛选、排序、时间范围和 CSV 导出。
- 控制面错误不触发主站退出。

### 13.2 数据对比

- 组、账号、有效请求和账单数量。
- Token、原始成本、实际收入、上游/采购成本、利润和利润率。
- 监控评分、排名、余额和倍率。
- 对账明细、异常数和日结阻断状态。

### 13.3 发布验证

- 后端单测、race、vet；前端单测、lint、typecheck、production build。
- 数据库克隆迁移和新旧版兼容验证。
- JSON、SSE、Responses 和 WebSocket 关键请求链。
- 官方 health/readiness、管理员身份、模型列表和核心管理 API。
- 定制页面桌面端/移动端视口和主要交互烟测。
- PostgreSQL、Redis、Caddy、worker 和非目标服务容器身份不变。

## 14. 可观测性与审计

每次官方候选记录：官方 tag/commit/asset/checksum；适配器、控制面和合同版本；迁移分类与哈希；每个资格阶段的时间、结果和稳定错误类别；槽位镜像/二进制身份；数据对比报告；切换前后健康、容器 ID 和回退证据。

读模型记录水位落后、消费重试、死信、重建进度和计算版本分布。

## 15. 回退

- 每个迁移单元有独立 feature flag，可不重建 Sub2API 而切回旧数据源。
- 前端资源和控制面镜像按不可变版本发布，保留上一合格版本。
- 读模型使用重建回退，不删除核心数据。
- 仅在旧 Sub2API 对当前 schema 仍兼容时切回旧槽位。
- 迁移已破坏旧版兼容时，不自动切回；备份恢复是独立授权的灾难操作。

## 16. 主要风险与控制

| 风险 | 控制 |
|---|---|
| 官方缺少稳定扩展点 | 保留极薄适配器，并优先向官方贡献通用事件/API |
| 菜单集成脆弱 | 使用版本化菜单清单/薄前端适配，不依赖 DOM 选择器猜测 |
| 读模型延迟或丢事件 | 事务 outbox、水位、幂等、重建和完整性状态 |
| 金额/倍率口径漂移 | decimal、计算版本、双读对比和黄金样本 |
| 外置服务误判 401 使主站退出 | 请求级会话恢复隔离和原始客户端身份透传 |
| 官方迁移破坏蓝绿回退 | 迁移分类 + 生产克隆实测 + destructive 手工门禁 |
| 迁移期双实现复杂 | 逐页/逐能力 feature flag，达标后删除旧路径 |
| 外置增加实时延迟 | 实时路由和计费不调用外部网络服务，只异步发事件 |

## 17. 非目标

- 不为追求“纯官方”而把计费或路由决策放到远程调用中。
- 不将当前大量源码改动制作成永久覆盖补丁。
- 不恢复 relay-ops 旧独立运维控制面或飞书入站命令。
- 不使用 GitHub Actions 进行发布、暂存或生产提升。
- 不在设计阶段修改生产服务或执行数据迁移。

## 18. 验收标准

### 架构

- [ ] 每个定制能力有明确归属：官方核心、薄适配器或外置控制面。
- [ ] 外置服务不直接写官方核心业务表。
- [ ] 实时路由和计费不依赖外部网络服务。

### 管理员体验

- [ ] 登录、2FA、主域名、菜单和主要 URL 不变。
- [ ] 现有字段、筛选、排序、详情、刷新和导出不减少。
- [ ] 只增加更新时间、数据来源、完整性和计算版本。
- [ ] 外置服务不可用时，主站会话不被清理且官方页面仍可用。

### 数据

- [ ] 账号、请求和账单数量双读一致。
- [ ] 成本、收入、利润、利润率、倍率和评分符合版本化口径。
- [ ] 读模型可重建，页面可见水位和完整性。

### 升级

- [ ] 新官方版本在管理员点击前已完成背景资格。
- [ ] 官方下载、checksum、版本识别和替换逻辑未被改写。
- [ ] 资格失败时活动生产槽位完全不变。
- [ ] 点击更新只执行最终门禁、切换和健康验证，不现场合并或编译。
- [ ] 破坏性迁移不进入自动升级通道。

### 生产完成口径

任何迁移单元只有同时满足“已推送到服务端 + 已生产部署 + 已验证生效”才能在项目总账标记“已完成”。

## 19. 结论

1. 长期外置大部分星桥业务，但不为追求 100% 外置牺牲实时计费和路由可靠性。
2. 官方核心保留事实和单一写入边界；外置控制面承载运营读模型、采集、对账和展示。
3. 管理员体验无感，现有数据查看能力不减少。
4. 官方升级在非活动槽位保留官方逻辑，宿主只添加隔离、合同验证和蓝绿提升。
5. 在深度 fork 收敛前，不启用官方原版直接替换生产。
