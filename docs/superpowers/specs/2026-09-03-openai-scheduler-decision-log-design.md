# OpenAI 调度决策日志设计

## 1. 背景与现状

当前管理员侧边栏仍有“调度设置”入口，但其中的统一质量调度开关只承担运行时回退作用，`extra_retry_count` 已不再控制普通 OpenAI HTTP 请求的真实重试/切号预算。真实调度决策已经发生在原生 OpenAI scheduler 与统一质量选择器中。

服务端已有 `OpenAIResilienceEvent` 进程内事件账本，能够投影候选、排除原因、选择层、质量字段、选中账号和恢复字段，但最多保存 4096 条，重启即丢失，也没有管理员查询页面。现有用量流水只覆盖成功记账，无法解释候选耗尽、重放被禁止、冷却未触发或恢复耗尽等失败请求。

## 2. 目标

1. 删除管理员可见的“启用统一质量调度”和“额外恢复次数”控制项。
2. 将侧边栏“调度设置”改为“调度日志”。
3. 首期仅覆盖 OpenAI/Codex 普通 HTTP 文本调度及其恢复尝试，生图、Responses WebSocket、alpha-search 和其他平台保持现有路径。
4. 以尽力异步方式记录每次调度 attempt，使管理员能够从第一性原理解释请求为何选中某账号。
5. 成功和最终失败请求均可查询；同一逻辑请求下的所有 attempt 使用同一关联 ID，并带 attempt 序号。
6. 默认保留 7 天，页面默认查询最近 1 小时并支持 24 小时、7 天游标分页。

## 3. 非目标

- 不改变账号资格、排序数学、原生槽位、冷却、账务、重放安全或恢复预算。
- 不恢复 `extra_retry_count` 的运行时控制语义。
- 不新增第二套评分或排名事实源；日志只保存调度器已计算出的请求时点快照。
- 不同步记录完整请求体、Authorization、API key、凭据、提示词或上游敏感响应。

## 4. 核心数据契约

调度日志事件以 `logical_request_id` + `attempt_id` + `attempt_number` 标识请求链。每次选择事件至少包含：

- 时间、平台、协议/端点、分组、模型；
- 算法版本（由服务端常量/版本字符串生成，不由前端传入）；
- 选择层及触发机制：previous response、guardian parent、session sticky、unified quality、load balance、half-open probe 等；
- 原始候选数、合格候选数、有效 Top-K、候选账号 ID 摘要；
- 被排除账号 ID 摘要及聚合排除原因；
- 选中账号、请求时点排名、质量综合分及可解释的质量分量/变化；
- 本次 attempt 的运行时重试预算、已使用额外 attempt、真实切号次数；
- 槽位等待、路由和上游首字/总耗时（已有字段时）；
- attempt 结果、最终结果、是否允许安全重放、是否触发冷却/请求级排除及原因。

同一逻辑请求必须另外记录失败/冷却/恢复转移事件，至少包含：上游状态分类、是否已产生输出或用量、是否安全重放、是否写入短冷却、是否加入请求级排除、下一次选择为何仍可命中同一账号或为何切换。历史没有关联 ID 的事件显示为证据不足，不回填。

## 5. 运行时架构

选择器和 handler 复用现有 `RecordOpenAISchedulerSelection`、`RecordOpenAISchedulerRequestOutcome` 及 resilience 事件字段，在请求上下文中捕获不可变的逻辑请求/attempt 元数据。事件进入有界内存队列，由单独 worker 批量写入调度日志表；请求线程不等待数据库、不重新查询账号或质量快照。

队列满、写入失败或进程退出允许丢失事件，但必须维护丢失计数/最近错误时间，管理端在相应时间范围显示“日志可能不完整”。日志写入失败不得改变选择、重试、计费或响应。

表按事件时间建立索引，并通过每日批量清理删除 7 天前事件；删除任务有界、可重入，避免长事务。候选账号数组和排除原因使用受控 JSON/数组字段，限制最大长度并在写入前复制，防止请求上下文数据竞争。

## 6. 管理端 API 与页面

新增管理员只读接口：

- `GET /admin/scheduler/logs?from=&to=&cursor=&limit=&group_id=&account_id=&outcome=&mechanism=&q=` 返回摘要列表和下一游标；
- `GET /admin/scheduler/logs/:logical_request_id` 返回该逻辑请求的 attempt 时间线及候选决策快照。

列表默认只返回时间、请求 ID 脱敏值、模型/分组、最终账号、实际算法版本、结果、切号次数和是否存在日志缺口。详情按需加载候选与因果链，不全量预取。

页面入口 `/admin/scheduler-logs`，标题“调度日志”。列表与详情并排；详情突出“为什么选中”“实际算法版本”“运行时重试预算”“真实切号次数”，并用时间线区分同一请求内的多次 attempt。旧设置字段不出现在该页面。

## 7. 性能与安全

- 选择路径仅做一次结构化事件复制和非阻塞入队；队列容量有界。
- 批量写入降低数据库 round-trip；查询必须游标分页并限制单页上限。
- 日志保存脱敏 ID 和白名单字段，不落完整请求体或凭据。
- 失败请求与日志缺口必须可见，禁止把缺失事件伪装成“无调度”。

## 8. 兼容与迁移

新增调度日志表和必要迁移；不修改 `usage_logs`，不回填历史事件。旧设置 API 字段可继续被后端兼容读取，但管理员前端不再提供编辑入口；如保留后端字段，必须标记为 legacy compatibility，不得映射为当前生效调度参数。

## 9. 验收矩阵

| 场景 | 预期 |
| --- | --- |
| 单次成功请求 | 显示算法版本、候选缩减、选中账号、排名/评分变化、预算和 0 次切号 |
| 安全失败后切换账号 | 同一逻辑请求出现连续 attempt，显示异常分类、排除/冷却动作和切号原因 |
| 异常后再次命中同一账号 | 明确显示是不同并发请求，或该 attempt 仍满足资格且未触发冷却；不得笼统写“调度成功” |
| 不可安全重放 | 显示停止原因，不生成第二次上游 attempt |
| 候选耗尽/恢复耗尽 | 无成功流水也可查询，显示最终失败和预算耗尽 |
| 队列满/写入失败 | 请求继续完成；页面显示时间范围日志可能不完整 |
| 7 天清理 | 超出保留期事件不可查询，清理不阻塞请求 |
| 页面性能 | 列表游标分页；详情点击后才加载候选时间线 |

## 10. 测试与发布

- Go：事件契约、逻辑请求/attempt 关联、异步队列丢弃语义、批量持久化、7 天清理、管理员过滤/游标 API。
- 前端：入口文案/路由、列表分页、详情时间线、失败与日志缺口状态、窄屏布局；不再渲染两个旧控制项。
- 必要的 server build、前端 typecheck、定向测试和 diff-check。
- 发布前检查迁移与来源门禁；无主站部署授权前不部署。

## 11. 风险与回滚

主要风险是事件量增长和日志队列丢弃。通过有界队列、批量写入、7 天清理和丢失计数控制。若日志表或 worker 出现问题，可关闭日志持久化 worker/回滚新增 API 与页面；调度选择和请求链保持原样，不需要回滚账号配置或账务数据。
