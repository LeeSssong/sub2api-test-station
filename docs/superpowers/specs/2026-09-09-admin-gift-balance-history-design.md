# 管理员赠送/扣除额度与用户记录弹窗修复规格

## 1. 问题证据与当前行为

当前测试站截图与原型存在四类差异：

1. 用户充值和并发变动记录弹窗仍显示“余额充值（管理员）”，且管理员记录没有展示赠送额度。
2. 额度摘要把可用、付费、赠送额度放在同一横向行，未按原型采用“可用额度独占第一行、付费/赠送额度位于第二行”的竖向层级。
3. 管理员 `add/subtract` 仍经过旧的 `AdjustBalance` 入口；额度钱包启用时该路径可能调整付费额度，而产品语义要求管理员只能增加或扣除赠送额度。
4. 用户记录弹窗的记录项只显示单一 `value`，未同时展示普通兑换码和支付订单产生的付费额度、赠送额度。

代码核验确认：

- `admin_user.go` 的 `UpdateUserBalance` 仍调用 `SetBalance`/`AdjustBalance`，并创建旧类型 `admin_balance` 的兑换码记录。
- 现有 `QuotaAccountingService` 已具备 `CreateAdminGiftGrant` 与赠送额度 FIFO 扣除能力，可作为管理员操作的原生事实源。
- `user_quota_grants` 已包含 `paid_quota_usd`、`gift_quota_usd`；`user_quota_adjustments` 已包含管理员赠送扣除的 `applied_gift_quota_usd`。
- `redeem_codes` 的旧管理员余额记录不能继续作为管理员额度账务事实源。

## 2. 目标与非目标

### 目标

- 管理员赠送只增加赠送额度；管理员扣除只扣除赠送额度，付费额度始终不变。
- 管理员新记录统一展示为“余额赠送（管理员）”或“余额扣除（管理员）”，并显示赠送额度变化。
- 普通兑换码和支付订单记录同时展示付费额度与赠送额度；普通兑换码/支付订单的既有语义保持为增加付费额度，并可附带赠送额度。
- 额度摘要与记录列表按原型完成竖向排版和信息层级调整。
- 通过一次可审计数据库迁移删除历史旧管理员余额调整记录，避免旧语义继续出现在用户记录中。

### 非目标

- 不改变普通用户消费顺序、原生扣费、支付金额、兑换码核销规则或支付订单状态机。
- 不删除普通兑换码、支付订单、赠送额度、付费额度或并发记录。
- 不回填或重算历史用户余额，不复制测试站数据，不触碰生产数据。
- 不保留旧管理员余额记录的兼容展示。
- 不新增第二套余额事实源或新的外部控制面。

## 3. 方案比较与选择

### 方案 A：仅修改前端展示

改动最小，但无法阻止管理员操作继续修改付费额度，也无法可靠展示支付/兑换的双额度来源。拒绝。

### 方案 B：复用现有 quota accounting，并统一历史投影（推荐）

管理员操作接入已有 `admin_gift` grant 和 `admin_gift_deduction` adjustment；记录接口将兑换码、支付订单、管理员赠送/扣除映射成统一展示 DTO；新增迁移清理旧 `admin_balance` 记录。该方案复用已存在的原子事务、幂等和 FIFO 语义，账务边界清晰，改动范围可控。

### 方案 C：新增独立管理员额度流水表

可以完全自定义展示，但会形成第二套账务事实源，需要额外同步、幂等和对账逻辑，违反原生优先约束。拒绝。

## 4. 端到端数据与控制流

### 管理员赠送

管理员提交 `add` 请求后，服务端校验正数金额和用户存在性，调用 `CreateAdminGiftGrant`，写入 `user_quota_grants(grant_type='admin_gift', gift_quota_usd=amount)`，付费额度写入为零。操作成功后失效余额/鉴权相关缓存，并返回最新用户信息和可用额度摘要。

### 管理员扣除

管理员提交 `subtract` 请求后，服务端调用现有赠送额度 FIFO 扣除能力。扣除只锁定并更新赠送额度 grant，若赠送额度不足则原子失败，不触碰付费额度；成功后写入 `user_quota_adjustments(adjustment_type='admin_gift_deduction')`，并失效相关缓存。

### 用户记录查询

用户记录接口返回统一记录结构。来源适配如下：

- 普通兑换码：从兑换码关联的额度 grant 读取 paid/gift 增量。
- 支付订单：从支付订单关联的额度 grant 读取 paid/gift 增量。
- 管理员赠送：从 `admin_gift` grant 读取 gift 增量。
- 管理员扣除：从 `admin_gift_deduction` adjustment 读取负 gift 增量。
- 并发记录和订阅记录：保留现有展示字段，双额度字段为零或不适用。

历史旧 `admin_balance` 记录在迁移后不再返回。

## 5. 接口与字段契约

记录项至少提供以下字段，字段名沿用现有前端 snake_case 风格：

- `paid_quota_delta_usd: string`：本条记录的付费额度增量。
- `gift_quota_delta_usd: string`：本条记录的赠送额度增量，可为负数。
- `value`：兼容旧记录类型的主展示值；新额度记录的展示以两个拆分字段为准。
- `type`/`source`：用于区分兑换码、支付订单、管理员赠送、管理员扣除、并发和订阅。
- `code` 或来源引用：非管理员记录保留脱敏来源标识；管理员记录显示管理员调整。

管理员写入接口保持现有 `operation=add|subtract` 兼容，但服务端不得再将其解释为付费余额调整；`set` 不属于本次管理员赠送/扣除入口，若仍被其他内部调用使用，须保持原调用边界并禁止从本入口触发。

## 6. 失败、安全与并发语义

- 金额必须为有限正数；零、负数、NaN 和无穷值拒绝。
- 扣除金额超过当前赠送额度时返回明确余额不足错误，事务整体回滚。
- 管理员赠送和扣除必须使用已有幂等/锁定能力，避免并发请求覆盖余额。
- 迁移只删除明确属于旧管理员余额调整的 `redeem_codes(type='admin_balance')` 记录；执行前后记录数量必须可审计，不能删除 `admin_concurrency`、普通兑换码或任何 quota accounting 记录。
- 迁移不从服务器运行目录或数据库导出数据作为代码来源，不携带凭据，不复制主站数据。

## 7. 兼容性与迁移

- 新代码兼容现有普通兑换码、支付订单、并发和订阅历史。
- 旧管理员余额记录按用户确认“不保留”处理，不做兼容显示；迁移是不可逆删除操作，必须纳入发布预检和回滚说明。
- 迁移不修改 `users.balance`，不重算或回填钱包余额。
- 若发布预检要求停机，必须在停机动作前取得用户明确授权；不能以本规格替代主站发布授权。

## 8. 场景化验收矩阵

| 场景 | 预期结果 |
| --- | --- |
| 管理员赠送 10 | 付费额度不变，赠送额度增加 10；记录显示“余额赠送（管理员）”和“赠送 +10” |
| 管理员扣除 10 | 付费额度不变，赠送额度减少 10；记录显示“余额扣除（管理员）”和“赠送 -10” |
| 赠送额度不足时扣除 | 请求失败，付费和赠送额度均不变 |
| 普通兑换码 paid=10,gift=5 | 记录显示“付费 10”“赠送 5” |
| 支付订单 paid=10,gift=5 | 记录显示“付费 10”“赠送 5” |
| 额度摘要 | 可用额度单独一行；付费/赠送额度位于下一行，桌面与窄屏不重叠、不溢出 |
| 历史旧管理员余额记录 | 迁移后不出现在用户记录接口和弹窗中 |
| 并发/订阅记录 | 既有标题、数值和时间展示不回归，仍能正常分页筛选 |

## 9. 测试策略

- 后端服务测试：管理员赠送只写 gift、管理员扣除 gift-only、赠送不足原子失败、幂等与缓存失效。
- 后端仓储/查询测试：兑换码与支付订单双额度映射、管理员 grant/adjustment 映射、旧 `admin_balance` 过滤。
- 迁移测试：只删除旧 `admin_balance`，保留普通兑换码、支付订单与并发记录；检查迁移幂等合同。
- 前端组件测试：双额度字段显示、管理员新文案、摘要竖向布局、各类记录的双额度显示及旧 tab/退款入口不再出现。
- 必要验证：受影响 Go 包定向测试、前端聚焦 Vitest、`go build ./cmd/server`、`pnpm typecheck`、`pnpm build`、`gofmt` 和 `git diff --check`。

## 10. 发布、验收与回滚

- 本任务先完成候选 worktree 的直接相关测试，不执行主站部署。
- 迁移属于账务相关且含不可逆删除，发布预检若返回 `downtime_required=true`，必须暂停等待用户授权。
- 测试站/主站发布仍必须从干净且已推送的根 `main` 发起，并遵守独立测试站和主站明确授权路径。
- 回滚代码使用上一已验证 commit/镜像；数据库删除无法通过回滚代码恢复，因此发布前必须保留受保护、脱敏且可审计的删除对象计数与必要恢复证据。不得把旧管理员记录重新导入运行环境作为自动回滚动作。
