# T82 调度器健康隔离与故障切换优化规格

## 状态与批准

- 任务：T82 scheduler health failover
- 基线：`main@3b8c0e81d`
- 用户批准：用户已确认“好的，就按这个方案优化”，并在确认轮次明确同意初始阈值、半开探活、滞回和可观测性方案。
- 范围：仅修改 Sub2API 原生后端调度、运行时隔离、请求级故障切换和相关测试；不改主站配置、数据库数据、凭据或发布链。

## 1. 问题证据与当前行为

2026-08-27 Asia/Shanghai 主站只读日志显示：9,757 个逻辑请求仅发生 48 次账号切换；`sticky_escape_triggered` 2,713 次，而 `openai.retry_decision` 955 次中仅 36 次允许切换，客户端仍收到约 536 个 502 与 864 个 503。现有实现存在四个缺口：

1. 质量门禁只有在分组显式配置 `QualityGate.Enabled` 时生效，默认生产分组未完整配置，导致大量逃逸仍是 legacy sticky escape。
2. sticky 逃逸记录了低质量证据，但同一逻辑请求没有稳定排除原账号，可能重新选回低质量账号。
3. 502/503 主要依赖请求级 cooldown；跨账号切换由 handler 安全重放条件控制，大量 `unsafe_to_replay` 没有结构化说明。
4. 余额不足和 401 的临时隔离、探测成功恢复没有统一接入健康状态机；现有余额隔离默认约 90 分钟过期，非 OAuth 401 可能直接 SetError。

## 2. 目标与非目标

### 目标

- 账号持久化状态保持 `active`；质量下降通过账号+模型+分组运行时状态隔离，不做永久不可用。
- 调度器在发现低质量账号时，当前逻辑请求排除该账号，并优先选择健康账号。
- 对余额不足、401、连续 502/503、连续高 TTFT/高耗时提供分级隔离、半开探活和滞回恢复。
- 只有安全重放时后台自动重试；流式已输出、已产生 usage/副作用或不可证明幂等时不强行换号。
- 记录候选、排除、最终账号、重试/切换允许或阻止原因、隔离截止时间。

### 非目标

- 不自动把账号永久置为不可用，不自动修改账号优先级字段为 3。
- 不改变计费、usage_logs、上游凭据、用户可见错误协议或主站部署流程。
- 不引入新的控制面、队列、数据库事实源或 GitHub Actions。

## 3. 方案比较与选择

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| A. 仅调大 sticky 权重/改配置 | 继续依赖现有 legacy escape | 改动小，但无法保证排除原账号、探活恢复和 502/503 分级 |
| B. 新建独立健康服务 | 另建数据库/控制面维护账号健康 | 能力完整，但违反原生优先和任务边界，迁移、部署风险高 |
| C. 扩展原生调度运行时状态机（推荐） | 复用现有 quality gate、transient state、RateLimitService、probe 和 handler failover | 复用事实源，按账号+模型+分组补齐默认策略、半开和证据；改动集中、可回滚 |

选择 C。

## 4. 端到端控制流

1. 请求进入 scheduler，读取分组策略和账号运行时健康状态。
2. 质量证据按账号+模型+分组聚合；满足样本和阈值后连续两个窗口进入 `DEGRADED`，权重降至 30% 并解除 sticky；再次异常进入 `OPEN`。
3. `OPEN` 账号不进入普通候选；冷却到期只允许一个半开探测请求。半开连续 2 次成功恢复 `HEALTHY`，失败按 60 秒、5 分钟、30 分钟递增。
4. sticky 逃逸触发后，本次逻辑请求的排除集加入原账号，禁止立即重新选回；若没有健康候选，按既有安全 fallback 返回，不破坏账号持久化状态。
5. 余额不足在账号级设置 `temp_unschedulable`，保持 `active`，恢复策略改为 `probe_required`；余额探测成功进入半开，连续 2 次成功清除临时隔离。
6. 401：OAuth 先尝试 refresh token；成功进入半开，失败保持隔离。非 OAuth/API Key 每 5 分钟后台探活，连续 3 次失败后指数延长间隔。
7. 502/503：仅在未输出、无 usage、无副作用且可安全重放时，同账号最多重试 1 次，之后最多切换 2 个账号；按 60 秒/5 分钟/30 分钟窗口升级账号+模型隔离。流式已有输出或不可重放时直接返回原安全错误。
8. 每次调度和故障处理写结构化事件，包含候选/排除原因、健康状态、最终账号、sticky escape、retry/switch decision 和 cooldown 截止时间。

## 5. 初始策略契约

- 质量门禁：样本数 ≥ 5；错误率 ≥ 50% 或 TTFT ≥ 15,000ms；连续 2 个观测进入 DEGRADED；权重 30%；解除 sticky；再异常 OPEN 60 秒。
- OPEN 递增：同一账号+模型在 5 分钟内再次失败为 5 分钟，15 分钟内累计 5 次为 30 分钟；半开连续 2 次成功恢复。
- 余额：`temp_unschedulable` + `probe_required`，探测成功连续 2 次恢复。
- 401：OAuth refresh；非 OAuth 探活周期 5 分钟，连续 3 次失败延长周期。
- 502/503：60 秒 2 次 → 60 秒隔离；5 分钟 3 次 → 5 分钟隔离；15 分钟 5 次 → 30 分钟隔离；同账号重试 1 次、跨账号最多 2 次。
- 复原采用滞回：进入和恢复阈值独立计数，状态变化必须满足连续成功/失败次数，冷却未到期不得提前恢复。

## 6. 接口与字段契约

- 继续复用 `OpenAISchedulerQualityGatePolicy`、`OpenAISchedulerSessionEscapePolicy`、`OpenAIAccountModelRuntimeDecision` 和 `AccountRuntimeBlocker`。
- 扩展运行时 decision/日志字段时保持 JSON/日志向后兼容；新增字段使用明确 snake_case：`candidate_account_ids`、`excluded_account_ids`、`exclude_reasons`、`final_account_id`、`switch_allowed`、`switch_block_reason`、`cooldown_until`、`health_state`。
- 账号 `status` 不变；余额/鉴权隔离通过已有 temp-unschedulable 和运行时 blocker 表达。

## 7. 失败与安全语义

- 不得为了隐藏 502/503 而重放已输出、已扣费、已产生副作用或不确定幂等性的请求。
- 同一逻辑请求必须有切换上限和排除集，避免活锁、重复计费和账号来回抖动。
- 探测失败只延长隔离，不清除已有成功快照或持久化凭据。
- 并发半开必须单租约；租约失败的请求不能绕过冷却直接进入普通候选。

## 8. 兼容性、迁移与发布

- 不新增数据库迁移；运行时状态在现有内存/Redis/账号 extra 结构中复用。
- 旧分组未配置质量门禁时读取默认策略并启用；显式关闭仍保持关闭。
- 仅在独立 worktree 完成本地直接相关测试和构建后，按验收站全局约束申请验收站发布；本轮不主站部署。
- 回滚方式：回滚候选 commit；无需数据回滚。失败候选和证据必须保留。

## 9. 场景化验收矩阵

| 场景 | 预期 |
| --- | --- |
| 低质量账号触发 sticky escape | 当前逻辑请求排除原账号，健康账号优先；账号仍 active |
| 样本不足 | 不触发质量隔离 |
| 连续高 TTFT/错误率 | 两个窗口后 DEGRADED/OPEN，权重降低并解除 sticky |
| 冷却到期并发请求 | 仅一个半开探测，其余继续排除 |
| 半开两次成功 | 清除运行时隔离，恢复 HEALTHY |
| 余额不足 | `temp_unschedulable`、`probe_required`，余额恢复后自动半开 |
| OAuth 401 | refresh 成功后探活恢复；失败保持隔离 |
| API Key 401 | 后台探活，连续 3 次失败延长间隔 |
| 安全可重放 502/503 | 同账号 1 次重试，随后最多切换 2 个账号 |
| 已输出/有副作用 502/503 | 不切换，记录阻止原因并返回安全错误 |
| 所有候选均隔离 | 使用既有安全 fallback，不伪造成功、不永久禁用账号 |

## 10. 测试策略

- 先为每个新行为写失败单元测试，再实现最小代码，验证红-绿循环。
- 重点覆盖质量门禁默认启用、sticky 排除、分级 cooldown、半开单租约、余额/401 恢复、安全重试上限和结构化日志字段。
- 最小验证：相关 Go 单测、`go build ./cmd/server`、`gofmt`、`git diff --check`；不运行全仓压力或无关回归。
