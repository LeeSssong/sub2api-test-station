# 上游故障的缓存感知调度与流式恢复设计

**日期：** 2026-08-08  
**状态：** 待用户确认，未进入实施  
**范围：** Sub2API OpenAI Responses/流式网关、账号-模型调度、计费幂等、客户恢复体验

## 1. 背景与问题

2026-08-08 的生产故障中，两个 Codex 任务在同一时间窗口持续收到 `stream disconnected before completion: Upstream request failed`。生产日志显示：

- 请求已经进入流式响应，HTTP 外层仍为 200，但每次响应只包含错误 SSE 片段；
- 同一账号（`account_id=153`）对 `gpt-5.6-sol` 连续失败；
- handler 记录了 `ReportOpenAIAccountScheduleResult(..., false, ...)` 和 `openai.forward_failed`，但账号仍保持 `active + schedulable`；
- 客户点击“继续”后，请求重新进入同一分组并再次选中该账号；
- 同一账号的其他模型探测成功，说明故障需要按“账号-模型”隔离，而不是直接封禁整个账号。

当前实现将“调度失败统计”和“运行时冷却”混在不同错误路径中：未开始流式输出的 HTTP 错误可以进入账号错误处理，而流式中途断流只记录调度失败，未触发 transient cooldown。这会造成重复失败、长连接等待和客户反复点击继续。

同时，调度不能简单采用“第一次失败立即换账号”的策略。上游前缀缓存可能与账号、项目或会话绑定，盲目切换账号会降低缓存命中，增加重复输入计费。因此本设计采用“缓存优先、故障递进”的混合策略。

## 2. 目标

1. 流式中途断流也必须进入统一的账号-模型失败状态机。
2. 单次偶发临时错误尽量保留账号/会话粘性，避免不必要的缓存损失。
3. 连续失败时快速隔离坏账号-模型，避免客户“继续”重复撞击同一上游。
4. 不因自动重试造成重复扣费、重复工具调用或重复外部副作用。
5. 当所有候选账号不可用时，以可恢复、可观测的方式进入半开探测，而不是立即清空全部冷却。
6. 客户无需重启客户端即可恢复；管理员能看到并手动处置具体账号-模型故障。

## 3. 非目标

- 本任务不重新设计上游缓存协议，也不保证不同上游之间共享缓存。
- 本任务不把所有 5xx 永久写入账号 `error` 状态；临时网络/服务故障默认使用运行时冷却。
- 本任务不在流式已经产生有效输出后静默重放整条请求。
- 本任务不顺带改变价格、倍率、分组优先级或生产上游选择。
- 本任务不通过 GitHub Actions 发布；生产发布继续使用现有本地/主机受控发布链。

## 4. 术语与状态

### 4.1 账号-模型键

所有 transient 状态使用：

```text
(account_id, canonical_scheduling_model)
```

其中 `canonical_scheduling_model` 是应用账号模型映射后用于调度的模型名，避免请求模型和上游映射模型产生两套计数。

### 4.2 失败等级

- **soft failure：** 单次可恢复临时错误，不立即改变未来调度，只影响当前请求的重试决策。
- **cooldown：** 账号-模型在一段时间内不可被普通请求选中。
- **hard failure：** 401、402、403、明确模型不存在、明确余额/权限问题等，需要沿用现有持久化禁用/不可调度逻辑。
- **half-open probe：** 全部候选暂不可用时，只允许一个受控探测请求验证恢复。

## 5. 总体设计

调度顺序改为：

```text
会话/缓存粘性
  -> 当前请求失败账号排除
  -> 账号-模型 transient cooldown 过滤
  -> 健康账号评分/并发/优先级选择
  -> 半开探测（仅在没有普通候选时）
```

健康时优先保留当前会话的首选账号；失败时逐级降低粘性，先保护缓存，再保护可用性。

## 6. 请求处理策略

### 6.1 尚未开始输出的临时错误

适用错误：502、503、504、520–524、连接建立失败、可确认的上游超时。必须同时满足：

- response 尚未向客户端提交有效输出；
- 请求被分类为可安全重放；
- 账号在当前失败窗口内没有达到连续失败阈值；
- 尚未执行不可幂等的工具/外部副作用。

动作：

1. 在同一账号上最多进行一次短重试，等待时间为 300–1000ms，并带少量抖动。
2. 同账号重试必须沿用同一请求幂等键/attempt 组，不能产生第二次客户扣费。
3. 同账号重试仍失败时，当前请求排除该账号，转向其他健康账号。
4. 将该账号-模型记为一次 soft failure；达到阈值后进入 cooldown。

### 6.2 已经开始输出后的断流

适用情况：已经发出有效 SSE/响应事件后，读取上游流失败、上游返回错误事件或连接断开。

动作：

1. 不自动把完整请求重放到另一个账号。
2. 记录该账号-模型失败，并立即将它加入当前请求的 `failedAccountIDs`。
3. 将错误包装为明确的可恢复 SSE error event：

```json
{
  "error": {
    "type": "upstream_temporarily_unavailable",
    "message": "当前上游暂时不可用，请稍后继续",
    "retryable": true,
    "resume_supported": false,
    "retry_after_seconds": 10
  }
}
```

4. 若上游已返回可用的 response ID，则保留该 ID 供客户端显式继续；否则客户端“继续”视为新请求，并由调度器选择其他健康账号。
5. 记录上游已产生的 usage；usage 不完整时进入待核对状态，不直接重复扣费。

### 6.3 不可安全重放的请求

包含工具调用、函数调用、外部副作用或幂等性未知的请求，不做自动同账号重试。返回 `retryable=true` 的错误，由客户显式继续，继续请求必须避开本次失败账号-模型。

## 7. 冷却与恢复状态机

默认运行时策略：

```text
首个临时失败       -> soft failure，无未来强制冷却
同窗口第二次失败    -> cooldown 10 秒
同窗口第三次及以后  -> cooldown 45 秒
连续稳定成功        -> 清除该账号-模型失败计数
```

具体要求：

- 失败窗口默认 1 分钟；窗口外的失败重新从 1 次开始。
- cooldown 只作用于账号-模型，不影响同账号的其他健康模型。
- 当前请求无论冷却状态是否已经写入，都必须排除已失败账号，避免同一轮请求重复命中。
- 401/402/403/余额不足/明确权限错误沿用持久化不可调度逻辑，不等待 transient cooldown。
- 半开探测每个账号-模型只允许一个并发探测；探测成功清除运行时状态，失败则延长 cooldown。
- 不允许在“所有账号都 cooldown”时立即清空全部状态；必须使用单探测和抖动，避免故障风暴。

## 8. 缓存与会话粘性

### 8.1 粘性保留规则

- 成功请求继续使用原有 sticky account/session。
- 单次临时失败不会立即清除全局粘性；只有当前请求重试失败或进入 cooldown 时，才将该账号-模型标记为不健康。
- 客户的“继续”如果对应同一 response/session，优先选择原账号；但原账号-模型处于 cooldown 或当前任务刚刚失败时必须跳过。
- 账号切换原因必须被记录为 `cache_preservation_mode=sticky|same_account_retry|failover_after_failure|half_open_probe`。

### 8.2 缓存收益可观测性

每次请求/尝试至少记录：

- 账号 ID、调度模型、尝试编号；
- 是否保持 sticky；
- 是否发生同账号重试或跨账号 failover；
- cache read/creation token（若上游提供）；
- 请求失败前是否已开始输出；
- 本次尝试是否产生 usage。

监控需要同时观察：

- 缓存命中率；
- 平均输入成本；
- 首 token 延迟；
- 流式失败率；
- 账号-模型 cooldown 命中率；
- failover 后的成功率。

## 9. 计费与幂等

自动重试不能导致重复扣费。实现必须满足：

1. 一个客户请求有稳定的 logical request ID，多个上游尝试有不同 attempt ID。
2. usage 入账按 logical request ID + upstream attempt 唯一约束或等价幂等键去重。
3. 未收到 usage 的 502/连接错误不扣除额外客户费用。
4. 已收到部分 usage 但流中断时，保留实际 usage；未知部分进入 reconciliation，不凭猜测重复扣费。
5. 同账号重试和跨账号 failover 都必须在账务记录中可追踪。

## 10. 客户与管理员体验

### 10.1 客户侧

- 错误不再只显示 `stream disconnected`，而显示“当前上游暂时不可用，请稍后继续”。
- 明确提供 `retryable` 和 `retry_after_seconds`。
- 流式已有部分输出时保留已显示内容，不自动拼接另一账号的重复完整回答。
- 客户点击“继续”时，服务端自动避开本次失败的账号-模型；客户无需重启客户端或重建 API Key。

### 10.2 管理员侧

管理员页面需要能看到：

- 账号-模型当前状态：healthy、soft-failed、cooldown、hard-disabled、half-open；
- 最近失败次数、最近错误时间、cooldown 到期时间；
- 上游状态码/错误类型/是否已开始流式；
- 一键“立即冷却”“恢复调度”“执行单次探测”；
- 失败账号是否仍被 sticky session 引用。

## 11. 可观测性与告警

新增或统一以下事件：

- `openai.stream_upstream_failure`
- `openai.account_model_soft_failure`
- `openai.account_model_cooldown_started`
- `openai.account_model_cooldown_skipped_for_cache`
- `openai.failover_after_stream_failure`
- `openai.account_model_half_open_probe`
- `openai.retry_billing_reconciled`

P0/P1 告警建议：

- 同账号-模型 5 分钟内连续失败超过阈值；
- 一个分组超过半数账号-模型进入 cooldown；
- 客户流式断流率升高且 failover 成功率下降；
- 失败后同一账号再次被选中的比例异常升高；
- 缓存命中率下降超过基线，同时 failover 比例上升。

## 12. 验证计划

### 12.1 单元测试

- 首次 502 允许一次同账号短重试；
- 第二次失败进入 10 秒 cooldown；
- 第三次失败进入 45 秒 cooldown；
- cooldown 按账号-模型隔离；
- 成功后清除失败状态；
- 流式已输出后失败不会自动重放完整请求；
- 当前请求失败账号始终被排除；
- 401/402/403 不走 transient retry；
- 所有账号 cooldown 时只允许一个 half-open probe；
- retry/failover usage 入账幂等。

### 12.2 集成测试

- 模拟上游“首字节前 502”；
- 模拟“首字节后断流”；
- 模拟一个账号 `terra` 成功、同账号 `sol` 连续失败；
- 模拟缓存命中计数，验证 sticky 路径不发生无意义切换；
- 模拟工具调用请求，验证不自动重放；
- 模拟客户端点击继续，验证选择新健康账号；
- 验证错误 SSE 结构和 `retry_after_seconds`。

### 12.3 生产灰度

1. 先收敛 blue/green 到同一已审查版本。
2. 以 report-only 记录 cooldown 决策，不改变调度，观察缓存命中率和失败账号重复选中率。
3. 开启“当前请求失败账号排除”。
4. 开启首错同账号短重试，仅限安全重放请求。
5. 开启账号-模型 cooldown 和 half-open probe。
6. 完成真实 SSE、继续请求、usage 对账和回滚验证后，才标记生产完成。

## 13. 验收标准

本设计实现并部署后，必须同时满足：

- 流式中途断流不再让同一账号-模型在短时间内无限重复被选中；
- 首次临时故障不会无条件切账号，健康会话的缓存命中率没有异常下降；
- 连续故障会在规定阈值内进入 cooldown；
- 客户“继续”能自动避开刚失败的账号-模型；
- 自动重试不会重复扣费或重复执行外部工具副作用；
- 所有账号不可用时有明确、可重试的错误，不会同步打爆全部上游；
- 管理员能看到并手动恢复账号-模型；
- 线上验证包含健康接口、SSE、继续请求、缓存 token、计费对账、容器身份和回滚证据。

## 14. 待用户确认的默认决策

本规格默认采用：

- 账号-模型级 transient cooldown；
- 首次安全重放错误允许一次同账号短重试；
- 流式已输出后不自动重放；
- cooldown 使用 10 秒 / 45 秒递进；
- 全部 cooldown 时采用单半开探测；
- 计费按 logical request + attempt 幂等；
- 生产先 report-only，再逐步开启实际隔离。

用户确认后，再进入实施计划；本文件本身不改变生产行为。
