# 行动晨报与账号名称告警设计

## 目标

把当前面向运营者的飞书日报从“全量账号报表”收敛为“行动晨报”：

- 先给出当天是否需要介入的结论；
- 只展开异常账号和可执行建议；
- 健康账号不再逐条占用卡片空间；
- 完整指标继续留在运维后台；
- 站内运行、余额、倍率与恢复告警在用户可见区域显示账号名称，不再显示 `account #35` 一类数据库对象标签。

目标读者是每天通过手机查看飞书消息的中转站运营者。首要成功标准是：读者在首屏内知道“今天是否需要处理、处理谁、为什么”，不需要先读完所有账号明细。

## 现状问题

生产截图暴露出以下问题：

1. 日报固定渲染质量、利润、待处理和全量明细四个 Markdown 大段。
2. 每个账号明细在一行中塞入账号名、成功率、TTFT、P95、倍率和毛利，移动端通常折成两到三行。
3. 异常账号同时出现在“待处理”和“明细”，信息重复。
4. 健康账号与异常账号使用相同视觉权重，真正需要介入的事项被长列表淹没。
5. 站内流量长期没有错误率和 SLA 数据时仍输出 `错误率 — · SLA —`，形成无效字段。
6. 告警渲染只收到 `{kind, id}`，标题和正文对象因此显示为 `account #35`，即使 `ListAccounts` 和 account-monitor 投影已经提供账号名称。
7. 上游定价兜底来源目前只在全量账号明细的倍率字段中可见；移除明细后仍需保留紧凑、可审计的利润覆盖口径。

## 设计原则

- **行动优先**：日报只展开需要运营者处理的对象。
- **结论优先**：质量和经营结论在行动项之前，全量证据在运维后台。
- **一个账号一个行动项**：同一账号出现多个问题时，只展示优先级最高的问题。
- **名称面向用户、ID 面向系统**：飞书展示账号名，事件键和证据哈希继续使用稳定 ID。
- **不伪造完整性**：数据不可用或利润无法核算时明确降级，不输出看似正常的零值。
- **不改变业务判定**：本次调整信息组织和身份展示，不修改健康阈值、告警阈值、探测频率或事件状态机。

## 行动晨报

### 卡片结构

标题缩短为：

```text
中转站晨报 · 7月27日
```

正文固定按以下顺序组织：

```text
运行概览
10 个稳定｜1 个降级｜0 个不可用
P95 中位 3.8s｜10 个偏慢

经营情况
今日无有效流量，利润暂不可核算
利润覆盖 10/11 个账号｜3 个采用上游公开定价

需要处理 · 4
严重  Pro20x-XN-0.25
      余额耗尽

注意  特惠-XM-0.045
      成功率 76%｜HTTP 错误

注意  claude-SHUAI
      倍率不可用｜利润未核算

调整建议
GPT-Pro：建议由 A 切换到 B｜成功率更高且延时更低

其余 7 个账号无待处理项

[查看运维后台]
```

实际卡片继续使用 Feishu 稳定版 interactive card 和 `lark_md`，不引入未验证的新版卡片组件。行动项使用短行和空行建立层级，避免依赖飞书客户端不一致的表格布局。

### 标题颜色

标题模板由当天状态决定：

| 条件 | 标题颜色 |
|---|---|
| 监控数据不可用 | 橙色 |
| 存在不可用账号 | 红色 |
| 存在降级账号、倍率问题或其他行动项 | 橙色 |
| 无待处理项 | 绿色 |

颜色只表达当日行动等级，不参与事件判定。

### 运行概览

运行概览保留：

- 稳定、降级、不可用账号数；
- TTFT P95 中位数；
- 偏慢账号数；
- 具备同口径昨日样本时的健康账号变化。

偏慢账号只在汇总中计数，不逐条进入行动项。现有健康判定中“偏慢不降档”的规则保持不变。

当账号监控数据不可用时：

```text
运行概览
数据不可用｜Sub2API 账号监控读取失败
```

不得同时输出 `0 个降级`、`0 个不可用` 或“无待处理项”。

### 经营情况

有真实流量且利润可核算时：

```text
经营情况
请求 57｜收入 $140.00｜成本 $49.00
毛利 $91.00｜毛利率 65.0%
利润覆盖 10/11 个账号｜3 个采用上游公开定价
```

无真实流量时：

```text
经营情况
今日无有效流量，利润暂不可核算
```

有流量但所有相关账号倍率不可用时：

```text
经营情况
利润暂不可核算｜N 个账号倍率不可用
```

部分账号倍率不可用时，汇总只包含可核算账号，并明确覆盖数。不得继续输出长期为空的错误率和 SLA 字段。

为保留上游定价兜底的可审计性，`ProfitLine` 增加：

- `TotalAccounts`：当日日报投影账号总数；
- `PricedAccounts`：具有可信倍率或上游定价兜底倍率的账号数；
- `UpstreamPricedAccounts`：实际采用 `upstream_pricing` 兜底的账号数。

使用上游定价的账号不进入待处理项，但计数必须在经营口径中可见。

### 行动项

行动项来源仍是日报现有健康判定、余额状态和倍率可用性，不新增探测。

`PendingItem` 增加结构化等级，渲染不得通过中文文案反推严重性：

| 等级 | 典型问题 | 展示标签 |
|---|---|---|
| critical | 余额耗尽、不可用 | `严重` |
| warning | 降级、HTTP 错误、成功率下降 | `注意` |
| accounting | 倍率不可用、利润未核算 | `核算` |

排序规则：

1. `critical`
2. `warning`
3. `accounting`
4. 同等级保持账号在原始投影中的稳定顺序

同一账号存在多个问题时只显示最高优先级项。问题详情必须使用运营可读文案，不展示原始响应、Base URL 或凭据。

行动项数量超过卡片预算时，优先保留高等级项，并显示：

```text
其余 N 项见运维后台
```

### 调整建议

只有 `accountrecommendation` 给出 `candidate_better` 且分组为公开分组时才显示。

建议不与账号异常混排，单独放在“调整建议”下。没有建议时整节省略。

### 移除全量明细

飞书卡片不再渲染逐账号 `AccountDetailLine`，并删除“明细”整节。

以下字段只在运维后台保留：

- 单账号成功率；
- TTFT P50；
- 延迟 P95；
- 单账号倍率及倍率来源；
- 单账号毛利贡献；
- 站内流量错误率和 SLA。

日报底部仅显示：

```text
其余 N 个账号无待处理项
```

这里的 `N` 是账号总数减去具有行动项的唯一账号数。数据不可用时不显示该行。

## 账号名称告警

### 展示规则

站内运行、余额耗尽、倍率变化及其恢复告警统一显示账号名称：

```text
站内运行告警：特惠-SHUAI

对象：特惠-SHUAI
```

用户可见内容不得出现：

- `account #35`
- `账号 #35`
- 单独的数据库账号 ID

账号名称为空时显示：

```text
账号名称不可用
```

不得回退为数据库 ID。

### 内部身份保持不变

`opsmonitor.object` 增加仅用于展示的 `name` 字段。以下内部身份继续只使用 `{kind, id}`：

- incident key，例如 `site:account:35:paused`；
- multiplier baseline key；
- evidence hash；
- 事件状态机查询与恢复关联；
- 通知去重键。

因此名称展示变更不会创建新的事件身份，也不会让恢复通知脱离原告警。

### 名称数据流

`Service.Run` 已经通过 `ListAccounts` 获取账号 ID 与名称。它构建：

```text
account ID -> account name
```

并在以下路径创建 `object` 时注入名称：

- active 但 paused；
- 15 分钟/24 小时站内运行指标；
- 倍率变化；
- 余额耗尽；
- 账号质量恢复。

account-monitor 投影自身也包含名称；实现必须以 `ListAccounts` 映射为统一展示来源，避免不同投影名称漂移。若某条质量证据只有 ID，则通过上述映射补齐名称。

公开分组告警不在本次名称修复范围内，继续使用现有公开分组身份；私有分组名不得因本次改动进入通知。

## 组件边界

| 组件 | 变更职责 |
|---|---|
| `dailyreport/health.go` | 计算账号总数、利润覆盖数、上游定价账号数和结构化行动等级；不再构建飞书全量明细 |
| `notify/digest_v2.go` | 渲染行动晨报、动态标题颜色、行动项排序/去重和卡片预算 |
| `opsmonitor/service.go` | 将账号名称传到渲染对象，同时保持 ID 事件身份不变 |
| `notify/feishu.go` | 继续提供稳定版 interactive card 类型与 30 KiB 上限；不扩大通用卡片模型 |
| `/ops` | 继续提供完整账号证据，本次不改页面 |

## 卡片大小与脱敏

- `maxCardBytes = 30 KiB` 保持不变。
- 摘要、经营和行动项分别走现有有界渲染逻辑。
- 预算不足时先截断低优先级行动项，再截断调整建议；运行概览和经营情况不得被截断。
- 账号名、问题详情和建议继续经过 `digestValue` / `safeValue`。
- 卡片不得包含 API Key、Access Token、Base URL、上游原始响应或用户身份标识。

## 测试策略

### 日报构建测试

- 统计 `TotalAccounts`、`PricedAccounts`、`UpstreamPricedAccounts`；
- 上游定价兜底计入利润覆盖，不进入倍率待处理；
- 同一账号多个问题只产生一个最高优先级行动项；
- 数据不可用时不生成假正常统计。

### 日报渲染测试

- 卡片顺序为运行概览、经营情况、需要处理、调整建议、无待处理账号数；
- 不再包含“明细”、TTFT P50、单账号 P95 和全量账号列表；
- critical、warning、accounting 稳定排序；
- 动态标题颜色符合红、橙、绿规则；
- 无流量和利润不可核算使用单句结论；
- 上游定价账号数可见；
- 行动项超限时保留严重项并显示剩余数量；
- Card JSON 不超过 30 KiB；
- 脱敏护栏继续生效。

### 告警测试

- paused 告警标题和正文显示账号名；
- 站内运行、余额耗尽、倍率变化和恢复告警显示账号名；
- 用户可见 Card JSON 不包含 `account #` 或数据库 ID 标签；
- 空名称显示“账号名称不可用”；
- incident key 仍为 `site:account:<id>:<metric>`；
- evidence hash 和去重身份不因展示名称变化；
- 恢复通知继续关联原事件。

## 部署与验收

- 从 Git 树导出部署，不同步脏工作区。
- 备份生产 `compose.yaml`；只构建和重建 `relay-ops`。
- Sub2API、PostgreSQL、Redis 和 Caddy 容器 ID 必须保持不变。
- 新容器必须健康且重启次数为 0。
- 部署后检查生成的 Card JSON 和容器日志，不人为绕过去重发送重复日报。
- 下一次正常 09:02 日报用于确认飞书移动端真实渲染。
- 新产生的账号告警必须以账号名为标题；内部 incident key 仍使用账号 ID。

## 不在范围内

- 修改健康、降级、不可用的判定阈值；
- 修改告警确认窗口、探测频率或 scheduler；
- 自动恢复或启用 paused 账号；
- 修改 `/ops` 页面；
- 使用 Feishu 新版卡片组件或自定义表格；
- 重新设计公开分组告警；
- 推送历史日报或制造故障来验证通知。

## 完成标准

1. 日报首屏能看到运行结论、经营结论和行动项数量。
2. 飞书日报不再包含全量账号明细。
3. 异常账号在卡片内只出现一次。
4. 健康账号仅以“其余 N 个账号无待处理项”汇总。
5. 上游定价兜底的账号数量在经营口径中可见。
6. 所有账号类告警标题和正文只显示账号名称。
7. 内部事件键、证据哈希和历史恢复关联保持基于 ID。
8. 卡片体积、脱敏、构建、测试和生产部署门禁全部通过。
