# 运维监测页与飞书双区监控设计规格

**日期：** 2026-07-23  
**状态：** 设计已获确认，待规格复核后进入实施计划  
**范围：** relay-ops `/ops` 管理员监测页、站内运行聚合、账号池质量投影、飞书日报/告警/恢复消息

## 1. 背景与目标

当前账号池质量巡检已经由 systemd 每 15 分钟执行，动态读取 Sub2API 原生 `active && schedulable` 账号，并记录稳定性、TTFT、倍率和明确余额不足。relay-ops 已有管理员 `/ops`、飞书主动告警/恢复/日报和 Interactive Card 发送能力，但页面与日报仍缺少统一的两类运行信息：

1. **站内运行情况：** 公开分组和当前实际参与调度的账号的请求量、错误率、稳定性、TTFT 和总耗时。
2. **上游账号质量：** 账号倍率、巡检可用性、巡检 TTFT、最近结果和余额不足状态。

本设计的目标是复用 Sub2API 原生管理员聚合和监控能力，把两类信息以同一套脱敏、可解释、可告警的口径展示在 `/ops` 和飞书中。

## 2. 非目标与硬约束

- 不修改 Sub2API 原生 `/monitor` 页面、接口或数据模型。
- 不写死任何供应商名称、Base URL、Key、模型响应或账号归属；“当前上游”只表示 Sub2API 当前 `active && schedulable` 账号集合。
- 不建立第二套路由、灾备、模型发布、账号权重或余额系统。
- 不提供浏览器录入 Base URL、Key、候选、账单会话、probe 或路由切换控件。
- relay-ops 保持 `RELAY_OPS_MODE=read_only`；飞书保持 `RELAY_OPS_FEISHU_COMMAND_MODE=dry_run`。
- `/ops` 页面和 `/relay-ops/api/ops-view` 继续使用隐藏管理员鉴权；匿名或非管理员请求返回隐藏 `404`。
- 不读取、输出或持久化生产密钥、Cookie、完整用户身份、模型响应正文或完整聊天 ID。
- 正常巡检不逐条发送飞书消息；不制造合成故障、不发送合成告警、不删除去重记录。

## 3. 方案与选择

### 方案 A：原生聚合投影（采用）

扩展现有 Sub2API reader，使原生 `snapshot-v2` 和 usage stats 支持 `account_id` 过滤；relay-ops 只做动态账号筛选、字段投影、脱敏、窗口判断和消息渲染。

优点：数据源唯一、与 `/monitor` 和 Sub2API 原生后台一致、改动小、不会产生第二套路由或聚合语义。代价是 `/ops` 刷新时会多读取若干只读聚合接口，需要设置有界超时并在单个对象失败时显示明确的“读取失败”。

### 方案 B：巡检脚本预聚合

由 systemd 任务额外写入所有站内聚合快照，`/ops` 只读快照。实现简单，但会引入延迟和第二份聚合数据，且账号质量与站内运行的时间窗口更容易漂移。

### 方案 C：独立监控 API

新建完整监控 API 和数据模型。扩展性高，但会重复实现 Sub2API 权限、聚合和监控历史，超出当前轻量目标。

采用方案 A。

## 4. 数据流与边界

```text
Sub2API 原生 Admin API
  ├─ ListGroups/ListAccounts
  ├─ snapshot-v2(time_range=24h, group_id/account_id)
  ├─ usage/stats(group_id/account_id, period=24h)
  └─ 原生 /monitor（页面保持不动）
          │
          ▼
relay-ops Native Reader
  ├─ 过滤 active && schedulable 账号
  ├─ 读取原生分组/账号聚合
  ├─ 读取账号池巡检结果文件
  ├─ 计算样本不足、过期和告警窗口状态
  └─ 生成脱敏 OpsView / Feishu 双区摘要
          │
          ├─ 管理员 /ops（只读）
          └─ 飞书 09:00 日报、确认告警、恢复通知
```

站内运行指标必须来自 Sub2API 原生聚合接口；账号池质量指标继续来自现有 `sub2api-account-quality-monitor.timer` 产出的严格无秘密结果文件。两类数据不互相伪造：原生聚合失败显示“读取失败”，巡检结果缺失或超过现有 20 分钟门限显示“证据过期/等待证据”。

## 5. `/ops` 信息架构

页面顺序固定为：

1. **状态条**：刷新时间、relay-ops 模式、飞书命令模式、原生 `/monitor` 链接。
2. **站内运行**：
   - 公开分组表：24h 请求数、错误率、稳定性/SLA、TTFT P95、总耗时 P95、样本状态。
   - 当前调度账号表：账号 ID/名称、所属公开分组、24h 请求数、错误率、稳定性、TTFT P95、总耗时 P95、当前调度状态。
3. **上游账号质量**：动态 `active && schedulable` 账号的倍率、巡检稳定性、成功率、TTFT P50/P95、最近结果、余额不足状态、证据时间。
4. **内测开放门禁**：保留现有只读门禁摘要，不新增写控件。
5. **事件与确定性只读分析**：保留现有事件/Agent 摘要。
6. **技术详情**：默认折叠，展示快照 ID、账号集合 hash、证据时间和状态码，不展示敏感值。

表格排序必须稳定：公开分组按 Sub2API 返回顺序；账号按账号 ID；质量记录按账号 ID。无数据时使用明确空状态，不显示伪造的 0%。

## 6. 统一状态语义

每个分组或账号的展示状态只能取以下语义：

- `正常`：数据新鲜且满足窗口条件。
- `样本不足`：15 分钟窗口请求数少于 20，仅展示观测值，不触发错误率/TTFT 告警。
- `读取失败`：Sub2API 原生聚合请求失败；保留上一次成功时间（如有），不当作正常。
- `证据过期`：账号质量结果超过现有 20 分钟门限。
- `暂停调度`：Sub2API 返回账号不可调度或暂时暂停。
- `余额不足`：仅当巡检结果明确为 `balance_exhausted` 时显示，普通错误不得推断为余额不足。

缺少成功样本时 TTFT 显示“无成功样本”，倍率缺失显示“未提供”，错误率缺失显示“未知”。

## 7. 告警与恢复规则

### 7.1 站内运行告警

- 15 分钟窗口请求数 `< 20`：标记样本不足，不告警。
- 错误率 `>= 5%` 且连续两个完整窗口：确认告警。
- TTFT P95 相对 24 小时基线恶化 `>= 30%` 且绝对值 `> 3s`，连续两个完整窗口：确认告警。
- 分组或账号连续完全失败：立即确认告警。
- Sub2API 返回账号暂停调度：立即确认告警。

### 7.2 上游账号质量告警

- 倍率发生变化：立即确认告警，消息显示旧值/新值和证据时间。
- 巡检结果明确为 `balance_exhausted`：立即确认告警。
- 连续巡检失败但未明确余额不足：先在 `/ops` 展示失败原因；只有满足站内连续窗口规则时才发送稳定性告警，不猜测余额归因。

### 7.3 去重与恢复

- 告警键由域、对象 ID、指标名组成，例如 `site:account:10:error_rate`；不包含供应商名称猜测。
- 相同告警仅在证据 hash 变化、严重级别升级或状态恢复时再次发送。
- 恢复需要一个完整健康窗口；恢复卡包含恢复窗口、当前值和观察建议。
- 正常 15 分钟巡检不发送飞书消息。

## 8. 飞书消息设计

### 8.1 09:00 双区日报卡

每天只发送一张 Interactive Card，使用现有 App Bot/Webhook 共用发送器和官方稳定 `elements + div/lark_md + action/button` 结构。

卡片固定包含：

- 标题和报告日期。
- **站内运行**：公开分组摘要行；随后列出当前 `active && schedulable` 账号摘要行。
- **上游账号质量**：倍率、巡检可用性、TTFT P95、最近结果、余额不足状态。
- **数据状态**：样本不足、读取失败、证据过期明确标注。
- 报告生成时间、证据快照 ID 和“打开运维后台”按钮。

卡片正文不能超过 30 KB；对象过多时按稳定顺序截断，并在末尾显示“其余对象请在 `/ops` 查看”，不得随机丢弃异常对象。

### 8.2 告警卡与恢复卡

告警/恢复继续使用独立卡片，不和日报合并。卡片字段固定为：对象、指标、当前值、基线、连续窗口、证据时间、状态、建议动作、`/ops` 链接。不得包含 Base URL、Key、模型响应正文或完整用户身份。

## 9. 错误处理与安全

- 每个 Sub2API 只读请求设置有界超时；单个账号或分组读取失败不泄漏敏感错误正文。
- `/ops` API 返回结构化状态，但不返回上游凭据、完整 API URL、Cookie、密钥或完整聊天 ID。
- 前端自动刷新失败时保留当前页面并显示“自动更新暂时失败”，继续定时重试；鉴权失败跳转隐藏 `404`。
- relay-ops 不执行任何路由、账号、倍率、价格、余额、Key、候选或 probe 写操作。

## 10. 测试与验收

### 本地自动化

- Sub2API reader：验证 `account_id` 查询参数、原生 snapshot/usage DTO、缺失字段和 HTTP 错误。
- Ops source/view：验证公开分组和 active/schedulable 账号双区、样本不足、读取失败、暂停调度、过期证据和稳定排序。
- 告警状态机：验证两窗口确认、完全失败立即告警、倍率变化、明确余额不足、恢复和证据 hash 去重。
- 飞书模板：验证双区日报字段顺序、状态标签、截断、脱敏、30 KB 上限和 App Bot/Webhook 共用 payload。
- 权限契约：匿名 `/relay-ops/api/ops-view` 返回隐藏 `404`；`/monitor` 路由和页面内容未被修改。

### 生产只读验收

- relay-ops healthy、重启计数为 0、模式仍为 `read_only + dry_run`。
- `/ops` 管理员可见，匿名 API 保持隐藏 `404`。
- `/monitor` 返回 Sub2API 原生页面，未发生内容或路由改动。
- `/ops` 展示的账号集合与 Sub2API `active && schedulable` 集合 hash 一致。
- 生产 Sub2API 路由、账号、分组、倍率、价格、余额、Key 和数据库写入计数不变。
- 不发送合成告警；自然告警/恢复视觉证据继续作为非阻塞观察项。

## 11. 主线变更

完成本设计的实现和只读验收后，飞书监控主线以“站内运行 + 上游账号质量”统一口径收口；下一主线回到 D04 首发用户生产低额验收和内测开放准备，不再扩展第二套上游监控或修改 Sub2API 原生 `/monitor`。
