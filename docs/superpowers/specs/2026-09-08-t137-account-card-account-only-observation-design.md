## 问题证据与当前行为

截图中的账号卡片同时显示 `533/549 有效观测`、`成功率 0%`、连续绿色近期请求。三个区域没有消费同一份统计结果：

1. 卡片标题中的有效观测由账号级 `request_count - error_count` 在前端推导。
2. 卡片成功率在分组 Tab 内被分组级 `ListGroupRealRequestAggregates` 结果覆盖。
3. 时间线读取账号级 `ListRealRequestTimelines`。
4. 分组级和账号级真实请求查询使用 `usage_logs.actual_cost > 0` 代理“成功”。`actual_cost` 是用户扣费/收入事实，不是请求终态；成功但零扣费、免费、赠送、舍入为零或账务尚未完成的请求会被误判为失败。
5. 当前统一查询采用“同一五分钟桶有真实请求时忽略主动探测，否则只取最新一条探测”的互斥补位规则。这不符合用户明确要求的“有效观测 = 真实请求 + 主动探测”。
6. `account_monitor_results` 与 `account_monitor_bucket_terminals` 可能保存同一次探测的不同投影，若直接相加会重复计数，必须按探测运行身份去重。

因此，当前 0% 既可能是卡片作用域错位，也可能是 `actual_cost = 0` 导致的真实成功请求假阴性。该错误会继续传入质量评分和分组内调度质量顺序，不能用前端改文案或把 0% 隐藏为 `--` 解决。

## 目标

1. 账号卡片的健康和性能指标只按 `account_id` 聚合，切换分组 Tab 不改变同一账号的有效观测、成功率、失败数、TTFT、完整响应耗时、时间线、当前状态和账号质量分。
2. 分组仅用于筛选哪些账号卡片可见，并提供明确标注的分组上下文，例如目标组、分组倍率和该组实际调度排名；不得覆盖账号观测指标。
3. 有效观测严格定义为：

   ```text
   有效观测 = 去重后的真实逻辑请求终态 + 去重后的主动探测终态
   ```

4. 真实请求和主动探测逐条独立计数。两者发生在同一五分钟桶时仍全部进入有效观测，不再互相覆盖或补位。
5. 成功率严格定义为：

   ```text
   成功率 = 成功有效观测数 / 有效观测总数
   ```

6. 请求成功与否只由请求终态决定，禁止继续使用费用、利润、token 数或 TTFT 是否存在代理成功。
7. 账号摘要、卡片成功率、时间线、账号质量评分和调度质量输入消费同一账号级统一观测流。
8. 主动探测继续不参与用户扣费、收入、账号成本、利润和业务 token 统计。

## 非目标

- 不修改真实请求的路由、切号、重试、冷却、限流或并发控制。
- 不改变主动探测频率、探测模型、题面、模型检测算法或手动刷新入口。
- 不把主动探测写入 `usage_logs`，不伪造业务流水。
- 不修改 Sub 原生计费、钱包、充值、退款或利润事实源。
- 不做历史数据回填，不修改历史账单，不新增平行监控系统。
- 不在本任务中重做账号卡片视觉布局；只修正数据合同和必要的字段展示一致性。
- 本规格确认不构成主站或验收站发布授权。

## 方案比较

### 方案 A：只修前端显示

在前端用 `request_count - error_count` 重算成功率，并把 0% 改成推导值。改动最小，但 API、质量评分和调度输入继续错误；不同页面仍会出现不同数字。不采用。

### 方案 B：保留分组聚合，只修 `actual_cost > 0`

把分组查询的成功判定改为没有错误日志，同时保留分组结果覆盖卡片。它能修复一部分零成功率，但同一账号在不同分组 Tab 仍会显示不同账号指标，也不满足“有效观测 = 真实请求 + 主动探测”。不采用。

### 方案 C：建立唯一账号级统一观测流，分组只做筛选和调度上下文（采用）

复用现有 `usage_logs`、`ops_error_logs`、`account_monitor_results` 和 `account_monitor_bucket_terminals`，按账号生成一份统一观测流。真实请求与主动探测分别去重后直接合并；所有账号指标和质量事实只从该流聚合。分组只筛选账号、计算分组账务和解释该组调度排名。

该方案直接满足用户的第一性原则，不增加事实源，无迁移，能够一次消除作用域错位、费用代理成功、探测补位、前端自行推导和调度质量输入不一致等问题。

## 核心数据合同

### 账号作用域

- 统一观测流的唯一归属键是 `account_id`。
- 同一账号属于一个或多个分组时，其账号观测指标在所有分组 Tab 中必须完全相同。
- `group_id` 可以用于保留原始请求归属、分组账务和分组调度上下文，但不得成为账号卡片健康/性能指标的过滤条件。
- 全站账号列表和任意分组内账号卡片必须引用同一账号快照，不允许服务层复制账号行后再用分组窗口覆盖指标。

### 真实请求终态

真实请求来自 `usage_logs` 与 `ops_error_logs`，按以下顺序形成一个用户可见逻辑请求终态：

1. 去重键优先使用 `logical_request_id`，其次使用能够精确关联的 `request_id`/`client_request_id`，最后使用带来源前缀的记录 ID。
2. 同一逻辑请求的内部重试、切号尝试和中间上游错误不得重复扩大有效观测。
3. 存在最终成功业务流水时，该逻辑请求计一次成功；与其关联的中间错误不再单独计失败。
4. 没有最终成功流水、但存在可归责服务端或上游终态错误时，该逻辑请求计一次失败。
5. 客户端请求错误、确定性不支持模型、入站校验失败以及既有明确排除项沿用当前排除规则，不计账号服务质量失败。
6. `usage_completeness = 'unknown'` 的记录不猜测成功或失败；在终态未明确前不进入有效观测。
7. `actual_cost`、`total_cost`、token 数、TTFT 和完整耗时均不得决定成功与否。

### 主动探测终态

- 主动探测来自账号监控原生事实，只有明确终态 `success` 或 `failed` 进入有效观测。
- `pending`、运行中、取消但未形成终态、数据不完整或未知状态不进入有效观测。
- 同一次探测可能同时出现在 `account_monitor_results` 与 `account_monitor_bucket_terminals`；以 `run_id + account_id` 为主去重键，没有可靠 `run_id` 时使用稳定的原始记录身份，禁止仅按时间猜测合并。
- 每个去重后的探测终态计一次观测。不得只取五分钟桶内最新一条，也不得因为同桶存在真实请求而忽略探测。
- 成功探测计成功，失败探测计失败；失败探测不产生 TTFT/耗时成功样本。
- 手动“刷新账号状态”和定时自动探测只要落入同一原生终态事实表，使用相同计数规则，不按触发方式区别待遇。

### 聚合恒等式

对每个账号和查询窗口 `[start, end)`：

```text
real_request_count = 去重后的真实请求终态数
active_probe_count = 去重后的主动探测终态数
request_count = real_request_count + active_probe_count

success_count = real_success_count + probe_success_count
error_count = real_failure_count + probe_failure_count
request_count = success_count + error_count

success_rate = success_count / request_count
```

- `request_count = 0` 时成功率为无数据，前端显示 `--`，不能显示确定性的 `0%`。
- 后端成功率保持现有账号监控 API 的 0 到 1 比例，前端负责格式化百分比；禁止某些接口返回 0 到 100、另一些返回 0 到 1。
- 卡片标题直接使用后端 `success_count/request_count`，不得继续用 `request_count - error_count` 在前端二次推导。

### 性能与时间线

- TTFT P95、完整响应耗时 P95只统计成功且对应时长非空的有效观测。
- 成功但没有 TTFT/耗时的观测仍计入成功率，只不进入相应性能分位数。
- 时间线对统一观测流按展示桶聚合；真实请求和主动探测均显示，不再执行同桶互斥。
- 桶状态：全失败为红色；至少有成功但超过现有慢阈值为黄色；有成功且未超过阈值为绿色；无有效观测为空态。
- 时间线、摘要、成功率和质量评分必须使用完全相同的窗口边界和同一次服务快照。

## 账号指标与分组上下文边界

### 必须保持账号级的字段

- 有效观测、成功数、失败数、成功率。
- TTFT 与完整响应耗时指标。
- 近期请求时间线。
- 当前健康状态、数据新鲜度、最近观测时间。
- 账号质量证据、质量分和全局账号质量顺序。

### 可以保持分组级但必须明确标注的字段

- 当前查看的目标分组和分组倍率。
- 该账号在当前分组中的实际调度排名与调度解释。
- 当前分组内该账号真实业务流水产生的收入、成本和利润。

这些分组字段不得修改账号级有效观测或质量事实。调度器可以按分组策略、优先级、负载、冷却和资格计算最终排名，但其质量输入必须来自账号级统一观测，不能重新读取分组成功率覆盖账号质量。

## 端到端数据流

```text

        | 逻辑请求终态归并、排除中间重试和客户端错误
        v

                                     |

+ account_monitor_bucket_terminals   |
        | 探测运行去重                |

账号主动探测终态 ------------> 账号级统一有效观测流
                                     |
              +----------------------+----------------------+
              |                      |                      |
        账号窗口摘要             账号时间线             账号质量事实
              |                      |                      |
              +----------> 账号卡片同一快照 <----------+
                                                   |
                                  分组调度器读取账号质量输入

usage_logs --按原生业务口径--> 分组收入/成本/利润
```

## API 与前端合同

- 保持 `GET /api/v1/admin/accounts/monitor?range=24h|7d|30d` URL 和现有账号/分组容器结构。
- 账号对象增加或稳定输出明确字段：`request_count`、`success_count`、`error_count`、`success_rate`、`real_request_count`、`active_probe_count`。
- 若为兼容已有客户端需暂时保留 `sample_count`、`success_sample_count`、`probe_*` 或 `real_request_*` 字段，这些字段必须由同一统一观测结果派生，不能存在数值冲突。
- `groups[].accounts[]` 中账号观测字段必须与顶层 `accounts[]` 中相同账号逐字段一致。
- 前端账号卡片不再计算 `request_count - error_count`；直接展示后端成功数和总数。
- 分组切换只能改变卡片集合、分组上下文和分组调度信息，不能改变同一账号的观测指标。
- 无观测显示 `--`；真实 0 次成功且存在失败观测时才显示 `0%`。
- API 查询失败沿用现有错误状态，不回退到旧分组聚合，也不填充假 0。

## 服务与仓储边界

- 在现有 `account_monitor_repo.go` 中建立一个可复用、可测试的账号统一观测选择器，供窗口聚合、时间线和累计计数复用。
- 不新增第二个 repository、缓存表或定时汇总事实源。
- 删除或停止使用账号卡片路径中的 `ListGroupRealRequestAggregates`/`ListGroupWindowAggregates` 质量覆盖。保留它们仅限仍有独立分组报表消费者时；若已无消费者则在本任务中删除死代码和对应测试。
- 服务层先生成一次账号快照，再按成员关系挂载到各分组，避免对嵌入账号副本重新投影不同质量字段。
- 调度投影继续调用原生 `schedulerProjection.Project`；只替换其 `QualityOrder`/质量事实输入来源，不自行重写调度算法。

## 失败与安全语义

- 任一统一观测查询失败时，账号监控接口返回错误或明确不可用状态；不得静默退回旧口径。
- 无法可靠关联的错误记录按现有安全规则保留为独立失败终态，不得错误并入其他账号或逻辑请求。
- 无法可靠去重的探测不得同时读取两套投影后相加；优先选择权威探测终态来源，并记录可诊断告警。
- 不返回凭据、请求体、完整 API Key、上游敏感响应或探测题面。
- 本任务不写生产业务数据，不修改账号状态，不触发主动探测，不改变调度配置。

## 兼容性与迁移

- 预期无数据库 schema 迁移、配置迁移和历史回填。
- 历史原始记录不改写；查询时按新合同即时重算所选时间窗口。
- API 以添加明确计数字段和统一旧字段语义为主，避免破坏现有前端和潜在客户端。
- 若实现调查发现缺少稳定探测去重键，必须停止并回到规格阶段；不得用时间近似去重或未经批准新增迁移。

## 测试策略

### 仓储测试

- 候选只完成功能实现与直接相关测试，提交后进入 `READY_FOR_ROOT_REVIEW`；不得从候选 worktree 构建或发布部署制品。

## 自审

- 无 `TBD`、`TODO`、占位符或模糊比例定义。
- 明确选择账号级作用域，分组只做筛选、账务和调度上下文。
- 明确真实请求与主动探测是相加关系，不再按桶互斥。
- 明确成功终态与费用解耦，并覆盖零费用成功。
- 明确探测双表去重、窗口、空值、性能样本、账务隔离、调度输入、兼容和失败语义。
- 范围可以由一个实施计划闭环，无需拆分多个任务包。
