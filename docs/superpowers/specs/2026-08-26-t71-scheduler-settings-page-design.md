# T71 调度设置独立页面与交互修复设计规格

## 问题与目标

T68 已将业务化调度策略投影到管理员设置页，但生产页面仍嵌在“系统设置 -> 网关服务”的大型表单中。数字优先级和三个三段控件仅更新 `aria-pressed`，没有对应的视觉类名；账号均衡的选择也没有在预览中给出可辨识的结果。这使运营无法确认点击是否生效，也无法快速理解均衡策略的影响。

本任务把该配置收敛为独立的管理员“调度设置”页面。运营能在一个页面中选择分组、配置业务优先级和三个固定运营控制，并在保存前看到当前草稿的平峰、高峰与会话场景结果。

## 原生能力与边界

- 继续使用 Sub2API 的 Vue Router `requiresAuth` / `requiresAdmin` 守卫和管理员侧栏。
- 继续读取活动 OpenAI 分组，读写既有 `/admin/settings` 与 `openai_advanced_scheduler_*` 字段。
- 继续使用服务端 T68 的业务策略编译、资格筛选、并发抢槽、冷却、sticky、fresh/DB recheck。
- 不新增调度器、API、数据库迁移、公平计数、第二配置事实源或按分组名称写死的运行时逻辑。
- “服务不中断”继续为不可配置、不可关闭的固定护栏。

## 方案选择

1. 在 SettingsView 内改善样式：改动最少，但仍把高频调度工作埋在通用设置中，不能满足独立管理员区域要求。
2. 新建页面但复制表单和状态：页面独立，但会产生第二套序列化/校验和后续漂移风险。
3. 新建 `SchedulerSettingsView`，抽取 T68 专用表单逻辑和呈现组件，复用原生 API：页面独立，同时保存仍由同一字段契约完成。采用此方案。

## 信息架构与交互

- 新路由：`/admin/scheduler-settings`，名称 `AdminSchedulerSettings`，管理员权限必需。
- 管理员侧栏在“系统设置”前显示“调度设置”；普通用户和非管理员不可见也不可访问。
- 页面只含一个调度工作面：顶部为调度实验开关与保存状态；开关开启后出现分组选择器。
- 已选分组以可点击的分组按钮组呈现，选中项有边框、背景、焦点环和 `aria-pressed=true`。下拉选择可作为窄屏等价入口。
- 每项经营指标的 1/2/3 均是按钮。选中数字应用明确的主色表面、边框、文字和焦点态；同一数字允许并列。
- “账号均衡使用”“高峰期保护”“会话连续性”均为固定三段控件。每次点击立即更新选中态、摘要和预览。
- 场景预览固定包含：平峰请求、高峰请求、会话切换。平峰文案必须反映 balance 选择；高峰反映 peak protection；会话反映 continuity。任何设置不绕过服务护栏。
- 保存前显示草稿状态；保存时禁用保存按钮并显示进行中；成功后更新快照与公共设置缓存；失败时保留草稿并显示原生错误信息。

## 视觉与可用性契约

- 产品界面采用克制蓝灰色阶，复用项目系统字体、按钮、Toggle 与深色模式，不引入新 UI 库。
- 单卡工作台用于完整配置工具；内部使用无嵌套卡片的分区、分隔线和紧密网格表达关系。
- 卡片圆角不超过 12px；不使用装饰性渐变、玻璃效果、彩色边条或超大阴影。
- 桌面优先为指标行与三列调整区；宽度不足时依次折叠成单列，文本不截断且触控目标至少 40px。
- 所有按钮具有 hover、active、focus-visible、disabled 和保存中状态；`prefers-reduced-motion` 下取消非必要过渡。

## 数据流与兼容性

1. 页面加载时读取现有系统设置和原生活动 OpenAI 分组。
2. 选择分组后用该分组已有业务策略生成草稿；无有效 priority 的遗留策略使用约定推荐值投影。
3. 交互只修改前端草稿；预览由草稿的 priority / operations 派生。
4. 保存时序列化既有 group policies，并只更新相关 `openai_advanced_scheduler_*` 字段，服务端继续忽略客户端 `compiled_snapshot`。
5. 从 SettingsView 删除 T68 的可见配置面，避免两个页面同时编辑同一字段。

## 验收与测试

- 路由有管理员守卫，管理员侧栏显示“调度设置”。
- 点击数字和每个三段选项后，`aria-pressed` 与可见选中样式均正确更新。
- 修改账号均衡后，平峰预览能区分“仅分散高负载 / 标准覆盖 / 优先补齐覆盖”。
- 高峰与会话预览分别随对应控件改变；服务不中断护栏始终可见。
- 选择分组、保存、保存失败和遗留无效 priority 回退均有直接 Vitest 覆盖。
- 运行 `pnpm vitest` 的直接测试、`pnpm typecheck`、`pnpm build` 与 `git diff --check`；部署前执行根合并后的同范围验证和蓝绿预检。

## 发布与回滚

本任务仅前端路由与呈现重构，没有迁移、后端接口或配置 schema 变化。发布必须从已验证的根 `main` 经 `ops/release-sub2api-blue-green.sh` 进行；预检若为 `downtime_required=true`，在任何切换前等待用户明确“允许停机部署”。回滚为重新发布此前生产提交；现有后端调度策略和已存策略值保持不变。
