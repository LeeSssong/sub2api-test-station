# Monitor V2 当前监控集合与历史边界设计

**日期：** 2026-08-09  
**状态：** 已批准（用户确认“是的，请你快速修复”）

## 问题

生产只保留三个启用渠道监控，但 `/monitor` 在管理员身份下仍枚举全部活动业务分组，导致四个未配置监控的分组也显示为卡片。三个现存监控又沿用了旧 monitor ID；更新端点、凭据、主模型或绑定分组不会建立新统计边界，7 天可用率、最新状态和时间线继续混入修改前历史。

## 目标

- `/monitor` 只展示当前启用监控能够稳定匹配到的活动分组。
- 普通用户继续看非专属活动分组；管理员可看已监控的专属活动分组。
- 保留旧探测记录用于审计，但当前状态、可用率和时间线只读取本次配置统计起点之后的记录。
- 端点、API Key、provider/API mode、主模型或绑定分组发生变化时推进统计起点；仅改名称、间隔、抖动、启用开关、模板或附加模型不重置主模型统计。
- 本次迁移把所有现存监控的统计起点推进到迁移执行时刻，使生产三个监控从新配置重新累计。

## 非目标

- 不物理删除 `channel_monitor_histories`。
- 不修改分组倍率、账号路由、调度、用户用量或客户计费。
- 不改变管理员原始历史查询的审计能力。
- 不引入停机迁移；只增加一列、一次有界更新和索引无关的查询条件。

## 数据与服务设计

`channel_monitors` 新增非空 `history_started_at TIMESTAMPTZ DEFAULT NOW()`。迁移对存量行写入迁移时刻。Ent/service 模型携带该字段；创建时使用当前时间。

更新监控前保存原身份快照。应用更新后，若 provider、API mode、规范化 endpoint、主模型、API Key（仅在提交非空新 Key 时）或 `group_id` 发生变化，则把 `history_started_at` 更新为当前时间。更新事务仍只修改监控配置，不删除历史。

当前状态聚合查询（批量/单项 latest、7/15/30 天 availability、Monitor V2 timeline）增加 `checked_at >= history_started_at`。管理员显式历史列表保持原始全量。

Monitor V2 先读取 enabled monitor user views，再将活动分组过滤为能通过 `group_id` 或 legacy `group_name` 匹配到至少一个 view 的集合，然后生成卡片。没有有效监控的活动分组不返回。

## 失败处理

- 监控读取失败仍沿用现有容错；没有 probe 时返回空卡片集合，而不是伪造分组状态。
- 绑定到已删除、停用或不可见分组的监控不出现在 `/monitor`。
- 迁移后尚无新样本时显示“样本不足/暂无探测记录”，直到主动或定时探测完成。

## 测试策略

- 服务测试锁定 public/admin 都只返回已监控且可见的活动分组，并保留 legacy name fallback。
- 更新服务测试锁定身份字段变化推进统计起点，非身份字段变化不推进。
- repository SQL mock/集成测试锁定 latest、availability、timeline 使用 `history_started_at`。
- 迁移测试锁定列非空、默认值及存量回填。
- 前端现有契约不变，运行 Monitor V2 全部测试和生产构建。

## 验收标准

- [ ] 生产 `/monitor` 只返回 GPT-Pro、GPT-Plus、GPT-特惠分组三张卡。
- [ ] 上线后旧 190 条历史不再参与当前 7 天统计和时间线。
- [ ] 三个监控重新探测后显示新配置的最新状态与延迟。
- [ ] 旧历史仍可通过管理员历史接口审计。
- [ ] 后端测试、前端测试、类型检查、构建、迁移和蓝绿线上验证通过。

## 风险

- 迁移到首个新探测之间会短暂显示样本不足；部署后立即对三个监控执行一次探测消除此窗口。
- 身份字段判定遗漏会再次污染历史，因此判定逻辑必须由表驱动测试覆盖。
