# 项目全局进度总账设计

日期：2026-07-31
状态：已确认

## 目标

解决多个窗口并行工作时无法快速判断“做了什么、是否部署、是否真正生效”的问题。项目设置一个唯一的全局进度总账，所有任务都先登记、后实施，结束时必须回填部署和生效结果。

## 唯一事实来源

`docs/project/project-progress.md` 是项目级任务状态总账。

- `AGENTS.md` 和 `CLAUDE.md` 负责约束工作流程。
- `docs/superpowers/specs/*`、`docs/superpowers/plans/*` 负责记录设计和实施过程。
- `docs/superpowers/reports/*` 负责记录验证证据。
- 任务当前状态以总账为准，验证报告作为证据链接。

## 状态定义

| 状态 | 含义 |
|---|---|
| 进行中 | 已登记但尚未完成部署闭环；包括实现中、待部署、待验证和外部阻塞 |
| 已完成 | 代码或配置已推送到服务端，已部署，且通过生产验证确认生效 |
| 准备完成 | 仅完成设计、研究、离线或本地验证；不算任务结束，也不计入完成数，是历史准备成果的非终态分类 |
| 暂停/取消 | 明确停止，不再作为当前进行中事项 |

一个任务的结束标准固定为：**已推送到服务端、已部署、已验证生效**。只完成本地测试、生成镜像、合并代码或写完报告，都不能标记为“已完成”。

## 登记内容

每个事项只保留以下信息：

1. 事项名称；
2. 为了解决什么问题；
3. 做了什么优化；
4. 可能影响什么；
5. 当前状态、更新时间和证据。

不在总账中保存密码、API Key、Cookie、Token、OAuth 凭据或其他敏感值。

历史回填条目的更新时间统一继承总账顶部的“更新时间”，以表示同一次证据复核快照；后续新增或状态变化的事项必须在本条内单独写明更新时间。

## 生命周期

1. 实施前：登记事项、目标、影响和初始状态“进行中”。
2. 实施中：发生范围、阻塞或风险变化时更新总账。
3. 部署后：补充部署版本、服务端结果和验证报告。
4. 只有部署和生效证据齐全，才将状态改为“已完成”。
5. 若只完成本地/离线准备，保持“准备完成”；若等待服务器、凭据、自然流量或用户操作，保持“进行中”并写明阻塞原因。

## 首次回填口径

首次回填从现有生产验证报告、项目当前状态文档和 Git 历史交叉核对：

- 明确写有生产部署并验证生效的事项，计入“已完成”；
- 只有本地、离线、研究、候选或镜像准备的事项，计入“准备完成”；
- 明确写有待部署、待验证、管理员更新待执行或生产激活待执行的事项，计入“进行中”；
- NO-GO、外部阻塞或仅保留历史证据的事项，单列说明，不伪造完成状态。

该口径优先保证“完成”代表真实可用，而不是代表代码或文档曾经写过。
