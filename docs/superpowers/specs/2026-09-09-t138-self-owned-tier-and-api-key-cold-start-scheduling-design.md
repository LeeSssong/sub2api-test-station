## 1. 问题与当前行为

### 1.1 运营目标

系统需要同时满足两种不同的运营意图：

1. 新增 API Key 账号时，管理员已经知道它的服务质量可能很好，希望通过调小账号 `priority` 数值让它立即获得真实请求，尽快形成质量样本。
2. 自购账号是管理员明确采购并维护的首选资源。正常情况下，自购账号应优先于 API Key 账号；自购账号之间不因历史样本多少互相制造虚假的质量差异。

运营目标不是让 `priority=1` 永久压过所有账号，也不是把没有样本的新账号伪造成满分账号，而是：

> 让管理员可以用现有账号优先级表达冷启动意图，让自购账号进入首选资源层，同时让后续真实运行结果能够纠正初始判断。

### 1.2 原生实现证据

- 账号已有 Sub 原生 `accounts.priority` 字段，当前约定数字越小越优先；新建账号需要保持默认 `50`。
- 旧/非统一质量路径已经在部分排序和 tie-break 中读取账号 priority，但统一质量调度路径主要按质量综合评分、成功率、TTFT、有效成本和账号 ID 组织候选，priority 不能可靠地帮助没有质量样本的新账号进入候选。
- 当前统一质量路径在硬资格、原生利润分区、候选池/Top-K、公平性和原生槽位获取之后完成账号选择；生图、Responses WebSocket 和 alpha-search 等已明确不属于统一普通文本质量路径。
- 现有 T95/T96/T114 质量、有效成本、利润保护、运行时健康、冷却、并发槽位和调度决策日志能力均属于原生调度链的一部分，本任务应在该链上最小扩展，不新增平行质量事实源。
- 当前代码已能区分账号类型和自购 OAuth/setup-token 等原生成本/调度语义；实施时必须复用现有自购归属判定，不新增重复的“是否自购”数据库事实字段。

### 1.3 根因

新 API Key 账号的质量证据为空并不代表质量差，但现有质量排序无法区分“未知”与“低质量”。如果未知账号被直接置底，管理员即使将 `priority` 调为 `1`，也可能无法改变实际候选池。

自购账号则是另一类信号：其首选性来自管理员采购与运营策略，不来自质量样本。把自购账号和 API Key 账号混入同一个质量数值，会导致：

- 为自购账号伪造质量分或伪造样本量；
- 质量排序与资源所有权策略混淆；
- 一个自购账号短期样本不足时错误落入 API Key 备用层；
- 运营无法解释“为什么同样没有样本的两个账号排序不同”。

## 2. 目标与非目标

### 2.1 目标

1. 在现有统一普通文本 OpenAI HTTP 调度路径中，将通过硬门禁的自购账号划入首选资源层。
2. 只要存在可用自购账号，正常请求优先在自购账号层内选择；没有可用自购账号时，才进入 API Key 账号层。
3. 自购账号层不依赖历史质量样本来证明“默认质量优于 API Key”；自购账号之间按管理员 priority、运行时负载、公平性和稳定 tie-break 选择。
4. API Key 账号质量证据为空或不足时，priority 作为有边界的冷启动先验，使管理员调低 priority 后账号可以进入候选并获得真实流量。
5. API Key 账号获得真实样本后，质量评分逐步取代冷启动先验；质量变差时不能因为历史 priority 低而永久保持首选。
6. 默认 `priority=50` 保持中性。所有账号均为默认值时，不改变现有质量调度的正常排序语义。
7. 账号 priority 修改后，后续新请求直接使用最新调度快照；不抢占已运行请求，不绕过 Sub 原生槽位。
8. 继续复用现有硬资格、利润控制、余额/额度、冷却、能力、失败隔离、候选池、Top-K、公平性、sticky 和安全切号边界。

### 2.2 非目标

- 不把 `priority` 变成永久硬覆盖，不保证 `priority=1` 每次都命中该账号。
- 不把自购账号写入一个伪造的固定质量分或固定样本量。
- 不新增“自购账号”数据库字段、独立控制面、独立质量系统、独立缓存事实源或外部排序服务。
- 不改变余额、模型能力、利润保护、冷却、账号状态、并发槽位、计费、重试和安全重放语义。
- 不修改生图、Responses WebSocket、alpha-search 或其他继续使用原生调度路径的入口。
- 不自动修改管理员维护的账号分组、priority、状态、采购成本或生产账号数据。
- 不恢复已经废弃的 admission、slow-session、首输出前账号锁或自定义账号并发限制。
- 不要求所有 API Key 新账号都获得请求；仅保证满足硬门禁且有明确低 priority 意图的账号具备有限冷启动机会。

## 3. 方案比较与选择

### 方案 A：把 priority 固定作为总评分的 50%（不采用）

优点是实现形式直观，但会让 priority 长期影响成熟账号；priority=1 可能持续压过真实质量较差的账号，priority=50 也需要额外归一化才能保持中性。它不能准确表达“新 API Key 账号的临时人工先验”和“自购账号的资源层级”。

### 方案 B：priority 永久硬排序（不采用）

优先级低的账号始终排在优先级高的账号前面，能立即改变排名，但无法让真实质量纠正管理员早期判断，且容易造成故障账号持续获得流量。它不符合“下一刻可能不再好”的要求。

### 方案 C：资源层分区 + API Key 冷启动先验（采用）

先执行所有原生硬门禁，再按账号所有权分为自购首选层和 API Key 备用层。自购层表达资源策略，不伪造质量分；API Key 层在质量证据不足时使用 priority 形成有界冷启动先验，证据积累后自动让真实质量接管。该方案与当前调度器已有资格、利润分区、候选池、Top-K 和原生槽位边界最匹配，且不需要新事实源。

## 4. 术语与排序契约

### 4.1 账号资源层

```text
self_owned
  现有 Sub2API 自购归属判定识别出的自购账号。
  不新增重复归属字段。

api_key
  当前自购归属判定之外的 API Key 账号。
  仍受原生平台、能力、余额、利润和运行时资格限制。
```

具体账号类型映射必须在实现报告中引用现有代码符号和测试证据；不能仅依据账号名称、BaseURL、备注或前端标签猜测归属。

### 4.2 硬门禁

两类账号在进入资源层分区前统一经过：

- 请求平台和模型能力匹配；
- 账号 active、可调度和凭据有效；
- 隐私/协议/请求能力要求；
- 原生余额或额度可用；
- 原生利润保护分区；
- 账号+模型/分组冷却与故障隔离；
- 原生并发槽、排队和实时可用性；
- 当前逻辑请求的排除账号、安全重放和 sticky 边界。

硬门禁失败的自购账号不得因为“自购优先”重新进入候选；没有可用自购账号时，才允许继续评估 API Key 层。

### 4.3 自购账号层内排序

自购账号不参与 API Key 的历史质量比较。自购层内使用以下顺序：

1. 管理员 priority，数字越小越优先；
2. 现有运行时负载/排队和原生公平性规则；
3. 现有 sticky、最近使用和稳定 tie-break 规则；
4. 账号 ID 作为最终稳定顺序。

自购账号的“默认质量最佳”是层级策略，不是质量评分值。真实失败仍然通过现有运行时冷却、故障隔离和硬资格机制影响候选资格。

### 4.4 API Key 冷启动先验

API Key 账号按以下状态处理：

```text
成熟账号：质量快照中有足够的近期有效观测
冷启动账号：没有有效观测，或有效观测不足以形成稳定质量排名
```

冷启动账号不能因为证据为空被当成失败账号，也不能直接获得成熟质量分。priority 只在冷启动状态作为有界先验：

- `priority=50` 为中性，不产生运营提升；
- priority 越小，冷启动先验越强；
- priority 越大，冷启动先验越弱；
- 先验只用于候选排序和进入 Top-K 的机会，不绕过硬门禁；
- 先验影响随近期有效观测积累衰减；
- 达到成熟证据门槛后，API Key 账号回到真实质量排序，priority 不再永久覆盖质量。

冷启动先验必须使用确定性的有界归一化函数，默认值为 50 时贡献严格为中性；不得把原始 1–100 数值直接与质量分相加。

### 4.5 冷启动流量机会

为了避免“分数可计算但永远拿不到第一笔请求”，priority 较低且通过硬门禁的 API Key 冷启动账号必须在现有候选池/Top-K/公平探索机制中保留可进入机会。实现应优先复用现有候选池和探索逻辑，不新增跨请求的独立配额状态。

冷启动账号获得真实请求后，成功、失败、TTFT、耗时和运行时错误按现有事实源进入质量和健康链路。冷启动不意味着自动重试、强制命中或忽略客户端/上游错误。

## 5. 端到端数据与控制流

```text
请求进入统一普通文本 OpenAI 调度
        |
        v
原生硬门禁、利润分区、请求级排除与实时槽位资格
        |
        +--> self_owned 可用候选 --按 priority/负载/公平性--> 选择
        |
        +--> 无 self_owned 候选
                    |
                    v
             api_key 候选
                    |
          成熟质量 / 冷启动判定
                    |
          priority 冷启动先验 + 真实质量
                    |
          现有 Top-K/公平性/原生槽位获取
```

选择过程不得在自购层和 API Key 层之间随机混合。只有自购层为空或全部被硬门禁排除时，才进入 API Key 层。

priority 更新后的下一次候选构建必须读取最新账号快照。已有的请求级候选、已获得的原生槽位和已进入上游的请求不被重新排序或抢占。

## 6. 后端接口与决策日志契约

### 6.1 内部候选字段

在现有 `openAIAccountCandidateScore` 或等价内部候选结构上增加最小内部信息：

- `resource_tier`: `self_owned` 或 `api_key`；
- `cold_start`: 是否处于 API Key 冷启动；
- `priority_signal`: 仅用于解释和排序的已归一化先验；
- `quality_confidence`: 质量证据是否达到成熟门槛；
- `quality_sample_count`: 当前质量快照实际有效样本数。

这些字段不得把凭据、完整 BaseURL、上游响应或敏感请求体写入日志。

### 6.2 调度决策日志

复用 T119 已有调度决策日志和详情接口，新增或复用有限字段表达：

- 候选资源层计数；
- 自购层是否存在可用候选；
- API Key 账号是否因冷启动参与候选；
- priority 原始值是否为管理员调整值；
- 冷启动先验是否影响排序；
- 账号进入/未进入 Top-K 的原因；
- 最终选择的资源层和账号；
- 硬门禁排除原因。

日志记录是尽力而为的诊断旁路，不得阻塞请求，也不得改变选择结果。

### 6.3 账号管理契约

- 新建账号的 Sub 原生 `priority` 默认仍为 `50`。
- 管理员可以通过现有账号创建/编辑/批量更新入口修改 priority。
- 本任务不新增另一个“冷启动优先级”字段。
- priority 范围沿用现有原生校验；若实现发现当前创建入口没有默认 50，补齐该原生默认并增加直接测试。

## 7. 失败、安全与兼容语义

- 自购账号全部不可用时，进入 API Key 层；API Key 也全部不可用时，返回现有无可用账号错误，不伪造成功。
- 自购账号的优先层不能绕过余额不足、能力不匹配、利润门、冷却、故障隔离或并发槽。
- priority 修改不触发正在运行请求的抢占，不改变已产生的账务、usage、上游请求和重试状态。
- 质量快照为空、过期、刷新失败或字段异常时，API Key 冷启动逻辑使用中性/保守回退，不能把异常解释成高质量；调度请求继续使用现有 fail-open/fail-closed 语义。
- 自购归属判定失败时，不得把不确定账号误判为自购首选；应按 API Key/未知的保守路径处理并写入无敏感信息的诊断原因。
- 质量证据积累后，真实运行结果可以降低 API Key 账号的排序；自购账号真实运行故障仍由现有健康门禁排除。
- 旧调度配置、旧客户端字段和旧日志读取保持兼容；没有新配置项时使用本规格默认行为。

## 8. 数据库、迁移与配置

- 不新增数据库表或迁移。
- 不新增第二套质量或账号归属事实源。
- 不回填历史质量数据，不修改历史 usage、监控、账务或账号配置。
- 不新增必填运行时配置；自购归属复用现有代码判定，冷启动参数使用代码内有界常量并由直接测试锁定。
- 不改变生产账号分组、priority、状态或采购成本；实际账号配置应用属于另一个明确授权的运维动作。

## 9. 场景化验收矩阵

| 场景 | 预期 |
| --- | --- |
| 一个健康自购账号和多个健康 API Key 账号 | 请求只在自购层选择 |
| 多个自购账号均健康、priority 不同 | priority 数字小的先进入层内候选；同值继续按负载/公平性选择 |
| 自购账号余额不足或冷却中 | 该账号被硬门禁排除，不能因为自购层级继续命中 |
| 所有自购账号均被排除 | 调度进入 API Key 层 |
| API Key 新账号无质量样本、priority=50 | 不因空样本获得额外提升，保持中性冷启动语义 |
| API Key 新账号无质量样本、priority=1 | 通过硬门禁后获得明显冷启动排序提升，并可进入现有 Top-K/探索机会 |
| API Key 新账号已有少量有效样本 | priority 仍可辅助冷启动，但真实质量开始影响排序 |
| API Key 质量样本达到成熟门槛 | 主要按真实质量排序，priority 不再永久覆盖 |
| API Key 新账号首次请求失败 | 失败进入既有健康/冷却/质量链路，不因 priority=1 继续强行优先 |
| 所有账号 priority=50 | 不改变既有成熟账号质量排序和现有自购层优先语义 |
| priority 修改后新请求 | 新请求读取最新 priority；运行中请求不被抢占 |
| 图像、Responses WebSocket、alpha-search | 保持原有非统一质量调度路径 |
| 调度日志不可用 | 请求选择不受阻，日志缺口按 T119 既有语义记录 |

## 10. 测试策略

### 10.1 服务层

- 资源层分类测试：自购/API Key/未知归属的确定性映射和保守回退。
- 自购层优先测试：自购健康时 API Key 不参与；自购全被硬门禁排除时 API Key 进入。
- 自购层内 priority、负载、公平性和稳定 tie-break 测试。
- API Key priority 归一化测试：50 中性、低于 50 提升、高于 50 降低、边界值有界。
- 冷启动衰减测试：无样本、少量样本、成熟样本三个阶段的排序变化。
- 冷启动候选池/Top-K 测试：priority=1 的新 API Key 在硬门禁通过时不被无质量数据直接置底。
- 真实质量接管测试：质量恶化后 priority 不能永久维持首选。
- 余额、利润、能力、冷却、并发和请求级排除门禁回归。

### 10.2 调度集成与决策日志

- 普通文本请求的最终资源层和账号顺序测试。
- 原生槽位获取、槽位失败、候选耗尽和安全切号回归。
- T119 日志字段和管理员详情接口兼容测试；日志失败不阻塞选择。
- priority 更新后新请求读取最新快照的缓存失效/刷新测试。

### 10.3 必要验证

- 直接相关 Go service/repository/handler 测试；
- `go build ./cmd/server`；
- 必要的前端账号编辑/默认值测试、`pnpm typecheck` 和 production build（若创建/编辑界面涉及前端）；
- `gofmt`、`git diff --check`；
- native-only guard 和范围检查。

不运行与本任务无关的全仓压力、长时间 soak、真实上游业务请求或生产配置写入。

## 11. 发布、回滚与验证条件

- 本规格不授权验收站或主站部署。

- 候选完成后状态为 `READY_FOR_ROOT_REVIEW`，交接必须包含基线/目标 commit、变更文件、测试、migration/config 变化、未验证项和回滚方式。
- 合并、推送、构建部署制品和发布只能由根总控在干净且与 `origin/main` 一致的 `main` 上执行。
- 预期无迁移，`downtime_required` 只能由实际发布预检决定；本规格不预先声明可部署。
- 回滚优先使用上一已验证蓝绿槽/镜像；本任务无数据库回滚和历史数据回填。
- 线上专项验证至少核对：自购存在时不使用 API Key、自购全不可用时 API Key 回退、新 API Key priority=1 获得冷启动机会、质量样本积累后排序变化、priority=50 默认兼容、调度日志解释和无错误/无横向越权。

## 12. 风险与控制

### 风险：自购账号层长期压住 API Key

控制：只要存在通过硬门禁的自购账号就使用自购层，这是明确业务策略；自购账号出现余额、冷却、能力或运行时故障时立即退出候选。API Key 仅作为备用资源，不承诺与自购长期混合负载。

### 风险：管理员误设 priority=1 导致 API Key 账号过度流量

控制：priority 只在 API Key 冷启动阶段有效；真实样本成熟后自动衰减。失败进入现有质量与健康链路，不能永久覆盖。

### 风险：自购账号没有质量分导致运行质量下降后仍被优先

控制：不使用质量分并不等于绕过健康门禁；连续失败、余额不足、冷却、能力失败和运行时隔离仍是硬门禁。必要时可在后续独立任务中增强自购层内质量排序，本任务不扩范围。

### 风险：新增排序与已有 Top-K/公平性冲突

控制：资源层分区和冷启动先验必须发生在 Top-K 截取前；后续继续复用现有候选池、公平性和原生槽位逻辑，并用决策日志验证候选总数与最终选择。

## 13. 未决事项

无产品未决事项。实现阶段必须从最新源码确认自购归属的具体原生类型映射，并把映射写入实现报告；不得通过新增字段或人工配置绕过该确认。

## 14. 规格自审

- 未引入永久 priority 硬覆盖；与“管理员意图可即时生效、真实质量可后续纠正”一致。
- 自购账号优先表达为资源层，不伪造质量分，不复制质量事实源。
- 两类账号均先经过硬门禁；自购优先不会绕过余额、利润、冷却、能力或并发限制。
- API Key 冷启动先验只在证据不足时有效，成熟质量接管排序；priority=50 保持中性。
- 现有非统一调度入口、账务、重试、安全重放和 Sub 原生槽位边界均列为非目标或兼容约束。
- 无迁移、无生产配置写入、无历史回填；实现计划和部署授权仍需后续独立门禁。
