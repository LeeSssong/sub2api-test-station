# 最近 1 小时质量窗口、快照刷新与原生不可用候选资格规格

## 1. 文档状态

- 日期：2026-09-09
- 状态：待用户书面确认，确认后方可进入实施计划
- 任务性质：OpenAI 普通 HTTP 文本请求调度规则收敛
- 当前范围：质量数据读取窗口、质量快照刷新、原生账号可调度资格、账号级质量排名及排名展示
- 本规格不授权代码修改、配置修改、数据迁移、合并、推送或部署

## 2. 用户已确认的决策

1. 完全不可用的账号必须直接退出候选池，使用 Sub 原生“不可用/不可调度”判断逻辑，不再只降低质量分。
2. 账号排名保持账号维度。被冷却账号不从排名展示中删除；不新增具体模型的排名或模型级可见资格排名。
3. 质量评分数据范围从 7 天缩短为最近 1 小时，并使用最近 5 分钟和此前 55 分钟两个互斥窗口。
4. 质量分固定每 5 分钟刷新；真实请求完成并写入有效结果后，触发合并式即时刷新。
5. 每次调度读取当前已生成的最新质量快照，不在每次调度中同步执行完整数据库聚合。

## 3. 背景与现状

当前统一质量调度同时存在质量评价和运行时资格两类事实：

- 质量仓储按时间范围读取 `usage_logs` 与账号归属的 `ops_error_logs`；当前快照 provider 的缓存 TTL 为 1 分钟，但数据库刷新尝试被节流为 5 分钟，且每次刷新仍从 `now-7d` 读取。
- 统一质量分当前包含成功率、TTFT P50/P90、输出速率和实时负载，排名主要按质量分降序，再按成功质量、TTFT P50 和账号 ID 稳定排序。
- 运行时已经存在账号阻断、临时不可调度、账号/模型冷却、传输错误保护、半开恢复和质量门禁等原生路径。T138 已在此链路上增加自购账号首选层和 API Key 冷启动 priority 先验；本规格不得覆盖这些资源层语义。
- 调度投影会过滤部分运行时阻断和质量门禁账号，但“全部被过滤时选择一个兜底账号”的行为可能重新放入已被阻断账号，必须明确禁止原生不可用账号通过质量兜底回流。

生产证据显示，账号可能在较长历史窗口内成功率很高，但随后短时间内完全不可用。若仍允许历史质量分直接参与选择，会出现“昨天很好、今天不可用但仍排名第一并继续接收请求”的错误行为。

## 4. 第一性原则

调度必须分开回答两个问题：

1. **资格**：账号当前能否被 Sub 选择并安全发起请求。
2. **质量**：在当前有资格的账号中，哪个账号的预期服务质量更好。

规则固定为：

> Sub 原生可调度资格决定账号能否进入实际候选池；最近 1 小时质量分只决定合格账号之间的优先级。

质量分不得抵消原生不可用、冷却、故障隔离、能力不匹配、并发和安全重放等硬约束。

T138 的规则优先于本规格的质量时效规则：本规格只提供更新后的账号质量证据，不改变自购账号首选资源层、API Key 冷启动 priority 先验、priority=50 中性或真实质量成熟后接管排序的定义。

## 5. 目标

1. 将统一质量日志的有效扫描范围改为最近 1 小时滚动窗口。
2. 将质量快照刷新频率与当前 5 分钟调度质量刷新节奏对齐，并支持真实请求完成后的合并式即时刷新。
3. 让每次调度读取最新可用质量快照，使最近质量更快影响账号级排名。
4. 使用现有 Sub 原生账号可用性/可调度性判断作为实际候选池硬过滤。
5. 防止不可用账号因为历史高质量分、质量快照陈旧或“全候选过滤兜底”重新被选中。
6. 保持账号级排名、T138 自购资源层和 API Key 冷启动语义稳定可解释。
7. 保留现有原生冷却、半开恢复、故障转移、利润控制、并发、账务和安全重放语义。

## 6. 非目标

- 不新增自定义“完全不可用”状态或第二套账号健康事实源。
- 不把质量分改造成新的硬性 TTFT 淘汰线。
- 不按模型拆分排名，不生成“账号 + 模型”排名项。
- 不因冷却状态从页面删除账号或重新编号账号质量排名。
- 不修改账号分组、模型能力、价格、利润、余额、并发上限或重试次数。
- 不修改生图、WebSocket、协议强制绑定或非 OpenAI 平台路径。
- 不启用一个新的主动探测体系来替代 Sub 原生不可用判断。
- 不做历史日志回填、删除或数据库迁移。

## 7. 方案比较与选择

### 7.1 方案 A：保留 7 天，仅提高近期分数

优点是改动小；缺点是旧数据仍会持续影响当前排名，无法解决账号当天完全不可用仍排名靠前的问题。且将近期异常通过加权补偿，仍无法替代真实的原生资格判断。不采用。

### 7.2 方案 B：移除 7 天窗口，剩余权重直接补中性分

优点是实现简单；缺点是会把原 7 天权重静默变成未知/中性证据，改变分数尺度并掩盖数据不足。不采用。

### 7.3 方案 C：原生资格硬过滤 + 最近 1 小时滚动质量评分 + 合并式即时刷新（采用）

先复用 Sub 原生可调度判断，再对合格账号使用最近 5 分钟与此前 55 分钟质量证据计算账号级分数。最近 5 分钟窗口提高响应速度，前 55 分钟窗口提供有限稳定性；原生不可用账号无论历史分数多高都不能进入实际候选池。质量快照按 5 分钟定时刷新，真实请求完成后触发合并式即时刷新；页面继续展示账号级质量排名，并把当前原生状态作为独立状态展示。

## 8. 端到端流程

```text
请求解析与协议约束
  -> Sub 原生账号/模型/能力资格
  -> Sub 原生不可用、阻断、冷却和安全门禁过滤
  -> 读取当前最新质量快照
  -> 计算账号级质量分
  -> 对实际合格账号按质量分排序
  -> 执行原有利润、并发、故障域和安全重放逻辑
  -> 发起请求前再次确认原生可调度状态
  -> 上游请求及既有 failover/cooldown/recovery
```

质量排名和实际候选池必须是两个明确集合：

- `ranking_accounts`：用于页面和解释，可包含冷却或当前不可用账号，但必须标注状态。
- `eligible_candidates`：用于实际选择，只包含当前通过 Sub 原生资格判断的账号。

任何“全候选为空”的兜底只允许在仍通过原生资格的账号中执行。若原生资格过滤后为空，返回现有无可用账号/容量错误语义，不得强行放回一个原生不可用账号。

T138 与本规格的组合顺序为：

```text
原生硬门禁
  -> 自购账号首选层（T138）
  -> 自购层为空时进入 API Key 层（T138）
  -> API Key 层内使用最新质量快照和冷启动 priority 先验（T138 + 本规格）
```

本规格不得用质量分把 API Key 账号提升到自购层，也不得为自购账号伪造质量样本或固定质量分。

## 9. 原生不可用资格契约

### 9.1 判断来源

实施时必须调用或复用当前 Sub 原生的账号可调度/不可用判断，包括现有：

- 账号禁用或原生阻断；
- 账号临时不可调度；
- 账号级或模型级冷却在当前请求上的原生影响；
- 上游传输错误触发的原生暂时不可调度；
- 半开恢复期间原生允许或拒绝尝试的状态；
- 模型、端点、协议和账号能力不匹配；
- 原生并发槽、故障域和安全重放门禁。

本规格不重新解释这些状态的持续时间、阈值或恢复算法。

### 9.2 过滤时点

至少在两个时点检查：

1. 质量排序前：排除当前已知不具备资格的账号。
2. 请求发送前：重新读取/确认原生运行时状态，避免质量快照计算期间状态发生变化。

若第二次确认失败，释放已经取得的临时资源并沿用既有重新选号、failover 或无可用账号语义；不得仅因为账号质量分最高而继续发送。

### 9.3 与质量分的关系

- 原生不可用是硬过滤，不进入实际候选排序。
- 质量分低不是不可用的替代定义。
- 质量分高不能绕过原生不可用。
- 主动探测或质量日志只能影响已有原生状态的输入路径；不得单独创建一个并行“不可用”布尔值。

## 10. 最近 1 小时质量数据与刷新契约

### 10.1 时间范围

质量仓储查询必须使用：

```text
start = now - 1h
end   = now
范围  = [now-1h, now)
```

`now` 必须由同一轮快照确定，查询、窗口归属和快照时间使用同一时间基准。禁止将本地自然日、服务器启动时间或不同查询各自获取的当前时间混入窗口边界。

### 10.2 窗口划分

最近 1 小时总质量窗口由以下两个互斥子窗口组成：

```text
W5  = [now-5m, now)
W55 = [now-1h, now-5m)
```

`W5 + W55` 恰好覆盖 `[now-1h, now)`；两个窗口不重叠，同一物理 attempt 只能归属一个窗口。旧的 `W7` 不再参与本规格版本的运行时质量分，也不应要求仓储为本功能继续扫描 1 小时以前的数据。

### 10.3 快照刷新与调度读取

质量快照刷新规则：

1. 固定每 5 分钟执行一次刷新尝试，作为无真实流量时的兜底。
2. 每个真实请求完成并写入有效 usage/error 结果后，触发一次即时刷新请求。
3. 即时刷新必须使用现有 singleflight/合并机制；同一时刻多个请求只能合并为一次实际刷新，不能按请求数放大数据库聚合查询。
4. 刷新成功后，以原子方式替换完整账号质量快照；调度读取快照时不得看到半更新数据。
5. 每次调度读取当前内存中的最新快照；“最新”指当前已生成的快照，而不是每次调度同步扫库。
6. 质量刷新失败时沿用陈旧快照或中性冷启动策略，但不得绕过 T138 和本规格定义的原生硬门禁。

当前实现基线需要在实施时修订为：缓存读取可以保持轻量，但数据库刷新窗口固定为最近 1 小时，刷新节流与 5 分钟定时一致；真实请求完成后的即时刷新不得阻塞请求响应。

### 10.4 为什么历史上使用更长窗口

此前使用 7 天主要是为了弥补以下统计问题，而不是因为 7 天本身是业务必需：

- 低流量账号需要更多样本，避免 `1/1` 成功就获得极端高分；
- P50、P90 TTFT 和输出速率需要足够样本才有统计意义；
- 较长窗口可以降低短时网络抖动造成的排名震荡。

切换为 5 分钟 + 55 分钟后，必须通过每指标独立置信度、无样本向中性回退、稳定 tie-break 和 T138 的 API Key 冷启动边界抵消这些风险。不能用延长日志扫描范围的方式重新引入旧历史滞后。

### 10.5 事实源与去重

继续复用现有原生用量和错误日志口径：

- 成功证据来自有效、完整、真实的上游 usage attempt；
- 账号归属的真实失败来自现有操作错误日志；
- 使用现有物理 attempt 去重规则，避免 usage 与 error 重复计数；
- 排除未知账务完整性、客户端责任、本地拒绝和明确模型不支持等不应归因账号质量的记录；
- 不新增质量事实表，不复制生产日志到新存储。

## 11. 质量评分与账号排名

### 11.1 指标权重

保留当前统一质量分的指标定义和指标权重：

```text
成功率质量：40%
TTFT P50：24%
TTFT P90：16%
输出速率：10%
实时负载：10%
```

TTFT P50/P90 合并为首字体验分：

```text
first_output_score = P50_TTFT_score * 0.60 + P90_TTFT_score * 0.40
```

质量分仍为 0 到 100 的账号级分数：

```text
quality_score =
    success_score     * 0.40
  + p50_ttft_score    * 0.24
  + p90_ttft_score    * 0.16
  + output_rate_score * 0.10
  + live_load_score   * 0.10
```

### 11.2 时间权重

为使当前质量更快生效，两个互斥窗口的基础权重为：

```text
W5  40%
W55 60%
```

每个指标继续按自身有效样本数计算置信度。窗口证据不足时，剩余权重向另一窗口或中性值回退；不得因为窗口无样本把账号直接判为 0 分，也不得因为 `1/1` 成功就直接排第一。

### 11.3 近期恶化行为

- 最近 5 分钟错误率、TTFT、输出速率明显恶化时，应优先影响下一次质量快照和账号排名。
- 前 55 分钟的稳定证据用于降低短时单点波动。
- 质量分只改变合格账号的相对顺序；不得用质量分替代原生不可用过滤。
- 慢首观测继续只影响后续质量证据，不取消当前请求、不创建第二个 attempt。

### 11.4 排序规则

实际候选排序为：

1. `quality_score` 降序；
2. `success_score` 降序；
3. TTFT P50 升序；
4. 账号 ID 升序，保证稳定性。

排序只对 `eligible_candidates` 执行。页面排名可对 `ranking_accounts` 执行，但必须明确这是账号质量排序，不是当前具体模型的保证可用顺序。

## 12. 页面与可观测性

页面继续展示账号级排名，不删除冷却或不可用账号。每个账号至少需要能够区分：

- 账号质量排名；
- 质量分及窗口/样本置信度；
- 当前 Sub 原生运行状态；
- 当前是否具备实际调度资格；
- 若不具备资格，显示非敏感的原生原因。

页面不展示模型级排名，不把一个账号拆成多个模型排名项，不因冷却状态重排或隐藏账号质量排名。

调度事件至少记录以下非敏感信息：

- 质量评分版本和快照时间；
- 1 小时窗口边界及其中的 5 分钟/55 分钟子窗口边界；
- 账号级质量分和排名；
- 原生资格过滤前后候选数；
- 被原生过滤的非敏感原因码；
- 是否发生请求前资格复核失败；
- 最终选中账号和既有 failover 结果。

事件不得记录 API Key、完整凭据、完整请求体或敏感上游响应。

## 13. 快照、缓存与陈旧数据

- 质量快照可以沿用现有缓存结构，但刷新节流必须与 5 分钟固定刷新和真实请求完成后的即时刷新规则一致；快照必须标注 `snapshot_at`、窗口范围和评分版本。
- 陈旧质量快照可以影响合格账号排序，但不能让原生不可用账号进入实际候选池。
- 质量查询失败时，沿用现有中性/陈旧快照策略；不伪造新鲜高质量分。
- 原生资格查询失败或状态为无法确认时，按现有 Sub fail-closed 语义处理，不以质量分放行。
- 快照刷新期间账号状态变化时，以请求发送前最新原生资格为最终裁决。

## 14. 兼容性与迁移

- 不新增数据库表和迁移。
- 仓储查询参数语义从“最多 7 天扫描”收敛为“最多 1 小时滚动扫描”；调用方必须统一传入同一轮 `[now-1h, now)`。
- 旧的 `W7` 质量数据字段、缓存内容或历史页面数据可继续被只读解析，但不得参与本规格版本的运行时排名。
- 质量评分版本必须递增，例如从现有版本切换到新的 1 小时窗口版本；旧快照不得被误当作新版本使用。
- T138 的自购资源层、API Key 冷启动、priority=50 中性和真实质量接管规则保持原样；本规格不得修改其账号归属事实源、层级顺序或冷启动公式。
- 现有原生冷却、利润、账务、并发和故障转移配置不迁移、不重置。

## 15. 失败与安全语义

### 15.1 全部账号原生不可用

原生资格过滤后没有候选时，返回现有无可用账号或容量错误。禁止选择历史排名第一的不可用账号作为兜底。

### 15.2 质量数据完全为空

若存在原生合格账号但没有有效质量证据，使用现有中性质量分和稳定 tie-breaker，从合格池中选择；不得把未知质量解释为高质量，也不得因此绕过原生资格。

### 15.3 账号在排序后进入冷却

请求发送前复核发现账号已不可调度时，禁止发送；沿用现有重新选号或 failover。页面排名保持账号级记录并更新状态。

### 15.4 当前请求已产生不可重放副作用

继续遵守现有安全重放边界：已产生语义输出、usage、工具副作用或客户端断开时，不因为排名变化自动换号或重放。

## 16. 直接相关测试与验收矩阵

| 场景 | 验收结果 |
|---|---|
| 查询发生在任意时间点 | 使用 `[now-1h, now)`，不按自然日计算 |
| 5 分钟内和前 55 分钟同一 attempt | 只进入一个互斥窗口 |
| 1 小时前的高质量历史 | 不参与新版本运行时排名 |
| 真实请求完成后 | 触发合并式即时刷新，不阻塞当前请求 |
| 多个请求同时完成 | 通过 singleflight/合并限制实际刷新次数，不按请求数重复查询数据库 |
| 账号历史质量第一但当前原生不可用 | 不进入实际候选池，不得被兜底选中 |
| 账号最近 5 分钟质量恶化 | 在下一次有效快照中更快降低账号级优先级 |
| 最近 5 分钟无样本、前 55 分钟有样本 | 按置信度回退，不产生极端高分或极端低分 |
| 账号处于冷却状态 | 页面仍展示账号级排名和冷却状态；实际请求不选择该账号 |
| 某一模型不可用但账号仍有其他资格 | 不新增模型级排名，按账号维度展示并遵守原生请求资格 |
| 排序期间账号进入冷却 | 请求前原生复核阻止发送并执行既有重选/failover |
| 所有账号都原生不可用 | 返回无可用账号，不强行选择排名第一账号 |
| 质量快照刷新失败 | 不绕过原生资格；合格账号按现有陈旧/中性策略处理 |
| 原生资格判断异常或 unknown | 遵守原生 fail-closed，不以质量分放行 |

## 17. 测试策略

实施时仅保留与本任务直接相关的最小验证：

1. 仓储 SQL 时间边界、1 小时扫描上限、窗口互斥和去重测试。
2. 质量评分窗口权重、样本置信度、无样本回退、即时刷新合并和版本测试。
3. 调度候选资格过滤测试，覆盖原生不可用、冷却、半开、全候选为空和请求前复核。
4. 账号级排名投影测试，确认冷却账号展示不被删除、不产生模型级排名。
5. 直接相关后端构建/测试和 `git diff --check`。

不在本规格内扩大到全仓压力测试、无关平台回归或生产真实请求验证；发布链自带的构建、原子切换、健康检查和回滚保护仍必须保留。

## 18. 发布、回滚与环境边界

- 实施必须从最新、干净且已推送的 `main` 创建独立任务 worktree。
- 规格批准后才能编写实施计划和修改运行时代码。
- 任何部署只能从合并后且 `HEAD/tree` 与 `origin/main` 一致的根目录 `main` 发起。
- 本规格不授权验收站或主站部署，不授权停机、迁移、重启或流量切换。
- 回滚方式为恢复上一已验证的代码版本/镜像；不得通过恢复旧质量窗口来绕过原生不可用资格硬过滤，也不得回滚 T138 的自购资源层和 API Key 冷启动保护。
- 如上线后发现排名异常，优先回滚本规格对应的质量评分版本或代码提交，同时保留原生资格过滤和不可用 fail-closed 保护。
