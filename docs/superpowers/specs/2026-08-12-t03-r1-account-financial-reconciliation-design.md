## 3. 目标

1. 在不扩展官方 `usage_logs` 结构的前提下，为功能启用后的每条可纳入流水登记独立、
   一对一、可溯源的上游成本证据。
2. Sub/NewAPI 的原生账单是上游账号的唯一扣费事实源；管理员打开详情时不再访问上游。
3. 把现有账号盈利页升级为管理员专属财务首页，先展示全站财务总览，再展示账号明细。
4. 提供使用记录的“异常流水”过滤 Tab，使管理员逐笔核对 `confirmed_zero` 与
   `unavailable` 流水，并支持逐笔、选中项批量和当前筛选范围批量确认。
5. 正常流水立即参与营收、成本和利润；待核对异常完全隔离；管理员核对后再纳入。
6. 支持按账号、北京自然日直接覆盖营收或成本，并保持覆盖之后的新流水和后来核对的旧
   异常继续累加。
7. OAuth 自购账号不查询上游、不产生上游扣费异常；由管理员填写账号每日人民币成本。
8. 全站增加“用户未消费金额”，汇总所有未删除用户当前 `users.balance`；包含已禁用用户，
   不随财务时间范围变化。
9. 全站与账号使用同一统计截止时间；页面打开、切换范围、修改、核对后立即刷新，并在停留
   期间每 60 秒自动刷新。

## 4. 非目标

- 不回填、扫描或修改功能启用前的历史 `usage_logs`。
- 不建立延迟补查、定时上游扫描或业务级上游重试。
- 不估算、不模糊匹配、不以 `account_cost`、采购倍率或可用额度冒充逐笔原生账单。
- 不做人民币与美元汇率换算；本站 `actual_cost`、Sub/New 原生账单数值均按人民币 1:1
  进入本功能。
- 不做 OAuth 采购成本分摊、可用额度折算或汇率模型。
- 不制作审计日志专用 UI，不提供一键撤销。
- 不修改账号监控评分、调度、计费、用户余额扣减或上游凭据。
- 不引入 `external-primary`、relay-ops 主账务路径、平行控制面或 GitHub Actions。
- 不启动或触碰 T05。

## 5. 影响用户与权限边界

### 5.1 管理员

管理员可使用财务首页、异常流水 Tab、结构化成本详情、逐笔/批量核对、每日金额覆盖和
OAuth 每日成本填写。

### 5.2 普通用户

- 普通用户导航中不出现财务首页或异常流水 Tab。
- 对应 API 必须强制管理员鉴权，不能依赖前端隐藏。
- 普通使用记录的 DTO、详情和导出不增加上游成本、利润、证据、复核或审计字段。

## 6. 方案比较与选择

### 6.1 方案 A：独立逐笔证据 + 查询时实时汇总（已选）

官方 `usage_logs` 保持不变。独立证据表一对一关联 `usage_log_id`；独立复核表记录人工
核对；独立账号日表记录 OAuth 成本与营收/成本覆盖。财务 API 查询时按统一截止点实时汇总。

优点：

- 对官方流水侵入最小；
- 上游证据与人工结果分离，原始事实不会被人工操作伪装覆盖；
- 逐笔可追溯，异常和财务首页共享同一事实；
- 不维护容易漂移的累计汇总。

代价：汇总查询和覆盖截止点计算比直接读缓存表复杂，需要精确索引和边界测试。

### 6.2 方案 B：独立证据 + 每日累计汇总表

每次登记、核对和覆盖都增量更新账号日汇总。读取快，但并发新流水、晚到证据、批量核对和
覆盖基数都需要维护增量一致性，容易出现汇总漂移和重复计入。

### 6.3 方案 C：完整财务事件账本

把证据、人工核对、覆盖和 OAuth 成本全部建模为不可变财务事件。长期扩展性最好，但需要
完整事件投影、重放和对账机制，明显超出当前 MVP。

选择方案 A。禁止把旧候选的“直接在 `usage_logs` 增加成本字段”作为方案 A 的变体恢复。

## 7. 总体架构与职责边界

### 7.1 官方流水

`usage_logs` 继续负责本站已经完成的用户计费事实，包括 `actual_cost`、账号、模型、请求 ID
和时间。它不知道上游证据、人工核对或财务覆盖。

### 7.2 上游成本证据

独立证据模型只负责“这一条官方流水的上游原生账单事实是什么”。它不负责修改
`usage_logs`，也不负责人工覆盖。

### 7.3 异常复核

独立复核模型只负责“管理员是否已处理该异常，以及最终纳入模型的人工成本”。它必须保留
原始证据状态。

### 7.4 账号每日财务值

独立日模型只负责：

- OAuth 账号每日人民币成本；
- 管理员直接覆盖的每日营收或成本；
- 覆盖发生时的纳入截止点和审计关联。

### 7.5 财务查询服务

财务查询服务在一次数据库读取快照中组合官方流水、证据、复核和每日值，返回全站汇总、
账号行、异常数量、受影响营收、用户未消费金额和统一 `generated_at`。

## 8. 端到端数据与控制流

### 8.1 非 OAuth 的 Sub/New 流水

1. 推理请求完成，官方链路生成并写入 `usage_logs`。
2. 官方插入成功后，复用现有响应后 usage 异步任务执行一次最佳努力证据登记。
3. Sub/New 适配器使用本次请求上下文中的精确 `upstream_request_id` 和结构化原生账单信息：
   - Sub：精确 `/v1/usage/records.actual_cost`；
   - NewAPI：精确 `/api/log/token.quota` 与 `/api/status.quota_per_unit`，标准化为
     `quota / quota_per_unit`。
4. 若现有协议实现必须通过原生账单端点才能完成本次登记，最多允许在该响应后任务内执行
   一次有界精确读取；不得在页面打开时读取、不得延迟重试、不得定时补查。
5. 登记服务以 `usage_log_id` 幂等创建一条终态证据。登记错误不能反向影响官方流水。
6. 财务首页、异常 Tab 和管理员详情只读取本地证据。

### 8.2 OAuth 自购账号

1. 只有账号类型明确为 `oauth` 时进入自购账号路径；不得因平台、名称或其他账号类型猜测。
2. OAuth 流水不访问 Sub/New 账单、不创建 `unavailable` 成本异常。
3. 管理员按账号和北京自然日填写人民币成本。
4. 当天成本未填写时，账号行显示“待填写”，利润和利润率不计算。

### 8.3 官方流水已写入但证据未登记

查询使用 `LEFT JOIN`。功能启用后的非 OAuth 官方流水若没有证据行，投影为：

- 证据状态：`unavailable`；
- 原因：`evidence_not_registered`；
- 复核状态：`pending`。

这保证证据写入崩溃或队列丢失不会把流水静默当成正常成本。

## 9. 持久化字段契约

最终 SQL 名称可在实施计划中按仓库风格微调，但语义和唯一性不得变化。

### 9.1 `usage_upstream_cost_evidence`

一条 `usage_logs` 最多一条证据：

- `id BIGSERIAL PRIMARY KEY`：用于登记顺序和覆盖截止点；
- `usage_log_id BIGINT NOT NULL UNIQUE`：关联官方流水；
- `source`：`sub` 或 `newapi`；
- `upstream_request_id`：精确上游请求 ID；
- `upstream_billing_time`、`upstream_model`：可选的账单溯源字段；
- `sub_actual_cost`：Sub 结构化原始数值；
- `newapi_quota`、`newapi_quota_per_unit`：NewAPI 结构化原始数值；
- `normalized_cost_cny`：标准化后的人民币上游扣费；
- `profit_cny`：登记时固化的逐笔利润，等于官方流水 `actual_cost - normalized_cost_cny`；
- `evidence_status`：`confirmed`、`confirmed_zero` 或 `unavailable`；
- `reason_code`：稳定失败原因；
- `recorded_at`、`created_at`、`updated_at`。

不保存完整上游响应、请求体、凭据、完整 API Key 或上游错误原文。

### 9.2 `usage_cost_reviews`

一条异常流水最多一条复核记录。MVP 只允许 `pending -> reviewed` 一次性确认；已核对记录不可
再次改写，事后总额纠错使用账号每日覆盖。核对请求追加现有 `audit_logs`：

- `id BIGSERIAL PRIMARY KEY`：复核纳入顺序；
- `usage_log_id BIGINT NOT NULL UNIQUE`；
- `review_status`：`reviewed`；没有记录即 `pending`；
- `manual_cost_cny`：管理员输入的成本；不输入金额确认时为 `0`；
- `manual_profit_cny`：核对时固化的逐笔利润，等于官方流水 `actual_cost - manual_cost_cny`；
- `reviewed_by`、`reviewed_at`、`updated_at`。

原始 `evidence_status` 永不因人工操作改变。

### 9.3 `account_daily_financial_values`

键为 `account_id + business_date`：

- `business_date`：北京自然日；
- `oauth_cost_cny`：OAuth 当日人工成本；
- `revenue_override_cny`、`revenue_override_at`；
- `revenue_evidence_cutoff_id`、`revenue_review_cutoff_id`；
- `cost_override_cny`、`cost_override_at`；
- `cost_evidence_cutoff_id`、`cost_review_cutoff_id`；
- `updated_by`、`created_at`、`updated_at`。

覆盖截止点在同一事务快照中冻结：覆盖值替换当时已纳入的金额；之后 `id` 大于相应截止点
的新正常证据和后来完成的异常复核继续累加。营收和成本可在不同时间分别覆盖，因此分别保存
截止点。

### 9.4 现有 `audit_logs`

复用现有管理员审计中间件和 `audit_logs`，记录：

- 异常逐笔/批量核对；
- OAuth 每日成本填写；
- 账号每日营收或成本覆盖；
- 旧值、新值、账号、业务日、筛选截止点、操作人、请求 ID 和结果。

MVP 不增加审计日志专用页面或撤销按钮。

## 10. 证据状态、异常和失败语义

### 10.1 `confirmed`

精确命中账单且成本为有效有限的非零数值，立即参与营收、成本和利润。

### 10.2 `confirmed_zero`

精确命中账单且成本明确为数值 `0`，或精确命中后实际扣费字段为 blank、`null` 或空字符串，
标准化为成本 `0`。它是需要人工确认的异常，复核前完全不进入财务汇总。

### 10.3 `unavailable`

以下情况永久登记为 `unavailable`，不补查、不重试、不估算：

- `evidence_not_registered`：官方流水存在但证据行未写入；
- `request_id_missing`：缺少精确上游请求 ID；
- `record_not_found`：没有精确账单记录；
- `endpoint_unsupported`：原生端点不支持；
- `credentials_unavailable` 或 `authentication_rejected`；
- `request_unavailable`：网络、请求构建或超时失败；
- `response_unavailable`：非法 JSON、非法非空数值、响应超限或 NewAPI 单位非法；
- `persistence_failed`：可记录的登记失败被恢复为缺证据投影时使用安全原因。

### 10.4 人工核对

- 待核对异常不进入营收、成本、利润或利润率。
- 管理员输入实际成本后确认：该笔 `usage_logs.actual_cost` 作为营收、人工成本作为本站支出，
  利润为两者之差并固化到复核记录。
- 管理员不输入金额直接确认或批量确认：成本按 `0`，该笔营收仍纳入。
- 人工核对不会把 `unavailable` 伪装成 `confirmed_zero`，也不会改写结构化账单字段。

## 11. 汇总与覆盖计算规则

### 11.1 单笔纳入

- 正常 `confirmed`：证据登记后立即纳入；
- `confirmed_zero` / `unavailable`：仅在人工复核后纳入；
- 未复核异常：完全隔离，但计入异常数和受影响营收；
- OAuth：按每日人工成本模型，不生成逐笔成本异常。

### 11.2 利润公式

所有页面统一使用人民币：

```text
利润 = 营收 - 本站支出（即上游扣费或 OAuth 人工成本）
利润率 = 利润 / 营收
```

营收为 `0` 时利润率返回 `null`/`—`，不得除零或伪造百分比。

### 11.3 每日直接覆盖

管理员只能覆盖“今日”的账号营收或成本；利润和利润率不可修改。

示例：

```text
14:00 已纳入营收 100，管理员覆盖为 95
之后新增正常营收 20
之前待核对异常营收 10 在之后被核对
最终营收 = 95 + 20 + 10 = 125
```

成本同理：

```text
14:00 已纳入成本 40，管理员覆盖为 35
之后新增正常成本 8
之前异常后来以成本 3 核对
最终成本 = 35 + 8 + 3 = 46
```

覆盖只改变财务读模型的当前基数，不改写逐笔官方流水或原始证据。编辑金额不自动核对异常。

### 11.4 OAuth 待填写

- 单个 OAuth 账号当日成本未填：账号行显示“待填写”，利润和利润率为 `—`。
- 全站四项财务指标只汇总数值完整的账号日；未填写成本的 OAuth 账号日整体排除，即其营收也
  不进入全站营收。
- 7 日/31 日按账号日处理：缺成本的账号日排除，已完整日期继续参与；账号行可显示
  “部分日期待填写”，但全站总览不增加提示。

### 11.5 全站用户未消费金额

```text
全站用户未消费金额 = SUM(users.balance)
WHERE users.deleted_at IS NULL
```

包含已禁用用户，不包含软删除用户，不包含 `frozen_balance`，不受今日、24 小时、7 日、31 日
筛选影响；它是当前余额负债快照。

## 12. 时间范围和刷新语义

- 今日：北京自然日 `00:00–现在`；允许编辑营收、成本和 OAuth 当日成本。
- 最近 24 小时：滚动实时流水口径，不应用每日覆盖；明确标记“实时流水口径”。OAuth 没有
  该窗口的人工成本，因而该账号在四项财务指标中保持不可计算；数值完整账号正常汇总。
- 最近 7 日、31 日：按北京自然日的每日最终值求和，只读。
- 页面打开、切换范围、修改金额、填写 OAuth 成本、核对异常后立即重新查询。
- 页面停留时每 60 秒自动刷新；保留手动刷新按钮。
- 全站卡片和全部账号行来自同一查询快照，返回同一 `generated_at`，页面显示统一截止时间。
- MVP 不建立定时写入汇总表，也不使用 WebSocket 逐笔推送。

## 13. 管理员 API 契约

最终路由可在实施计划中按现有管理员路由风格命名，但能力必须包括：

1. 财务报告查询：时间范围、账号搜索、来源、状态，返回全站总览、账号行、异常数、受影响
   营收、用户未消费金额和 `generated_at`；
2. 今日账号营收/成本覆盖；
3. OAuth 账号每日成本写入；
4. 异常流水分页查询、搜索、日期、账号、证据状态和复核状态过滤；
5. 单笔核对、选中 ID 批量核对、当前筛选范围批量核对；
6. 管理员使用记录详情返回持久化的结构化证据和复核结果；
7. 管理员普通使用记录列表 API 投影同一证据状态、上游成本和逐笔利润；页面可把完整成本
   溯源列集中在异常 Tab 与详情，避免普通列表过宽；
8. 兼容 `/admin/usage/:id/upstream-cost` 时只读本地证据，不访问上游。

金额写接口必须进行有限数值、非负数、业务日、账号类型和管理员权限校验。批量接口返回请求
截止点、匹配数、实际更新数和跳过数，便于管理员确认结果。

## 14. 页面与交互契约

### 14.1 财务首页

升级现有 `/admin/operations/account-profitability`，不新建第三套运营入口。

顶部全站总览显示：

- 全站营收；
- 上游扣费/本站支出；
- 利润；
- 利润率；
- 待核对异常笔数与受影响营收；
- 全站用户未消费金额；
- 统一统计截止时间、自动刷新倒计时和手动刷新。

下方账号明细显示账号、来源、营收、上游扣费、利润、利润率、异常数。今日视图的营收与成本
可直接编辑；利润和利润率只读。OAuth 成本未填时显示“待填写”。

### 14.2 异常跳转

- 点击全站异常卡片：进入异常流水 Tab，保留当前日期范围并显示全部账号；
- 点击账号异常数：额外带入该账号过滤；
- 跳转参数使用明确路由查询字段，刷新页面后筛选仍可复现。

### 14.3 异常流水 Tab

它是管理员使用记录页的过滤视图，不复制 usage 行。复用搜索、日期、分页、详情、导出和批量
选择，但裁剪为成本溯源字段：

- 本地 usage ID、请求 ID、时间、账号、模型、营收；
- 来源 Sub/NewAPI；
- 精确上游请求 ID；
- 上游账单时间、模型；
- Sub `actual_cost`；
- NewAPI `quota`、`quota_per_unit`、标准化成本；
- 证据状态、稳定原因码；
- 复核状态、人工成本、操作人、复核时间。

支持逐笔输入成本并确认、选中项批量确认、当前筛选范围批量确认。当前筛选批量操作在服务端
冻结匹配条件和最大 `usage_log_id`；执行期间新产生的流水不被误确认。写入以
`usage_log_id` 唯一幂等，重复确认不重复纳入。

### 14.4 使用记录详情

管理员详情直接使用正常详情响应中的本地持久化证据，不再单独请求上游。普通用户详情保持
原样。

## 15. 兼容性与数据库结构迁移

“迁移”仅指随版本新增数据库表和索引，不是搬迁、回填或改写历史流水：

- 新增上游成本证据表；
- 新增异常人工复核表；
- 新增账号每日财务值/覆盖表；
- 为一对一关联、异常过滤、账号日期查询和覆盖截止点增加经查询证明的最小索引；
- 复用现有 `audit_logs`，不新增审计表；
- 不新增或保留旧候选中的 `usage_logs.upstream_actual_cost`、`profit` 等字段。

迁移应为 expand-only。旧版本不会读取新表，应用回滚时新表保留。发布预检必须输出真实
`downtime_required=true|false`；若为 `true`，在任何停服或切换前停止并等待用户确认。

## 16. 场景验收矩阵

| 场景 | 证据/复核 | 财务纳入 | 页面结果 |
|---|---|---|---|
| Sub 精确命中有效非零 `actual_cost` | confirmed | 立即纳入 | 显示人民币成本和利润 |
| NewAPI 精确命中有效 quota 与单位 | confirmed | 立即纳入 | 显示结构化字段和标准化人民币成本 |
| 精确命中数值 0 | confirmed_zero / pending | 不纳入 | 进入异常 Tab |
| 精确命中 blank/null/empty | confirmed_zero / pending | 不纳入 | 成本证据为 0，进入异常 Tab |
| 无精确记录/端点/鉴权/网络/解析失败 | unavailable / pending | 不纳入 | 显示稳定原因，进入异常 Tab |
| 证据记录未创建 | unavailable / evidence_not_registered | 不纳入 | 不会静默成为正常流水 |
| 异常输入成本 5 后确认 | 原状态保留 / reviewed | 营收与成本 5 纳入 | 汇总立即刷新 |
| 异常不填金额直接确认 | 原状态保留 / reviewed 0 | 营收纳入、成本 0 | 汇总立即刷新 |
| 选中项批量确认 | 每个选中 ID reviewed 0 | 各自纳入 | 新流水不受影响 |
| 当前筛选批量确认 | 截止点内匹配项 reviewed 0 | 各自纳入 | 截止点外新流水仍 pending |
| OAuth 当日成本未填 | 不建成本异常 | 账号日不进入全站四项汇总 | 账号行“待填写” |
| OAuth 填入人民币成本 | 日值完整 | 账号日纳入 | 自动计算利润和利润率 |
| 今日营收覆盖后新增/核对流水 | 保存覆盖截止点 | 覆盖基数 + 后续纳入 | 不覆盖后续增量 |
| 最近 24 小时 | 不应用日覆盖 | 实时完整流水 | 标注实时流水口径 |
| 7/31 日 | 汇总每日最终值 | 完整账号日求和 | 只读 |
| 已禁用未删除用户余额 | 当前快照 | 纳入未消费金额 | 不随范围变化 |
| 已删除用户余额 | 当前快照 | 排除 | 不显示 |
| 管理员打开详情 | 只读本地证据 | 无变化 | 上游 HTTP 调用为 0 |
| 普通用户访问 | 管理员鉴权拒绝/字段不存在 | 不适用 | 页面、API、导出均不可见 |
| 功能启用前历史流水 | 不回填 | 不纳入 | 不形成历史异常洪水 |

## 17. 测试策略

### 17.1 后端

- Sub/NewAPI 适配：非流式、流式及实际接线入口；精确请求 ID；结构化字段；有效非零、数值
  0、blank、`null`、空字符串、非法值和所有稳定失败码；
- 官方流水隔离：证据失败、队列拒绝或持久化失败均不阻断官方 usage 插入；
- 证据仓储：一对一唯一性、幂等、`LEFT JOIN` 缺证据投影、敏感字段不落库；
- 复核：逐笔、重复确认、修改人工成本、选中项批量、筛选批量、并发新流水截止点；
- 汇总：正常/异常隔离、人工纳入、每日覆盖截止点、分别覆盖营收/成本、跨日、北京时区、
  7/31 日、24 小时口径、利润率除零；
- OAuth：仅字面 `oauth` 类型不建异常、每日成本待填写/填写、范围内缺日处理；
- 用户未消费金额：包含 disabled、排除 deleted、只累加 `balance`；
- 权限：所有新路由管理员专属，普通 DTO、详情和导出不含财务字段；
- 审计：所有写操作产生脱敏审计，旧值、新值和截止点完整。

### 17.2 前端

- 全站总览与账号行使用同一截止时间；
- 时间范围切换、60 秒刷新、手动刷新及修改后的立即刷新；
- 异常卡片/账号异常数跳转并恢复筛选；
- OAuth “待填写”和部分日期待填写；
- 营收/成本编辑，利润/利润率不可编辑；
- 异常 Tab 的裁剪列、逐笔/批量确认、详情和导出；
- 管理员详情不调用 `getUpstreamCost` 或任何 Sub/New 上游接口；
- 普通用户路由与页面没有新入口。

### 17.3 验证

- 聚焦 Go 测试、必要集成测试、`go vet`、server build；
- 聚焦 Vitest、typecheck、前端生产构建；
- 数据库迁移合同、迁移集合哈希、发布预检和 `git diff --check`；
- 独立任务复审和最终全分支终审。

## 18. 发布、线上验证与回滚

### 18.1 发布门禁

### 18.2 线上验证

- 记录功能启用时间，仅观察其后的自然流水，不制造付费请求；
- 验证 Sub/NewAPI 正常证据无需打开详情即可存在；
- 验证零成本和 unavailable 进入异常 Tab，人工核对后汇总按合同变化；
- 验证 OAuth 待填写和填写后计算；
- 验证全站总览、账号行、余额快照、统一截止时间和 60 秒刷新；
- 验证详情打开产生 0 次上游账单 HTTP 调用；
- 验证普通用户无入口、无字段；
- 验证 API、worker、PostgreSQL、Redis、Caddy 和活动槽健康，无异常重启。

### 18.3 回滚

- 应用回滚到前一已验证镜像；
- 新增表、证据、复核、日值和审计记录保留，不执行收缩迁移；
- 旧版本不读取新表，因此可以安全回退；
- 重新启用时记录新的功能启用时间，仍不回填旧流水；
- 若迁移、部署或线上验证失败，保留候选、失败证据和修复内容，在同一任务继续修复。
