# 管理员赠送额度扣除报错修复规格

## 1. 问题与现状

管理员用户弹窗通过 `POST /api/v1/admin/users/:id/balance` 执行赠送或扣除。后端要求管理员身份和 `Idempotency-Key`，扣除路径只能调用 gift quota deduction，不能消耗 paid quota。

当前需要覆盖的失败体验包括：

- 请求缺少幂等键时，后端返回通用内部错误，前端提示不清晰；
- 赠送额度不足时，前端或后端错误信息不够明确；
- 弹窗打开后额度可能已变化，提交时需要再次以实时赠送额度为准校验。

## 2. 目标与非目标

目标：

- 每次管理员赠送/扣除请求都携带非空 `Idempotency-Key`；
- 扣除失败时明确提示“赠送额度不足”，不显示误导性的通用错误；
- 前端限制扣除金额不超过实时赠送额度，并在提交前再次校验；
- 保证重复请求不会重复扣除。

非目标：

- 不从充值额度扣除；
- 不改变 paid-first/gift-second 的用户消费顺序；
- 不修改充值、退款、兑换码和历史账务数据；
- 不新增数据库迁移或配置；
- 不部署主站或测试站。

## 3. 方案选择

采用在现有原生管理员余额接口上做最小修复：API client 生成并发送幂等键，后端保留现有 gift-only 调整器，弹窗统一读取额度摘要并映射业务错误。

不新建第二个扣除接口，也不把扣除改成 quota-ledger refund。这样可以保留现有路由、审计记录、幂等边界和充值额度隔离。

## 4. 数据与控制流

1. 弹窗打开时读取 `/admin/users/:id/quota-summary`。
2. 用户输入扣除金额时，最大值为 `gift_quota_balance_usd`。
3. 提交前检查摘要存在、金额为有限正数且不超过赠送余额。
4. API client 调用旧兼容接口，并发送 `Idempotency-Key`。
5. 后端读取管理员身份和幂等键，通过既有幂等执行器调用 `DeductGift`。
6. `DeductGift` 在事务中锁定赠送额度，余额不足则原子失败；成功时只减少 gift quota，并写入管理员扣除审计记录。
7. 前端将余额不足错误显示为明确业务提示，其他错误保留后端错误详情。

## 5. 错误与安全语义

- 缺少幂等键：返回可识别的客户端错误，不执行任何账务操作。
- 赠送额度不足：返回业务错误，不允许透支、不动 paid quota。
- 重复幂等键且请求体相同：返回原结果，不重复扣除。
- 同一用户并发扣除：由现有事务锁和额度校验保证只有足额请求成功。
- 所有失败均不得修改用户余额、钱包或账务流水。

## 6. 兼容性

保持 `/balance` 路由、请求体字段和 `add/subtract` 操作值兼容。仅补充请求头、错误映射和前端校验。充值/退款接口不受影响。

## 7. 验收矩阵

| 场景 | 预期 |
| --- | --- |
| 赠送 10 美元 | 仅 gift quota 增加 10，paid quota 不变 |
| 赠送额度 5，扣除 6 | 明确提示赠送额度不足，余额与流水不变 |
| 赠送额度 5，扣除 5 | 成功，gift quota 归零，paid quota 不变 |
| 请求自动生成幂等键 | 请求头存在且非空 |
| 相同幂等键重复提交 | 不重复扣除 |
| 只有充值额度、赠送额度为 0 | 扣除失败，不得扣充值额度 |
| 后端返回未知错误 | 显示后端可用错误信息或通用兜底 |

## 8. 测试与发布边界

先补充或调整失败测试，再实现最小修复；至少运行相关 Go service/handler 测试、前端 API 与余额弹窗测试、typecheck、生产构建和 `git diff --check`。

本任务无迁移、无配置变化、无生产数据写入。代码完成后只进入候选分支，等待根总控按项目门禁审查、合并和部署。
